Git becomes your single source of truth, not just for your code, but for everything your infrastructure needs to run. Every configuration, every deployment, manifest, every environment variable, it all lives in Git. Nothing runs on your cluster unless it's defined there. Now, GitOps isn't a tool you can buy. It's an operating model, like DevOps or DevSecOps. A set of principles that guide how you manage your infrastructure. The open GitOps standard lays out four core principles, and I want to walk through each one. First, your system has to be declarative. That means you describe the end state, not the steps to get there. So instead of writing a script that says, "Created deployment, scale it to five replicas, expose port 8080, you write a YAML file that says I want five replicas on port 8080, and the system figures out the steps. That's declarative. Second, it must be versioned. Every change you make to your cluster state is a commit in Git. So you get a complete history who changed what, when and why, no more guessing or digging through logs. Third, changes are pulled automatically. The cluster reaches out to Git to see what's new. Later, I'll explain why this matters so much. And fourth, the system is continuously reconciled. There's a software agent running inside your cluster that constantly compares what's in Git to what's actually running. If they don't match, it fixes the difference. That's the reconciliation loop. Think of it this way. Git is your architect's blueprint. It describes exactly what the building should look like. Kubernetes is the construction site. And the GitOps operator, that's the foreman. He walks around with the blueprint, checking every wall, every beam, every window. If something doesn't match, he fixes it. Suppose someone on the crew makes an unauthorized change. He spots it and reverts it. The blueprint is always the source of truth. But here's where the real shift happens, how deployments actually work. In traditional CI/CD, you push changes to the cluster. In GitOps, the cluster pulls them. And that difference is more important than it sounds. Pull-based deployments versus push-based. Let's talk about how deployments actually work because this is where GitOps changes everything. In the traditional push-based model, your CI pipeline does everything. Azure Pipelines, Jenkins, GitHub Actions. It builds the container, runs tests, and then pushes that image directly to your Kubernetes cluster. The pipeline holds credentials that give it direct access to the cluster API. It says, here's the new deployment, apply it now. And that works, but it creates a security problem. Here's the thing. If that pipeline gets compromised, someone injects a malicious step, a token leaks, a dependency gets hijacked. That pipeline has a direct line to your production cluster. It can destroy deployments, delete namespaces, change configurations, all with the permissions you gave it to do its job. Now look at the GitOps model. The flow starts the same. CI builds the container and pushes it to a registry like Azure Container Registry. That's where CI stops. It does not touch the cluster. Instead, CI updates a Git repository with a new image tag. It changes a single line in a YAML file, the image version, and commits that change. That's it. No direct cluster access. Then the GitOps operator running inside your cluster sees that change. It pulls the latest state from Git and applies it. The cluster reaches out to Git, not the other way around. This is the pool-based model. Your cluster never exposes its API to external systems. It only pulls from Git. If someone compromises your CI pipeline, the worst they can do is change and manifest in a repository. They can't touch the cluster directly. The operator decides what to apply and when. There's another benefit too. You decouple building from deploying. CI does what it's good at, building, testing, scanning. The GitOps operator handles deployment. Each system focuses on one job. If the build fails, nothing changes in the cluster. If the deployment fails, the operator retries or alerts you. Clean separation. So instead of a pipeline pushing changes into your cluster, your cluster pulls its desired state from Git. That simple inversion makes your infrastructure more secure, more auditable, and harder to break by accident. The reconciliation loop. So how does the operator know when to update? It doesn't wait for a notification. It runs a continuous loop. Watch Git, compared to the cluster, apply changes if needed, then do it again and again forever. This is called the reconciliation loop. It runs constantly every few seconds or minutes, depending on your configuration. The operator never stops watching. Think of it like a thermostat in your house. You set the desired temperature, say 21 degrees, the thermostat constantly checks the actual temperature. If it drops below 21, the heating turns on. If it goes above the heating turns off, it keeps adjusting to match your setting. The GitOps operator works the same way. Git holds the desired state, the cluster has the actual state, and the operator compares them continuously making adjustments. So what happens when someone manually edits a deployment in the cluster? Maybe they run Quebecal Edit to change a replica count. The operator detects that difference on its next reconciliation cycle. The cluster now has three replicas, but Git says five.
