Why global traffic routing matters? Let's break it down. Most people hear load balancing and think of a single server distributing traffic across a few machines inside one data center. That's Azure Load Balancer and it works great for a single region. But what happens when your users are spread across continents? A user in Japan hitting a server in Virginia is never going to get a fast response. The physics of the internet just won't let it happen. Light travels at a fixed speed and every network hop adds delay. You can't fix that with better code or faster servers. Here's the thing, slow apps lose users. A one second delay cuts conversions by 7% and a regional outage that doesn't just slow things down, it takes your entire app offline. Your users can't reach you, your revenue stops and your reputation takes a hit. 20 years ago, the old approach was to build servers in every region and manually direct users to the right one. You'd update DNS records by hand, maintain spreadsheets of which users went where and pray you didn't make a mistake during a failover. That approach is impractical and brittle because it doesn't scale and breaks under pressure. The new approach is a single DNS-based traffic director that picks the best endpoint per user per request. It requires no manual updates or fragile spreadsheets. Instead, it looks at where the user is, checks which endpoints are healthy and returns the best one. Think of it like a global air traffic control system where each data center is an airport and traffic manager is the control tower directing each user to the nearest available server. That's where traffic manager comes in. So let's talk about what it actually is. What traffic manager actually is. Here's the simplest definition. Traffic manager is a DNS-based load balancer that runs at global scale. Think of it like a smart reception desk at the entrance of a worldwide office building. When you walk in, the receptionist doesn't handle your phone calls or process your paperwork. They just point you to the right floor. That's all traffic manager does. It points users to the right server. Here's the key distinction. Traffic manager never sees your actual traffic. It doesn't proxy requests, inspect packets or cache content. When a user types your domain name into their browser, a DNS query goes out. Traffic manager answers that query with the IP address of the best endpoint, the closest one, the healthiest one, the one you've configured as the priority. Then the user connects directly to that endpoint and traffic manager steps out of the way completely. That means it adds zero latency to your traffic path. Because it's not in the middle of the data flow, it can't slow things down. It also works with any internet facing endpoint, Azure services, servers in another cloud, even your own on-premises data center. As long as the endpoint has a public IP address or a domain name, traffic manager can root to it. And because it's a global service, it's resilient to regional failures. If an entire Azure region goes down, traffic manager keeps running and roots users to healthy endpoints elsewhere. So how does traffic manager know which endpoints are healthy? It probes them every 30 seconds by default, sending an HTTP or HTTPS request to a specific path on each endpoint. If the endpoint responds with a 200-level status code within a timeout, it's healthy. If it fails to respond multiple times in a row, traffic manager marks it as degraded and stops sending users there. When the endpoint recovers, traffic manager detects that too and brings it back into rotation. This health monitoring is what makes automatic fail over possible. Now, let's look at the different ways traffic manager decides which endpoint to send users to. That's where the routing methods come in. Priority routing? Disaster recovery made simple. Priority routing is the simplest method to understand. You rank your endpoints from one to however many you have. That's it. All traffic goes to priority one. If that endpoint fails, traffic shifts to priority two, then three and so on down the list. It's an active passive setup. One endpoint handles everything. The others wait in the wings. Here's a real world example. Say your primary servers run in East US and you have a backup in West Europe. You set East US as priority one, West Europe is priority two. Normal operation, every user goes to East US. But when East US has an outage, maybe a power failure, maybe a network issue, traffic manager detects it within seconds. It stops sending new users to East US and starts redirecting them to West Europe instead. Your app stays online, your users might not even notice anything happened. Now, there's an important detail here. Existing users keep their current connection. DNS based routing only affects new DNS lookups. So if someone already loaded your app and has an active session, that session keeps going to the original endpoint until it ends or the DNS cache expires. That's why you want to set your DNS TTL low 30 to 60 seconds is the sweet spot. A low TTL means DNS resolvers check for updates more frequently. So when traffic manager switches endpoints, the change propagates faster. One common mistake people make is for getting to test the failover. You set a priority routing, you deploy your backup region and then you just assume it works. But here's the thing, your backup region needs to handle the full load. If your primary handles are million users a day and your backup only handles 100,000 during normal operations, that backup might fall over when all that traffic suddenly shifts to it. Test your failover, actually simulate an outage and watch what happens. That's the only way to know it works. Priority is about keeping your app alive during failures. But what about making it fast for everyone? Performance routing, speed over everything. Performance routing works differently than priority routing. Instead of saying always use this endpoint first, it says send each user to whatever endpoint gives them the fastest connection. So a user in Tokyo gets routed to a server in Japan. A user in London gets routed to Ireland. A user in Sao Paulo gets routed to Brazil. Every user gets the fastest possible experience, no matter where they are. How does traffic manager know which endpoint is fastest? It uses something called an internet latency table. Think of it as a map that Azure keeps up to date. It tracks the actual network latency between different parts of the world and each Azure region. When a DNS query comes in, traffic manager checks where the user's DNS resolver is located, looks up the latency table and returns the endpoint that gives that user the lowest latency. Now here's something that might surprise you. It's not based on physical distance. A user in India might actually get lower latency to East US than to Southeast Asia, depending on how the undersea cables and internet exchanges are routing traffic at that moment. The latency table captures real network conditions, not just straight line distance. So the closest endpoint isn't always the one that's geographically nearest. Performance routing is a great fit for globally distributed apps where user experience depends on speed. Ecommerce sites, video streaming, real-time collaboration tools, anything where a slow response means a lost user. But there's a catch. It doesn't consider how much load each endpoint is already handling. If your East US region is running at 95% capacity in your West Europe region is at 20%, performance routing might still send new users to East US because that's the lowest latency for them. It doesn't know about your server load. So you typically combine performance routing with other load balances inside each region. Azure load balancer or application gateway to handle the actual distribution of traffic across your servers once the user arrives at the right region. Performance routing optimizes for speed, but what if you need to control how much traffic each endpoint gets? Weighted and geographic routing, control and compliance. So performance routing is about speed. But what if you want to control exactly how much traffic each endpoint gets? Or, root users based on where they're located in the world? That's where weighted and geographic routing come in. Let's start with weighted routing. This one is exactly what it sounds like. You assign a weight to each endpoint, a number between 1 and 1000. Traffic manager then distributes traffic proportionally based on those weights. So if you have endpoint A with a weight of 80 and endpoint B with a weight of 20, roughly 80% of your users get sent to A and 20% go to B, simple math. Now, why would you want to do that? Think about a canary release. You've built a new version of your app and you want to test it with real users before rolling it out to everyone. You set up a second endpoint running the new version, give it a weight of five and give your current production endpoint a weight of 95. Five percent of your users hit the new version. You watch for errors, monitor performance, and if everything looks good, you slowly increase the weight on the new version, maybe 20% next week, then 50, then 100. If something goes wrong, you drop the weight back to zero and the problem is contained. No big bang deployment, no rolling back a broken release in front of all your users. Same idea applies to A, B testing. You want to see if a new feature improves engagement. Send half your users to version A and half to version B using equal weights compare the results or your migrating users from one region to another. Gradually shift the weight from the old region to the new one over a few weeks. Here's something important to understand though. Weighted routing is not round robin. It doesn't alternate between endpoints one request at a time. It's a statistical distribution over a large number of requests. The traffic splits according to your weights. But a single user making multiple requests might keep hitting the same endpoint because their DNS resolver caches the result. So don't think of it as perfect load balancing. Think of it as controlling the overall proportion of traffic over time. Now let's talk about geographic routing. This one roots users based on where their DNS query originates. Country, continent or a specific region. So a user in Germany gets sent to your endpoint in Frankfurt. A user in Brazil gets sent to your endpoint in Sao Paulo. That level of granularity. Why would you use this? Data sovereignty is a big one. European Union regulations might require that user data stays within Europe. Geographic routing lets you enforce that at the DNS level. A user from France resolves your domain and traffic manager returns the IP address of your European endpoint. Their data never leaves the continent. Same thing for localized content. If you want users in Japan to see a Japanese language version of your site, geographic routing sends them to the endpoint that serves that content. There's one key rule you need to know. Every geographic region must map to exactly one endpoint. You can't split a single country across two endpoints. So if you have users in Germany and you want 50% to go to Frankfurt and 50% to Berlin, you can't do that with geographic routing alone. You'd need to use a nested profile instead. Nested profiles are exactly what they sound like. You put one traffic manager profile inside another. So at the top level, you use geographic routing to send European users to one profile, North American users to another and so on. Then inside each of those profiles, you use weighted routing to split traffic between endpoints within that region. Geographic at the top for compliance, weighted inside for control. It's a powerful combination. Two more routing methods handle more specific scenarios. Let's look at those. Multi-value and subnet routing for fine-grained control. Multi-value routing is a simple but useful trick. Instead of returning just one endpoint in the DNS response, traffic manager sends back multiple healthy IP addresses all at once. Your browser or app picks the first one from the list, which spreads the load without traffic manager needing to decide for every request. But there's a catch. Multi-value only works with IPv4 and IPv6 endpoints, so you can't use it with app service, cloud services, or any endpoint that uses a domain name instead of an IP address. It's purely for IP-based endpoints. When you have those though, it makes the system more resilient because if one IP fails, the client can try another from the list without doing a new DNS lookup. That means faster failover on the client side, subnet routing is even more niche, but powerful when you need it. It routes users based on the source IP subnet that DNS query comes from. So you can map your company's office IP range to a staging endpoint and everyone else gets the production version. Or you can route users from a specific VPN subnet to a dedicated backend for testing. Picture an internal testing scenario where your development team is working from the office. The DNS queries come from your corporate IP range and you map that range to a staging environment where they can test the latest build. Everyone else on the internet gets the production version. No special URLs, no VPN configurations, just transparent routing based on where the request comes from. Both of these methods are niche. Most people will use priority, performance, weighted, or geographic for their main traffic management, but multi-value and subnet are there when you need them and they solve problems that the other methods can't. Health monitoring and failover in practice. All these routing methods depend on one thing, knowing which endpoints are actually healthy. Routing traffic to a broken server doesn't help anyone, so let's talk about how health monitoring works in practice. Traffic manager sends a health probe to each endpoint every 30 seconds by default and that probe is an HTTP or HTTPS request to a specific path on your endpoint. It expects a response with a status code between 200 and 299 within a certain timeout period. If the endpoint responds correctly, it's healthy. If it doesn't, traffic manager tries again. After a configurable number of failures, default three, traffic manager marks that endpoint as degraded and excludes it from routing until it starts passing health checks again. You can configure the probing interval and the timeout. Faster probes mean faster failover. If you set the interval to 10 seconds instead of 30, traffic manager detects failures sooner and redirects traffic more quickly. But there's a trade-off. Faster probes put more load on your endpoints because every probe is a request your server has to handle. So if you have thousands of endpoints and you're probing every 10 seconds, the requests add up. And speed against overhead. The real impact of proper health check configuration is the difference between a seamless failover and a false alarm that breaks your routing. If your probe is too sensitive, you might mark an endpoint as degraded when it's actually fine. A temporary spike in latency, a brief network glitch, a slow database query. Any of these could trigger a false positive. When traffic manager stops sending users to that endpoint, you've just created an outage that didn't need to happen. Here's a common pitfall. A couple set the probe path to the root of their application, just a forward slash. That's fine for a basic health check, but it's not ideal because the root page might load slowly if it renders a full page with database queries, images, and JavaScript. A better approach is to create a dedicated health check endpoint, something lightweight. A simple endpoint that returns a 200 status code quickly and confirms the application is running. No database queries, no heavy processing, just a heartbeat. That way your probes are fast, reliable and less likely to trigger false alarms. Let me wrap up with when you should actually use traffic manager versus other options. Conclusion and decision guide. So here's the quick recap. Traffic manager is a DNS-based global traffic director with six routing methods. It doesn't actually handle your traffic. It just points users to the right place based on the method you pick. Priority routing is for disaster recovery. It keeps your app running even if an entire region goes down. Performance routing is all about speed. It sends each user to the endpoint with the lowest latency. Weighted routing lets you do controlled rollouts like canary releases or A/B testing. Geographic routing handles compliance. You keep data in the right region according to where your users are located. Multi-value is for simple IP-level distribution across multiple addresses. And subnet routing routes based on the source IP of the DNS query. Now let's talk about where traffic manager fits into a real architecture. Think of it as the first layer. It roots users to the right region. Once they arrive there, you need other services to handle the actual traffic. Azure Load Balancer distributes traffic across VMs inside a single region. Application gateway gives you layer 7 routing and a web application firewall. Front door adds global caching, TLS termination and deeper security features. Traffic manager works alongside all of these. It's not a replacement for any of them. Here's a quick mental shortcut. Use traffic manager for cross-region routing. Use Azure Load Balancer for within region distribution. Use Front Door when you also need WAF caching and TLS termination at the edge. Each one solves a different problem.
