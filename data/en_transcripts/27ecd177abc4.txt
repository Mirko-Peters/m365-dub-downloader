Begin with the substrate SharePoint. Pillar 1 SharePoint, Float Substrate and Force Discipline. SharePoint is fine until you treat it like a database and a file share and a workflow engine on the same Tuesday. It's a collaboration platform with lists that behave like lightweight tables and document libraries that behave like content stores, that dual nature is why it's powerful and why it's fragile. If you don't draw the line, makers will. They will draw it with a highlighter and a random choice column named "Status 2". The thing most people miss is this. SharePoint isn't the villain. In consistent design is, lists scale exceptionally for thousands of items when queries are delegable and indexed, but they feel like wet cardboard when you bolt on 347 columns, 5 look-up chains and a gallery trying to filter across non-indexed text. Do you think you need more horsepower? You really need fewer anti-patterns. So here's the Enforce Discipline. First, Schema. Name the list for the business noun, not the project nickname. Incidents, not Jen's trial tracker. Set column names that never include spaces, punctuation or future regret. You can relabel for humans in power apps. You can't renegotiate the API later. Use single line of text number date and yes, no for most fields. Use choice sparingly when you control the vocabulary. Use look-up when you actually need a relationship, not when you're too tired to maintain a choice list. Second, relationships. SharePoint look-ups are fine for one hop, too if you're lucky. After that, galleries cry in delegation breaks. If your design needs multi-hop joints or transactional integrity, stop. That's a dataverse or SQL conversation. The rule, one look-up per list view that your app relies on. Index the look-up column and the primary filter column. If it must filter by two fields, index both and use a composite view. Don't rely on hope, rely on indexes. Third, versioning and retention. Turn on major versioning for lists where humans edit data. Set a sensible cap 50 or 100, so you have a rollback window without exploding storage. Require checkout for document libraries where edits are frequent and sensitive. And set content types on the library if you need different document schemas. This is where you stop final v7 final before it reproduces. Fourth, permissions. Break inheritance at the site, not at the item. Item level permissions are a treadmill. You'll trip if you must protect rows, design separate lists with different scopes and aggregate via power apps with the user-taggate, or move to a platform that does row-level security without voodoo. Owners, members, visitors use them cleanly. Stop granting direct access to just one person. Groups exist for a reason. Fifth, views and thresholds. The 5,000 item list view threshold isn't a myth. It's the guardrail. You can store way more, but you must slice the data with indexed filters in default views. Create a safe filter view that every app uses as its base. Filter by status or modify GE today and 30 indexed. Teach makers to respect it. If they need full history, they can run a scheduled extract to a data lake, not live query the universe. Sixth, files versus attachments. Attachments are a convenience text. Use document libraries for real files. Store the list item ID as metadata on the file or use a folder named with the item ID if you enjoy pain. Libraries give you co-authoring, retention labels and previews. Attachments give you drama. Seventh, ALM reality. SharePoint is stubborn in ALM. Lists don't package cleanly across environments, so you standardize a provisioning script, JSONSite scripts, or P&P templates, creates sites, content types, lists, columns, views and indexes. The app never creates schema. Humans never create schema in production. If that sounds strict, good. It's cheaper than reconstruction. Eighth, DELEGABL logic. Power apps can query SharePoint efficiently if you write DELEGABL formulas. That means filter sort, search with indexed columns. No for all over entire lists. No giant with chains as pseudo queries. If you need fuzzy matching and composites, build a helper column that concatenates normalized keys at right time. It's ugly, but it keeps the query on the server instead of dragging 25,000 rows to the client. Ninth, data ownership. Every list has an accountable owner, not IT. Expiring ownership reviews run quarterly. If the owner leaves, the site's secondary owner is notified and the app is re-homed. No orphans. No mystery lists with business critical data and a dead mailbox. Finally, a sanity rule. If your list needs more than one multi-line rich text field, several lookups and people fields, stop and reassess. You're designing a relational model with a collaboration tool. Move the core data to dataverse. Keep SharePoint for files and light reference tables and connect them. Hybrid beats heroic hacks. Enforced discipline isn't glamorous. It is the difference between predictable performance and slow motion collapse. You stabilize the substrate or everything above it inherits the wobble. Now we move up the stack. Pillar 2. Power Apps. Deterministic canvas. Not a scrapbook. Stabilize SharePoint. Then make the app behave. A canvas app is either deterministic or it's chaos with a save button. We bias every decision toward predictability, repeatability, and clear failure modes. No improvisation. No ransom node UI. Started the connector. Add SharePoint as a data source but never let controls query lists directly. Centralize reads and writes. On app, on start, define a configuration record and pre-compute the queries you'll need repeatedly. Not everything loads at startup. Only seed data and user context. Example. Set var user. User. Set var today. Today. Clear collect. Call my filter. Status. Active. Then defer heavy list loads to screen level on visible with controlled filters. This prevents the first paint lag that people blame on SharePoint when it's really your app dragging a list view by the ankles. Gallery's versus forms is not a style choice. Gallery's display. Forms commit. Use a gallery for list browsing with a strictly delegable items formula. filter, incidence, status, eighth, active, intent modified, ill var, today, 30. Both status and modified must be indexed. Don't compose data inside the gallery with if chains and lookup calls. Pre-compute lookups into lightweight collections at app start if you must display friendly names. The goal is one delegable server query. Not 10 client stunts. For editing default to edit form with submit form when your schema is simple and you can live within its life cycle. Submit form handles validation tied to data cards, patches attachments behind the scenes, and manages optimistic concurrency the way SharePoint expects. But treat submit form as an atomic operation. Don't wrap it in five other steps and hope. Use on success and on failure explicitly. On success logs what changed and navigates. On failure surfaces the error with a message that means something. Notify save failed check required fields or concurrency. Notification type dot error. Now the hard truth. The thing most people miss is knowing when to step outside the form. If you need partial updates, transformations before write or cross entity coordination, patch is the tool patch writes exactly what you tell it and nothing else that's good and dangerous. Guard it. Use a typed template record to make patch readable and maintainable. Patch incidents ID var edited, do data, itag, var itag, status, drp status, selected, value priority, drp priority selected, value title, text, title, text, always include the itag for basic concurrency defense. If SharePoint returns a conflict, you'll get a clear error instead of a silent override, handle it in a retry pattern with a Rack query and merge prompt, not a brute force write. Never patch attachments. Use a document library bound by item ID. Store the file in the library with metadata item ID equals this item. ID then display via an nested gallery that gives you co-authoring previews, labels and zero ambiguity. The just add an attachment shortcut is why your users keep emailing copies for reference. Control state explicitly. Apps drift when every control sets global variables. Prefer context, update context for purse screen flags, and a small set of global bars for cross app concepts like var user and feature toggles. Build a single record for the edit buffer, set var edit defaults incidents, then write forms and controls to bind to var edit fields. When you save map var edit to patch, that isolates UI twitching from data integrity and makes undo trivial, set var edit blank or reload it from the source. Validation belongs in three places in order. First server side rules in SharePoint where possible, required columns max lengths unique constraints via calculated keys. Second data card required and valid properties aligned with those rules not invented on the fly. Third presubmit guardrails. If form incidents, valid notify fix validation errors, warning, return. The reason this works is you're reusing the engine's validation instead of reinventing it 12 times. Navigation patterns should be linear and idempotent. Users start at a filtered list, select a record, edit in a separate screen, commit, return to the same filter with the same scroll position. Don't rebuild the universe on every navigate. Cash the list query seed in a variable. When you save, refresh only the changed row with a targeted update, if into a local collection bound to the gallery, that avoids full round trips and preserves context. Styling is a governance problem disguised as taste. Define a theme record in app. On start, set of our theme, primary, test 0, 0, 4, 5, 7, 8, text, su11, danger, c50, f1, all controls reference for theme. Lock fonts and sizes. If someone demands a gradient, you decline. Consistency isn't pretty. It's maintainable. The app should look boring and run fast. Offline is not a checkbox. If you don't have a tested store load pattern with JSON serialization and conflict resolution, you don't have offline. Say no until you can say yes properly. Half offline creates full incidents. Finally, instrumentation. The app logs its own behavior. On start, write a session record. On every save, log patch with request id, user, record id, operation, duration, success, error. If a flow is involved, correlate with a guide passed into the trigger. When the O347 spike hits again, you won't guess. You'll see. Deterministic apps tell you what they did, not what they hoped to do. Pillar 3. Power automate. Timebombs. Defused with protocols. Flows fail the same way buildings burn, quietly at first, then all at once. The O347 spike wasn't mysterious. A SharePoint column was renamed, an approval owner was on leave, and a flow with 47 unguarded steps marched straight into nulls and stayed there. We don't fix this with hope. We fix it with protocols that make failure loud, contained, and reversible. Start with triggers. When an item is created or modified is not a strategy, it's a floodgate. Scope it. In the trigger, add filter queries that match your app's delegable base. Status EQ pending and modify GUTC now. Sub 1. Index those columns in the list. If you need a change detector, use a calculated hash column. The app updates only when a meaningful field changes. Your trigger wakes up for intent, not background noise. Next, concurrency. Turn on trigger concurrency control and cap degree to one for workflows that touch the same record, or you'll race yourself into conflicts. For bulk handlers, batch by partition keys like site or department with a degree of 5 to 10. Unbounded parallelism is how you turn a hiccup into a pile-up. Conditions aren't decorations. Use guard clauses early and often. The first branch in the flow should answer, should I even be running? If the item status isn't pending, terminate is succeeded with a reason. If required fields are blank, terminate is failed with a specific code. Dead end quietly is not resilience. It's a cover-up. Approvals look simple until someone goes on vacation. Use the built-in start and wait for an approval for human decisions. But rapid with reality. Set a business realistic timeout. 72 hours. Not forever. On timeout, branch to an escalation path. Notify the requester. Notify a backup approval group and log a governance event. If your culture requires reassign, use entra-groups instead of individuals, so-coverage rotates without edits. The thing most people miss is that approvals are state machines. Your list item should reflect that state. Write a status, ex-awaiting approval, then approved, or rejected, and a decision by field. The flow reads and writes that state explicitly to survive retries and human drift. Data operations are where promises go to die. Parse Jason everywhere is shape matters. Stop guessing at dynamic content. Define a contract for each connector's response and fail fast if it changes. Use try catch patterns with scope actions. A try scope for your main logic, then a catch scope configured to run on failure, timeout, or skipped. In catch, gather context. Flow run ID. Item ID. ETAG. Correlation ID from the app. And send a single consolidated alert. The game changer nobody talks about is correlation. Pass a guide from the app into the flow trigger and write it into every log, email, subject, and team's card. When the spike hits, you follow one ID through app, flow, and SharePoint updates without guessing. SharePoint writes need optimism with proof. Before you update item, get the current item to retrieve the ETAG, write back with if match header, where available, or use the update item action and check for 412 precondition failed in the error. If someone edited the record between trigger and write, don't bulldoze. Branch to emerge path, read fresh, compare changed fields, and either reapply or ask the requester to reconcile. Silent overrides are how you lose trust. Long flows need checkpoints. After each critical mutation, persist a last processed step field to the list, or a shadow tracking list, keyed by the item ID and correlation, key UID. On rerun, the first action reads that check point and jumps to the next block that makes your flow id important. Replace, don't double charge you, or send two emails to the CFO. Files are their own trap. If the flow handles documents, use document libraries and content types, not list attachments. Use get file content using path, only when you must, prefer IDs to avoid path drift. When generating files write metadata first, then upload content, then update the metadata that depends on the file version. It's boring and keeps preview retention and labels intact. Error handling is not just a catch scope. It's classification. Not all failures are equal. Build three paths, retriable, permanent, and unknown. Retriable errors include 429 and 5xx responses, RAP with exponential delay max 3 attempts, permanent errors include 400-level validation failures, notify the maker with exact field names and values, unknown errors dump the raw body and headers to a secure log store with the correlation, GUID and environment. Do not paste secrets into teams. Mask payloads by default. Notifications must be quiet and useful, one message per incident, not per action. Use adaptive cards with the correlation GUID, the item link, the failed step, and the next action. Send to a monitor channel, not a person. The channel has an incident header that flips from green to amber when any unknown error posts, back to green when a resolver clicks acknowledge, and the system confirms the next run succeeded. Speaking of next runs, build a manual replay, add an HTTP triggered flow or a power app admin screen that takes the correlation GUID, looks up the item, and restarts from the last safe checkpoint. Log who replayed and why, humans will intervene, make it auditable. Finally document the contract. In the list description, link to a runbook, trigger filters, required fields, approval SLAs, error classes, checkpoint fields, and replay steps. Make us come and go. Protocols persist. When someone renames a column at midnight, the flow doesn't collapse. It complains loudly with a map. That's the difference between a time bomb and a controlled burn. Pillar 4. AI builder. Documents with a sober human in the loop. The spike didn't start with code. It started with a PDF. Invoices arrived, someone retiped line items by hand, and a flow tried to guess which totals mattered. Guessing is how you get midnight incidents. So we extract data like adults with a trained model, a stable schema, and a checkpoint where a human confirms. Here's the disciplined pattern. Use AI builder's document processing model for structured forms you see repeatedly. Invoice intake form inspection report. Train on 5 to 10 clean exemplars that match the layout. Define the exact fields your system cares about. Vendor name, invoice number, invoice date, subtotal, tax, total, purchase order, and a calculated hash that your downstream logic uses to detect duplicates. Keep the field names boring and permanent, boring prevents drift. In Power Automate, trigger on a document arriving in a dedicated library with a content type like invoice. Pass the file content into the predict action. Immediately parse every field with parse jason using a contract you control. No dynamic content roulette. Compute your own total, equal, subtotal, plus tax, and compare to the models total. If mismatch branch to human review equals required, human in the loop is not an apology. It's a gate, create an approval, or a custom review screen in a lightweight admin app that binds to a review queue list. Store the extracted fields, a confidence score, a file link, and a correlation guide he handed down from the app or generated ad ingestion. The reviewer edits fields if needed and clicks confirm. Only then does the flow right to the system of record and move the file to a processed folder with a retention label. The thing most people miss is grounding the model with deterministic checks. Validate vendor name against a supplier table. Validate invoice number uniqueness per vendor. Validate invoice date within a sane range. If any validation fails, you don't hope it's fine. You route to review and tag the incident with a reason code for telemetry. Low confidence, math mismatch, unknown vendor duplicate. That turns random review into measurable work. Storage is clear, do not save business files as list attachments. The document lives in a library with content types, labels, and versioning. The extracted fields live in a list or dataverse table, keyed by document ID and correlation guide. If finance wants exports, schedule an extract to a data lake. Do not let them build wild queries against live libraries. Retraining is periodic, not impulsive. When you see repeat low confidence for a vendor's new template, you add two fresh samples, retrain and version the model. You only switch the production flow to the new model ID after a test run with held out documents passes your validation checks. Models get change control like code. Finally, every step logs with the correlation guide. File captured, prediction complete. Validation pass, fail, human decision, write committed. If the O347 pattern returns, you trace it by G-wide, not by rumor. AI helps when it's fenced, measured, and humble. The fence is the human checkpoint. The measurement is validation and telemetry. The humility is knowing when to ask. Ah, pillar five, Copilot Studio, chat with boundaries, not a megaphone. The other spike came from words, not numbers. A chat agent answered a sensitive question, a little too well. That's not intelligence, that's a megaphone with no volume knob. We build agents that know their lane, cite their sources, and go silent when the question crosses a line. Start with purpose. The agent does one thing. Resolve how to and policy questions for a bounded domain like expense, policy, and process. Knowledge sources are white listed SharePoint pages with current policies and FAQ list. No broad web search. You set that to off. The agent reads from curated content only. Every response includes citations to the exact page or list item. If it can't cite, it won't say. Next, guardrails. You define instruction rules that survive clever prompts. It answers operational questions. It does not generate or summarize personal data, customer records, or anything labelled confidential. It refuses requests that require HR legal or security to act. It routes those to a human queue with a templated message in a link. The thing most people miss is output constraints. You set max response length, required sections, answer source, next step, and a tone, concise, neutral, literal. No creative flourishes. Tools are surgical. If you connect Outlook, you restrict to one action. Send an email to the authenticated user with a summary and links, never to third party addresses. If you connect a power automate flow, it must accept a correlation guide and an action token for idempotency. The agent doesn't mutate data directly. It requests a workflow and reports the result. That separation prevents a chat from becoming an admin console. Privacy is explicit. The agent runs with the user's identity and adheres to DLP. It cannot see content the user can't see. It does not store chat transcripts with sensitive content beyond retention policy. You configure logging to record intent, route, and decision, but mask values that look like emails, IDs or amounts. Logs include the correlation GUID, the knowledge source IDs used, and the refusal reasons when applicable. When someone asks for all salaries, the agent refuses, logs, refusal policy, and links the compensation policy page. You don't hide the refusal. You make it boring and consistent. Escalation is a path, not a shrug. When the agent can't resolve, it creates a ticket with structured fields pulled from the chat. Category, user, source page, last answer, correlation, GUID. It tells the user exactly what happened and the expected response window. The human responder sees the chat context and the source is consulted. No retiping, no telephone game. Change control applies here too. When you update policies, you republish the knowledge base, then run test prompts through a regression set. If responses drift, you adjust instructions, not vibes. If the business wants broader scope, you add sources and retest. Scope creep is an incident waiting to happen. In short, copilot is a librarian, not an oracle. It finds, sites and stays in bounds. When the question is outside the stack, it roots. That's how AI keeps you out of the news and inside your SLA. Pillar 6. Non-negotiables. The governance spine. Entropy starts where protocols end. These are the controls that don't blink, don't debate and don't wait for consensus. They are enforced because they prevent the U347 pattern. DLP first. You define connector groups. Business, non-business blocked. SharePoint teams, outlook, live, and business. Twitter, personal dropbox, and anything you wouldn't email to legal land in blocked. No app can mix business with non-business across environments. The rule is absolute. If a maker needs an exception, they open a request, its time bound, logged, and expires without ceremony. The reason this works is simple. Data moves along, allowed rails, or it doesn't move. Environment strategy is next. You get dev, test, prod, and personal. Dev is noisy, open to makers, seated with fake data, test mirrors, prod shape with mask data. Proud is locked behind change and solution imports only. Personal is a sandbox with DLP set to play nice with nothing. Unmanaged creations in Proud are deleted or migrated on site. New environments require a purpose and owner and an end date. Exploration notices go to owners monthly. If no response, environment is paused, then archived. You don't negotiate with sprawl. Solutions and ALM pipelines carry the change. Anything real ships as a managed solution. No manual edits in Proud. You package power apps, flows, environment variables, and connections. You never bind connections to named users. Service principles or service accounts only with least privilege. Pipelines validate, solution builds, solution checker passes, unit tests run, and connection references resolve. A failed check holds the deploy. Human override is logged with a change number, reason, and approver. If you're clicking next in the designer at midnight, you're doing it wrong. Ownership is enforced. Every app, flow, list, and environment has an accountable owner and a backup. Orphan detection runs weekly. Orphans are reassigned or retired. When someone leaves, assets auto transfer to the backup via policy, not kindness. If an asset has no business owner, it has no business existing. Naming and tagging aren't style. They're search keys. You define prefixes for solutions, apps, and flows per domain. Finn, HR, OPS. Everything gets tags. Data class, own adept, criticality, expiry. Your inventory isn't a rumor. It's a query. Telemetry is mandatory. Every app and flow emits a correlation guide per transaction writes to a central log with environment, solution version, user, duration, error class. Dashboard surface spikes often risk DLP incidents and environment drift. Alerts go to channels, not inboxes. Green Amber, red visible and boring. Access is role-based. Makers get maker, approvers get approver. Admins don't run the apps. Break class accounts exist, are monitored, and expire. Secrets never ride in plain text. Key Vault or environment variables only. Finally, change control, policies, models, and connectors version. You test on dev, validate on test, publish to prod with a rollback plan. No silence swaps, no, we just tweaked it.
