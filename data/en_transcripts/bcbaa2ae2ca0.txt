And that simple fact is where more migrations go wrong than anywhere else. Dependency analysis. Sizing one server is straightforward. The trap is that servers are almost never really alone. Picture a web server that handles logins for a whole department. You assess it. It's ready. The size is right. The price is fine, so you move it to Azure over a weekend. Nothing was broken in the technical sense because you just moved one half of a pair. Dependency analysis exists to stop exactly that. It watches which servers are talking to each other. That lets you see which ones belong together, so you can move them as a set instead of splitting them up by accident. Microsoft's recommended version is called Agentless Dependency Analysis, which is a mouthful for a simple idea. It needs no software installed on the servers at all. It just observes the network connections going in and out every five minutes or so and turns them into a map. Those connections get grouped into applications, so instead of a wall of machine names, you see the shape of how your systems lean on each other. What you get back is a map of your environment as it really works with servers grouped into applications, and the ones that must travel together clearly flagged. The payoff doesn't show up on any chart, but it's huge because you avoid the surprise outage that nobody predicted, and you stop finding out about a hidden connection the hard way at the worst possible moment with everyone watching. Agentless or agent based. By this point, you know what's in your environment, what it will cost, and what has to move together. The next decision is how to copy a server. And again, there are two routes. The first is Agentless. Agentless means nothing gets installed inside the server. You're moving for VMware, the same appliance you used for discovery also handles the copy. It uses something called a snapshot, which is a quick point in time picture of the machine, plus change tracking that copies only the parts that changed. For Hyper-V, the work happens on the host, which is the physical machine running your virtual machines. It's Microsoft's recommended method for most VMware and Hyper-V cases, precisely because you don't have to touch the servers themselves. The second route is agent based. Here, a small piece of software called an agent gets installed once inside each server, alongside a separate replication appliance that handles the transfer. It's a bit more work, but it reaches places Agentless can't. That's why it shows up so often in mixed environments where old physical servers sit next to newer virtual ones. There are four cases where you need it instead. The first is when agentless prerequisites aren't met, which means snapshots or change tracking aren't available or access is locked down. The second is when the server runs an operating system that Agentless can't prepare for the cloud. The third is when it has an unusual disk or boot setup. And the fourth and simplest is when the server isn't running on VMware or Hyper-V at all, which covers physical machines and servers hosted with other cloud providers. The way to think about the trade is this Agentless is the simpler hands off option, and it fits the common case. Agent based is the one that reaches everything else. It hands you finer control per machine at the cost of installing and looking after an agent on every server you move.
