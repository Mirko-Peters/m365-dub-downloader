With those two words sorted out, the pipeline itself gets much easier to walk through as walking through the stages. Now we get to the machinery in the order a change actually travels. A pipeline is really just a sequence, and each stage has one job, which is why a beginner can follow it without knowing the tools. Everything starts with a trigger. Something sets the run going, and most of the time that something is a saved change. Though it can also be a schedule or a person pressing a button. Next comes the build. The machine takes the code and turns it into something runnable. It does the compiling and packaging that a human used to do by hand, and it never varies. Then the tests run. These range from tiny unit tests that check a single function to security scans that look for known problems in the libraries you pulled in. The goal isn't perfection, it's catching the cheap mistakes before a customer finds them. The run then produces an artifact, which is the finished versioned package that everything downstream will use. This is where the most important rule in the whole pipeline lives, which is that you build the package once and then move that same package forward. Rebuilding for each environment is a quiet disaster because you end up testing one thing and shipping a slightly different thing. The version that passed in the test environment has to be the exact version that reaches production, or the test proved nothing. The order is fixed on purpose. You can't test a package you haven't built, and you can't deploy a package that failed its tests. So each stage exists partly to protect the next one. Finally, the package gets deployed first into a test environment and then into production with the pipeline repeating the same steps and reporting the same results each time. If you have ever clicked through a manual release checklist, you already understand the value here. The machine doesn't get tired after a long day, and it never skips the boring line. The strategies differ mainly in how much safety you buy and how much complexity you pay for it. A basic deployment swaps everything at once. It's simple, cheap, and the riskiest of the lot because there's no safe half to stand on while you fix the problem. A rolling deployment swaps the machines in batches, so some of them keep serving the old version while the rest update. It's simple to undo and gentler on your users, though it finishes more slowly and needs the old and new versions to tolerate each other. Blue green deployment keeps two identical environments and flips traffic from one to the other, which makes rollback almost instant because you simply flip it back. The catch is cost. The failures that still happen usually come down to a short list of habits, and that list is worth walking through. The mistakes that break pipelines. If recovery is the hero of this story, the villain is usually a habit rather than a tool. Most broken pipelines fail in a handful of predictable ways, and every one of them is avoidable. The first and biggest is the giant batch. Research from the Dora program has studied software delivery for over a decade, and it keeps landing on the same advice. Make each change as small as you can. Small changes are easier to reason about, faster to move, and easier to undo. Then there are flaky tests, the ones that fail randomly and pass when you run them again. A test like that teaches the whole team to ignore red, and once people ignore red, the pipeline is decoration. Imvu set the bar almost absurdly high here. Their standard was that a test shouldn't fail. More often than once in a million runs. They treated intermittent failures as bugs to hunt down rather than reruns to click. Rebuilding instead of promoting is another quiet killer. If the package you tested isn't the package you shipped, you tested nothing. And this is why the artifact gets built once and carried forward. Secrets deserve a mention, too. Passwords and keys belong in a secure store, such as a variable group in Azure Pipelines. Typing them into a script leaves them where everyone on the team can read them. Then there's ownership. When the build goes red and nobody feels responsible for it, the habit collapses because continuous integration works as a team promise rather than a plugin you install. The last trap worth naming is the measurement trap. Dora warns that turning a metric into a target mostly invites people to game the number. Demand a certain number of deploys per day and you'll get that number rather than better work. The newest wrinkle is AI, and the research is more interesting than the headlines. Dora found that a rise in AI adoption was associated with better individual work, including a three point four percent improvement in code quality. The same research tied it to a small drop in delivery throughput and a larger drop in delivery stability. The lesson is that faster writing doesn't fix a slow pipeline.
