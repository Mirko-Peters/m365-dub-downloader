Once you have committed to local inference, the next decision is the vector database. And this is where many architects make their first real mistake. Vector databases and embeddings. Embeddings are the bridge between human language and machine search. A sentence transformer model takes a piece of text and converts it into a dense vector of floating point numbers. That vector captures semantic meaning. Sentence is about similar topics produce vectors that are close together in high-dimensional space. Sentence is about unrelated topics produce vectors that are far apart. This isn't keyword search. A keyword search for termination policy might miss a document titled off-boarding procedures. An embedding search finds it because the semantic meaning is similar. The model understands that off-boarding and termination are related concepts. It encodes that relationship into the geometry of the vector space. Sentence transformers come in many flavors. The all-mini LML6 V2 model is small, fast, and runs well on CPU. It produces 384 dimensional vectors. The BGE large and model is larger, slower, and more accurate. It produces 1,024 dimensional vectors. Chunking is the process of breaking extracted text into semantically meaningful pieces that can be embedded and retrieved individually. The goal is to create chunks that are self-contained enough to answer questions, but specific enough to avoid dilution. This is attention. You can't satisfy both perfectly. You optimize for your document types and your query patterns. For word documents, the best approach is heading aware chunking. Pass the document structure, identify headings and subheadings, group paragraphs under their nearest heading. Each group becomes a chunk. If a group is too large, split it at natural boundaries like paragraph breaks. If a group is too small, merge it with the next group under the same heading. The result is chunks that carry semantic context. A chunk from the termination policy section includes the heading termination policy and the paragraphs beneath it. When a user asks about termination, the retrieval engine finds this chunk because the heading is embedded along with the content. For PDFs, the challenge is layout. A research paper has clear sections. A scanned contract doesn't. A brochure mixes text and images. The chunking strategy must detect the document structure. For structured PDFs, use section headers as chunk boundaries. For unstructured PDFs, use fixed size chunking with overlap but include page numbers in the metadata so retrieval can sight sources accurately. For image-heavy PDFs, consider OCR if the documents contain critical text in images. But OCR adds complexity and error. Use it only when necessary. For Excel spreadsheets, chunk by row groups include column headers in every chunk. A chunk that says row 45, 5,000 approved 2025, 06, 01 is meaningless without knowing that the columns are budget, status and date. The chunk should read budget 5,000, status approved, date 2025, 06, 01. And it should include the sheet name and file name. If a spreadsheet has multiple sheets, each sheet becomes a separate chunking context. For PowerPoint text, chunk at the slide level. Each slide is designed as a self-contained unit. Extract the slide title, the bullet points and the speaker notes if available. Combine them into a single chunk per slide. If a slide is dense, split it into two chunks but preserve the slide number in metadata, so citations point back to the correct source. The chunk size depends on your embedding model and your LLM context window. A common starting point is 500 tokens per chunk with a 50 token overlap. The overlap ensures that sentences split across chunk boundaries appear in both chunks, reducing the chance that a critical connection gets lost. But this is a starting point, not a rule. If your documents are dense legal contracts with cross references, you might need larger chunks. If they're FAQ documents with short answers, you might need smaller chunks. Let me walk you through what good chunking looks like for a specific document. Imagine a word document titled Corporate Travel Policy. DocuX. It has sections for booking, expense limits, approval workflow and reimbursement. A heading aware chunker passes the document structure. It creates a chunk for booking that contains the heading and all paragraphs under it. It creates a chunk for expense limits that contains the heading, the paragraph about daily limits and the table showing per-dium rates by city. It creates a chunk for approval workflow that contains the heading, the paragraph about manager approval and the paragraph about executive approval for international travel. Each chunk is self-contained. A user asking about per-dium rates in New York gets the expense limits chunk. A user asking who approves international travel gets the approval workflow chunk. The retrieval is precise because the chunk boundaries match with semantic boundaries. Now imagine the same document with bad chunking. A fixed size chunker breaks the document every 500 tokens. The first chunk ends in the middle of the expense limits section. It contains half the daily limits paragraph and the beginning of the per-dium table, but not the table headers. The second chunk starts with the rest of the per-dium table, but not the section heading. When a user asks about per-dium rates, neither chunk fully answers the question. The first chunk lacks the table headers. The second chunk lacks the context that this is about travel policy. The retrieval engine returns both chunks because they are topically related, but the LLM can't synthesize a coherent answer because the information is fragmented. This is how bad chunking destroys a rag accuracy silently. For Excel spreadsheets, chunking must preserve row relationships. Consider an employee directory with columns for name, department, manager, office location, and start date. A naive chunker might create chunks of five rows each. Row one through five get one chunk, row six through ten get another. But if a user asks who manages the engineering team, the relevant rows might be scattered across multiple chunks. A better approach is to chunk by department group. All engineering rows become one chunk, all sales rows become another. This way, a query about engineering managers retrieves a single coherent chunk containing all engineering employees and their managers. For PowerPoint decks, slide-level chunking is usually correct, but some slides are dense. A quarterly review slide might contain six bullet points with detailed metrics. If you put the entire slide into one chunk, the embedding might dilute because the vector must represent six different ideas. In this case, split the slide into two chunks. The first chunk contains the first three bullets. The second contains the last three. Both chunks carry the same slide title in their metadata, so the retrieval engine knows they came from the same source. Metadata preservation during chunking is critical. Every chunk must carry its source document URL, its position in the document, its heading hierarchy, its document type, its library name, its author, its last modified date, and its permission level. This metadata doesn't get embedded. It gets stored as payload data alongside the vector in the database. During retrieval, the metadata is returned with the vector. During answer generation, the metadata becomes the citation. Without metadata, an answer is unverifiable. And an unverifiable answer is worthless in an enterprise context. The embedding model converts each chunk into a vector. As I mentioned earlier, run this model locally. Popular choices include all Mini-LML6, V2 for speed and BGE-large and for accuracy. Performance tuning for local inference involves several knobs. Context window size determines how much text the model can process in one call. With rag, your context window must fit the system prompt, the retrieved chunks, and the user question. Five retrieved chunks of 500 tokens each is 2,500 tokens. Plus the system prompt plus the user question plus the response. A 4,000 token context window is tight. An 8,000 token window is comfortable. A 16,000 token window is generous. Larger context windows require more VRM. Balance this against your hardware. Batching at the LLM level is different from batching at the embedding level. LLM inference is harder to batch, because each user query is independent and latency sensitive. For a chat interface serving 10 concurrent users, you might run a small batch of 2 to 4 requests if your GPU supports it. But most local deployments process queries sequentially or with minimal batching. The throughput is lower than cloud APIs. The latency is acceptable for interactive use. GPU utilization is your infrastructure metric. A GPU sitting at 10% utilization is wasted money. A GPU at 90% utilization is near capacity. Monitor utilization during peak hours. If you consistently hit 80% or higher, add a second GPU or upgrade. If you sit at 20%, you have headroom for a larger model or more users. Let me talk about context window sizing in more detail because this is where many local deployments fail silently. You retrieve five chunks of 500 tokens each. That's 2,500 tokens of context. Your system prompt is 200 tokens. Your user question is 50 tokens. The model needs a few hundred tokens to generate the answer. Total context is roughly 3,000 tokens. If your model has a 4,000 token context window, this fits. But it leaves no room for longer documents or more retrieved chunks. If you want to retrieve 10 chunks or process longer contracts, you need an 8,000 token window or larger. Larger context windows require more VRM, the KV cache, which stores the main and value matrices for each token during attention computation, grows linearly with context length. A model with 70 billion parameters and a 4,000 token context might need 30 gigabytes of VRM. The same model with a 16,000 token context might need 45 gigabytes. This is why hardware planning must account for your expected context size, not just the model weights. Quantization affects context window capacity. The Q4 quantized model uses 4 bits per weight instead of 16. This reduces VRM usage by roughly half for the weights. But the KV cache isn't quantized by default. It remains in full precision. So even with aggressive quantization, the context window is still the limiting factor for memory. Some advanced inference engines now support KV cache quantization, which can reduce memory further. But this is bleeding edge and may affect accuracy, test thoroughly before deploying. For production, I recommend starting with an 8,000 token context window. It provides enough room for five to seven chunks of 500 tokens each, plus system prompt and user question. If your documents are unusually long, or your queries require cross-document synthesis, increase to 16,000. But don't increase beyond what your hardware can serve with acceptable latency. SharePoint already has role-based access control. Your AI must mirror it exactly, not approximately, not eventually, exactly. Every library has permissions. Every document inherits or overrides them. Every user has an effective permission level, determined by their group membership, direct grants, and denied permissions. Your vector database must respect the same matrix. The naive approach is to build a single vector index for the entire organization and filter at the application layer. This fails. Because application layer filters can be bypassed by bugs. It fails because a single compromised query interface exposes the entire index. And it fails because it doesn't scale to find grained permissions like document level access control. The correct approach is to tag every vector with its required permission level at ingestion time. When the ingestion service processes a document from SharePoint, it queries the SharePoint API for the documents effective permissions. It maps those permissions to a permission tier, executive, manager, standard, public, or whatever taxonomy your organization uses. It stores that tier in the vectors metadata payload. At query time, the user's permission tier is determined by their Microsoft EntraID group membership. The query interface passes this tier to QDRIND as a filter condition. QDRIND only searches vectors where the permission tier is less than or equal to the user's tier. A standard user searching for budget information doesn't see executive budget documents. A manager searching for HR policies sees manager level policies, but not executive compensation details. NIST defines a role-based access control as enforcing three rules. Role assignment every user must be assigned a role. Role authorization every role must be authorized for the user. Permission authorization every permission must be authorized for the role. In our architecture, role assignment happens in EntraID. Role authorization happens when the query interface resolves the user's groups to permission tiers. Permission authorization happens when QDRIND filters by tier during vector search. This isn't a new concept. It's our back applied to vector databases. The novelty is that most drag implementations ignore it. They build a single collection. They search everything. And they hope the LLM doesn't say something sensitive. That's not security. A few hundred documents is trivial. 10,000 documents with daily updates is a different problem. The architecture scales, but only if you tune it. GPU batching for embedding generation is your first optimization. Embedding models process chunks in parallel. A batch of 64 chunks isn't 64 times slower than a batch of one. It's perhaps 10 times slower. Batching amortizes the overhead of loading the model and transferring data to GPU memory. Use the largest batch size that fits in your GPU memory. For all Mini-LM on a 24 gigabyte GPU, you can batch thousands of chunks. For BGE large, the batch size is smaller, experiment and measure. Incremental Delta indexing replaces full re-indexing. After the initial index is built, you only process change documents. SharePoints changes API returns modified items since a timestamp. Your ingestion service stores a watermark and processes only the Delta. This keeps indexing time proportional to change volume, not total volume. A 10,000 document library with 50 daily changes takes minutes to update, not hours. Multi-collection sharding by department or document type reduces index size per collection. QDrand searches a single collection in parallel across segments. But if a collection grows too large, search slows. Splitting into smaller collections, one per department or one per major library keeps each collection fast. The query interface roots the search to the appropriate collection based on the user's query context. Or it searches multiple collections in parallel and merges the results. Caching frequent queries reduces redundant work. Some questions get asked repeatedly. What is our vacation policy? How do I submit an expense report? Cache the query vector, the retrieved chunks and the generated answer. Serve the cached answer for identical or near identical queries. Invalidate the cache when the source documents change. This can eliminate 50% or more of LLM calls for FAQ style queries. Monitor vector DB query latency. QDrand exposes Prometheus metrics, track P50, P95, and P99 latency. If P95 exceeds 200 milliseconds, investigate. Increase EF and rebuild the index with higher EF construction add query replicas or chart the collection. If P99 spikes, you may have a hot chart where one segment is overloaded. QDrand can rebalance segments automatically but you should verify it's doing so. For embedding throughput, schedule re-indexing during off-peak hours. Users query during business hours. The ingestion service indexes during nights and weekends. This separation prevents resource contention. If your organization operates globally, define off-peak by region or run ingestion on dedicated hardware. CPU fallback for embedding is viable if GPU is saturated. Modern sentence transformers run well on CPU. An AMD EPIC or Intel Zeon processor with many cores can embed hundreds of chunks per second. It's slower than GPU but cheaper and more available. If your GPU is fully utilized by LLM inference, move embedding to CPU. The latency increase is acceptable for background indexing. When embedding saturates add CPU workers or a second GPU, when the vector database becomes a bottleneck, run Q-drand on its own server with fast SSDs and plenty of RAM. The architecture is horizontally modular. Each component can scale independently. Cost reality is worth stating. Local hardware has high upfront cost. The rack pattern is model agnostic. The Vector database doesn't care which LLM generates the answer. The chunking logic doesn't care. The query interface doesn't care. They care about the prompt format and the API endpoint, standardized on the Olama API or an open AI compatible local API like the one provided by VLLM or text generation inference. A/B testing is responsible model migration. Maintain a test suite of representative queries with expected answer characteristics. Run the old model and the new model against the same queries. Embedding models also evolve. A new sentence transformer might offer better accuracy for your domain. But switching embedding models requires re-embedding your entire corpus. The old vectors and new vectors exist in different semantic spaces. You can't mix them. The full pipeline has seven layers. Each layer runs inside your perimeter. Each layer has a specific job. And each layer connects to the next through a well-defined interface. Layer one is SharePoint Online or SharePoint on premises. This is the storage tier. It holds your documents, enforces access controls, manages versions, and applies retention policies. It's the source of truth. Nothing in the AI layer overrides SharePoint governance. Layer two is the ingestion service. It authenticates via Microsoft EntraID using OAuth 2.0. It enumerates document libraries using the SharePoint REST API or Microsoft Graph. It extracts text from Word documents, PDFs, Excel sheets, and PowerPoint text. It detects changes using Delta Sync. And it outputs clean text chunks with structural metadata. Layer three is the chunking engine. It detects document type. It applies heading aware chunking for Word. Page aware chunking for PDFs. Row group chunking for Excel. Slide level chunking for PowerPoint. It preserves metadata at every step. Source URL. Document title. Author. Last modified date. Permission level. It outputs chunks ready for embedding. Layer four is the local embedding model. It runs a sentence transformer like all mini-LML6V2 or BGE large N on your local GPU or CPU. It processes chunks and batches. It converts each chunk into a dense vector. And it outputs vectors with metadata payloads. Layer five is the vector database, QDrand or VV8 running on your local network via Docker. It stores vectors in a collection with HNSW indexing. It supports metadata filtering for permission or wear retrieval. It handles point updates for Delta Sync. And it returns the top-k nearest neighbors in under 100 milliseconds. Layer six is the local YAMA runtime. Olamar serving a quantized YAMA three or LAMA four model on your GPU server. It exposes a local REST API. It receives prompts containing system instructions, retrieve chunks and user questions. It generates answers with low temperature for factual grounding. And it streams responses back to the query interface. Layer seven is the query interface. A minimalist web application authenticated through Microsoft Enter ID. It embeds user questions. It queries the vector database with permission filtering. It constructs prompts. It calls Olamar. It displays generated answers with clickable citations back to SharePoint documents. It logs every interaction. And it never exposes data to external APIs. And that's the architecture. Seven layers. All local, all under your control. Now let me address common concerns. If a user asks a question in German or French, while your documents are in English, multilingual embedding models like multilingual E5 large handle this scenario. They map semantically equivalent sentences in different languages to nearby vectors. A user asking for Urlobs Richtlinien in German retrieves the English vacation policy chunk because the embeddings are close in vector space. The LLM then generates the answer in the user's language. This isn't machine translation in the traditional sense. It's cross-lingual retrieval followed by monolingual generation. And it works surprisingly well with modern multilingual models. If a document contains a table that the extraction process fails to pass, the chunk contains garbled text. The embedding represents noise. When a user asks about the table content, the retrieval engine returns the noisy chunk. The LLM generates an answer based on partial or incorrect information. This is a data quality problem, not a model problem. The fix is better extraction, not better prompting. Invest in PDF table extractors like Camelot or Tabular Pi. Test them on your actual document corpus. And fall back to manual review for documents that automated extraction can't handle. If the LLM refuses to answer a question because the system prompt is too restrictive, this happens when users ask about topics that are adjacent to sensitive areas. A user asks about employee benefits. The system prompt says only use provided context. The retrieved chunks contain benefits information. But the LLM interprets the question as potentially asking about other employees and refuses. This is over refusal. The fix is to tune the system prompt carefully. Allow answers that are clearly supported by the context. Only refuse when the context genuinely doesn't contain the answer. And monitor refusal rates, a system that refuses 50% of queries isn't useful. If a document contains outdated information, a policy from 2024 might be superseded in 2025. Both versions exist in SharePoint because the old version is retained for legal reasons. The ingestion service indexes both. The retrieval engine returns both. The LLM synthesizes an answer that mixes old and new rules. This is a version control problem. The fix is metadata. Tag every chunk with effective date and superseded status. Filter out superseded documents at query time unless the user explicitly asks for historical versions and train users to check the last modified date incitations.
