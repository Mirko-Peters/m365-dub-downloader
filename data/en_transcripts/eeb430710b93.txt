The edge also keeps the event trail intact when the network drops, because production doesn't pause politely because a one-root failed. Machine states continue changing, parts continue moving, and operators still need a view of what is happening. Local buffering lets the edge hold events with their original timestamps and sequence details then forward them when the connection returns, which prevents a false gap in the shift record and prevents later-riving events from looking like they happened after the outage, which can distort OEE calculations and confuse every investigation that follows. MES adds the production context that the machine cannot know alone. The machine can report that it produced 4,000 units, and MES can connect those units to an order, an operation, a work center, a planned quantity, and the current work in progress state. It can guide the reason code workflow when a line stops, so the operator or supervisor can distinguish material shortage from change over, planned maintenance, quality hold, or an equipment fault. And that distinction changes the conversation. Without a reason code, downtime becomes a generic red bar, but with a reason code tied to a defined workflow and subject to review, the team can separate a recurring equipment issue from a scheduling problem or an upstream material issue. The data still needs care, because people will choose the fastest option when the list contains 20 vague choices. Keep the reason codes practical. They should describe decisions someone can act on, not create a taxonomy that only survives in a PowerPoint file. Fabric sits above that operational record and connects it to the wider business picture, joining line events with order data, material records, shift calendars, quality cost, energy use, and other facts that help explain the consequence of lost performance. A 10 minute stop doesn't carry the same impact in every case. It may occur during a low priority run, with spare capacity, or during the final hours of an order that has no room left before shipment. The machine event stays the machine event, but the business context changes how teams prioritize the response. This is where real-time visibility can become useful without pretending it is perfect. A dashboard should show the current state, current counts, active stops, and whether incoming data remains healthy and it should also show uncertainty. If a source is offline, if events are still queued locally, or if a reason code remains pending, the display needs to say so. Don't fill the gap with a clean number. A dashboard that reports 87.3% OE, while the count source and MES production record disagree isn't giving management clarity. It's giving them a decimal place. The argument should move upstream, toward the source state, count logic, time boundary, and ownership of the production record. The same applies when one report calls a machine idle while another calls it planned downtime. You don't solve that by averaging the two values in fabric. You define the state model, document the rule, and keep the source facts visible enough to test it. Real-time visibility means you can see what the process currently reports, how confident the system is in that record, and where the data came from. It doesn't mean every chart deserves blind trust because it updates every few seconds. Once that foundation is in place, OE can help teams find the right questions instead of producing another screen everyone argues about during the morning meeting. And scheduling needs a different type of decision boundary. APS ERP, MES, and the decision horizon. Scheduling starts to break down when you expect one system to answer every question. ERP keeps the business facts. It tracks orders entered, inventory received or consumed, purchase activity, production confirmations, and cost and financial records. It tells the company what it committed to, what moved, and what closed. That record matters, but it doesn't run a line. APS, advance planning and scheduling, works with a different question. It looks forward asking what plan can still work given demand, available capacity, material limits, labor, changeover rules, maintenance windows, and routing choices. A plan is not a command. APS can test whether an urgent order fits before a promised chip date, and it can show the knock-on effect of moving a job from one line to another. It can also compare options when a material delivery slips or a bottleneck asset loses capacity. The output is a feasible future scenario based on the constraints it knows, at that point. MES sits between that plan and the physical work. It dispatches work to the shop floor, tracks work in progress, records completion, and applies the production rules that belong to execution. If an order moves through several operations, a mess keeps track of where it is, what quantity passed, what quantity failed, and what still needs to happen before the order can close. The edge sees a much shorter horizon. It sees that a machine is faulted now, that a conveyor is blocked, that a tool change is taking longer than expected, or that a station can't accept the next part. Those facts can change fast, and they are not always visible in a planning model until someone sends them upward in a usable form. Consider a line that loses a filler halfway through a shift. The local systems detect the fault and the line enters its defined response state. Operators work the immediate problem, while MES records the disruption against the active operation and work order once the event has enough context to be recorded properly. That event can trigger planning questions upstream. Can the remaining line capacity still complete the order? Should another line take part of the volume, does the change create a material issue later in the route? Is there a maintenance window that now needs to move? APS can test those options against the wider schedule because it sees constraints the line itself doesn't. But the plan must come back down as a proposal for execution, not as a remote hand on the machine. A central system may decide that order 4/7 should move to another work center. But before that change reaches the floor, MES needs to check whether the order is released, whether the material is available, whether the recipe applies, whether the work center can run it, and whether the current production state allows a safe handoff. The edge needs to confirm the local conditions too. It checks whether the machine is actually available, whether a changeover is in progress, whether there is still product in the line, and whether the operator has completed the required checks. A plan built at 10 and 2 arc can already be wrong at 10/07 if the local state changed. This is where cloud first scheduling ideas become risky. A cloud planner may have good information about demand and capacity, but it should not issue direct machine command simply because it found a better schedule. Machines don't execute schedules, they execute validated sequences under current physical conditions. The controller owns the machine sequence while the edge reports local state and applies only the local logic it has been approved to apply. MES owns execution workflow and work in progress records. APS evaluates future options across constraints. ERP remains the business system of record. Those roles can exchange information quickly without becoming the same system. A useful rescheduling loop looks like this. A local disruption occurs, the edge and plant systems capture the facts with the right time and asset context. MES records the execution impact. APS receives a planning relevant event, tests alternatives, and returns a revised plan or dispatch priority, and MES validates that plan against the live execution state before work changes on the floor. That may sound slower than letting the cloud control everything, but it is safer, easier to explain and far less likely to produce a schedule that looks perfect while the plant cannot run it. There is also a human decision in this path. A plan may accept the proposed change, but a production supervisor may reject it because a line carries a quality hold, a changeover would create too much loss, or the local crew lacks the needed skill. Planning systems should expose those trade-offs, not hide them behind an automatic instruction that appears on the screen after the useful moment passed. The same separation appears when people talk about digital twins. A twin needs live-state close to the process, but it also needs a place to reason across relationships, history, and possible futures.
