What a control plane actually is, we need to define this term precisely because it gets thrown around until it loses all meaning. A control plane is not infrastructure and it is certainly not a collection of servers. It is the underlying system that governs who accesses what when they do it. And the specific conditions required for that access to be granted. In the era of traditional enterprise IT, Active Directory functioned as the primary control plane. It sat physically in the data center and controlled which users could log into which machines while managing group memberships and enforcing password policies. Everything in the environment flowed through it because it represented the single authoritative source of truth for identity. In the cloud, the control plane has shifted into something more complex. It is no longer just about managing machines but rather about identity, policy enforcement and compliance across every fragmented environment you own. This includes your cloud footprint, your remaining on-premises hardware, the edge and every SAS application your employees touch. A modern control plane is defined by three specific architectural components. First identity must be the origin point. I'm not talking about federation or synchronization but the actual origin where user accounts are created, managed and eventually revoked. This is the authoritative source where a person exists first when they join the company and where they are deleted first when they leave. In a functional architecture, every other system is merely downstream from this point. Second, policy must travel with the identity rather than sitting as a static rule in a database. These are dynamic policies that evaluate context in real time to determine if a login should be allowed. The system asks where the user is signing in from, whether their device is compliant and if their risk profile has suddenly spiked. Based on those shifting signals, the engine can enforce MFA, block access entirely or demand full device management. This is the reality of conditional access and continuous verification, which stands as the direct opposite of the old model where authentication equaled permanent trust. Third, governance must span every environment instead of being isolated to a single platform. You need one audit trail, one compliance dashboard and one centralized place to review who has access to what across the entire enterprise. This provides a single location to enforce data residency rules and prove to regulators that you are managing access correctly without jumping between a dozen different consoles. Now let's look at how AWS IAM compares to this model. AWS IAM is a resource-centric system designed specifically to control access to AWS resources. You define roles and attach policies to those roles to specify exactly which actions can be performed on which buckets or instances. An IAM user might assume a role to read from an S3 bucket while another role allows them to launch EC2 instances. While this is granular and undeniably powerful, the system is fundamentally built around resources, not people. The critical distinction is that AWS IAM does not originate identity for the enterprise. It originates identity specifically for AWS. When you create an IAM user, that user exists within an AWS account rather than within your actual organization. If your company operates multiple AWS accounts, you end up with multiple identity silos that require federation or AWS organizations to manage. Even then, the origin of that identity remains tethered to AWS. Microsoft Enter ID is an identity-centric system that attempts to control access to everything. It starts by asking who the person is, which applications they should access, what data they are allowed to see, and which devices they are using. It originates in the workforce. When you create a user in Enter ID, they are a person in your organizational directory who can access Azure, Microsoft 365, and thousands of SAS apps. They can even access AWS via SAML or OIDC trust. When Enter ID federates AWS, the Microsoft Identity Engine is the one issuing the tokens that grant access to the Amazon Cloud. The enterprise sees one identity system managing multiple platforms, which effectively turns AWS into just another resource that enter authenticated users can access. This is not a state of coexistence, but rather a form of architectural subordination. This distinction matters because of scale and what I call control plane gravity. When identity originates in one place and governs everywhere, that gravity begins to compound over time. Every new application that needs to authenticate users naturally gravitates toward that origin point, and every new policy requiring enforcement moves toward the governance layer. Eventually, that gravity becomes inescapable for the organization. This is not a simple feature comparison, but a fundamental architectural difference. One system is built around the resources being accessed while the other is built around the people doing the accessing. Entra-Curbos and Cloud-only identities. Entra-Curbos is a cloud-native authentication protocol that finally kills off a fundamental architectural requirement that has haunted enterprise environments for decades. Historically, if you wanted Kerberos authentication, you needed active directory domain controllers living on premises. That was a non-negotiable law of the data center. Accessing file shares or using Kerberos-based security meant you had to maintain a domain controller and show a constant line of side connectivity and swallow the massive infrastructure overhead that came with it. Entra-Curbos changes that equation completely. This shift makes Entra-ID the KDC, the key distribution center. Instead of relying on a physical box in a server room to issue Kerberos tickets, Entra-ID handles the heavy lifting from the cloud. An employee using an Entra-joint laptop can now authenticate to Azure files without ever talking to an on-premises domain controller. They can jump into an Azure virtual desktop session without a VPN tunnel back to the home office allowing them to work from anywhere while maintaining full Kerberos security. This is not just a new feature, it is a massive architectural shift. To understand the operational impact, you have to look at the old way of doing things. Traditionally, migrating file service to Azure created a specific kind of architectural friction because while Azure file supports SMB, and SMB supports Kerberos, Kerberos always required a KDC. You were trapped in a cycle where you either kept your aging on premises domain controllers running or you settled for weaker, less secure authentication methods. Entra Kerberos removes that trap by turning Entra-ID into the KDC itself. Cloud-only identities, users who exist solely in Entra-ID with no footprint in a local AD, can now authenticate to Azure files using pure Kerberos. The entire flow is cloud-native, which means you no longer need on-premises infrastructure, VPN tunnels, or fragile line-of-side dependencies to keep things running. The implications here are significant for any organization looking to decouple from Legacy Hardware. You can now decommission your domain controllers, shut down your local identity systems and operate entirely in the cloud with enterprise-grade encryption.
