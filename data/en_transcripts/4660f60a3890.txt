Single turn evaluation won't tell you whether a multi-turn execution path collects parameters correctly, validates preconditions, calls the right tool and writes to the system of record. It won't show you item potency failures. It won't show you what happens when a connector throws an HTTP error halfway through a workflow. So for execution scenarios you need multi-turn automated testing. That's where bulk testing approaches like the Copilot Studio Kit become the adult option. You run test conversations that include the messy user request, the clarification turns, the confirmation steps, the tool invocation, the error path and the escalation path. And you run them at scale because non-determinism hides in volume. The goal isn't to prove it works. The goal is to discover where it fails before users do. Now add the most ignored part of agent testing. Identity profiles. An agent that works under a maker account proves nothing. You test with designated user profiles that reflect real entitlements, standard employee, privileged operator, regional user, contractor, service desk, analyst, same intent, different identity, different access graph. That's not a corner case. That's the system. Because many agent failures are just authorization reality finally becoming visible. The test discipline has to surface that deliberately, not by surprise in a team's channel. Then you treat tests as architecture artifacts. They are versioned. They are owned. These systems drift and drift creates incidents. And drift does not require malice or incompetence. It only requires time. Drift shows up in three places. First you change the agent. Instructions, triggers, prompts, knowledge, tools. That's a behavior change wearing a friendly UI. Second, dependencies changed. Access, schemers, catalogs, choice values, conditional access, DLP, tokens, secrets, licensing, capacity. Third, the platform moved. Models update, retrieval indexing shifts, throttling changes, preview features, sunset. The agent didn't get weird yet. Your runtime changed. So the mandate is simple. Treat agents like services. Services have runbooks. They have telemetry. They have incident reviews. They have backlogs. They have owners who get paged when reality disagrees with the demo. But with reliability patterns, because most agent incidents are boring in the same way. Timeouts, partial completions, duplicate execution, silent tool failures, inconsistent routing, users resubmitting the same request because the agent went quiet. So you design for that. Retrieves exist, but only where the operation is idempotent. If a create ticket action can run twice and create two incidents, you don't retry. You add a correlation ID and a deduplication check in the execution layer, then retry becomes resume, not repeat. Timeouts exist. So every long-running action needs explicit time budgets and user-visible state transitions, accepted, queued, awaiting approval, executing, completed. If it fails, the agent returns a receipt with a record ID or escalation artifact, not a paragraph. Fallbacks exist, but fallbacks must be engineered. If the model can't confidently root, it should ask a disambiguation question or escalate with context. A fallback that produces plausible text is not resilience. It's fraud with better grammar. And human in the loop checkpoints aren't a concession. There are control points. High-impact changes require a human approval gate, even if the agent did everything else. That's how you keep autonomy from turning into liability. Now observability, this is where most agent programs collapse because they rely on chat transcripts like their logs. They're not. Transcripts are narrative, not telemetry. You need instrumentation for, which intent fired, which topic ran, which tools were invoked, which identity executed them, how long each step took, what errors returned, how often users abandoned, and how often escalation happened. Uncalled telemetry matters more than the agent said something. And you need to capture latency because latency creates user behavior. When agents take too long, users resubmit, resubmission creates duplicates. Duplicates create rework. Rework destroys trust. This is not user training. This is system behavior. Then you need an operational posture. Weekly review, not quarterly post-mortems. Look for drift signals, rising intervention rate, rising fallback rate, increased unrecognized utterances, increased tool call failures, rising latency, more escalating. In the specific intent, those are leading indicators. If you wait for the incident, you've already lost adoption. When an incident does happen, the review has to be brutally specific, not the model hallucinated. That's not a root cause. The root cause is always architectural. Missing precondition checks, ambiguous rooting, overbroad tool surface, unowned knowledge, identity mismatch, or inadequate logging. And every incident produces a backlog item that hardens the system. Titer contracts, better validation, narrower tools, improved escalation artifacts, additional tests, and clearer runbooks. That's the real promise of agent ops. Not that incidents disappear. That incidents become containable, explainable, and less frequent over time. If you choose vibes, drift becomes your entire story, where it's in the executive playbook. The five decisions leadership must force. At this point, the pattern should be obvious. Agent failure isn't a tooling problem. It's a leadership problem disguised as a maker problem. Because agents sit at the intersection of accountability and automation. And if leadership doesn't force a few hard decisions up front, the system will make those decisions for you. Accidentally, inconsistently, and usually during an incident review. So here are the five decisions leadership has to force. Not suggest, not encourage, force. Decision one. The agent owns end to end and what stays human. This is the boundary between assistance and delegation. If the agent owns an outcome, it owns the workflow path, the tool calls, and the evidence. If a human owns it, the agent can guide, summarize, and prepare, but it does not commit. Leadership has to pick because ambiguity here creates blame later. And the fastest way to kill adoption is to ship an agent that sometimes acts and sometimes doesn't with no reliable rule behind it. Decision two. The identity model and the least privileged boundary. Leadership has to decide whether execution runs as the user or as a service identity per intent. Then enforce least privilege as a design constraint, not a security aspiration. This is also where leaders stop tolerating temporary access. Agents will operationalize whatever access that you've accumulated. If the business wants action-capable agents, the business funds, identity hygiene, access reviews, app permission discipline, and a clear run as pattern that survives staff turnover. Decision three. This record and the audit requirement, an agent that acts without writing to a system of record is not an enterprise system. It's an opinionated chat session with side effects. Leadership has to name the record authority per workflow, service now dynamics a line of business system, and make it non-negotiable that agent actions produce reconstructable evidence. Request, identity, preconditions, approvals, tool invocation outcome. If that evidence doesn't exist, the agent isn't allowed to execute. Simple rule. Massive impact. Section four. Release gates. Testing thresholds and rollback expectations. If leadership wants deterministic ROI, leadership forces deterministic release discipline. That means pre-production environments, version changes, test sets that cover core intents under real identity profiles and a past threshold that blocks promotion. It also means rollback is designed, not improvised. When the platform shifts under you, and it will, you need a way to revert behavior quickly without a late night prompt edit in production. Decision five. Decision metrics tied to outcomes, not democquality. Leadership has to kill vanity metrics early. Session volume is not success. Positive reactions are not success. Success is an operational delta that survives outside the agent team. Reduced escalations with strict definitions, reduced rework, faster approvals with preserved compliance, measurable cycle time reduction, improved throughput and intervention rates trending down over time. And leaders have to assign metric ownership. If nobody owns the metric, the agent doesn't have a goal. It has a launch date. When these five decisions are explicit, the rest becomes execution, contracts, tools, context, orchestration, governance, measurement and operations. And when they're not explicit, what you get is predictable too.
