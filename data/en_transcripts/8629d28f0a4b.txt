It returns a segmented version where every chunk starts and ends at a point that makes semantic sense, an installation procedure stays as one unit. Every document you process requires one additional LLM call, for a document library that updates slowly, which is the case for most corporate sharepoint sites. That cost is easily absorbed during the ingestion cycle. The system isn't under pressure to perform in real time here. It processes files as they change, so a document updated once a month only triggers one agentech chunking call once a month. The math changes if you have high frequency ingestion. If you have thousands of new files arriving every hour from automated processes, agentech chunking creates a bottleneck and a bill that probably isn't worth it. In that specific scenario, recursive characters splitting with semantic overlap is the better move. But for a standard corporate knowledge base, agentech chunking should be your default. The improvement in retrieval quality compounds over time, and you only pay that ingestion cost once per update. Once the chunks are sized correctly and cut at logical boundaries, they are almost ready for the vector database. But before they go in, we have to handle the images. Image processing and storage, Mral OCR doesn't just ignore images when it sees them, it annotates them. It places an inline reference in the markdown output, a placeholder that marks exactly where the image was in the original file, along with the description of what it shows. That annotation stays with the text as it moves through the pipeline. But a placeholder is just text. If you want the agent to actually show an image to a user, those placeholders have to become real URLs pointing to real files. That is the job of the image processing step. Once the OCR is done, the pipeline scans the text for those image annotations. When it finds one, it pulls the corresponding image data, which Mral provides in its response and uploads it to a super-based storage bucket. Super-based gives us a storage layer on top of Postgres specifically for these kinds of files. Each image gets a public URL, and that URL replaces the placeholder in the markdown. By the time the document reaches the chunking and embedding stage, the image references have already been turned into live links. The word public is very important here. For the agent to show an image in a chat, and for the UI to render it properly, the URL must be accessible without a login. Open Web UI doesn't have the credentials for your super-based bucket. It just tries to display whatever the agent sends back. If that image URL requires assigned token or a session cookie, the process fails silently, and the user just sees a gap in the answer, we configure the bucket for public read access, which means these images are not secret. Anyone who has the URL can see them. This brings up a major GDPR caveat. If your documents contain images with personal data, like photos of people, signatures on contracts or scans of ID cards, a public bucket is a mistake. You would need to change the model. Either the bucket stays private and the agent generates short-lived links at the moment of the response, or you filter those images out entirely. The default setup assumes your images are technical diagrams or equipment photos. If your SharePoint library has sensitive personal info, you need to check your bucket policy before going live. When this works correctly, the experience is completely different from standard search. A user asks how to fix a machine, and the agent gives a structured answer. Step one, step two, step three. And right next to the text, the actual image from the manual appears in the chat. It isn't a link or an attachment. It is an in-line image exactly where it belongs. That happens because Mistral captured the position the pipeline preserved it through the chunks, and the system prompt told the agent to put the images exactly where they appeared in the original document. Now that the text and images are resolved, the final step is turning those chunks into vectors. Vectorization and the embedding model. A chunk of text is still just text, and your vector database cannot search it directly. Before anything lands in storage, that text has to be converted into a form that allows for mathematical comparison. This takes the form of a list of numbers, usually ranging from several hundred to over a thousand, where every digit captures a specific aspect of what the text actually means. That list is what we call a vector. When two chunks discuss similar concepts, they produce vectors that sit close together in that numerical space, while unrelated topics produce vectors that sit far apart. Similarity search is just the process of finding which stored vectors are closest to the one generated from a user's question. The model that handles this conversion is the embedding model. It takes text in and returns a vector out, and it does this with total consistency, so the same input always produces the same output. That reliability is exactly what makes retrieval work. If a user asks how to operate the espresso machine and a document chunk says to press the button on the left to start the heating cycle, those two strings don't share many words. But because they describe related things, their vectors end up as neighbors in the embedding space, and the similarity search surfaces that chunk is relevant. In this stack, the embedding model runs through Azure OpenAI using a text embedding model deployed under the EU data zone standard configuration. This specific deployment choice is a critical detail. Azure OpenAI offers two ways to deploy these models, which are global standard and data zone standard. Global standard routes your requests to whichever Azure region has open capacity at that moment, which means your text and your organizational knowledge might be processed on servers outside the EU. Data zone standard is different because it constraints all processing to Azure regions inside EU member states. For this system, that setting is not negotiable. The documents being embedded contain internal business information, and letting that content leave EU jurisdiction during the embedding step would create a transfer risk that breaks the entire GDPR architecture. The Swedish Azure region hosts the deployment for this project. Microsoft's EU data boundary commitments apply here, so the embedding calls go in and the vectors come back without any part of that exchange crossing outside European infrastructure. Those vectors eventually land in a Postgres table inside SuperBuddy. The table uses a vector column powered by the PGVector extension, which is a Postgres add-on that adds a native vector data type and support for similarity queries. The index type used here is H and S W or hierarchical navigable small world. It is an approximate nearest neighbor algorithm that trades a tiny bit of precision for significantly faster query times when compared to an exact search. For retrieval at conversational speed, that is the right trade off to make. A user waiting for an answer in a chat interface does not care about the microsecond precision improvement of an exact search, but they definitely benefit from a response that arrives fast enough to feel like a real conversation. Performance at this scale is not a major concern. A corporate SharePoint library rarely produces more than a few million chunks, even if it is quite large, and per vector handles that volume on modest hardware without slowing down. If the system ever grows into a multi-tenant deployment or starts ingesting libraries from across an entire global organization, the SuperBaseVector bucket architecture is a path that can handle tens of millions of vectors. For a single tenant enterprise rack system, the standard PGVector table is the best starting point. Each row in that table stores more than just the embedding. It keeps the file ID, the original file name, and the chunk index, which tells the system exactly where that piece of text sat within the original document. This metadata is what allows the agent to tell a user where the answer came from instead of just what the answer is. Every response is traceable back to a specific section of a specific file, which is vital for building user trust and maintaining GDPR accountability. The answer is never a black box, because the source is always visible. How the agent retrieves information. The ingestion pipeline is finished. The documents are processed, chunked, embedded, and stored, so now the system just needs to answer a question. When a user opens the interface and types a message, that text travels from the browser to n8n through a webhook. This is a simple HTTP post that carries the question and a session identifier to link the message to the conversation history. Once n8n receives the data, the retrieval pipeline starts moving. The first step is a mirror of what happened during ingestion. The question text goes to the same Azure OpenAI embedding model that processed the document chunks. And the model returns a vector representing the meaning of that question. That vector is then compared against every single vector stored in the super-based table. The database calculates a similarity score between the question and each stored chunk, sorts them by that score, and returns the top results. The system is set up to return 25 candidates from that initial search. 25 sounds like a lot, and in reality it is. If you pass all 25 chunks directly to the language model, you create a new problem because the model's attention gets spread across too much material. Answers start to become vague as the model blends details from multiple chunks rather than grounding itself in the most relevant one. The constraint here isn't the size of the context window, but rather the quality of the model's attention. A model given 25 chunks of moderately relevant content almost always performs worse than a model given 4 chunks of highly relevant content. This is where re-ranking enters the pipeline. Cohere re-rank v3.5 takes those 25 candidates and scores each one specifically against the user's question. This is a different process than the first search. Vector similarity measures how close two pieces of text are in a mathematical meaning space, which is a geometric relationship. Re-ranking is a relevance judgment that measures how well a specific chunk actually answers a specific question. While those two things usually correlate, they are not the same thing. A chunk might be semantically related to a question without being useful for answering it, and re-ranking is what catches that difference. The re-ranker produces a new ordering of those 25 chunks based on how well they support the specific question asked. The system takes the top four from that new list and discards the rest. Four chunks go to the agent while 21 chunks get dropped, and that filtering step is what keeps the agent's context tight and its answers specific. The number four is not a random choice. During testing, four chunks represented the sweet spot where the context is rich enough to answer multi-part questions without becoming so diluted that the responses lose focus. If you use fewer than four, you run into gaps when a question requires information from different sections of a document. If you use more than four, the precision starts to drop. While the right number can shift depending on how dense your documents are, four is the correct default for a corporate knowledge base built from typical enterprise files. There is one part of this pipeline that requires a GDPR note, and that is the cohere re-ranking call. Cohere is a Canadian company, and the EU has formally recognized Canada as a country that provides adequate data protection under GDPR article 45. This means that data transfers to Canadian processes do not require extra safeguards like standard contractual clauses. The question text and the 25 candidate chunks pass through coheres model and that transfer is compliant as it stands. If you work in a sector like financial services or health care where any data leaving EU infrastructure triggers a manual review, you should verify this against your specific legal requirements. For most enterprise use cases, the adequacy determination covers the transfer. The four re-ranked chunks and the original question finally go to the agent as context. The agent's job at this stage is not retrieval because the retrieval is already done. Its job is generation, which means reading the question, looking at the provided chunks, and producing a coherent answer grounded in that content. But before it writes a single word, it checks whether the retrieval path was actually the right tool for the job because sometimes it isn't. The three agent tools, the agent has three tools at its disposal, understanding when it uses each one, and why that decision happens at the agent level rather than being hard-coded into the workflow is what separates this architecture from a basic chatbot. Tool one is vector store retrieval. This is the default path for the system. When a question comes in and the re-ranked chunks cover the right information, the agent reads those snippets and generates an answer. Most questions in a corporate knowledge-based land right here. You might ask about the return policy for enterprise customers or which safety protocol applies to a specific facility or what a service agreement says about response times. These are semantic questions about pros and the vector pipeline handles them perfectly. Tool two exists because vector retrieval isn't always enough. Imagine the agent gets a question about a specific product specification. The re-ranked chunks return a few relevant sections, but the agent can tell from those fragments that the full answer requires reading the entire document. It sees that the chunks are just pieces of a larger argument that only makes sense in sequence. In that case, the agent calls tool two for full document retrieval. It takes the file ID from those chunks, queries the vector table for every piece belonging to that document, and reconstructs the full content in the correct order. This is more expensive than returning four small chunks, but it's the right move when those chunks aren't sufficient. The agent makes that judgment call, so you don't have to guess which documents will need a full read. Tool three handles a class of questions that neither of the first two tools can answer. Anything involving arithmetic, filtering, or comparing data across tables goes here. Instead of searching for text, the agent queries the document rows table directly using SQL that it writes itself. That last part is important, so let's look at it closely. The agent doesn't get a pre-written SQL query, and it doesn't use a template with empty slots for column names. It reads the question, figures out what data operation is needed, and writes the query from scratch. When a user asks for total salary expenses in the third quarter, the agent determines this requires summing a column and filtering by a date range. It writes the select statement, the database executes it, and the agent returns the final result. Why let the agent write SQL instead of doing the math itself? Because language models are structurally unreliable at arithmetic, it isn't an occasional glitch. The way a model processes numbers is fundamentally different from how it handles language. It predicts tokens. For text, token prediction works because language has patterns, the model understands. For math, token prediction produces outputs that look like numbers, but aren't always right. The error rate on multi-step calculations is a real problem even for the best models. SQL has no such limitation. The database calculates the answer exactly every single time, regardless of how many rows it has to count. Using SQL isn't a workaround for a week model, it's just using the right tool for the job. The system prompt connects these three tools into one framework. It tells the agent the sequence to follow. Start with Rag. If the vector results don't have a clear answer, check the metadata, find the right file, and pull the whole thing. If the question involves a calculation, skip the vector path, and go straight to SQL. There is one more instruction every deployment needs. When none of the tools return enough information to answer the question, the agent must say so. It shouldn't synthesize an answer from nearby content or fill gaps with details that sound plausible. It needs to respond with a clear statement that the answer isn't in the documents. This ability to decline is what makes the system trustworthy. A system that always gives an answer is a system that eventually gives a wrong answer with total confidence. That is a much harder failure to catch than a system that simply admits it doesn't know. Writing the system prompt. The system prompt is where the architecture actually becomes a behavior. Everything we've built so far, the tools, the pipeline, and the image handling exists only as a capability. The prompt is what turns that capability into reliable action. Without it, the agent has the right tools but no way to choose between them. If the prompt is weak, the agent defaults to what it knows best, which is treating every single problem like a vector search. Think of the system prompt as the contract between you and the agent. It defines the terms of engagement by telling the agent what it knows, what it should do in specific situations, and what it must never do. Every messy case the agent hits in production is something the prompt either handled or it didn't. The ones that missed become the edge cases, you only discover when the system fails. Four core instructions make this architecture work. The first is to always start with rag. The vector store is the default path and the agent should reach for it first no matter how the user phrases the question. This prevents the agent from jumping to full document reads for every query. Those full reads are expensive and slow so they should only happen when the initial search fails to provide enough context. The second instruction covers escalation. If rag returns insufficient context, the agent must consult the metadata and retrieve the full content of the most relevant file. This path is for questions that are document specific rather than fragment specific. You have to be explicit here because agents don't escalate on their own. They usually try to answer with whatever they have, even if it's incomplete. Telling the agent to recognize when it's missing information is the only way to make this reliable. The third instruction is about the math. If the question requires any calculation or cross-row comparison, the agent must use the SQL tool. It should never attempt arithmetic through the language model itself. This needs to be a direct command saying use SQL for numerical questions is much better than preferred database operations where appropriate. vague instructions lead to inconsistent results. The fourth instruction is one most people miss. When images appear in the retrieved chunks, the agent should render them in line exactly where they appear in the document. It shouldn't collect them all at the end of the response. This matters more than you might think. The default behavior for a model is to finish the text first and then list the media at the bottom. That disconnects the image from the step it's supposed to illustrate, putting the image where it belongs makes the response feel like a real manual instead of a text file with attachments. Two more instructions finish the prompt. Tell the agent to always cite the source file name when it uses document content then tell it to be honest when it doesn't know the answer. No making things up, no guessing and no pulling from unrelated files just to fill the space. If you leave those out, the agent starts blending content from different documents without telling you where it came from. It starts building answers that sound right but are actually wrong. Both of these behaviors kill trust fast. Once your users stop trusting the system, they'll stop using it entirely. The system prompt isn't something you write once and forget. Every time the agent mis-roots a question or fails a calculation that's feedback that your instructions need to be sharper. Treat the prompt as a living document that grows alongside the rest of your workflow. Self-hosting, infrastructure decisions, where your system runs determines what it can actually do. Every production system breaks in ways your development environment never predicted, and this setup is no different. But the failures that actually matter aren't the obvious ones. You won't always see a credential that won't connect, a node throwing a bright red error or a workflow that just stops. Those are easy to fix because you can see them.
