A pipeline is a logical grouping of activities that together do one unit of work. That's Microsoft's definition, and it translates to something simple. The easiest way to hold it is as a recipe where each activity is one step on the recipe card. Those steps can run one after another, or several can run at the same time when they don't depend on each other. So a pipeline stays readable not to box you in. Activities come in three flavors, and the names mostly tell you what they do. The first group moves data and the star. There is the copy activity, which takes data from a source and drops it into a destination. The second group transforms data and that's where you find data flows, data bricks, and stored procedures. The third group controls the flow, the activities that decide what happens next. A for each loop repeats a step for every item in a list, and if condition branches down one path or another and a lookup fetches a value that a later step can use. Hold on to the word runtime as we go, because that's the piece that does the actual heavy lifting, and we'll get to it in a few minutes. The control activities are what turn a simple recipe into something that can think for itself because they handle chaining, branching, and looping. The engine room connections and addresses are useful, but on their own they just sit there. Something has to actually do the work. Microsoft describes it as the bridge between the activity and the linked service. Because the activity says what to do and the linked service says where while the runtime supplies the machine that actually runs it. A handy detail is that the runtime can sit in the region closest to your data, which is how the service keeps things fast while keeping data close to where it belongs. There are three kinds, and most beginners only ever meet the first one. There's good news before we even get to them. If you don't pick anything at all, the service uses a default Azure integration runtime that works out the closest region for you. The self-hosted integration runtime works differently. So far, we've assembled steps, connections, addresses, and an engine. What we don't have yet is a start signal, and that's the trigger. A trigger is the unit that decides when a pipeline run begins. A run is just one instance of the pipeline executing, and every run gets its own unique ID. So you can always look up exactly what happened and when. That detail matters more than it sounds, because when something breaks in the middle of the night, the run history is where you find out why. Three trigger types exist and two of them are easy to tell apart. The schedule trigger runs your pipeline on a clock. You might set it to fire every morning at six or every Monday at nine. Think of it as an alarm clock for your data. The event based trigger runs when something happens. The classic example is a file landing in storage, and the moment that file arrives, the pipeline springs to life. This one is more like a doorbell than an alarm clock. The tumbling window trigger is the third, and it's the one for people who care about reliability. It fires on a fixed repeating window, and it remembers its state, which means it can fill in gaps from the past, retry when a run fails, and cap how many runs happen at once? The plain way to describe the difference is this the schedule trigger starts a run and moves on while the tumbling window waits for that run to finish and reports back on whether it worked. When a process truly has to be dependable, that waiting is the feature you want. Mapping data flows, transforming without code. We keep saying transform, so it's finally time to open that box. Azure Data Factory versus fabric pipelines. There's a question that comes up in every beginner conversation about this tool, and it deserves a clear answer. Microsoft now has two versions of this idea, and people want to know which one to learn. The older established one is Azure Data Factory, which you set up inside Azure. It's what's called platform as a service, which means you get the pieces and you assemble them, and you pay for what you use as you go. It's mature, it's widely used. And most existing jobs today run on it. The newer one is called Data Factory in Microsoft Fabric, and Microsoft describes it as the next generation of Azure Data Factory. Fabric is software as a service, and it arrives as one connected package built around a single storage layer called One Lake. Instead of assembling separate pieces, you work inside one workspace that already holds your data, your pipelines, and your reports. The differences you'll notice are mostly about friction in fabric. Data sets go away and you connect to your data with simple connections instead. There's no publish step, so you just save and run. And you don't manage integration runtimes at all because fabric handles the compute for you. What stays familiar is just as important. The pipeline and activity model is the same, and the expression language is nearly identical. So what you learn in one transfers to the other. Microsoft says roughly ninety percent of the activities you can use in Azure Data Factory are already available in fabric, and fabric adds a few of its own. What surprises people is that Microsoft's own guidance now tells anyone new to data integration to start with fabric, and it says the two platforms keep separate roadmaps, which means new features land in fabric first. That's worth knowing before you decide where to spend your learning time. What it costs and how to keep it cheap. Whichever version you use, someone eventually pays the bill, so the meter is worth understanding. The first thing to understand is that the service is pay as you go. You pay per activity run, which covers the orchestration, the behind the scenes work of starting and tracking each step. You also pay for the data you move, measured in something called data integration unit hours, which is really just a way of charging for the size of the copy and how long it takes, and data flow transformations billed by the V Corps hour, because those spin up that spark compute. Activity runs about a quarter per data integration unit hour for movement, and about a quarter per V core hour for general purpose data flow compute. The reassuring part for a beginner is this a small daily pipeline that copies a file and loads. It will cost you pennies to a few dollars a month. Not a scary number. The thing that moves the needle is data flows, because each run spins up compute with a minimum of eight cores.
