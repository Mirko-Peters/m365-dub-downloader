But in reality, it's a trap. If you look at the micro benchmarks, the numbers seem clear. A STDO call between two processes on the same machine takes about one to four milliseconds. HTTP adds overhead because you have the network, roundtrip, TLS negotiation, and parsing to deal with. You're looking at 50 to 100 milliseconds per call. On paper, that is a 25 to 100 times difference. On the surface, STDO wins. But this is where the benchmark tells you a lie. Those numbers only measure transport latency. They show you the pure protocol cost. What they don't measure is what actually happens in a real enterprise system. In the real world, a dataverse query doesn't execute in five milliseconds. A typical query to dataverse runs somewhere between 515 milliseconds. That is just the back-end work. The database, the business rules, and the security checks that happen after your request arrives. Your total time is 1,000 and two milliseconds. Now do the same thing over HTTP. The request takes 100 milliseconds, dataverse executes for 1,000 milliseconds. The response takes another 100. Your total is 1,200 milliseconds. That is 200 extra milliseconds out of a total of 1,200. It's about 17% overhead. But it introduces a security problem that traditional applications never had to solve. How do you authenticate when your client cannot keep a secret? This is not a hypothetical concern. Claude desktop is installed on a user's machine. The configuration file that points to your dataverse endpoint lives on that same machine. If that configuration file contains a client's secret. Which is basically a password that proves the application's identity. You have a problem. Anyone with access to that file can impersonate the application and request tokens from your authorization server. The same applies to GitHub co-pilot. The same applies to any client. You do not directly control. Traditional OAuth solved this by assuming the client was a web server running in a secure data center. The server could store secrets in environment variables or encrypted vaults. The secret never left the server. A public application could not use OAuth because it could not protect a secret. PKCE, proof-key for code exchange pronounced pixie, removes that requirement. It lets public clients authenticate securely without storing any secret at all. Here is how it works. Instead of a static secret, the client generates a random value called a code verifier. It hashes that verifier into a code challenge. The challenge goes into the authorization request. The authorization server receives the request, verifies who you are, and returns an authorization code. The client then redeems that code by sending the original verifier alongside it. The authorization server hashes that verifier, checks that it matches the challenge, and issues a token. The security comes from the verification. If an attacker intercepts the authorization code, they cannot use it because they do not have the verifier. The code is useless without the verifier. Only the original client can provide the verifier. Because only the original client generated it. The verifier never travels over the network. The challenge, which is derived from the verifier, is what crosses the wire. And you cannot reverse a hash to recover the original verifier. This is not theoretical. It is formalized in RFC 76636, and is now a required component of OAuth 2.1. Every major identity provider supports it. EntraID supports it, Claude supports it, GitHub co-pilot supports it. Data versus MCP server is built with the assumption that clients will use PKCE. The practical implication is straightforward. Your Dataverse MCP endpoint asks EntraID for tokens. EntraID authenticates the user. The user's browser opens, they sign in, they are redirected back to the client with an authorization code. The client exchanges that code with the verifier it generated and receives a token. No secret sits in the configuration file. No secret leaks into logs. No secret appears in the client's prompts or behavior. This is what enables the multi-LLM integration model. You can point Claude at your Dataverse endpoint. You can point GitHub co-pilot at the same endpoint. You can point the custom orchestrator at the same endpoint. They are all using PKCE. They are all securing themselves without requiring any shared secret that you have to manage, rotate, and protect across every client installation. Redirect URIs, the callback contract. With the app registered, you need to define the redirect URIs. This is where the architecture meets the real world. When a user authenticates through Dataverse MCP, they're going to see an authorization screen where they enter their credentials.
