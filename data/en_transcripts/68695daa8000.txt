This is going to map the failure modes, why they happen, why they persist, and why they're inevitable unless you enforce design, not etiquette. The foundational misunderstanding. Fabric is not a platform, it's a decision engine. Fabric gets sold as one platform, but the UI supports that story. The marketing supports that story. Execs love that story because it sounds like consolidation. Fewer tools, fewer vendors, fewer invoices, fewer problems. Architecturally, it is something else. Fabric is a composed system of engines that share a control plane and a capacity pool and then make thousands of runtime decisions on your behalf. Those decisions don't align to your org chart. They don't align to your project boundaries. And they definitely don't align to the PowerPoint data strategy you presented to the steering committee, that distinction matters. A platform implies a consistent execution model. One set of guardrails, one predictable cost behavior, one place where intent becomes enforcement. Fabric behaves more like a distributed decision engine. A compiler for analytics workloads. You submit work, refreshes, queries, pipelines, notebooks, streaming, mirroring, and the system chooses how to run it within a shared set of constraints. And the moment you accept that the governance story changes, let's break down the four myths that create the rot. First, unified versus composed. Yes, you can build in one place, but behind the curtain, fabric isn't one runtime. You have power BI's semantic model behaviors. You have spark-based workloads. You have warehouses with their own query patterns. You have event house and KQL. You have data factory style orchestration. You have background operations that no human asked for in a meeting. But the system executes anyway. One UI does not equal one execution model. In reality, it is many engines with one veneer. And every engine has different tuning knobs, different failure modes, and different cost signatures. Second myth, capacity is a boundary. Capacity is not a project boundary. It is not a tenant boundary. It is not a safety boundary. Capacity is a shared compute pool. So when team A runs a heavy refresh, team B doesn't just see slower dashboards. Team B inherits contention. Team B inherits throttling. Team B inherits the smoothing behavior. And then team B files an incident. Not because they did something wrong, because the shared pool reallocated pressure. This is where deterministic planning dies. Executives want cost predictability. Architects want workload predictability. Capacity provides neither when you treat it as a shared commons without enforced allocation. The system did what it was designed to do. Share.
