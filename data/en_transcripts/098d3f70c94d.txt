The plan is reasonable. It executes and calls the device "lookup function" which works perfectly. Then it calls the compliance check, but the device is non-compliant. The plan was based on the assumption that the device was compliant and that assumption just broke. The agent recalculates. If the device is non-compliant, the issue might not be about licensing, it might be that conditional access is blocking the login. The agent loops back to planning and creates a new plan to check the conditional access policies. It executes the new plan and evaluates the result success. The agent found the specific policy that's blocking the login. Now it needs to decide what to do. It probably shouldn't fix this autonomously because changing a conditional access policy is high risk. This is a decision point where the agent needs human judgment, so it builds a structured proposal instead of executing a fix. It tells an IT manager what the issue is and asks if it should apply the fix. The manager approves it in Teams and then the agent executes. This is the plan "execute refine loop in action". The agent isn't following a predetermined script. It's building a mental model and adjusting based on what it learns. When things go sideways, it doesn't fail. It adapts. Orca-strating multi-step workflows. Now we need to look at what actually makes this useful for real work, because the reality is that IT tickets are almost never simple. They don't just show up as a clean request to reset a password. Instead, they arrive as a messy tangle of interconnected problems that touch five different systems at once. Take a common ticket like user can't access Teams. On the surface, that sounds like a single problem, but in reality, it's a dozen. To figure out what's actually happening, you have to check if the user exists in Azure AD, verify their Teams license, and see if the service is even enabled for the company. Then you have to look at their device compliance, check for network blocks, investigate mailbox sync states, and confirm they're in the right groups. That isn't a two-step process. It's a 10-step investigation, where the order of operations matters. You can't check for a license if you haven't confirmed the user exists yet, and you can't verify device compliance if you don't even know which hardware they're using. Some of these checks are prerequisites, some are fallbacks, and others only matter if the first three things fail. A traditional script tries to hard-code this entire sequence from step one to step 10. If anything goes sideways, the script relies on conditional logic that you had to anticipate months ago, but you can't predict everything. Maybe a serial number is missing from the ticket, or an API call times out, or the mailbox is in a weird state that your code wasn't built to handle. When that happens, the script either hits a dead end, or it just fails. An agent doesn't follow a hard-coded map. It reads the ticket, and decides what needs to happen next based on the evidence. It understands that the first logical move is to confirm the user exists, so it makes that decision and executes it. When the result comes back, that data either confirms or destroys the next assumption, and the agent adjusts its plan accordingly. Watch how this workflow actually unfolds. The agent reads a ticket from JSmith@Company, comes saying they can't get into teams. The agent plans to check the user's state and the service state, so it calls the lookup function first. The result shows the user exists with ID, ABC123. Next, it checks the license and sees its active. It checks if the service is enabled, and the answer is yes. Then it hits a snag. It needs to check the device state, but the ticket doesn't say which device is the problem. The agent sees two registered devices and realizes it can't move forward without knowing which one is failing. It leaves a note for the human asking for clarification, but it doesn't just stop there. It keeps digging and finds a conditional access policy that's currently blocking all unmanaged devices. Now the agent has the full picture. The likely culprit is that one of the user's devices isn't managed, and the security policy is doing its job. The agent decides on a fix, like enrolling the device or creating an exception, but it knows these are high-risk moves. It won't act autonomously here. Instead, it builds a structured proposal for an IT manager. The manager gets a notification in teams with a clear breakdown. The user is blocked on an unmanaged device. And here are the three ways to fix it. The manager clicks "Approve for device enrollment" and the agent handles the rest. It runs the enrollment, verifies the fix, and tells the user they're good to go. This entire loop, the diagnosis, the adaptation, the escalation, and the final execution is what a multi-step workflow looks like. The agent decided the sequence and adapted when it hit a gap in the data. It didn't break just because a condition was unexpected. It reasoned its way through. A hard-coded script fails here because the person writing it couldn't predict every single variable. You can only code for the problems you've already thought of. An agent reasons about what matters based on the live ticket, deciding what to query, and in what order based on what it learns at every step. This is why agents handle variety without needing a script rewrite every week. The human in the loop isn't a feature you bolt on later. It's built into the logic. The agent knows exactly when it's moving from looking at data to changing things. And it stops to ask for permission before it crosses that line. Error handling and fallback strategies. We have to be honest about scripts. They are incredibly brittle. The moment an error happens, the whole thing stops, an exception is thrown, and the process dies. Then a human has to step in to find the bug, edit the code, test it, and redeploy the whole thing. That recovery cycle is slow, manual, and expensive. Agents have to work differently. When a problem pops up, they shouldn't just quit and report a failure. They need to recover, try a new path, and stay resilient. The difference is in the logic. A script says, "Do this and if it fails, stop." An agent says, "Try this." And if it fails, let's look at why and try the next best thing. Let's look at a password reset. The agent calls the reset function, but the system returns an error saying the user wasn't found. A standard script would just stop and escalate to a human. The agent, however, reads that error and thinks about what it actually means. Maybe the user exists in a different directory, or perhaps their name was misspelled in the ticket. Instead of quitting, the agent tries a different angle. It might search by a partial name, a phone number, or look for recently updated accounts. It can loop through these fallback strategies until it finds a match that works. The secret is that the agent has to be able to classify what kind of error it's looking at. Not all errors are created equal. A temporary error might be a service throttling your requests, which just means you need to wait 30 seconds and try again. A permanent error is something like a deleted account where no amount of retrying is going to help. Then you have recoverable errors like a missing user that might be found elsewhere and fatal errors like a lack of permissions. An agent that understands these categories can handle them with some intelligence. If it's temporary, it uses an exponential back-off to retry. If it's permanent, it skips to the next logical step. If it's recoverable, it tries a different tool. And if it's truly fatal, it stops and asks for help. In practice, this looks like an agent handling an access ticket. It tries the email address and gets nothing. That's a failure for that specific tool. But the agent knows it's a recoverable situation. It tries searching by the display name, finds the right person, and keeps moving. If every single search method fails, the agent finally stops and tells the human that the user doesn't exist anywhere in the system. When the human gets that message, they have all the context they need to make a fast call. They can see it's a typo or a new hire that hasn't been onboarded yet. Because the agent did the legwork, the human isn't starting from scratch. The goal here is graceful degradation. If the agent can't solve the whole ticket on its own, it doesn't just crash. It hands the problem to a human and explains exactly how far it got, what it tried, and what finally blocked it. The human isn't wasting time on diagnostics anymore. They're just the tiebreaker. To make this work, you have to build explicit error classification into your functions. You can't just return a success or fail flag. You need to provide enough data, so the agent can decide if there's a recovery path or if it's time to escalate. Resilient systems are designed for failure. You have to expect that things will break and give your agent the tools to try a plan B. By letting the agent navigate these small hurdles on its own, you keep the workflow moving instead of letting every minor error turn into a manual task for your team. Human in the loop approval gates, you need to draw a very clear line. On one side, you have things an agent can decide on its own. On the other, you have things that require a human judgment call. Getting this boundary right is the difference between a helpful tool and one that goes rogue. Not every decision should be autonomous. Some actions are low risk because they don't actually change anything. If an agent wants to pull a list of users, check forwarding rules on a mailbox or look at device compliance data, that's safe. It can do those things without asking for permission, but other actions are high risk. Deleting a user account, resetting MFA or changing access permissions can break someone's entire workday. These actions change the state of your environment and could even create a security hole. Because of that, you need a human to say yes before the agent pulls the trigger. The best practice for 2026 is simple. Agents propose and humans approve. The agent does all the heavy lifting during the diagnostic phase that gathers the context, looks at the situation, and reaches a conclusion about what needs to happen, but it doesn't execute high risk changes on its own. Instead, it creates a structured proposal that explains what it found, what it wants to do, and why it thinks that's the right move. Then it waits. The word "structured" is the most important part here. The proposal isn't just a big block of text that's hard to read. It's a specific object with clear fields like the proposed action, the reason, the risk level, and the potential impact. It shows which checks passed and if there are any blockers. By laying it out this way, a human can review the facts in seconds and make a fast decision. Think about how this looks inside Microsoft Teams. When an agent hits a situation that needs a human eye, it builds that proposal. But instead of sending a message, it sends an adaptive card. The card is clean and easy to scan. You see the username, the status, the proposed action, and the impact. It tells you if the user will be notified or if an audit log will be triggered. At the bottom, you have three simple buttons. Approve, reject, or ask me more questions. A human gets the notification and looks at the card. It takes maybe 10 seconds to review the details. If they hit "approved" the agent goes to work, if they reject it, the agent takes that feedback and tries a different path. If they have questions, the agent can provide the diagnostic data it used to reach that conclusion. The human is making an informed choice, not a guest. This is what we call "risk-based" tearing. Low-risk actions stay autonomous, but medium-risk tasks might need a team lead to sign off. High-risk actions like deleting a user should require a manager or a security officer. Your policy layer defines exactly what fits into each tier. This gives humans control over the decisions that actually matter while letting the agent's handle the small stuff. The beauty of this model is that it scales. One person approving decisions won't become a bottleneck if most of the work doesn't need approval. The agent handles the easy stuff, like running diagnostics and fixing low-risk queries. Humans are no longer stuck doing the busy work or running routine tasks. They are making the calls that matter. Their time is spent on actual decision-making rather than the administrative work that leads up to it. In this setup, the agent is a decision support system. It isn't there to replace human judgment, but to augment it. It gathers all the relevant info, analyzes it, and hands over a clear recommendation. The human still brings their expertise and organizational knowledge to the table. The difference is that they're making that choice with complete information instead of operating in the dark. This is also how you build trust. Organizations don't trust machines that make irreversible changes without asking first. But they do trust systems that propose a plan, explain the logic and wait for a green light. You aren't handing over the keys to the kingdom. You're just letting the machine do the analytical work so you can focus on the final decision. The agent becomes a collaborator rather than a replacement worker. It does what is best at, which is rapid analysis and calling APIs. You do what your best at, which is weighing risk and understanding nuance. When you work together like this, you move much faster than either of you could alone. Case study. Autonomous ticket resolution. Let's look at a real scenario to see how this works. The result is a level of speed and accuracy that you just can't get when you're working alone. Scaling to enterprise operations. One agent resolving one ticket is a great proof of concept, but in a real organization, you don't deal with one ticket a day. You deal with hundreds or thousands. This is where the model breaks. We have to stop talking about a single agent and start talking about a fleet of agents running in parallel. The architecture changes fundamentally when you move to this level. Instead of one agent and one orchestrator, you have a pool of agents, a work dispatcher, and a monitoring system that watches everything. Think of the dispatcher as the nervous system of the entire operation. Tickets come in and get routed to the first available agent with the right skill set, which keeps the flow moving. An identity agent handles user account issues, while an infrastructure agent manages device compliance and an application agent deals with licensing. The dispatcher looks at the incoming request, categorizes the problem, and sends it to the right specialist. If every identity agent is busy, the ticket sits in a queue until someone finishes their current task and picks up the next one. This is load balancing, but it is much smarter than just assigning tasks in a circle. Each agent tracks its own performance metrics in real time, measuring success rates, resolution times, and how often it has to escalate a problem. The dispatcher uses this data to root work intelligently. If one agent consistently results password resets in eight minutes while another takes 18, the dispatcher roots more of those specific tasks to the faster agent. This isn't a permanent change because agents improve or decline over time, so the system adjusts dynamically based on current capability. To make this work, your infrastructure has to be cloud native. You aren't running fixed agents on fixed servers anymore. Instead, you are spinning up agents as the load increases and tearing them down when things get quiet. This is orchestration at a different level where Kubernetes handles the container life cycle while the dispatcher manages the actual flow of work. The monitoring layer watches both the hardware and the agents themselves to ensure everything stays healthy. Monitoring is the most critical piece of this puzzle. A central dashboard shows you exactly how many tickets are in the queue, how many are being worked on, and how many were resolved in the last hour. It tracks agent health and availability constantly. If an agent starts crashing repeatedly, the system pulls it from the pool and flags the issue for the operations team. It also reveals escalation patterns. If a certain type of ticket is being kicked back to humans more than expected, it tells you that something is wrong with the training or the classification. The data shows you whether the problem is outside the agent's scope or if it just needs better documentation. This is where feedback loops finally start to matter. Every ticket and agent resolves in every decision it makes becomes part of a massive pool of training data. Your system is actually learning. Some organizations feed this data directly back into the model while others use it for periodic retraining, but the result is the same. The agent that used to take eight minutes per ticket gets faster and the escalation rate on difficult issues drops as the agent learns from human corrections. Load balancing also gives you the power to handle massive traffic spikes. On a typical Monday morning, you might get a wave of tickets because everyone had issues over the weekend, but you can just spin up more agents to clear the queue. By Wednesday evening, when things slow down, you scale back and stop paying for compute you don't need. Parallel execution changes your throughput completely and if you had one script running one ticket at a time, you would be limited by the clock and a hundred tickets would take hours to finish with a fleet running in parallel though same hundred tickets might be done in 30 minutes. The time it takes to resolve an individual ticket doesn't change much but your total capacity multiplies. This is the shift from running a script to running an operation. You aren't just launching a PowerShell command anymore. You are operating a complex system of agents, orchestration and governance. The agents are just the workers, while everything else is the machinery that makes them reliable at scale. This requires a real infrastructure shift. You need a message queue for work distribution and deep observability through logging and metrics. You also need policy engines to enforce rules and human approval workflows to keep things safe. Most importantly, you need an audit trail for every single action. It also forces you to change how you think about governance. You have to decide who approves what, how the escalation path works and what happens if an agent makes a mistake or gets attacked. These are operational questions, not development ones. Moving from a pilot to full production isn't about writing better code. It's about building the system that the agents live inside. Governance and guardrails. Autonomous agents running at scale need boundaries that are clear, enforced and unchangeable. Without these limits, you are just giving away access and hoping for the best. The governance layer is what turns an agent from a wildcard into a predictable reliable system. Think about the level of access you are actually granting here. You have agents that can query sensitive user data, reset passwords, modify permissions, and even send emails on behalf of the entire company. Any one of those powers is a massive risk if it's used in the wrong context. Putting all of them together in an agent without guardrails is a guaranteed way to end up explaining a massive security breach to your board. The policy layer is what defines these guardrails. It is a declarative model that states exactly what an agent can do, which data it can touch and under what specific conditions it can act. This isn't buried in a block of code or a forgotten configuration file. It is a living document that the governance team controls and auditors can review at any time without needing to redeploy the agents. In practice, this looks very specific. You might define a policy that says a password reset agent can only help users in the HR department if it gets approval from an HR manager first. You can even add a rule that it only works if the user hasn't asked for a reset in the last 30 days. Because the rules are measurable and specific, the agent checks them every single time it tries to act. If the conditions aren't met, the agent stops and either refuses the request or escalates it to a human. Policies can be incredibly granular. You don't just say an agent can read all user data, you say it can read six specific fields for users in the sales department during business hours. The access is scoped to exactly what is needed for the task and nothing more. These policies also determine when a human needs to step in. A simple read-only query might not need any oversight, but modifying an email address or deleting a device certainly does. Your policy layer maps every possible action to a specific approval tier. This means the agent knows whether it needs a yes from a human before it even attempts to perform the action. The audit trail is the necessary partner to these policies. Every single move an agent makes is logged, including what triggered the action, which policy allowed it, and what the final outcome was. If something goes wrong, you can rewind the tape to see exactly what happened and who approved it. This audit trail serves several purposes at once. Regulators need to see that you are tracking who accessed what and when, but it's also vital for troubleshooting. If an agent starts behaving strangely, you can replay the logs to see exactly where its reasoning went off the rails. It also provides the feedback you need to improve the system by showing you where policies are too tight or where agents are making repeated mistakes. Compliance requirements are baked directly into this layer. If you have rules about data classification, the agent has to respect them. It won't export confidential files or keep personal data longer than the retention window allows. The policy isn't just a suggestion. It is a hard constraint that the agent cannot break. The shift happening here is fundamental because you are moving from trusting the script to trusting the policy. With old school scripts, you had to trust that the author wrote secure code, which meant you had to audit the code itself before it ran. If something broke, the script was the problem. With agents, you trust that the policy is correct and the enforcement is airtight. The agent is just a worker following orders. If something goes wrong, it means the policy failed, not the agent. This also changes how you handle updates. With traditional scripts, every update is terrifying because a small error could break everything. With agents, you don't change the code to change the behavior. You just update the policy. If you want an agent to be more autonomous, you adjust the governance layer. If you need to restrict it, you do the same. The capability of the agent stays the same in the code, but its permissions change in the governance. Governance is actually what enables you to scale. It isn't a hurdle or a constraint. It's the foundation that lets you spin up more agents with total confidence because the boundaries are clear and the audit is complete. You don't have to worry about what might go wrong. You have a perfect record of everything that happens and a system that ensures it stays within the lines. Security considerations for autonomous agents. The moment you give an agent the power to execute commands, you have created a high-value target. Unlike a human employee, an agent never gets tired, and it won't stop to question a suspicious instruction. It simply follows its logic to the end. This creates a massive risk if the agent is compromised or if someone manages to inject malicious instructions into its context. You have to ask yourself, what is the blast radius if this goes wrong? You need a real-world threat model based on what actually matters in your specific environment. The danger isn't just that an agent might malfunction. The real threat is that someone outside your organization or even a malicious insider turns that agent into a weapon. Isolation is your first line of defense here. Agents shouldn't run on the same infrastructure as your critical systems. Instead, they need to live in containers, Kubernetes pods, or isolated network segments. If an agent is compromised, that isolation keeps the damage contained. It prevents the attacker from immediately pivoting to your domain controllers or email servers. Think of it as a sandbox. This is a major shift from how we usually run scripts. A script running on a server with admin rights can reach your entire environment, but an agent in a properly configured container can only see what you explicitly allow through network policies. Credential handling has to change as well. Traditional scripts usually store credentials in an encrypted vault or a config file. The script authenticates once, gets it token, and uses that token for as long as it lives. If that credential leaks, it stays valid for a long time. An agent should never store credentials like that. It shouldn't have long-lived tokens at all. Every time it needs to perform a task, it should request a new credential from an identity broker that is only valid for that specific job. Because these credentials expire in minutes, they are worthless to a thief almost immediately after they are issued. This ties back to headless authentication in CAE, but the security angle is much more aggressive. It isn't just about checking a compliance box. It's about ensuring that even if someone dumps the agent's memory or reads its logs, there are no usable credentials sitting there. If that agent starts behaving strangely by making unauthorized API calls or accessing data it doesn't need, the policy engine can revoke its access instantly. Behavioral analytics serves as your early warning system. If an agent that usually processes password resets suddenly starts scanning every user in the directory, that is a major signal. If an agent that typically runs during business hours suddenly wakes up at 3am, or if it jumps from 10 API calls to 1,000, your monitoring system needs to flag it. This is actually easier than traditional monitoring because agent behavior is incredibly predictable. You know exactly which commands it should run, what data it needs, and how long the process should take. Any deviation from that baseline is a red flag that likely indicates an attack. While a script has broad boundaries because humans might run it in different ways, a production agent has a very narrow path. Anything outside that path deserves an immediate investigation. The principle of least privilege becomes much tighter with agents. A human might need broad permissions because their job requires flexibility across different domains. An agent only needs exactly what is required for its one specific function. A password reset agent has no business reading email servers and a device provisioning agent doesn't need to see financial data. You enforce this at the API level so the agent can call a function, but the function itself is restricted to specific objects. This represents a profound shift in how we think about security. With scripts, you focus on securing the code by scanning for vulnerabilities and auditing changes. It's a code security problem. With agents, you are securing the identity and the context. The code is actually secondary. The real question is what this agent is authorized to do right now in this exact moment with this specific identity. If that answer is tightly scoped and constantly re-evaluated, the agent stays secure even if the code has flaws. Security architecture is moving away from the traditional perimeter. We are moving toward a zero-trust model where every single agent action is evaluated, every identity is verified and every behavior is monitored. The agent doesn't get a free pass just because it's software. In fact, you should treat it with less trust than a human user because it operates autonomously. Your security team will find their roles changing too. They won't just be auditing lines of code anymore. Instead, they will be defining policies, reviewing behavioral baselines and managing the identity life cycle for an entire fleet of agents. They have to think about attack surfaces that simply didn't exist a few years ago which requires a completely different skill set, measuring agent performance. When you move from scripts to agents, your measurement system has to change completely. You can't rely on the old metrics because you aren't evaluating the same type of work anymore. With scripts, success was a binary outcome. You check to see if it ran, if it crashed or if the logs showed any errors. These are mechanical measurements. The script either finished its sequence or it didn't. You measured things like runtime and error frequency. And if the script finished without a crash, you just assumed it worked. The logic was hidden inside so you couldn't see why it made certain decisions. Agents are a different story. A script might run perfectly but still fail to solve the actual problem. On the other hand, an agent that stops and escalates a ticket to a human might actually be making the smartest possible move. Success isn't about the agent running smoothly. It's about the agent achieving the final goal. You should start by looking at your automation rate. This is the percentage of tasks that are fully resolved by the agent without any human stepping in. If you handle a thousand tickets a month and your agents resolve 400 of them, your automation rate is 40%. This is your headline metric because it shows exactly how much work the agents are taking off your plate. You should expect this number to climb as you refine the agents though it will never hit 100%. Some problems will always be outside the agent's scope but the trend will tell you if you're moving in the right direction. The escalation rate is the other side of that coin. When an agent can't finish a task, you need to know how often it escalates versus how often it just fails. A well-designed agent will escalate more than it fails. Escalation means the agent tried, realized it couldn't finish and handed the ticket to a human with all the necessary context. Failure means it just crashed or threw an error with no way forward. You want to see low failure rates and high escalation rates. An agent that hands over a complete diagnostic report to a human is much more valuable than one that fails silently. Approval time is another critical factor because humans are often the bottleneck. When an agent suggests a fix that needs a sign off, how long does that take? If your agents are fast, but your humans take two days to review the work, you've just traded one bottleneck for another. You want these approvals happening in minutes rather than hours. This metric tells you if your workflow is actually efficient or if it needs to be redesigned. Quality metrics are harder to track, but they are essential. Accuracy asks if the agent did the right thing, diagnose the problem correctly and apply the proper fix. You measure this by having a human expert sample agent decisions to verify they were correct. Over time, this builds a reliable quality score. You also need to measure completeness. Did the agent solve the whole problem? Or did it stop after fixing just one part of a multi-step issue? Then you have the business metrics. Cost per resolution is the total cost of your compute power and human approval time divided by the number of tickets resolved. This tells you if automation is actually saving you money. If your agents end up costing more than your human staff, your model is likely broken. You also want to track the mean time to resolution or MTTR. When agents are involved, the time from ticket submission to closure should drop significantly. Finally, check user satisfaction to see if people are actually happier with the faster response times. The shift here is moving from, did the system work? To, did the system solve the problem? Scripts let you measure execution, but agents require you to measure helpfulness. This also changes your feedback loop. With scripts, you look at logs to find bugs in the code. With agents, you look at quality metrics to see where the decision making went wrong so you can retrain the model or update your policies. You aren't just debugging code anymore. You are improving the way the system thinks. New observability practices are starting to emerge around this. You need real-time dashboards that show these trends and historical data to see if your improvements are actually sticking. You need to break things down by category so you can see if your agents are great at one task but struggling with another. You also need drill-down views that let you inspect a specific ticket to see exactly what the agent decided and why it made that choice. Measurement becomes a constant conversation between you and your agent fleet. The metrics will show you exactly where to focus your energy next. If your automation rate is stuck at 30%, you need to look at the 70% that is still escalating. If your approval time is creeping up, your process is becoming a bottleneck. Moving an agent from a lab experiment to a production workhorse requires a specific path. The technology isn't actually the hard part because you have already built the core logic. The real challenge is shifting how your team works, what they monitor, and how they build trust in the system. You have to follow a roadmap with distinct phases and if you try to skip them, it will cost you. Phase one is the pilot. You pick one narrow domain and one specific capability like password resets and that is it. You build a single agent that does one thing. It only runs queries with read-only access to Azure AD and Intune so there are no rights and no approvals yet. When a user submits a ticket saying their password expired, the agent reads the account status, confirms they exist, and checks that they aren't locked out. It resets the password and notifies the user before closing the ticket. This phase proves the fundamental concept that an agent can interpret natural language and execute a sequence of actions to solve a real problem. You aren't doing anything fancy or using complex reasoning yet but you are showing the team that the idea works so they can gain confidence. This pilot usually runs for four to eight weeks while you measure success rates in error patterns. This is where you discover the operational infrastructure you are missing, like better logging or a plan for updating agent behavior. You might realize that approval workflows are much harder than you thought but these discoveries are exactly why you run a pilot. You are learning what it takes to run the system at a low scale where mistakes don't cause a massive collapse. Phase two is expansion. You add a second domain, perhaps access requests or device provisioning, which means you now have two agents running in parallel. This is where scaling starts to matter because you are adding complexity instead of just doing more of the same. The orchestration layer now has to root tickets to the right agent and your monitoring must track which agent handled which specific task. You can start introducing low risk right operations here. The access request agent might assign a user to a group if the request is valid but you still avoid high risk changes like deletions or MFA resets. You only allow straightforward modifications that you can easily undo if something goes wrong. You also start introducing approval workflows for medium risk decisions during this six to ten week period. You are proving that multiple agents can coexist and that the routing works without the approval system becoming a bottleneck. This is when you start seeing patterns in what the agents get right and where they struggle and that feedback becomes the fuel for your retraining and policy adjustments. Phase three is scale. You have a fleet now with five or six agents handling different domains from a shared ticket queue. The orchestrator distributes work based on capability and availability. And while high risk operations are finally in the mix they all have strict approval gates. This phase is about proving the system can handle real production volume. You aren't testing 100 tickets a week anymore but instead you are running hundreds every single day. This is where your infrastructure scaling happens and you find out if your Kubernetes setup can actually handle the load. You will see which types of tickets the agents nail and which ones cause them to stumble. This phase typically runs for three or four months as you ramp up the volume and the business impact becomes visible. Tickets that used to take two hours now take 15 minutes which clears your backlog and frees your IT staff from routine drudgery. This is the moment you get the organizational buy-in needed for the final stage. Phase four is optimization. Your agents are production grade so now you focus on making them better. You feed resolution data back into the model so the agents can learn from human corrections. You adjust policies based on the patterns you see and optimize routing so the right agent gets the right ticket more often. You reduce approval times by refining what actually needs human judgment versus what the agent can decide on its own. This phase is continuous because it isn't a checkpoint but an ongoing operational mode. You are constantly measuring ROI and tuning performance while adding new domains as opportunities appear. The entire journey from pilot to production usually takes six to 12 months. It isn't because the technology is slow but because operationalization requires a high level of discipline. You cannot skip phases or try to pilot everything at once. You have to prove at each stage that the system works that your team knows how to run it and that the business impact justifies the next step.
