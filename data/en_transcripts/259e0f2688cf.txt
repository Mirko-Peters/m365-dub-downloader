In a giant shared retrieval chain, poor behavior spreads across many use cases and becomes much harder to isolate. So remember the hierarchy. The expert owns the task. Retrieval supports the expert, not the reverse. Once teams get that right, the architecture becomes much easier to govern because data access is no longer treated like a universal pool. It becomes part of a bounded role. And the moment data starts getting segmented that way, governance stops being something you add later. It becomes part of the structure from the beginning. Governance changes completely in multi-agent systems. When you move from one agent to many, governance stops being a side layer and becomes part of the runtime design. That is the shift. A lot of teams still think in all terms. They focus on prompt safety, output filtering, and maybe a few blocked words. Those controls still matter, but they belong to a simpler world where one model answered one question and stopped there. Multi-agent systems do not work like that. They read, they root, they call tools, they hand work off, they pull data from different places, they might trigger workflows or involve different identities and permissions in the same user journey. Because of this, the risk surface is no longer just the answer. It is the whole chain. That changes everything. The failure point might be the root, not the response. It might be the wrong specialist receiving the task, or perhaps a connector with too much access. It might be a handoff that loses context while keeping authority or an oneless flow still running in production. It might be a model switch that nobody reviewed or a transcript gap that leaves security teams unable to reconstruct what happened. In a multi-agent setup, we control usually shows up between components instead of only inside one. So the first governance question becomes inventory. What agents exist? What models do they use? What flows do they trigger? What connectors do they hold? What data can they reach? Who owns them? What is their purpose? When do they expire? If you cannot answer those basics quickly, you do not have a governed agent system. You have agents sprawl with a nice interface. The research is very consistent on this point. Inventory is not admin overhead. It is the foundation. Without it, you cannot do lifecycle control, permission review, incident response or meaningful risk assessment. Ownership has to be explicit too. Not the AI team in general, not IT in broad terms. A named owner for the front door agent, a named owner for the policy expert, a named owner for the workflow path, a named owner for the data source. The moment a routed system crosses departments, accountability gets blurry fast unless you force clarity into the design. Blurry accountability is how risky automation survive longer than they should. Permissions become even more important here. In a single agent world, people often debate model quality first. In a multi agent world, least privilege is usually the sharper control. An average model with tight permissions is easier to contain than an excellent model with broad access and vague tool rights. The biggest harm often comes from what an agent can reach or trigger, not from whether its wording is elegant. If one specialist only needs one site, one table and one action, give it exactly that. Nothing wider. Logging has to expand as well. Final answers are not enough anymore. You need prompts, routes, tool calls, handoffs, actions, outcomes and timestamps. You need enough trace to answer four questions later. What happened? Why did it happen? Which component decided it? And what data did it touch? If your logs only capture the final user message and final user answer, you are blind to the actual behavior of the system. This is also why deployment governance cannot wait until after launch. You need review gates before production. You need environment separation. You need different permissions in dev, test and prod. You need policies around model approval, connector approval and action approval before agents start multiplying. Once they spread through the tenant, cleanup gets harder, not easier. Multi-agent systems reward discipline early and punish improvisation late. And this is where the Microsoft Conversation changes too. Because once governance has to span identity, inventory, policy, life cycle and oversight across many agents, you need more than good intentions and scattered admin settings. You need a control plane. That is where agent 365 enters the picture. What agent 365 changes and what it does not. So now we can place agent 365 properly. A lot of people hear the phrase and assume Microsoft has delivered one master answer for agent governance. One place to switch everything on. One surface that solves inventory, policy, risk, identity and runtime control in a single move. That is too generous. Agent 365 matters, but it matters in a more specific way. It changes governance posture because it treats agents as first class managed things. Not as random side projects, not as invisible flows, not as clever assistance floating around the tenant with unclear status. The research points to a few concrete shifts. Agent 365 brings a registry idea to the center. It gives each agent a managed identity pattern through agent ID concepts. It connects policy, ownership, life cycle and discovery into one governance surface. And it ties that surface into the rest of the Microsoft Control stack, especially Entra, Per View, Defender and the admin center. That is a real change. Because once agents become visible as governed identities, you can start asking better questions. Which agents exist? Who owns them? What permissions do they hold? Which data sources do they touch? Which tools can they invoke? Which environments are they running in? Which ones are experimental? Which ones are production? Which ones should have been retired already? But are still hanging around. Without that inventory spine, enterprise agent governance stays fragmented. That is where Agent 365 is strongest. It gives you a place to anchor identity and oversight across specialized agents, including agents that reach into different services and workflows. In a routed architecture, that matters more than it would in a single agent setup. Because specialist systems multiply fast. The number of models, connectors, sub agents, and delegated parts increases and the chance of often logic rises with it. Agent 365 helps reduce that blindness. It also strengthens policy enforcement through connection, not isolation. An agent ID can sit inside the larger-entra model. Per view can shape data controls around prompts, responses, and access patterns. Defender can monitor unusual behavior or risky relationships between agents and data. Admin services can help discover, govern, and review what is active. That connective role is why I would call Agent 365 a governance spine. It does not replace the rest of the body. It gives the body structure. That distinction matters because expectations are running ahead of reality. Agent 365 is not a full cross-cloud answer to every agent problem. The research is pretty direct about that. Governance gaps still exist when agents move across external clouds, external run times, third-party tools, or partially integrated ecosystems. Visibility may weaken. Enforcement depth may vary. Some telemetry may still be incomplete. If your architecture spans Azure, Microsoft 365, outside SAS, custom MCP servers, or other clouds, you still need deliberate design. Agent 365 helps, but it does not excuse sloppy boundaries. It also does not remove the need for charters. You still need to define what each agent is for. You still need owners. You still need risk tiers. You still need approval logic. You still need connector discipline and environment separation. If an organization treats Agent 365 as a reason to stop doing architecture, it will just centralize confusion more efficiently. So use it for what it is actually good at. Use it to register agents. Use it to anchor identity. Use it to apply policy consistently. Use it to support life cycle reviews, discovery, and monitoring. Use it to connect governance across the Microsoft stack, but do not confuse a control plane with a complete design. A control plane can tell you what exists, constrain what is allowed, and help you stop unsafe things faster. It cannot decide your expert boundaries for you. It cannot magically clean up overlapping missions. It cannot turn a messy routing model into a clean one. Those are still architecture choices. And this becomes even more important once model choice itself starts varying across experts and routes. Because the moment you allow model optionality, you need governance not only over agents, but over which models those agents can use in the first place. That means the next layer is not agent governance alone. It is model governance. Use as your policy to control model switching. Once you accept that a rotted system uses several models, a new governance problem appears fast. Who gets to choose them? If every team can swap models whenever they want, your architecture stops being governed at the exact point where it becomes more powerful. A rotted system without model policy doesn't stay flexible for long, and instead it turns into a moving target where behavior shifts and compliance reviews fall behind. Cost assumptions drift when nobody can explain why the same prompt behaves differently this week than it did last week. That's why model choice has to be a platform decision rather than a developer preference. This is where Azure Policy matters. The practical Microsoft pattern in the research is very clear because Azure Policy can restrict which models are allowed from Azure AI Foundry. It covers approved registries, model asset IDs, publishers, and deployment types, which means the platform defines the catalog where teams are allowed to operate. That changes the conversation entirely. Teams are no longer asking if they can use anything, but are instead asking which approved options fit the workload. That is the right framing. In a rooted architecture, switching models is not a minor detail because it affects cost, latency, safety, and even the quality of downstream handoffs. If one expert path quietly changes from one model family to another, the route may still succeed while the system characteristics change underneath it. That is exactly the kind of drift mature governance should prevent. So start with allow lists, approve models, approve publishers, approve deployment patterns. If your organization wants different options for different contexts, that's fine, but you have to define them centrally. Maybe development gets a broader catalog for experimentation while the test environment narrows that list down. Production should only permit a smaller set of fully reviewed models to ensure the architecture doesn't turn into a moving experiment. And one level deeper, routed systems, make this more urgent than single model systems. In a single model setup, one bad decision only affects one primary path, but in an expert fabric, a loose policy can create dozens of unstable combinations. The router model changes, the specialist model changes, and the fallback model changes until the system is no longer one governed service. It becomes a collection of shifting dependencies. Azure Policy helps you compress that sprawl back into an approved operating boundary. The research also points to another useful idea where dynamic model switching is still possible inside the approved catalog. That is the balance. You do not need to freeze the architecture completely because you can still build cheap first patterns that escalate later. One route can still select between approved models based on the task type or the environment as long as the evolution happens inside a bounded space. The policy does not kill routing, but it does make routing governable. This also creates a cleaner relationship between platform teams and builders. Platform teams own the model catalog and the rules around what gets approved. Builders design workflows and expert paths using that catalog. Security and compliance teams review additions to the catalog instead of chasing unknown deployments after the fact that division of labor is healthier than asking every project team to invent its own model risk posture. Now policy alone is not enough. You still need supporting controls around it because being approved does not mean a model is a affordable at scale. Content filters and guardrails should sit beside model policy to ensure safety in every context. Tracability is also required so you can actually observe the traffic once it starts moving. Policy sets the boundary but these other controls make that boundary operational and there is one more reason to care about this. When a route performs badly, teams often blame the model but sometimes the real problem is that too many models were allowed in without any disciplined evaluation. Once model choice is governed, you can finally test the route on purpose which is exactly where we need to go next. How to evaluate routing? Not just model quality. Once you add routing, the unit you need to test is no longer just the model. It is the decision system. That sounds obvious but a lot of teams still evaluate routed architectures as if the only meaningful question is whether one output sounds better than another. In a rooted setup, the first failure may happen before the final answer is even generated because the router might choose the wrong path. It may escalate too often or avoid escalation when it shouldn't and sometimes it sends work to the right expert but with the wrong structure. If you only score the final response, you are measuring the last visible step and ignoring the logic that shaped it. Start with a baseline. Take your current fixed model setup and measure it honestly for quality, latency, cost and task success. Then compare the rooted design against that baseline using a representative workload rather than a polished demo set. You need a set of real requests that reflect what users actually do including messy phrasing and big ears asks and the routine traffic people complain about later. Representative matters because routing systems are extremely sensitive to traffic shape. If the test set is too synthetic, the router may look cleaner than it really is but real users don't write benchmark prompts. They write partial sentences, mixed requests and vague questions with too much context or too little. A good evaluation set has enough variation to show where the route starts bending under pressure. Then measure four things together. Quality is one, cost is another, latency is another, success rate is the fourth and it is often the most grounded measure and enterprise systems because it reflects whether the request was actually completed. A route that saves money but lowers completion quality is not a win for the business. A route that improves answer quality but destroys latency on common tasks will also fail in practice which is why these systems need multimetric evaluation. You also need trace-based evaluation. This is much more useful in agent systems than isolated prompt scoring because traces show how the route actually behaved. You can see which path was selected, which expert was called and whether retrieval or a specific workflow was used. Without traces you are mostly guessing why a result happened but with them you can learn if the problem came from routing or specialist behavior and then look at distribution. Where is the traffic really going? This question matters more than people expect because a rooted system can look elegant on paper and still fail economically. If too much traffic ends up in premium parts or if the system clings to low cost parts too aggressively the architecture will underperform. Inspect the model distribution after test runs to see what percentage stayed cheap and which domains triggered fallbacks most often. Distribution tells you whether the architecture you designed is the architecture you are actually running. Approval thresholds should come before production, not after. Define what acceptable looks like before you roll anything out to users. Maybe the routed system must preserve task success within a narrow range while cutting cost or perhaps the P95 latency cannot exceed a certain limit. The exact thresholds will vary but the discipline is the same because you have to decide the gate before the rollout. Otherwise teams will just keep adjusting their expectations after they see mixed results. And one more thing, evaluate the router itself. Not just the whole chain. Take labeled examples and check whether the router picked the intended path so you can measure mis-routes separately from specialist failures. If the route is wrong, tuning the expert won't fix the system and you need to know exactly where the mishapen. Because once routing becomes explicit evaluation has to become architectural too. And only after you trust the route can you decide something even more important when the system should escalate. Escalation logic is where good architecture become great. This is the point where an expert fabric either finds its discipline or turns into a very expensive maze. Routing by itself is never enough. The system needs to know when a cheap path should stop when a stronger path should take over and when no autonomous path should be trusted at all. That judgment is escalation logic. In practice, this is where professional architecture separate themselves from impressive demos. Most teams think about escalation too late. They build a cheap first flow, add some specialists and wire in a larger model for hard cases while hoping the system will just know when to move upward. It won't. If your escalation rules are vague, one of two things usually happens. Either the system escalates far too often which destroys the savings you designed for or it escalates too rarely. That means weak results keep slipping through cheap paths that were never meant to handle that much ambiguity. So you have to define the triggers clearly. Confidence is one trigger, but it cannot be the only one. A model sounding confident is not the same as a task being safe. You also need ambiguity thresholds. Is the request underspecified? Does it combine multiple goals? Does it cross domains? Does the retrieval evidence conflict? Then add risk thresholds. Is the user asking for an action with compliance, financial HR or legal impact? Does the system need to write back into business data? Does it involve sensitive content or policy interpretation? That combination matters because escalation should reflect business reality, not just model uncertainty. A system might feel highly confident about a low quality answer in a high risk workflow and that still should not pass. On the other side, a mildly uncertain classification in a low risk path may not justify premium inference at all. Your design has to combine model signals with policy and business value because technical confidence alone is too narrow. In a healthy architecture, escalation works like a ladder. Simple requests stay on low cost paths. Harder requests move to a larger model or a deeper specialist chain. High impact actions pause for human review that last step is easy to skip when teams want autonomy to look impressive but it is also where a lot of preventable risk enters the system. If an action changes records, triggers approvals, moves money or commits something externally, human approvals should stay in the design. The workflow only earns more trust through long measured evidence and keep the escalation output structured too. When a lower tier escalates, it should not just throw the whole problem upward with a vague message that it isn't sure but it should pass a clean package. What it saw, why it escalated, what evidence it found, what path it already attempted. That preserves context, reduces repeated work and makes review faster for both larger models and humans. There is also an economic rule here, cheap first, expensive last, not because cheap is always better but because the architecture should spend capability with intent. Premium reasoning should be a deliberate exception path, not the default emotional reaction to uncertainty. If the system cannot hold that line, the route may be technically elegant while remaining financially useless. So watch for over escalation. This is one of the most common hidden failures in routed systems. Early tests look good because the system appears safe and polished but under the surface, almost everything drifts upward into premium paths. Cost climbs, latency stretches. Teams still tell themselves they built a small model first architecture they didn't. They built a premium system with a decorative front filter. The fix is not just tighter thresholds, it is better task design, narrower experts, cleaner outputs, better evidence packaging, more explicit business rules. Escalation improves when the lower paths are designed to fail clearly instead of failing messily. If you want the architecture to stay useful and governable, treat escalation as a first class design object, define it, measure it, review it. Every savings model, every latency target, and every safety promise in an expert fabric eventually runs through that decision about what happens next. Once you see that, cost stops looking like something attached to inference alone. It starts showing up in every layer of the system. The full cost stack of an expert fabric. Now we need to get more honest about cost. Once people accept cheap first routing, they often swing too far in the other direction and pretend token pricing is the whole story. It isn't. Token pricing is only the visible part. The system costs, sits across every layer that makes the fabric work. Start with inference. Yes, you still pay for router calls, specialist model calls, fallback model calls, and sometimes verification or summarization at the end. That matters. But in a real Microsoft environment, that is only one line in the bill. The moment you operationalize the fabric, more cost surfaces appear, and some of them grow quietly. Workflow execution is one of them. If Copilot Studio hands work into power automate, external APIs or connected business systems, every interaction can trigger additional runs, connector usage, and downstream compute. In a monolith, you might waste premium inference. In a fabric, you may reduce that waste but increase orchestration activity. That is not automatically bad, but it means the comparison has to be honest. Storage is another piece. Traces, logs, prompt records, retrieval indexes, and evaluation data sets all need to live somewhere. If you are doing this properly, you are also retaining enough evidence for audit, review, and incident analysis. Govern systems store more than optimistic prototypes do. That adds cost, but it also buys control. Then there is support cost. Who reviews escalations? Who tunes routes? Who maintains expert charters? Who updates model allow lists? Who validates connectors after business system changes? Who investigates strange traces? In a monolithic setup, waste hides inside one oversize model path. In an expert fabric, part of the spend moves into platform operations. That trade can still be very favorable, but only if the workload volume and business value justify the added discipline. So the right comparison is not monolith versus orchestration overhead in isolation. It is monolith waste versus orchestrated efficiency plus operational burden. That is a more serious equation. A single model design often looks cheaper at first because the architecture diagram is smaller. Fewer parts, fewer routes, fewer owners. But that simplicity can be fake if high-volume traffic keeps hitting expensive inference paths, weak answers, create rework, and governance gaps generate manual cleanup later. The bill is not just what Azure or OpenAI charges. The bill is also what the organization absorbs when the system behaves badly or inefficiently. On the other side, an expert fabric can absolutely become overbuilt. Too many agents, too many hops, too many thin specialists that barely justify their own existence. Too much logging with too little use, too much ceremony for low-value tasks. That is why architecture discipline and cost discipline are really the same thing here. If an expert path exists, it should earn its place. If an orchestration step adds latency and admin work without improving quality, safety, or savings, remove it, volume changes the picture fast. High-volume systems usually benefit first from an expert fabric because repeated low-complexity traffic is where routing and specialization payback quickly. Classification heavy flows, policy lookup, extraction, and templated support are all good examples. The more routine traffic you divert from expensive paths, the more the structure starts working in your favor. Low-volume systems are different. If the request count is modest, the task variation is still fuzzy and the team is small. Orchestration overhead may outweigh inference savings for a while. In that case, the right move may be a simpler architecture with one bounded model path and strong guardrails at least until the workload becomes clearer. So the cost question is never just, what is the cheapest model? It is. What is the cheapest system that still delivers the right outcome under governance? That is the level leaders need to design that. Because if you only optimize token price, you can still build an expensive machine. And if you ignore token price, you will definitely build one, the hidden risk of emerging behavior. There is one risk that does not show up when you test agents one by one. That only shows up once the system starts interacting with itself. This is the part many teams miss, because each individual component looks reasonable in isolation. The router behaves, the policy expert behaves, and the workflow expert follows the rules. But when those pieces start handing work back and forth, new behavior appears that nobody designed. That is emerging behavior. And in multi-agent systems, it is a structural issue rather than a fringe one. What makes it dangerous is not drama. It is accumulation. A small rooting preference becomes a pattern. A pattern becomes a norm. A norm becomes the default path through the system. Even if nobody intended for it to harden that way, that can look like delegation loops where agents keep passing work along because each one finds a reason to defer. It can look like toolcascades, where one decision triggers a tool call that triggers another, until the cost and complexity drift far past the original request. It can look like rubber stamping, where one specialist confirms another without adding any real check or norm drift, where agents slowly become more permissive because the system keeps treating that behavior as acceptable. That is why testing a single prompt is never enough. A single prompt tells you if one agent can answer one question, but it does not tell you what happens after 30 handoffs and repeated retreats across a live environment. The system behavior lives in the interaction pattern. Not just in the text any one model returns, this is also where a lot of false confidence comes from. Teams see safe outputs from each agent and assume the whole system is safe. But local safety does not guarantee system safety. An individual agent can follow its instructions and still contribute to a bad collective outcome. One agent may escalate correctly, while another interprets that escalation too broadly and a third takes that interpretation as evidence that the task is approved. No single step looks catastrophic, the chain does. So the controls have to operate at the system level. Start with chain limits. Decide how many handoffs are allowed before the system stops for a review or how many tools can be called in one uninterrupted path. These are not cosmetic settings. They are boundaries that stop small feedback loops from turning into expensive or risky behavior. Then add kill switches. If a route starts producing abnormal handoff volume or strange tool usage, the platform needs a way to pause that path immediately. The research around agent governance is very clear on rapid revocation and containment because in these environments, recovery speed matters as much as prevention. You also need anomaly detection. This is not just for security events but for behavioral drift. You have to watch if one route is escalating more than expected or if a specialist is suddenly touching data sets outside its normal pattern. If an approval chain becomes automatic even though humans are still in the loop, those are system signals that someone has to monitor. Roll separation helps too. Do not let the same agent propose a proof and execute high impact actions through minor variations of the same path. Keep analysis separate from authorization and recommendation separate from writeback. That friction is healthy because it reduces the chance that convenience becomes pseudo-autonomy. And for the highest risk workflows, keep human anchoring in place, not because humans are faster but because humans are the only layer that can step outside the logic of the chain and ask if the chain itself still makes sense. Once agents start reinforcing each other, that outside judgment becomes more important. So this is the deeper governance lesson. Emergence is not a prompt problem. It is a system problem. And if the risk is systemic, the answer cannot live only inside isolated prompts. The answer has to live in the topology, the limits, the monitoring, and the ability to stop a path before the system teaches itself the wrong habit. Which is exactly why the next design question is not just what the agents say but how the topology between them is shaped. How to design safe multi-agent topology in co-pilot studio? So now we get concrete. If emergent risk is shaped by topology, then topology cannot be an afterthought in co-pilot studio. You have to decide upfront how agents relate to each other, who speaks to the user and which permissions apply in each environment. If you leave those choices loose, the platform will still let you build something but it will be harder to test and much easier to misread later. Start with one orchestrator. One user facing voice. That pattern matters more than it seems. Co-pilot studio now supports multi-agent orchestration but that does not mean every specialist should be a peer chatbot exposed directly to the user. In most enterprise cases, that creates noise through different tones and different assumptions. The cleaner pattern is one parent agent at the surface with a set of bounded specialists behind it. That parent agent owns the conversation. It receives the user request, keeps the interaction coherent and decides when to call specialists. The specialists do not negotiate with the user in public. They operate more like internal tools with domain intelligence. They return work products and the orchestrator decides how those results become a response or an action proposal. That design reduces a lot of confusion. It also reduces cross-agent prompt bleed because the user is not bouncing between multiple conversation identities with overlapping roles. One front door, one visible context owner, everything else stays structured behind it. Inside that topology, specialist agents should return structured outputs. Not long pros, not brand new conversations, structured outputs. That is important in Co-pilot studio because orchestration works better when the downstream result is predictable enough to branch on and validate. A policy specialist can return a decision and its constraints, while a workflow specialist returns action status and execution detail. Once the output stays structured, the parent agent can combine it safely without guessing what the specialist meant. Knowledge and connectors should also be segmented by role. This is where topology and governance meet directly. If a specialist is supposed to answer benefits questions, give it the benefits corpus and only the connectors it actually needs. Do not let every sub agent inherit a broad shared data surface just because they live under one parent. The topology should reflect separation. Not erase it and keep state outside the model where control matters. Conversation flow can use conversational context but approvals and execution records should be stored in managed systems. Dataverse or SQL exist for a reason. If critical state lives only inside transient agent context, you lose auditability and operational control. Externalized state makes the topology inspectable. That is what you want. Environment design matters too. Development, test and production should not just be copies with different names. They should have different permissions and different connectors scopes. Development needs flexibility while production needs tight control. If every environment can reach the same systems with the same authority, you are not really separating risk. You are only renaming it. This is also where maker freedom needs guardrails. Copilot Studio makes it easy to connect tools and agents but safe topology means the patterns are opinionated. Parent agent at the front, specialists behind, narrow tools and managed state. If teams drift too far from those basics, the architecture starts widening again and the governance work begins to thin out. So the goal is not maximum agent interaction. It is disciplined interaction. Enough specialization to improve fit. Enough structure to keep control. Enough separation to make failure containable. And once that topology is in place, you can stop talking about abstract patterns and finally show how to build the first practical version of this in the Microsoft stack. Practical build path in copilot studio and AI foundry. So what does the first real build look like if you want to do this without creating a giant architecture project on day one? Start with one front door agent in copilot studio. Not three, not ten, one. That agent should own the user interaction, the channel presence and the orchestration logic at the surface. It should know how to collect context, apply basic policy checks, and decide when to call something behind the scenes. Keep the mission narrow, one business scenario, one user group, one entry path. If you start with a vague enterprise assistant, you'll rebuild the same generalist problem with better branding. Then connect intelligence behind that front door through AI foundry. There are two practical patterns in the research. One is bring your own model prompts in copilot studio where a prompt tool connects directly to an Azure AI foundry model endpoint. The other is connecting to external or foundry agents through supported endpoints and entrabased access patterns. Which one you choose depends on how much logic lives in foundry. If the back-end need is mostly model access, bring your own model is enough. If the back-end needs multi-step reasoning, tool use or agent logic, push that into foundry and let studio call it. That split matters because a lot of teams put complex reasoning directly into copilot studio prompts and then wonder why the system becomes hard to test. Studio is strong at orchestration, channels and workflow composition. Foundry is stronger where model control, evaluation, routing and back-end reasoning need more structure. So for the first practical version, build the back-end experts in foundry. Use prompt flow if the expert needs a chain of steps, tool calls or controlled input and output handling. Use foundry agent logic if the expert behaves more like a bounded specialist service with its own internal actions. In both cases keep the output structured and narrow. The copilot studio parent should receive something machine-friendly first, then turn that into the user-facing response. Now make the first expert the router, not the final answer generator. This is the shortcut most team skip, and it is where the economics of the whole design start. Use a small low-cost model path first to classify the request. Domain, complexity, risk, action type, whether retrieval is needed, whether no model is needed at all. If the request is just a deterministic workflow trigger, root directly to the workflow. Do not pass every sentence through premium inference just because AI is available. Then add one or two specialists behind that router that is enough for a serious pilot. For example, one knowledge specialist and one workflow specialist or one policy specialist and one extraction specialist. The point is not to show variety. The point is to prove that the root improves fit. If you cannot show value with a router and two bounded specialists, adding six more will only hide the problem. Data should come in through approved indexes and narrow scopes. If the specialist needs retrieval, connect only the corpus that belongs to that role. If the root needs a sharepoint-backed knowledge path, scope it deliberately. If a workflow needs dataverse or another connector, limit the rights to what that workflow needs. This is where many early pilots go wrong. They prove the user experience by quietly overexposing data and then governance has to unwind the pilot later. Do the opposite. Constrain early. That forces the architecture to stay honest. Before you publish anything, evaluate the route and the outputs together. Use representative prompts, inspect traces. Confirm where traffic goes. Check whether the router is classifying the request types you expected. Look at latency across the end-to-end path, not just the model call and make sure policy, logging, and ownership are in place before production publication. A working demo is not the same thing as a deployable service, so the practical sequence is simple. One front door copilot studio agent, one cheap routing layer, one or two back end experts in Foundry, narrow data scopes, structured outputs, evaluation before release. That is enough to move from theory into a governed pattern without pretending you need a massive agent estate on day one. And that matters because the right first architecture is not the most advanced one. It is the one your organization can actually operate, review, and improve without losing control. Maturity model from pilot to enterprise fabric. At this point, the biggest mistake is assuming the architecture has to appear fully formed on day one. It shouldn't. A mature expert fabric is not a starting position. It is a progression. And if teams skip that progression, they usually build too much too early, add governance after the fact and end up managing complexity they have not earned yet. So the useful question is not, what is the perfect end state? It is. What stage are we actually in? And what does the next responsible step look like? Stage one is the narrow pilot, one agent, one fixed model, one bounded task. Not because that is the final answer, but because it gives you a clean baseline. You need to know the workflow, the failure modes, the user behavior, the data needs, and the operational burden before you multiply parts. If the task is still fuzzy at this stage, that is a warning. It means your expert boundaries are not ready yet. A pilot should reduce ambiguity, not scale it. Stage two is where routing starts to enter, add a cheap router and one premium fallback. That is the first meaningful architectural shift because now the system begins distinguishing between common traffic and difficult traffic. It is still manageable. You are not running a network of specialists yet. You are proving that cheap first logic works in your environment with your users on your workload. This is where you learn the basics of root accuracy, escalation behavior, and cost distribution without taking on full multi-agent governance. Then come stage three, multiple specialists with governed handoffs. Now the architecture starts behaving like a real expert system because the root no longer just chooses between cheap and expensive. It chooses between different kinds of work, a knowledge path, a workflow path, a policy path, maybe an extraction path at this point ownership matters more. Logging matters more, connector discipline matters more. You are no longer just optimizing model spend. You are shaping a controlled operating structure. And because handoffs now affect quality and risk directly, each specialist needs a clear charter and a clear stop boundary. Stage four is the enterprise fabric that means policy-controlled model catalogs, life cycle reviews, telemetry, environment discipline, central inventory, and an operating model that clearly separates platform ownership from domain ownership. This is where agent 365, Azure Policy, trace-based evaluation, and cost governance stop feeling optional. The architecture is wide enough now that without those controls, drift becomes normal. So stage four is not more agents. It is stable coordination across agents, models, tools, and teams. This progression matters because organizational readiness is just as important as technical readiness. A team may be able to build a multi-agent demo in a week. That does not mean the organization is ready to own one. In production, do you have a model approval process? Do you have named owners? Do you have logging standards? Do you have a place to review incidents? Do you know how to revoke access quickly? If the answer is no, then your architecture maturity is lower than your prototype maturity. And that gap becomes dangerous fast. This is why I would always match the target design to the current operating discipline. If governance is still immature, stay closer to stage one or two. If the workload is high volume and well understood, move into stage three with care. If multiple business units are already building agents and the platform team can provide controls, then stage four starts making sense. But don't romanticize the end state. Enterprise fabric is not automatically better just because it is bigger. It is only better when the next layer of structure solves a real problem that the previous layer could not handle cleanly. So the practical rule is simple. Prove the first route before you expand the map. Prove the first specialist before you add three more. Prove the first governance gate before you depend on 10 of them. That pacing keeps the architecture honest. It also prevents teams from turning future ambition into present complexity. And once you see maturity that way, one final design question becomes much easier to answer. When should you not build a mixture of experts at all? When not to use a mixture of experts? Now we need the counterweight because once people understand the expert fabric, they swing too hard. They start treating it like the default answer to every AI problem. It isn't. A mixture of experts is a structural answer to a specific kind of complexity. If that complexity isn't there yet, the structure just becomes overhead. The first case is low volume. If your request count is small and the task is stable, a rooted architecture solves a problem you don't actually have. The design might look cleaner on a whiteboard and specialist boundaries sound mature, but the math doesn't always work. If the workload only sees limited traffic, the savings from routing will never outrun the cost of building and testing those extra moving parts. In that situation, one well-bounded model with clear prompts and strong review discipline is usually the better decision. The second case is low risk. If the agent isn't touching sensitive data or triggering business actions, heavy orchestration is often unnecessary, you still need controls and ownership, but the full fabric might be more structure than the situation demands. A simple architecture isn't a failure if it fits the task. Actually, that's usually the more responsible choice, variation matters too. If the team is still learning what users want, your expert boundaries will be weak because the task itself is moving. When boundaries are weak, specialists start overlapping and one agent ends up handling the same work as another. Escalation rules get fuzzy and routes become unstable because the categories underneath them aren't settled yet. That's a sign to pause and simplify. Before you create multiple experts, make sure the work actually separates into distinct categories. Small teams need to hear this clearly. A multi-agent system creates ongoing obligations that don't go away once the code is written. Someone has to maintain the prompts, someone has to review the traces and someone has to update the connectors and policies. If the team doesn't have the capacity to run that operating model, the architecture becomes fragile very quickly. You don't get maturity just by drawing more boxes. You get it by sustaining the controls around those boxes over time. Governance maturity is another real limit. If your organization still struggles with basic ownership or permission hygiene, adding more agents increases risk faster than value. The system might look advanced, but underneath it, the same old weaknesses stay in place. Unclear owners broad access, missing logs. In that condition, the right next step is to strengthen the platform baseline before you start multiplying specialists. There is also a temporary case where one strong model is simply the smarter answer. If the workload is broad and the task design is still emerging, one capable model gives you a cleaner learning period. You gather evidence and see which request repeat, which helps you discover where real specialist boundaries might eventually sit. That isn't anti-architecture. It's sequencing. Sometimes the shortest path to a good expert fabric is starting with a simple setup and only splitting it once the patterns are obvious. Another warning sign is when people want a mixture of experts mainly because it sounds sophisticated. That leads to decorative specialists and experts with weak missions. Those routes exist because the architecture team wanted elegance, not because the users actually needed it. If a specialist cannot explain its unique role and its unique data scope, it probably shouldn't exist yet. So the real decision rule isn't more agents equals more maturity. It's fit. User mixture of experts when workload, shape, cost pressure, and governance capability all point in the same direction. Hold back when they don't. The point isn't to replace every single model system on principle. The point is to stop forcing one model to do jobs that clearly need different treatment. And that brings us to the final layer because even when the architecture is right, it only holds if the organization knows who owns what. The operating model behind the architecture. Now we get to the part that decides whether any of this survives. Because architecture on paper is easy. Operating it is where the truth shows up and expert fabric doesn't run on prompts alone. It runs on ownership. If ownership stays blurry, the system drifts back toward the same confusion we started with just spread across more components. So split responsibility on purpose. The platform team should own the guardrails. That means the model catalog, the routing standards, the policy controls, and the observability stack. They aren't there to write every expert prompt or babysit every business workflow. They are there to define the safe operating envelope, which models are approved, which deployment paths are allowed, which traces must be captured. Without that platform layer, every domain team rebuilds governance differently and the fabric fragments almost immediately. Then domain teams own the experts. Not the whole platform. They're experts that includes the expert charter, the prompt logic, the data boundaries, and the escalation rules for their specific process. If an HR policy expert exists, the team accountable for HR should own whether that agent is correct and useful. If a finance workflow expert exists, finance operations should define what the agent can recommend and where human review sits. This is where a lot of AI programs fail. They centralize everything in one technical team and then the specialists stop being real specialists because the business never truly owns them. Security and compliance sit beside both groups, not underneath them. Their job isn't to become the routing designer. Their job is to review controls, map risk, and make sure the fabric can be defended when something goes wrong. In a multi-agent system, incidents are rarely neat. You need predefined response paths, who pauses an agent, who revokes access, who decides whether a route goes back online. If those answers only exist informally, the first serious problem turns into organizational improv. Finance and operations also need a real seat here. Once you move into a rooted architecture, spend has to be measured per outcome. Not just as one total AI bill. You need to know which expert path costs more and which domain escalates too often. If finance only sees aggregate spend, the architecture becomes hard to improve. Cost needs to map to behavior. That's how you see whether the structure is actually working. This is exactly why a center of excellence pattern helps, provided it's done properly, not as a vanity committee. As a working review layer, the COE can publish templates for expert charters and route designs so teams don't solve the same problem five different ways. It shortens the path between innovation and control because teams don't have to invent the model from scratch every time. But the COE should not become a bottleneck that owns everything. If it owns everything, domain ownership collapses again. The healthier pattern is shared structure, local accountability. Platform defines the rails. Domain teams drive the mission, security validates the controls. Finance tracks value and waste. The COE helps the whole system stay consistent. And one level deeper, this is why the architecture changes behavior only when ownership is explicit. A routed system is really an operating model for decision making. It decides who is allowed to define expertise and who is responsible when a route fails in production. If those lines are clear, the fabric can evolve without dissolving. If those lines are weak, every new expert adds ambiguity instead of capability. So after all of this, the shift is bigger than model choice. You are replacing a generalist bot with a managed system of bounded responsibilities. And that is the actual promise we opened with. The shift is simple, even if the build is not, stop treating one generalist bot like the answer. Start designing a governed fabric.
