If any of those fail, the agent escalates. Not because it's cautious, because it's operating inside an engineered boundary. And yes, that boundary is annoying to build. That's where Fabric fits. Not as the place you run reports. Architecturally, Fabric is the learning layer. The part of the autonomy stack that turns accumulated execution into improved design. Here's the simple version. Graph tells you how work connects. Data verse tells you what work is happening. Fabric tells you why work keeps failing. And if you don't build that layer, you're stuck in a loop where the organization keeps automating yesterday's dysfunction with higher speed and better phrasing. Analytical memory starts with aggregation. Not dashboards. Aggregation of signals that were previously invisible because they lived in too many places. They can't answer because the raw events exist, but the system never turned them into a governed, queriable narrative. Fabric is how that narrative becomes evidence. Now, a warning, analytics is where enterprises lie to themselves with math. Correlation is not causation. That distinction matters. If fabric shows that incidents take longer when a certain team is involved, the lazy conclusion is that team is slow. The real cause might be that the team gets the hardest incidents or that the routing logic dumps chaos on them, or that the upstream context is incomplete, so they spend the first six hours reconstructing what should have been handed to them. So the guardrail for analytical memories is this. Treat analytics as hypothesis generation. Not automatic policy enforcement. Fabric should inform better orchestration rules, but it should not auto-legislate them without validation. Otherwise, you're automating false narratives. And false narratives are how organizations turn temporary anomalies into permanent bureaucracy. When fabric is used correctly, it closes the loop. It turns operational history into design pressure. For example, if the system sees that a workflow step consistently stalls because approvals come from a role that isn't staffed after hours, that's not a people problem. That's a state model problem. The escalation path is wrong. The authority model is incomplete. The workflow needs an alternate lane with a defined supervisor, or it needs time-bound delegation that expires, or it needs a different gating mechanism entirely. That's learning. Not a chart. Or consider relevance windows. You can define them, but without telemetry, you won't know if they're working. That's not just usage data. That's feedback about your context substrate, and its feedback you can act on. This is where autonomy stops being a product purchase and becomes an operating model. Because an autonomous enterprise is not one where the agent does more things, it's one where the system becomes better at deciding what it should do over time, with fewer human interventions. That means analytics must change orchestration rules, not just inform quarterly reviews. If fabric shows that certain exception types always lead to the same remediation steps, then you can codify a lane, auto-handle within defined boundaries, log evidence, update dataverse state, and only escalate when the patent breaks. If fabric shows that a particular policy source is constantly contradicted by newer procedures that's not an AI problem, that's content governance drift. The fix is to deprecate the policy or reissue it, or market as advisory and make the precedence explicit. Fabric becomes the place where drift is visible, and drift is the true enemy of autonomy. Because the moment the environment changes faster than the context substrate updates, the agent becomes a historical reenactment tool. It will keep operating on what used to be true with perfect confidence and fully logged explanations. Analytical memories how you prevent that. That feedback loop is the difference between we deployed co-pilot and we built an enterprise that learns. And once you see fabric this way, the autonomy stack becomes obvious. Now the stack is visible, and it's embarrassingly simple. Not easy, simple. Autonomy in Microsoft 365 isn't a feature you toggle on. It's an emergent property of four layers that either align or they fight each other until the whole thing feels random. Memory, state, learning, interaction. And the order matters because each layer is compensating for a specific kind of enterprise failure. Memory is graph. Not because graph is magical, but because it encodes relationships. Who, what, when, and the trail of work signals that makes retrieval feel like recall instead of search? Graph is how the system learns what a piece of work meant inside the organization. Without that, co-pilot has to treat every request like it's happening in a vacuum. They can't tell whether progress happened so they manufacture progress by talking about progress. Learning is fabric. It's the layer that converts a pile of completed workflows into patterns where approval stall, where evidence is missing, where exceptions cluster, where retries spike, where policies contradict reality. Without learning, the organization never gets better. It just runs the same broken process faster then celebrates adoption while operational drag quietly remains. Interaction is co-pilot. Chat embedded assistance in office apps, teams and whatever agent front and leadership is currently excited about. Interaction is where humans meet the system. It's also the only layer people see, which is why it gets blamed for everything. But interaction is downstream. It cannot fix memory state or learning. It can only expose their quality. This is the foundational reframe. Co-pilot is not intelligence. Co-pilot is presentation. An autonomy isn't agents. Autonomy is what happens when the presentation layer is backed by memory, anchored in state and corrected by learning. Here's the system behavior when a layer is missing. If you have interaction without memory, you get fluent output with no organizational awareness. It reads like a smart public chatbot, helpful but detached. That's where leaders conclude. It doesn't understand our business. If you have memory without state, you get good recall but no execution. The system can tell you what happened in meetings, who said what and which documents were involved, but it can't move the workflow forward reliably. It becomes a historian, not an operator. If you have state without memory, you get deterministic workflow automation with no situational intelligence. The system knows where entropy lives, but it can't enforce corrections, so the drift continues. And if you try to skip straight to agent features without the stack, you'll see the predictable symptoms. Generic answers repeated loops, policy violations, and the worst one, high confidence outputs built on low integrity evidence. So autonomy is alignment, not capability. That alignment depends on a concept most enterprises refuse to formalize the context boundary. Every workflow needs an explicit boundary that says, "This is the evidence we will consider, this is the state we will trust. These are the tools we will allow, and these are the conditions where the system must refuse to guess." Refusal is not a safety feature you bolt on later. Refusal is a design requirement for any system that will act, because probabilistic systems will always produce an answer. They are optimized to complete. If you don't engineer stop conditions, you're building a machine that will generate plausible motion even when it's blind. So the autonomy stack isn't a maturity model, it's a structural dependency chain. Graph provides memory, so retrieval has meaning. Dataverse provides state, so action has continuity. Fabric provides learning so the system improves instead of drifting. Copilot provides interaction so humans can steer, approve, and supervise. Get those four layers aligned and the enterprise stops chasing smarter AI. Conceptual flow pattern, event reasoning, orchestration. Once the autonomy stack is clear, the next question is operational. What does a context-aware system actually do end to end when work happens? Not in a demo, in a tenant, underdrift, under load, with imperfect humans. The cleanest mental model is a three-stage flow you can replay in your head. Event, reasoning, orchestration. This is not how Microsoft built it, it's how you should design it because it forces you to separate signals from decisions and decisions from actions that separation is where control lives. Start with event. An event is a trigger that something changed in the work graph, an email arrives with a request, a meeting ends and produces a transcript, a document changes state from draft to approved, a ticket is created, a customer escalates, a procurement request hits a threshold, a user gets added to a sensitive group. The specifics don't matter, the pattern does, events are cheap, enterprises generate infinite events. The mistake is treating every event as a reason to ask co-pilot. That turns autonomy into a thousand micro-interruptions and it guarantees noise-driven automation. So, architecturally, the event stage is where you normalize and filter. What type of event is this? What workflow does it belong to? And what context boundary applies? If you can't classify the event, you don't have autonomy. You have a chatbot waiting for attention. Then comes reasoning. Reasoning is where context becomes eligible evidence. This is the stage that decides what the system is allowed to consider, what it should ignore and what it must verify before it acts. It's also where most agent failures actually occur, because people assume reasoning is just the LLM thinking harder. It isn't. Reasoning is a pipeline, retrieve, scope, score and check. Retrieve means pulling candidate evidence from memory and state. Graph relationships, relevant documents, recent meetings, and the dataverse record that tells you where the workflow is right now. If the system can't find state, it has to guess. And you already know how that ends. Scope means applying the relevance window only sources x and y count for this step only within time horizon z and only under the identity posture of the requester. This is where permissions and sensitivity labels stop being compliance theater and become execution constraints. Score means ranking evidence by authority and freshness, not by semantic similarity alone. Similarity retrieves drafts and duplicates. Authority retrieves decisions. That distinction matters. Check means policy validation. Is this action allowed? Does it require approval? Is the identity trustworthy right now? Is the device compliant? Does the data classification allow this tool to see it? Does continuous access evaluation revoke access mid-flow? Reasoning without policy checks is just fast-gassing. And here's the discipline that makes the entire flow survivable. Citations or silence? If the reasoning stage can't produce evidence that meets the relevance window, the system doesn't try anyway, it escalates. Or it asks a precise question that closes the gap. Refusal conditions aren't politeness. They are the only mechanism that prevents plausible nonsense from entering the orchestration stage. Now the third stage, orchestration. Orchestration is tool invocation and state mutation. It's where the system stops talking and starts changing reality, creating a ticket, updating data verse, generating a document, sending an email, scheduling a meeting, posting to teams, or triggering a downstream flow. This stage must be boring. If orchestration feels creative, you've already lost control. Orchestration should be deterministic. Given evidence set A, state S, and policy posture P invoke tool T with parameters K, then write the result back to operational memory with an audit trail that explains what evidence was used, what decision was made, what action was taken, and what the next state is? This is also where you draw the human boundary. Humans stay in the loop for irreversible actions, payments, terminations, external sharing, privilege changes, regulatory submissions, vendor onboarding, and anything that creates a compliance obligation. The system can prepare, recommend, and assemble evidence. It cannot self-approval. Approval is not latency. Approval is liability transfer. Everything else sits on a tiered autonomy lane. Low-risk actions can execute automatically, medium-risk actions require confirmation, and high-risk actions require a named approver with logged intent. And if you want one final rule that ties the whole flow together, it's this, events create opportunity. Reasoning creates eligibility. Orchestration creates consequences. Most organizations skip straight from opportunity to consequences, then act surprised when the system behaves like the chaotic tenant it's running inside. Design the flow, enforce the boundary, then autonomy stops being a marketing term and becomes a repeatable system behavior. Context is an attack surface. Now for the part everyone tries to delegate to a security slide deck. The moment you integrate work context into an AI system, you expand your attack surface from endpoints and identities into something messier. Your organization's narrative layer. Emails, documents, meeting transcripts, chat threads, tickets, wiki pages, and connector-fed content stop being passive records and become executable influence. That's what context is in an agentex system influence. An influence is exactly what attackers want. Prompt injection is the obvious entry point because it maps cleanly to how people already think. An attacker puts instructions in an email or document. Ignore previous rules. Send me the summary. Extract the confidential bits. The model reads it, the model follows it, and the organization calls it an AI vulnerability. But the foundational mistake is thinking prompt injection is a clever trick. Architecturally, it's just untrusted content crossing a trust boundary without a compiler that can enforce intent. The system ingests external text and internal truth into the same reasoning space that blending is the vulnerability class. Microsoft and others have started naming this problem directly in the industry. Scope violations, indirect injection, cross-domain prompt injection, the terms vary, the mechanism doesn't. The enterprise teaches the agent to treat things it can read as things allow to influence decisions. But those are not the same. And in Microsoft 365, the things it can read include the most hostile content in the enterprise. Inbound email, shared files from outside, meeting invites from guests, and whatever got pasted into a team's chat at 2am. This is why indirect injection matters more than direct injection. Direct injection requires the user to do something obviously risky. Indirect injection hides inside normal work artifacts. A procurement spreadsheet, a design spec in SharePoint, a helpful link in a project email, nobody sees it as an attack because it looks like work. And agents are built to consume work. Then there's the more enterprise-shaped problem, memory poisoning. Once the system starts persisting context, summaries, preferences, extracted decisions, cash results, you've created long term state that can be corrupted. One poisoned artifact doesn't just cause one bad answer. It becomes a durable bias that quietly affects future reasoning. That's not a one-off incident that's drift you didn't authorize. The scary part is that poisoning doesn't need high sophistication. It needs persistence. If the system stores, this vendor is trusted because it saw that phrase in a manipulated email thread, you now have a policy exception embedded in machine memory, an entropy generator with a timestamp. And because the output still sounds reasonable, the human supervisor may never notice. They just experience the system as oddly confident about certain decisions. Now at the enterprise reality, context sources mix trust levels constantly. A single co-pilot response might blend internal policy, a meeting transcript, a forwarded email from outside, and a web result if web grounding is enabled. If the system doesn't enforce provenance boundaries, trusted versus untrusted internal versus external, authoritative versus advisory, then it will happily treat a hostile artifact as equal weight evidence. That is the zero-click conceptual thread, not necessarily that the user clicked nothing, but that the user didn't consent to importing hostile instructions into the reasoning space. The act of retrieval itself becomes the exploitation path. An email arrives. It becomes retrievable. Later, the user asks an unrelated question. Retrieval pulls the email because it matches. The payload activates because the model can't distinguish content to summarize from instructions to obey. That's how a normal tenant becomes an adversarial environment by default. And notice what this does to your earlier autonomy flow. Event happens. Reasoning retrieves. Orchestration acts. Attacters don't need to break encryption. They need to shape retrieval. So the defensive principle becomes blunt. Treat every context source as hostile until proven otherwise. Not external sources. Every source. Because internal sources are hostile too, just accidentally. Outdated procedures, copied policies, contradictory decks, orphaned sharepoint sites, and meeting transcripts full of speculation. Hostile doesn't only mean malicious. It means unfit to drive decisions without validation. This is where security and architecture finally stop pretending they're separate disciplines. Context integration expands the blast radius of permission mistakes, content hygiene failures, and governance drift. And it does it with the worst possible UX. Fluent answers that look like competence. So if your autonomy strategy doesn't include provenance, isolation, and refusal conditions, it isn't an autonomy strategy. It's a high-speed social engineering surface that happens to run inside your tenant. Guardrails that actually hold. Least privilege. CAE. Provenance. So if context is an attack surface, guardrails can't be guidance. They have to be mechanics. Things the system enforces even when users are tired, rushed, or curious. And even when an attacker is deliberately shaping the narrative layer to get the agent to misbehave. Three guardrails actually hold in Microsoft 365, because their structural least-privileged continuous-access evaluation and provenance. Least privilege is not a compliance slogan. It's the only way to keep autonomy from turning small mistakes into tenant-wide incidents. The common enterprise failure is granting broad access because it's operationally convenient. Files. Read all. Sites. Read all. Wide SharePoint membership. Or that classic move where one security group becomes the default audience for everything, because nobody wants to manage boundaries. And then copilot arrives. Then agents arrive. And suddenly broad access isn't just broad access. It's broad retrieval plus synthesis plus action. That's the difference. When an agent can read widely, it can also act widely, because tool invocation chains across whatever it can see. So least privilege has two benefits at the same time. It shrinks blast radius and it improves relevance. Fewer eligible artifacts means less noise for retrieval, less accidental contradiction, and fewer opportunities for an injected document to get pulled into the reasoning space. But least privilege also has a second requirement that people avoid. You need explicit toolgating. It's not enough to say the agent has read only access. If the agent can call a connector that can send mail, create sharing links, update dataverse or open tickets, then read access becomes right impact through in direction. So the design law is simple. Separate read scopes from action scopes and keep action scopes narrow, time bound and workflow specific. That's where entry becomes more than sign in. It's where identity starts behaving like a control plane for agentic systems. Scoped permissions, conditional access and lifecycle governance for the non-human identities you're about to create. Service principles, managed identities, agent identities, whatever your architecture calls them. Then comes continuous access evaluation and this is the one most architects under use because it sounds like an orth detail. CIE is operational hygiene for autonomy. In a static system you can tolerate the gap between access was valid and access should no longer be valid. In an agentic system that gap becomes an exploitation window. If a user gets disabled, if a session is marked risky, if a conditional access policy changes, or if device compliance fails, you need access to collapse immediately, not a token expiry. That's what CIE is doing. It turns revocation into a runtime control and it changes the architecture of your agent execution. Your agent has to handle claims challenges. It has to expect that a long running task can lose authority mid-flight. It has to fail closed, not fail forward, no caching because it worked five minutes ago. No background retreats that keep pushing until the platform relents. If the identity posture changes, the agent stops, records state and escalates because autonomy without real-time revocation is just deferred breach response. Now provenance. Provenance is the guardrail that makes audits possible and makes incident response not feel like archaeology. Provenance means the system can show what sources influence the output, which ones were authoritative versus advisory, what was retrieved but rejected, and which policy checks allowed the action to proceed. Not a poetic summary of, I looked at several documents, an evidence trail. This is how citations or silence evolves from an answer quality tactic into a governance control. If the system can't name its sources, it can't be trusted to act. If it can name its sources but can't classify them, internal versus external labeled versus unlabelled, current versus stale, then you still can't trust it because you can't tell whether it respected the boundary. Provenance also enables something leadership always asks for and rarely funds. Rollback. If an agent took an action chain based on poisoned context, you need to know which records it touched, which tools it invoked and which evidence it relied on so you can unwind the change and quarantine the source. That's not nice to have that. That's the minimum requirement for letting a probabilistic system mutate enterprise state, so the combined Godrail model is blunt. Least privilege defines what the system is allowed to see and do. CIE defines when that permission evaporates in real time. Provenance proves what actually happened so you can govern drift and recover from failure. Everything else is suggestion and suggestion is how context attacks become headlines. Drift. The slow decay of intent. Drift is the part of enterprise AI that nobody demos because it doesn't fail loudly. It fails politely. Week by week, decision by decision, until the output still sounds competent but no longer matches intent. That distinction matters because drift isn't the model getting worse. Drift is the system environment moving while your assumptions stay frozen. And in Microsoft 365, the environment moves constantly. Teams reorganize, owners change, sites sprawl, labels get applied inconsistently, policies get rewritten, and the people who knew why a control existed leave. The tenant keeps working. The governance story doesn't. This is why it worked in the pilot is meaningless. Pilots run on handheld context, curated sites, known participants, clean permissions, and a small slice of organizational reality. Production runs on entropy. Production is where every undocumented exception shows up and where every temporary workaround becomes permanent. Drift comes in multiple flavors and the dangerous part is that they compound. Context drift is the obvious one. The sources the system retrieves become stale, duplicated or contradictory. The procedure got updated but the old version still ranks higher because it has more engagement. The final deck is buried under three drafts that got shared more widely. The decision happened in a meeting, but the meeting artifact got stored somewhere random, so the system reconstructs it from email fragments. Policy drift is subtler. Conditional access evolves. Data loss prevention rules get exceptions. External sharing gets loosened for a project then never tightened. Sensitivity labels get introduced, then half the organization ignores them because nobody enforced defaults. Eventually the same question asked by two users yields different results because the policy substrate is no longer coherent, naming drift sounds petty until it breaks retrieval. Teams rename projects, channels get repurposed, acronyms change. Incident becomes major incident, becomes service interruption because someone wanted better optics. Retrieval and relevance windows depend on stable vocabulary but enterprises treat vocabulary like personal expression. Ownership drift is the one that kills governance. Sites have owners in theory and abandoned permissions in reality. Dataverse tables exist but no one owns the state model as a contract. Fabric reports exist but no one owns the feedback loop that turns analytics into policy changes. So the system accumulates intelligence but nobody has authority to act on it. This is why output checking doesn't work as a drift strategy. Enterprises keep trying to govern by sampling outputs, review a few copilot responses, spot check a few agent runs, and declare it acceptable. That's governance theatre. Drift doesn't show up consistently in outputs. It shows up in behavior, what the system retrieved, what it ignored, what it attempted to do, how often it escalated, how often it retried and where it wrote it work. Behavioral evaluation is the only thing that scales. You measure the system like you would measure a distributed service. Exception rates, time to resolution, escalation frequency, evidence coverage, tool invocation patterns and permission faults. Not did it sound right but did it act within the context boundary we designed. Now the uncomfortable truth. Drift accelerates when you treat prompts, policies and connectors as informal artifacts. If you don't version them you can't control change. If you can't control change you can't roll back. And if you can't roll back every improvement becomes a one-way door. So versioning becomes a first class capability. Prompts, grounding rules, relevance windows, connector configurations and orchestration policies need explicit versions with owners, with change logs, and with roll back parts. Not because it's elegant. Because the alternative is debugging a living system with no memory of who changed what. This is also where audit stops being a compliance exercise and becomes a drift detector. If you can trace which sources influence decisions over time you can see when the system starts leaning on different evidence. If you can trace which identities access which context you can see when permissions drift expands eligibility. If you can trace which workflows generate the most exceptions you can see where state models no longer match reality. And once you can see drift you can govern it. Not by freezing the system but by accepting that autonomy is entropy management. You don't eliminate drift, you detect it early, constrain its blast radius and correct it with control changes. Because in an autonomous enterprise the most dangerous system is not the one that fails. It's the one that keeps working while it slowly stops obeying you. Context governance. Turning trust into an operating model. Drift is inevitable. That's not pessimism. That's how tenants behave once they scale past a few discipline teams and a few passionate owners. So the only serious question is whether the organization governs context like an operating model or whether it governs it like a project. A burst of effort, a set of slides and a slow slide back into entropy. Context governance is not a committee that reviews AI outputs. It is the set of enforcement mechanisms that keep your context substrate trustworthy over time. Freshness. Permission correctness. Providence. Drift detection. And escalation. When the system encounters ambiguity it is not allowed to solve with creativity. The first move is to stop treating context as a single thing. Governance has to map to the same layer boundaries you're building. If you can't name the owners of memory state learning and interaction you don't have governance. You have vibes plus an admin portal. So governance starts with ownership. Graph memory needs an owner model that is accountable for. Content container hygiene, life cycle policies and what authoritative means in each domain. Not at a global level. At the workflow level who owns the incident knowledge base, who owns the procurement procedure library, who owns the HR policy corpus. If the answer is everyone then the system is onerless. That means it will rot. Dataverse state needs a product owner because state is a contract. Somebody has to own the entity model, the status transitions, the refusal conditions and the approval gates. If the state machine can change without review you've just created a silent bypass for autonomy. Fabric learning needs an owner that is responsible for closing loops. Turning analytics into updated relevance windows, rooting rules and exception handling. If fabric only produces dashboards, it's not a learning layer, it's a reporting cost and co-pilot interaction needs an owner who is responsible for the human boundary. What the system can do automatically. What requires confirmation, what requires approval, and what must be blocked by design. This is where AI policy becomes real because it becomes enforceable behaviors, not training posters. Now, once ownership exists governance becomes a set of lanes. You define tiered autonomy lanes that match risk, not ambition. A low-risk lane is where the system can draft, summarize, classify and root. With auditable logs and no irreversible actions, a medium-risk lane is where the system can execute bounded actions, create tickets, update-known fields, notify stakeholders under explicit scoping and rollback capability. A high-risk lane is where the system can only recommend, assemble evidence and escalate to a named approver. This matters because autonomous enterprise does not mean everything automated. It means automation is proportional to liability. Then you define evidence standards because trust isn't a feeling. It's a rule set. For certain workflows, the system must side sources or abstain. For others, it can act on state alone because the state is the source of truth. For still others, it can only proceed if evidence is both authoritative and fresh. Reviewed within a declared window, labeled correctly, and retrieved from the governed container. And you make that standard explicit when the system cannot meet the standard, it refuses and escalates, not because it's safe, because it is controlled. The next piece is drift detection as a continuous control. You don't wait for a quarterly review to discover that permissions sprawl expanded eligibility or that your relevance window quietly widened because new content sources appeared. You instrument it, permission fault rates, exception rates, escalation frequency, evidence coverage and provenance gaps. Those aren't AI metrics. Those are context integrity metrics. And the final piece is the escalation model, because governance without escalation is just documentation. Escalation needs named paths, who gets notified when a workflow hits missing evidence, conflicting evidence or policy violations, and escalation needs time. If nobody responds, the system must either pause safely or root to an alternate approver. Otherwise, the agent becomes a nagging bot and humans root around it and governance collapses. This is the operating model, clear ownership, tiered lanes, explicit evidence standards, continuous drift detection and enforced escalation. And once you have that, trust stops being an argument about whether co-pilot is good, trust becomes a property of the architecture, which is the only kind of trust an enterprise can defend in an audit. Case study, industrial manufacturing, reframed as context redesign, take a global industrial manufacturing organization with a familiar symptom, average issue resolution sat at 72 hours. Not because the engineers were slow, because the enterprise ran the workflow through human memory, email archaeology and team's thread roulette, a line went down, someone opened a ticket, then the real work started. Who owns this system? What changed? What was the last approved configuration? Which vendor is on the hook? What did we decide the last time this happened? None of that lived in one place. It lived in people, in inboxes, in a spreadsheet, someone trusted until they retired. Leadership saw this and concluded they needed AI for faster troubleshooting. And they were wrong. They needed context architecture, so troubleshooting had a substrate to stand on. The intervention wasn't framed as deploy co-pilot. It was framed as unify identity context, engineer organizational memory, track operational state, then add a learning loop. Only after that do you add an interaction surface. Start with identity and memory. Entra plus graph. The organization didn't have a single reliable mapping between a production line incident and the humans, systems, documents, and prior decisions that mattered. Graph already contained signals. Maintenance meetings, shift hand-over notes, files, work orders attached to emails, recurring team's chats and the real social structure of who asks who, when the line is down. Then they treated permissions like a compiler. They ran permission trimming specifically for the incident response domain, reduce overshared libraries, fix inheritance where it had drifted, and eliminate the classic pattern where a broad operational group had read access to everything just in case. So they built a simple state contract, not a giant transformation program. A state model with the minimum entities required to stop the loop. Incident, impacted asset, owner, current step, SLA approval gates, exceptions, and escalation path. Now the workflow could be replayed deterministically, the system didn't need to infer whether an approval happened. It could check, it didn't need to guess who owned the next step, it could read it. And when the workflow hit a refusal condition, missing evidence, conflicting procedure versions, or an action that required a human signature, the system escalated instead of improvising. Then analytical memory and fabric, they captured the signals the business never had. Time spent in each workflow state, which steps produced the most exceptions, which incidents reopened, which evidence sources were repeatedly retrieved but never cited, and where the same problem reappeared with different labels. Fabric didn't optimize the plant, though it exposed where the organization was lying to itself. It showed, for example, that certain approvals were pure theatre, always granted, always late, and always the bottleneck. It showed that a specific set of procedures caused delays because they were stale, contradicted by newer practices and still socially dominant. Those insights fed back into the relevance windows and governance. Old procedures became ineligible by default. Ownership got assigned, review dates became real. The system stopped treating archives as decision-grade evidence, only after all of that did co-pilot enter the narrative. Co-pilot's role was deliberately constrained. Synthesis, recommendation, evidence assembly, and escalation prompts. Not final decisions, not autonomous actions on production systems. The interaction layer served the humans supervising the flow, not the other way around. The result was not better answers. It was fewer loops, average resolution time dropped from 72 hours to 28. Coordination threads dropped by roughly 40% because people stopped re-asking basic state questions. Duplicated workflows dropped by about 30% because the system could see existing cases in their status, and audit preparation time was cut in half because provenance and state were already recorded as part of normal execution, not reconstructed during panic week. The outcome wasn't a smarter enterprise. There was a less ambiguous one. Autonomy didn't remove humans. It moved them up the stack, from context reconstruction to context supervision. What leaders get wrong when they scale co-pilot? Leaders usually don't fail at scaling co-pilot because they lack ambition. They fail because they scale the visible layer and ignore the substrate that makes it behave. The first mistake is treating licensing as strategy. Procurement loves this mistake. It feels decisive by more seats, watch usage climb, declare momentum, but licensing only changes who can ask questions. It doesn't change whether the tenant can answer them with evidence, with permission, correctness, and with stable definitions. So leaders end up measuring adoption while the organization quietly trains itself to work around the system. Co-pilot's fine for drafts, but don't trust it. That's not success. That's normalized distrust with a renewal. The second mistake is treating prompt training as the primary lever, prompting looks like leverage because it's immediate. Run workshops, publish templates, share top prompts for managers. And yes, it helps people communicate intent, but it doesn't fix context fragmentation. It doesn't fix stale procedures. It doesn't fix overshared libraries. It doesn't fix broken inheritance. It doesn't fix the fact that half the organization stores decision-grade work in personal one drive with ambiguous naming. So prompt programs become a mask. The enterprise gets slightly better at asking for answers. It does not get better at making those answers defensible. The third mistake is scaling agents before scoping tools. Executives here agent and assume automation, then ask why the organization isn't using it for approvals on boarding procurement, incident response, and customer coms. The problem is that tool access is where autonomy becomes liability. If an agent can read broadly and act broadly, you've built a high-speed pathway from retrieval mistakes to real-world consequences. The enterprise then reacts the way it always reacts. It adds exceptions. Entropy generators. This one team needs broad access. This workflow can bypass the approval in emergencies. This connector is fine because the vendor is trusted. Over time, the autonomy layer becomes conditional chaos. Lots of rules. No enforceable intent. And an execution surface that's impossible to audit. The fourth mistake is ignoring oversharing until it becomes a headline. Most copilot security incidents are not copilot incidents. Their permission reality made observable. Copilot simply retrieves what the user can already access. That's the design. So when leadership discovers copilot surface something embarrassing, they tend to blame the assistant instead of the access model. Then they overcorrect. Block features disable web grounding everywhere, restrict everything indiscriminately, and kill value for the teams that could safely use it. The stable move is boring. Permission hygiene and relevant scoping. Reduce eligibility. Raise authority. Make fewer things retrievable by default. Not because secrecy is good, but because noise is dangerous. The fifth mistake is using the wrong success metrics. Number of chats is not a business metric. Neither is ours saved reported through self-assessment surveys. Those are adoption signals. They're not integrity signals. If leaders want to scale copilot into autonomy, the metrics have to shift to system behavior. Reduction in rework, fewer approval loops, lower exception rates, fewer duplicated workflows, shorter cycle times, and quietly the most important, fewer permission faults discovered in the act of using the system. When those move value is real, because the enterprise is less ambiguous, not because the assistant is more charming. And there's one mistake that sits under all the others. Leaders assume scaling is a rollout problem. It isn't scaling is an architecture problem. It's about whether the organization can keep intent stable as the environment shifts, whether it can maintain freshness rules, whether it can version evidence standards, whether it can detect drift, whether it can enforce refusal conditions when evidence is missing. Because if the system can't refuse, it will guess. And in an enterprise, guessing doesn't just create wrong answers. It creates wrong actions, wrong approvals, and wrong records that live forever. So when a leader says we want to scale copilot, the only responsible response is to translate that into an architectural commitment, scale memory quality, scale state discipline, scale learning loops, scale control planes, copilot scales naturally after that. Before that, it scales confusion faster than it scales work. The seven day context inventory. So here's the part leaders usually skip because it feels unglamerous, a context inventory. Not a data inventory, not a we have share point inventory, a context inventory. Where does the enterprise actually store identity, evidence, state, and learning in a way an agent can use without guessing? And it has to be a seven day exercise for one reason. If you can't get clarity in a week, you're not doing architecture. You're doing therapy. You're collecting opinions until the calendar saves you from making decisions. This inventory has one goal. Expose the top three context breaks where work loses continuity, where it drops state, loses authority, or loses control. Those breaks are where copilot looks random. Those breaks are also where agents become dangerous. Start with the first question, where does identity context live? Not we use Entra, everyone uses Entra. Identity context means where is the current enforceable truth of who can do what, from an access and risk posture perspective? Which groups actually govern access to decision-grade content? Which conditional access policies define the boundary conditions for sensitive workflows? Which roles exist in name only? Which users carry historic privilege they no longer need? And which non-human identities, apps, service principles, connectors have permissions that nobody can justify anymore? If you can't name the owner of your authorization model per workflow domain, you don't have identity context, you have a directory and a pile of entitlements. Second question, where is workflow state tracked? Not in tickets. Ticket status is not state. It's a label. State means the contract that proves the workflow's reality. Approvals, exceptions, ownership, SLA, gates, and refusal conditions. If a critical workflow can't answer what step are we in? Who owns it and what is allowed next without reading a team's thread? You don't have state. You have coordination and coordination can't be automated safely. Third question, where does historical intelligence live? This is where organizations fool themselves with storage. Historical intelligence isn't, we have archives. Do you have an analytical layer that can tell you what keeps repeating, what keeps stalling and what keeps generating exceptions? Can you quantify rework and permission faults? Can you see where evidence conflicts and where policy drift creates ambiguity? And can you feed those signals back into governance? Or do they die as dashboards that nobody trusts? If you can't answer that, you don't have learning. You have telemetry exhaust. Fourth question, where are permissions actually enforced? This sounds like identity again. It isn't. Permissions enforcement means where is the boundary that copilot and agents will inherit and is it coherent? Which SharePoint sites are overshared? Where inheritance is broken? Which teams have guests and external sharing but store decision-grade content? Which containers have no owner? Which content lacks labels? So DLP can't act. In other words, where is the tenant poorest and are you pretending it's fine? Because nobody complained yet. Because copilot will complain for you publicly in a meeting. Fifth question, where is your signal telemetry centralized? If the organization can't observe behavior, it can't govern drift. You need to know what evidence sources get retrieved most, where citations fail, where refusal conditions trigger, which workflows escalate constantly, which identities experience CAE revocations midrun. And where tool invocation patterns look abnormal. That's not AI monitoring. That's the control feedback required to run a probabilistic system without lying to yourself. Now, the deliverable from the seven day inventory is not a report. It's three decisions. Decision one, map owners. For each context domain, memory, state, learning, interaction, assign a named owner with authority to enforce standards. Not a steering committee, a person. If you can't assign an owner, you've learned the most important truth. Autonomy will collapse into exception handling because nobody can enforce intent. Decision two, identify the top three context breaks. These are the points where work loses its spine. Common examples. Approvals tracked in email only. Policy stored in ungoverned wikis, incident artifacts scattered across personal drives, vendor onboarding, living in spreadsheets, or sensitive content stored in teams with guest access. Because it's easier. Write them down. Don't debate them. Context breaks aren't philosophical. They're observable. Decision three. Pick one workflow for a 30-day pilot. One, not enterprise-wide, not all-knowledge work. One workflow with visible pain and manageable blast radius where you can implement the four layers. Graph memory, dataverse state, fabric learning, co-pilot interaction with explicit refusal conditions. If leadership can't choose one workflow, they're not blocked by technology. They're blocked by accountability. And that's what the seven day context inventory really does. It forces the enterprise to admit where reality lives, where it doesn't and where the system will be forced to guess. Because once you see where guessing happens, the architecture stops being abstract. It becomes unavoidable. The 30-day pilot pattern. One workflow, four layers, enforced assumptions. Pick one workflow where failure is visible, frequent, and expensive. Approvals, incident response, onboarding, procurement. Anything with handoffs, delays, and a paper trail, you can't reliably reconstruct without begging three inbox owners for screenshots. Then do the one thing enterprises avoid? Define the assumptions upfront and make the system enforce them. Because the pilot isn't about proving co-pilot works. Co-pilot always works. It produces words on demand. The pilot is about proving your context substrate can support evidence bound decisions without improvisation. Start by defining the workflow boundary in plain language. What triggers it? What done means? And what irreversible actions exist inside it? If done isn't defined, the agent will keep acting until someone stops it. That's not autonomy. That's entropy with good grammar. Now implement the four layers, but keep them deliberately small. First, graph memory. This is where you stop treating M365 as file storage and start treating it as organizational recall. Choose the authoritative containers for the workflow, the SharePoint site, the Teams channel, the policy library, the decision log, then fix the obvious garbage, broken inheritance, abandoned owners, and the everyone group that turns retrieval into noise. Don't boil the ocean. Just make one domain coherent enough that retrieval can be precise. Second, Dataverse state. Create the minimum state machine that prevents relitigating work. Request record status owner, SLA, approver exception flag, and a small set of explicit transitions. The point isn't to model reality perfectly. It's to give the system a place to store truth that isn't buried in narrative. When the agent asks, has this been approved? It should query state not guess based on tone in a Teams message. Third, fabric learning. Instrument the workflow from day one. Track cycle time per state, number of escalations, number of retries, evidence coverage, and the top reasons for refusal. You're not building a dashboard for leadership theater. You're building a feedback loop that tells you where context broke. Missing sources, conflicting sources, permission faults, or state transitions, nobody owns. Fourth, co-pilot interaction. Put co-pilot where humans already work and constrain its role. It should assemble evidence, summarize state, draft responses, propose next steps, and generate the audit narrative. It should not execute irreversible actions. It should not decide policy. And it should not have silent tool access that can change systems without a gate. Now the critical part, enforce assumptions. Define refusal conditions like you mean it. If required evidence isn't found in the authoritative container, the system escalates. If the user's permission posture is inconsistent, the system refuses. If the request crosses an external boundary, the system requires confirmation. If the workflow state is ambiguous, the system asks a single targeted question, then writes the answer back to dataverse, so it never asks again. This is where you learn whether you have an autonomy problem or an accountability problem. Because refusal conditions force ownership, someone has to decide what counts as evidence, what counts as stale, and who approves exceptions. Without that, the pilot becomes another demo environment where the only reason it works is because smart people babysat it, measure four things for 30 days, and ignore the rest. Cycle time. Did it actually get faster? End to end? Not just in drafting email? Rework. Did people stop repeating the same steps, the same approvals, the same clarifications? Exception rate. Did the system have to escalate constantly because the process is undefined or because the context is dirty? Permission faults. How often did retrieval fail because access is wrong? And how often did retrieval succeed? Because access is dangerously broad. If those metrics improve, you don't just have a successful pilot, you have a repeatable pattern. Then you clone it, not by copying flows, by copying architecture. The same four layers, the same boundary discipline, the same refusal mechanics, the same telemetry loop, and the same ownership model. That's how you scale without turning autonomy into a tenant-wide rumor, and AI won't transform your enterprise. Context architecture will, because it forces probabilistic outputs to stay bound to evidence, state, and control.
