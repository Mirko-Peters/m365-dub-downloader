Now we need to control how that traffic flows through reasoning. Enterprise AI workloads aren't single model calls. A user makes a request. The system doesn't just send that request to Azure OpenAI and return the response. What actually happens is far more complex. The system retrieves relevant context from your knowledge base. It structures that context for the model. It calls the model with the context and the user's question, the model response. If validation fails, the system might call the model again with different parameters. If it passes, the system stores the result, logs the interaction and returns the response to the user. That's one complete reasoning chain, a single interaction that flows through multiple steps, multiple services, multiple decision points. Most enterprises have dozens of these chains running simultaneously. Some are simple, retrieve an answer. Some are complex retrieve, analyze, retrieve again, call external APIs, aggregate results, validate, respond. The complexity grows as your organization scales AI usage. As your AI foundry agents are the orchestration layer where these chains get defined and controlled. An agent isn't just a model. It's a system that coordinates reasoning. You can define multiple agents with different roles. A retrieval agent focuses on finding relevant information in your knowledge base. An analysis agent takes that information and performs calculations or transformations on it. An action agent takes the analysis results and makes changes in other systems, creating records, sending notifications, triggering workflows. Bicep must deploy these agents as a coherent system. The module doesn't just create an agent. It creates the agent with specific roles defined. Most governance failures in AI orchestration happen because agents have too much autonomy. An agent is created, it's given access to a data source and some external API. Nobody explicitly controls what the agent can do with those tools. The agent tries something unexpected. Data flows somewhere it shouldn't. An API gets called with parameters that break something. If the agent shouldn't be able to modify data, only read it. You enforce read only access. The permissions aren't something the agent requests and gets because nobody set up controls. Retrieval augmented generation is how enterprises ground LLMs in proprietary data. The pattern is straightforward conceptually. Before the model generates a response, the system retrieves relevant documents from your knowledge base and passes them to the model along with the user's question. The model reads the retrieved context and answers based on it. This solves a critical problem. It prevents the model from hallucinating answers and keeps responses tied to sources your organization actually owns. But rag introduces a new governance challenge that orchestration patterns don't fully address. When you retrieve documents to pass into an LLM, you're not just selecting information. You're exposing that information to the model's reasoning process. If those documents contain sensitive data, customer information, financial records, proprietary research, you're now allowing the model to process that data. The question becomes, who should the model be allowed to see? If user A asks a question and user B's confidential data appears in the retrieved context, has the model just leaked information? This is where data governance becomes architectural rather than aspirational. When documents enter your knowledge base, they must be classified by sensitivity level. Public data can appear in retrieved context for any user. Internal data should only appear for employees of your organization. Confidential data should only appear for people with explicit clearance. Restricted data shouldn't appear in LLM contexts at all. It's too sensitive to risk exposure, even to a model, but classification alone doesn't solve the problem. You also need filtering based on user permissions. A document might be classified as internal, but that doesn't mean every employee should see it. Maybe it's internal finance data, only finance team members should get that document in their retrieved context. Maybe it's HR records, only HR and authorised managers should access it. The retrieval system needs to know who's asking the question, check their permissions, and only include documents they're authorised to see. This filtering happens at query time, not at index time. The same document might appear in retrieved context for one user and be filtered out for another asking nearly identical questions. Audit trails must track what got retrieved and used. When an LLM generates a response based on retrieved context, you need to know which documents were included. If something goes wrong later, a user claims they received incorrect information or an auditor questions how a decision was made, you can reconstruct the exact context the model was working with by-seps structures this entire pattern.
