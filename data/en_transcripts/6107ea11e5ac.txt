So the next stop is the parts that make an agent work. How a copilot agent actually works. An agent looks complicated from the outside and underneath it's really a few moving parts. Microsoft reduces those parts to three questions, which are what it knows, what it processes, and what it can do. Every agent you meet is some answer to those questions, and once you can see them, the mystery mostly disappears. One of these pieces causes more trouble than the rest, and it's the one people rush past, so keep an eye out for it. What it knows comes from two places and both are under your control. One is the instructions you write, which work like the agent's job description, and the other is the knowledge you connect, which is the material it's allowed to read. Instructions tell the agent who it is and knowledge tells it what's true. Instructions matter more than beginners expect, because vague ones produce vague answers. Tell an agent to help with HR questions and it will guess at its role and drift. Tell it to answer questions about parental leave using the official policy document, and to admit when the document doesn't cover something. That second version behaves like a careful colleague, and the only thing that changed was the wording you gave it. What it processes is the middle piece, and you can't see it directly. This is the reasoning that decides which knowledge to use and which tool to reach for. It's also why the same agent can feel sharp one day and shaky the next. You can't tune it directly, so you shape it with clear instructions and clean sources. The next piece is what it can do, which is where tools come in. A tool is any action the agent is allowed to take, like sending an email, updating a record, or fetching live data from another system. Knowledge lets an agent answer and tools let it act, which is the difference we keep coming back to. Then there's the trigger, which is simply how the agent knows to start. Most agents begin when someone types a phrase in chat and some begin on their own. Building your first agent is less about technology and more about choosing well. The best first project is a small, repetitive job with a clear right answer, because that's where an agent shines and where you can tell whether it's working. Pick the task that makes you sigh when it lands in your inbox, and keep the first version small enough to finish in an afternoon. Nail this first one and every agent. After it gets easier to build, start by writing the instructions the way you'd brief a new teammate. Say who the agent is, what it should help with, and what it should do when it isn't sure, and keep the language plain. A specific job description is the single biggest lever you have over quality. Next, give it a small set of trusted documents instead of everything you own. A tight set of sources makes it easier for the agent to tell what's true, and it's far easier for you to keep those sources current. If a document changes, the agent follows the new version, so someone has to own that job. Add a tool only if the agent needs to act rather than just answer. If it only needs to explain. Knowledge is enough, and adding tools you don't need widens. What can go wrong when you do Add one. Start with a single action and test it hard before you add another. Testing is the step beginners skip and it's the step that saves you. Ask the agent the questions real people will ask, including the awkward ones, and try the phrasings a confused colleague would use.
