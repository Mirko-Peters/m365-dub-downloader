The word rest has an origin story that changes how you hear it. It was coined in two thousand by a computer scientist named Roy Fielding in his doctoral dissertation at the University of California, Irvine. That's the part everyone repeats. What they leave out is what the dissertation was actually about. It wasn't about building web APIs, it was about the web itself. Fielding co-authored the HTTP one point one specification, published in nineteen ninety nine, and his dissertation pulled out the design principles that had guided it. He described an architectural style for connecting documents across the internet, and he named six constraints client and server statelessness, caching, a uniform interface, a layered system, and code on demand. Only one chapter of the dissertation even covers rest. Fielding also pushed back on the idea that one style fits everything. He argued that a good designer should pick a style that matches the problem being solved, rather than treating any single approach as a silver bullet for all software. The path from a design essay about the web to the default label for APIs runs straight through soap. Soap was an earlier way to build web services, and it was verbose, XML heavy, and painful to work with. Ruby on Rails dropped its Soap support in two thousand and seven, and developers walked away. They wanted to ride on plain HTTP and rest handed their approach a respectable name. The deeper wrinkle is that strict rest is hypertext driven, which means a real rest API lets you discover every endpoint by following links from a starting point. Almost none of the APIs we call RESTful actually do that, and fielding himself pointed it out in two thousand and eight. The name got borrowed, stretched, and pinned to something that was never written for. That's the head fake. And it's the reason this topic finally makes sense. None of this makes the pattern a bad idea. Rest APIs work well for the job most people need, which is letting one program ask another for data over the web. The point is narrower and more useful. The word describes a set of design choices from two thousand, not a set of laws. So nobody is grading your API against a hidden rulebook where you already meet rest.
