Graph is a distributed system. Sometimes, requests fail. Sometimes the response takes longer than expected. You're building continuous automation on top of an infrastructure that doesn't guarantee instantaneous success. Just reality. The question isn't whether failures will happen. The question is whether your pipeline survives them. Four types of failures matter in practice. Rate limiting returns HTTP 429. You've exceeded your quota. Temporary service issues return HTTP 503. The backend is overloaded or temporarily down. Authentication failures return HTTP 401. Your token expired or your credentials are invalid. Permission issues return HTTP 403. Your app doesn't have permission to access what you're asking for. Each one requires a different response strategy. When you hit rate limiting, you wait and retry. The response header tells you how long to wait. Respect that. Don't be aggressive. Don't hammer the API, hoping it recovers faster. The system is telling you to back off. Once you wait the requested duration, retry the request. It'll usually succeed. Temporary service issues are similar. The backend is having trouble. Wait and retry. But don't use the same wait duration as rate limiting. Service issues might need longer. Use exponential back off. Start with one second. If the retry fails, wait two seconds before the next attempt. If you wait for, then wait until you hit a maximum. Maybe five minutes. Add randomness to the wait duration so you don't have a thousand applications or retrying at exactly the same time. That randomness is called jitter. It prevents thundering herd problems where synchronized retry attempts hammer the service and keep it down longer. Authentication failures need a different approach. Your token expired. Don't retry the same request with the same token. You'll just get 401 again. Instead, refresh your token, get a new one, then retry the original request. If refreshing the token fails, something's wrong with your credentials. Don't keep retrying. You won't fix it by trying harder. You need human intervention. Permission issues mean your application doesn't have permission to access what you're asking for. Retrying won't fix that. The problem isn't transient. It's structural. You need higher permissions. Log the error. Skip this request. Move on. Don't consume retries on something that will never succeed. Identity is where most automation fails. The solution is IDEM potency. Design your system so that processing the same alert twice produces the same result as processing it once. Use the duplication. Check if an alert with this ID already exists before storing it. If it does, skip it. If it doesn't, store it. Now duplicates don't create problems. Latency handling is about accepting reality.
