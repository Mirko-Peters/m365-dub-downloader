They repeat across tenants in the same order for the same reasons, and each one undoes work you thought was finished. Common failure patterns and their fixes start with the quietest one. A custom policy gets built. Someone spends an afternoon on it. Threshold set protected users added actions chosen. Then it never touches a single recipient. Maybe the scope was left empty. Maybe it was scoped to a group that got renamed, Or maybe a preset policy already covers everyone, so the custom one never gets a turn. The policy exists, the review says configured, and nobody is protected by it. The fix is a check, not a rebuild. For every custom policy, ask the portal who it applies to and confirm that at least one real recipient lands there. Run it after every scope change and keep a name next to the answer. The second pattern starts during an incident. A supplier's mail is stuck. The CFO is asking, so someone adds an allow entry or a do not rewrite exception or a bypass rule in mail flow. And the pressure lifts. Everyone moves on. Nobody comes back. Six months later, the exception is still there and the supplier's domain was compromised in March. You've been waving their mail through ever since. Incidents are when exceptions get written fastest and reviewed least. So change the rule for emergencies, not the speed. Anything added under pressure gets an expiry date on the spot, even a short one. And the monthly review we covered reads that list first every time. Third, the protected user list. It was built at deployment from the org chart as it stood that week. Twenty names carefully chosen. Then a new finance director joined the head of procurement changed. Someone got promoted into payment approval. None of them are on the list and the people who left are still on it. So the impersonation protection defends a company that no longer exists and attackers don't use last year's org chart. They read the current one off LinkedIn. The fix sits in the quarterly pass. Compare the list against who approves payments today. Who holds admin roles today? Who leads each team today? Add, remove and write down the date you checked for quarantine notifications turned off. It usually happens for a good reason. Users complained about extra mail, so someone switched the digest off. Quiet inboxes. Fewer complaints. Problem solved. But now blocked mail is invisible. A real invoice gets held and the user finds out only when a vendor calls to ask why nobody paid. Or worse, the user learns that quarantine exists at all and starts asking it to turn the filtering down. So turn the notifications back on and fix the actual complaint. Pick a calmer cadence. Limit the digest to verdicts the user is allowed to act on. Remember admin release only verdicts sent nothing, So the digest is already smaller than people expect. And fifth, the simulation run. Once a campaign goes out, the click rate comes back at eleven percent. The report goes up with the word pass on it, and the program is considered done for the year. But one run is one lure on one day to one group. It proves nothing about next quarter's lure or about the people who weren't centered. A single test is a photograph. What you need is the film. So schedule the next campaign before you present the results of the last one. Rotate techniques, rotate groups and compare like with like and report the trend. Never the pass. Look at the five together a policy. Nobody hits an exception. Nobody removes a list. Nobody updates a notice. Nobody sends a test. Nobody repeats different features. Same structure. Each one is a setting that got configured once and then trusted conclusion from configuration to measurement. So here's the shift. The old model says email security is something you set up, pick the policies, flip the switches, and the product protects you from then on. It sounds reasonable. It's also why most tenants run on defaults and call it protection. The new model says it's something you run a loop of measuring, reviewing, and adjusting with a name on every step the product ships capable. Whether it works for you depends on the habit you build around it, and the order of decisions is simple enough to keep in your head. Start with presets and let Microsoft's tuning cover the broad population. Check scope so you know who each policy really reaches. Treat every exception as debt with an owner and an expiry shape quarantine so users can act where the stakes are low and can't wear their high. Test your people with realistic simulations and read the results honestly. Then measure all of it on a rhythm so the next change rests on evidence.
