At its core, MCP is a JSON RPC 2.0 protocol that means it uses a standard remote procedure core format where a client sends a structured request and a server returns a structured response. But MCP adds something critical on top of that foundation. It adds discovery. An MCP server doesn't just expose endpoints, it exposes capabilities. When an MCP client connects to a server, they perform an initialization handshake. The server announces what tools it offers, what resources it can provide, and what prompts it supports. The agent then selects a tool, provides the parameters, and receives a structured response. This means your agent can adapt to new capabilities without code changes. Before you start building, you need to understand how MCP actually works under the hood, not the marketing description, the wire protocol. Because the architecture decisions you make here will determine whether your MCP deployment scales, whether it remains secure, and whether your agents can actually discover the capabilities they need. MCP runs on JSONRPC 2.0. If you've worked with remote procedure calls before, this will feel familiar. If you haven't, the concept is straightforward. A client sends a request with a method name and parameters. A server processes the request and returns a response. If something goes wrong, the server returns an error object with a code and a message. But MCP adds a critical layer on top of raw JSONRPC. It adds the initialization handshake. When an MCP client first connects to a server, they don't immediately start invoking tools. They negotiate. The client sends an initialized request with its protocol version that supported capabilities and its implementation details. The server responds with its protocol version its capabilities and its implementation details. Only after both sides agree on the contract, do they transition to the ready state and begin normal operation. This handshake is why MCP servers and clients can evolve independently. A server running protocol version 2025, 1125 can talk to a client that supports version 2025, 0618. Then negotiate the common subset. If the server offers a feature, the client doesn't understand, the client simply ignores it. If the client requests a feature, the server doesn't support, the server returns a clear error. This is capability negotiation in practice. And it's fundamentally different from REST API versioning with REST, you typically version the entire API surface. V1, V2, V3. When V2 drops a field that V1 had, every client breaks unless it was already updated. With MCP capabilities are granular. The server advertises what it has. The client selects what it needs, changes are additive by default. Let's look at the four primitives in detail. Tools are the most commonly used primitive. A tool is a calibable function exposed by the server. The server defines the tool's name, provides a description that explains what the tool does, and specifies a JSON schema for the parameters. This schema is typed, it tells the client exactly what inputs the tool expects, what types they are, and which parameters are required. When an agent wants to use a tool, it doesn't just guess the parameters. It reads the schema. It reads about what values to provide, and it invokes the tool with a properly structured request. The server executes the tool and returns a result. Here's where the 2025 0618 protocol update changed things significantly. Before that update, tool results were typically simple strings. A tool might return a block of text, and the agent would pass that text to extract meaning. This was fragile. If the tool output format changed, the agent's passing logic broke. The 2025 0618 update introduced structured tool output. Now tools can return typed objects, arrays, and nested data structures. The agent receives a structured result. It can reason over directly. No passing, no rejects extraction, no brittle string manipulation. This matters for enterprise integrations because your business systems already return structured data. Acquery against your ERP returns records with typed fields, an inventory check returns quantities, locations, and status codes. With structured tool output, that data flows directly into the agent's reasoning pipeline in its native shape. Resources are the second primitive. Where tools are active operations, resources are passive data sources. A resource is addressed by a URI, just like a web page. The server defines what URIs it supports, and what content they return. When an agent needs context, it can request a resource by URI. The server returns the content, typically as text that the agent can embed into its reasoning context. This is how an agent reads a policy document, pulls a project charter, or retrieves a customer record. Resources are read only by design. If an agent needs to modify data, it uses a tool. This separation creates a clean architectural boundary. Resources provide context. Tools perform actions. Prompts are the third primitive, and they're often misunderstood. An MCP prompt is not a user message. It's a template that the server offers to help the client structure its reasoning. A server might expose a prompt for generator quarterly financial summary in the CFO's preferred format. The prompt includes the template structure, variable slots, and instructions for how to fill them. When an agent needs to perform a complex reasoning task, it can request a relevant prompt from the server. The server provides the template. The agent fills in the variables and uses the resulting structured instruction to guide its output. This is particularly valuable in Microsoft environments where organizations have standardized formats, compliance, templates, and brand guidelines. The MCP server encodes these standards as prompts, and every connected agent automatically produces output that follows them. Sampling is the fourth primitive, and it's the inverse of the other three. Sampling allows the server to request generative reasoning from the client when a server encounters a problem that requires AI reasoning instead of hosting its own model, it asks the client to generate a response. This creates a distributed intelligence pattern. The server handles business logic, data access, and system integration. The client handles language understanding, summarization, and generative reasoning. They collaborate through a standardized contract. In a Microsoft environment, this pattern is powerful because your MCP servers don't need to host or manage language models. They use the reasoning capabilities of co-pilot, Azure OpenAI, or whatever AI client is connecting to them. Now let's talk about the lifecycle of an MCP session. The client connects. The initialization handshake happens. The client requests the list of available tools, resources, and prompts. The server responds with the catalog. The agent reasons about what it needs. It invokes tools. It reads resources. It may request prompts, and when the work is complete, the session closes. Throughout this lifecycle, the protocol maintains state. The server knows which client it's talking to. The client knows which capabilities the server offers, and both sides can send notifications, not just requests and responses. Notifications are one-way messages. A server might notify the client that a resource has changed, prompting the agent to refresh its context. A client might notify the server that it's shutting down, allowing the server to clean up resources. This event-driven pattern keeps agents working with current context rather than stale snapshots. When a SharePoint document is updated, the MCP server can notify all connected agents that the resource has changed. The agents pull the new version and update their reasoning. The message format itself is worth understanding because you'll see it in logs, traces, and debugging sessions. A JSON RPC request is a JSON object with four fields. JSON RPC is always 2.0. I'd is a unique identifier that the client generates, so it can match the response to the request. Method is the capability being invoked like tools, call, or resources, read. And Params is an object containing the method-specific parameters. A JSON RPC response is similarly structured. JSON RPC is 2.0. I'd match the request and result contains the response data. If something goes wrong, result is replaced by error, which contains a numeric code, a message string, and optional data with additional context. This format is intentionally simple. You can read it in a text editor. You can pass it with any JSON library. And you can trace it through network logs without specialized tools. The initialization handshake uses the same format. The client sends an initialized request with method, initialize, and Params containing protocol version, capabilities, and client info. The server responds with a result containing the server's protocol version, capabilities, and server info. Only after this exchange does the client send an initialized notification, and only after that notification does the server accept normal requests. This sequence matters for debugging. If your agent can't discover tools, the first thing to check is whether the initialization handshake completed. Look for the initialize request in your logs. Look for the response. Check that the protocol versions are compatible, and verify that the initialized notification was sent. Most connection failures happen at this layer, not at the tool invocation layer. Illicitation is a pattern where a tool can ask the client for additional information before completing its execution. Instead of failing when a required parameter is missing, the tool can prompt the client to provide it. The general rule is this, target the oldest version that supports all the features you need. This maximizes client compatibility. If you don't need structured tool output, targeting an older version means more clients can connect. If you do need it, targeting 2025 0618 or later is the right call. But SSE connections often run a foul of course configurations, especially in enterprise environments where strict security policies are the norm. Firewalls and proxies sometimes buffer SSE connections. This creates latency. Messages arrive late or in bursts. And some corporate proxies drop long-lived connections entirely, causing intermittent failures that are hard to diagnose. So the MCP specification deprecated SSE. And replaced it with streamable HTTP. Streamable HTTP is a fundamentally different approach. Instead of maintaining a single long-lived connection, it uses standard HTTP post and get requests. The client sends requests as post operations. The server responds immediately or streams the response over the same connection. If the server needs to send notifications, the client opens a get connection that the server can write to. This means streamable HTTP works with standard HTTP infrastructure. Load balancers handle it. Firewalls understand it. Chores policies apply cleanly. And authentication is straightforward because every request is independent and can carry its own orthotocons. For Microsoft environments, this is the transport you want. Streamable HTTP integrates with Microsoft Enter Authentication. Every post and get request can include a bearer token from Enter ID. Conditional access policies apply per request. Multi-factor authentication can be enforced at the API gateway level. And session management follows patterns that Microsoft security teams already understand. Streamable HTTP also supports session management. When a client connects, the server can assign a session identifier. Subsequent requests include this identifier, allowing the server to maintain state across multiple HTTP requests. This is how an MCP server remembers what tools it has exposed, what resources are available, and what notifications the client has subscribed to. For Azure deployments, streamable HTTP is the natural fit. Azure functions can handle streamable HTTP requests through HTTP triggers. An agent sends a post to your function endpoint. The function processes the JSON RPC request and returns the response. If the operation is long running, the function can return and accept its status and send the final result through a callback or a subsequent get request. Azure API management sits in front of your MCP servers and provides unified routing, rate limiting, and monitoring. You can expose multiple MCP servers through a single API management gateway. The gateway handles authentication, throttling, and request transformation. And your backend servers focus on business logic. Azure Container Apps can host persistent MCP servers that need stateful session management. If your server maintains long-lived connections to backend systems, or if it needs to cache resource data between requests, a containerized deployment gives you the control you need. And as your front door or application gateway can distribute MCP traffic across multiple regions, providing geographic redundancy and failover, the choice between transports is not really a choice anymore. STDO for development. Streamable HTTP for production. SSE is deprecated and should not be used for new deployments. If you have existing SSE deployments, you should plan a migration to streamable HTTP. The protocol changes are not dramatic. The JSON RPC message format is the same. But the connection model shifts from persistent streams to request response pairs. And that shift unlocks enterprise grade authentication, scaling, and monitoring. Here's the decision matrix. If you're building a local tool or developer utility, use STDO. It's the fastest path to a working server. If you're deploying to Azure, use streamable HTTP. It's the only transport that integrates cleanly with Entra, API management, and standard enterprise security policies. If you're evaluating SSE for a new project, stop, use streamable HTTP instead. SSE is deprecated in the MCP specification and will not receive further enhancements. This transport decision is one of the most important architectural choices you'll make. Because once you have hundreds of agents connecting to dozens of MCP servers, the transport layer determines your authentication model, your scaling strategy, and your observability footprint. Get this right and the rest of your MCP architecture follows cleanly. Get this wrong and you'll be fighting connection issues, or failures and firewall rules while your AI team waits for the connectivity layer to work. This is where your business systems live. Your Dynamics 365 ERP, your SharePoint sites, your SQL databases on Azure, your custom line of business applications. Your one drive files, your team's conversations. This layer doesn't change. These are the systems you've built and bought over the past decade. They are your source of truth. Above the data layer is the MCP server layer. This is where the connectivity happens. Each MCP server wraps one or more business systems and exposes their capabilities through the standardized protocol. You might have an ERP MCP server that exposes tools for inventory checks, order creation, and supplier lookups. You might have a SharePoint MCP server that exposes resources for project documents and policy manuals. You might have a custom application MCP server that exposes tools for your proprietary business processes. Each MCP server is a net application built with the official CESDK. Each server registers its tools, resources, and prompts through the SDK's attribute system. Each server handles the JSON RPC protocol, the initialization handshake, and the capability negotiation. And each server runs on Azure, either through Azure Functions for Event-driven workloads or Azure Container Apps for persistent services. Above the MCP server layer is the Intelligence layer. This is Work IQ. It sits alongside the MCP servers rather than replacing them because it serves a different purpose. MCP server's exposed business operations, Work IQ exposes organizational context, it knows who works on what, it knows what meetings decided, it knows which documents changed. And it provides this context through its own MCP server so that any agent can discover and consume it. Above the Intelligence layer is the protocol layer. This is where MCP and A2A operate. MCP handles agent tool communication. A2A handles agent to agent communication. Both protocols use HTTP, both use JSON RPC 2.0, both integrate with Microsoft Entra for authentication. And both can root through Azure API management for gateway services. API management is the critical hub in this layer. It receives all incoming protocol requests. It validates baritokens against Entra agent ID. It applies rate limiting based on the agent's tier. It roots requests to the appropriate back end MCP server based on the tool name or the resource URI. And it logs every request for auditing and monitoring. This means your MCP servers don't sit on the public internet. They live in a private VNet. API management has a private endpoint in that VNet. All traffic flows through the gateway. And your network security team applies the same policies to MCP traffic that they apply to every other internal API. Above the protocol layer is the agent layer. This is where your agents live. Copilot Studio agents that uses interact with through Teams chat. Custom agents that run background processes. Specialized agents that handle procurement, customer service or financial reporting. Each agent has an agent ID identity in Entra. Each agent discovers tools through MCP. Each agent delegates tasks through A2A. And each agent operates within the scope defined by its conditional access policies. At the top is the presentation layer. This is where users engage with the agents. Teams chat. Copilot in Outlook, Power Apps Interfaces, Custom Web Applications, the user asks a question. The question flows to an agent. The agent reasons. The agent discovers tools. The agent invokes tools through MCP. The tools execute business logic. The results flow back. The agent synthesizes the answer. And the user receives a response that is grounded in real-time business data. That's the vertical stack. Now let's look at the data flow horizontally. A user asks their Copilot Studio agent, what's the status of the Phoenix project? And are we on track to deliver by Friday? The agent receives the question. It initializes its MCP connections. It discovers available tools from the registered MCP servers. It sees a tool from the work IQ MCP server called GetProjectStatus with a project name parameter. It sees a tool from the ERP MCP server called CheckDeliverySchedule with a project code parameter. The agent reasons. It decides to invoke both tools. At first, conditional access evaluates the agent's identity. API management receives the request. It validates the bearer token. It checks the agent ID against EntraAgentID. It confirms the agent is authorized to invoke these specific tools. It checks the rate limit. And it roots the requests. The work IQ tool executes. It queries SharePoint for project documents. It reads Teams conversations about the Phoenix project. It checks planner tasks. And it returns a structured summary of the project status, including risk flags identified from recent meeting transcripts. The ERP tool executes. It queries the delivery schedule database. It checks inventory levels for required components. It verifies supplier lead times. And it returns a structured delivery forecast. The agent receives both results. It synthesizes them. It recognizes that while the project status is green, a supplier lead time has slipped by two days, putting the Friday delivery at risk. It drafts a response for the user. And it optionally triggers a notification tool to alert the project manager. The user sees a concise answer grounded in real project data and real supply chain conditions. Not a demo. That's a production architecture. And it scales. When you have 10 users, this architecture works on a single Azure function. When you have 10,000 users, API management distributes the load. Azure Functions scale horizontally. Container apps handle persistent state. Cosmos DB caches session data. Application insights monitors every request. And Azure Front Door roots traffic across regions. The scaling patterns are standard Azure. The protocol is standard MCP. The identity is standard Entra. And the architecture is standard enterprise integration applied to a new domain. Now let's talk about failure modes. Because architects don't just design for success, they design for failure. What happens when an MCP server is down? The agent discovers the server is unavailable during initialization or receives an error during tool invocation. A well-designed agent handles this gracefully. It informs the user that a specific data source is temporarily unavailable. It falls back to alternative tools if they exist. And it queues the request for retry if the operation is critical. What happens when an MCP server is slow? API management applies timeout policies. If a tool execution exceeds the configured threshold, the gateway returns a timeout error. The agent receives the error and decides whether to retry, to inform the user, or to proceed with partial information. What happens when an agent is compromised? Entra agent ID detects the anomaly. Conditional access blocks the request. The agent 365 control plane alerts the security team. And the compromised agent's credentials are revoked before significant damage occurs. What happens when a tool returns unexpected data? The agent's reasoning pipeline handles the structured response. If the response doesn't match the expected schema, the agent flags the inconsistency rather than hallucinating an answer. The error is logged. The MCP server operator is alerted. And the schema is corrected. These failure modes aren't hypothetical. They are the standard resilience patterns that every enterprise architect already applies to APIs and microservices. MCP doesn't change the resilience model. It extends it to the agent layer. Finally, let's address the anti-patterns. The most common mistake is putting business logic in the agent instead of the MCP server. The agent should reason. It should decide which tools to invoke. It should synthesize results. But it should not implement business rules. Business rules belong in the MCP server where they can be versioned, tested and reused across multiple agents. The second common mistake is using SDDO transport and production. SDDO is for development. Streamable HTTP is for production. Deploying a SDDO server to Azure and trying to connect remotely is a category error. The third common mistake is hard coding authentication. Every MCP server should validate tokens through Entra agent ID. Encoded API keys, connection strings or credentials create security debt that will eventually cause a breach. The fourth common mistake is building one giant MCP server that exposes every tool in the organization. This creates a monolithic dependency. When that server needs maintenance, every agent that depends on it stops working. Instead, build focused MCP servers for specific domains. One for ERP, one for SharePoint, one for Custom applications. This limits blast radius and enables independent deployment. The fifth common mistake is ignoring observability. MCP servers are infrastructure. They need monitoring, they need logging, they need alerting. Without application insights or an equivalent observability platform, you'll be debugging production issues in the dark. A sixth mistake is skipping capacity planning. An MCP server that handles 10 requests per minute during testing will collapse under 1000 requests per minute when 1000 users start using the agent simultaneously. Load test early. Understand your latency distribution. Identify the P9 response time and set your scaling rules based on real traffic patterns, and set up optimistic estimates. A seventh mistake is neglecting backward compatibility. When you add a new parameter to a tool, older clients might not provide it. When you rename a tool, existing agents lose access until they reinitialize. When you change a response schema, agents that depend on specific field names break. Version your tools carefully. Add parameters as optional before making them required. Deprecate tools before removing them and communicate changes to agent owners before deployment. An eighth mistake is failing to document the server capabilities. The MCP protocol provides tool descriptions and parameter schemas, but it doesn't provide business context. An agent developer needs to know what business process or tool supports. They need to know what data quality to expect. They need to know what error conditions to handle. Write documentation that lives outside the protocol. Share it with agent teams. And keep it current. A ninth mistake is deploying without a rollback plan. When a new MCP server version breaks an agent, you need to revert quickly. Blue Green deployment is the standard pattern, but it requires automation. The rollbacks take too long, build a deployment pipeline before you need it. Test the rollback procedure before you deploy to production and practice the failure recovery during plant maintenance windows. Avoid these mistakes and you'll have an architecture that lasts.
