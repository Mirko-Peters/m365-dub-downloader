Under the hood, a component is built from a few moving parts, and once you see them, most of the mystery goes away. The first part is a manifest. A manifest is a small file that declares the component's name, the inputs it expects, and the outputs it can send back. Think of it as a label and a wiring diagram on the side of a box so the app knows what's inside. That label does real work. It's what makes the component reusable and predictable. Because the inputs and outputs are declared up front, the app can wire a field or a data set straight into the component without guessing. The second part is the lifecycle, which is just a word for the moments in a component's life. A component starts up and developers call that in it. It draws itself and redraws whenever the data or a setting changes, which is update view. It handles values back to the app when something changes, which is get outputs and when it's no longer needed, it shuts down and cleans up after itself, which is destroy. If that sounds like a lot of machinery, try holding it this way. Picture a light switch in a room where you flick it on and the light comes on. When something changes in the room, the light adjusts and when you leave, you switch it off. The lifecycle is that same rhythm applied to a piece of an app instead of a room. The third part is the data link. Everything the component declared in its manifest arrives as a context when it redraws. In plain terms, the component always knows what the app is showing it at that moment. Change the record and the component sees the new value right away.
