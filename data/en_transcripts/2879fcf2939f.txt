Leased privilege doesn't mean minimize what the agent can access. It means give the agent exactly what it needs to do its job. Nothing more, nothing less. A sourcing agent needs to read from the ATS and LinkedIn, but it doesn't need to read HR files or access the finance system. And it definitely doesn't need to modify anyone's record or delete data. The permission model has three layers. First, graph scopes. What APIs can this agent call? Second, connector access. If this agent uses external data, which connectors can it query? Third, data classification. Some data is marked sensitive or confidential. Can this agent access it? An agent that sources candidates might have these permissions. Read from the ATS connector. Read from LinkedIn connector. And read public teams channels where open roles are discussed. Not write to ATS. Not read from Salesforce. Not access personnel files. It's a narrow permission set. Specific to its job. Auditable down to the individual scope. The compliance specialist agent has different permissions. Read from the ATS connector to see the candidates. Read from the HR data repository to check policies. And read from external compliance databases to verify regulations. It doesn't have right access to anything. It can flag issues, but a human or a supervisor agent makes the decision to act on them. And that's where things change. Because most deployments get it wrong, they over-permission agents to avoid having to manage complex permission hierarchies. They give an agent access to everything it might need, plus some things it probably doesn't. An agent that handles hiring gets full sharepoint access because it might need to read policies and an agent that manages IT tasks gets permissions to every system because we might ask it to do different things later. Over-permissioning is the number one cause of AI breaches. Not because agents are malicious, but because overly broad permissions create a tax surface. A compromised agent with full system access isn't just dangerous because of what it was designed to do. It's dangerous because of all the things a compromised agent could be tricked into doing. A prompt injection attack that makes an agent export confidential data becomes viable when the agent has export permissions, it never needed. Conditional access for agents applies the same policy framework that protects human users, not just permissions but risk-based controls. If an agent is accessing resources from an unusual location, block it. If an agent is making a pattern of calls that looks like data expiltration flag it, if an agent is running at a time outside normal operating hours, require additional validation. These are the same controls that protect humans. Now they protect agents, a real example, an email triage agent. It can read emails from a specific mailbox. It can flag urgent ones. It cannot delete emails. It cannot forward them externally. It cannot access attachments. It cannot modify the inbox rules. Every constraint is explicit. Every permission maps to a specific job function. The agent is useful because it understands context and escalates appropriately. It's safe because it cannot cause damage even if it's reasoning is wrong. Identity is the foundation. Now let's talk about what happens when things go wrong. Audit trails and observability, making agents accountable. Here's what keeps compliance officers awake at night. We don't know what the agent did. You have an agent operating in your system, something goes wrong. Customer data leaked, a financial record was modified incorrectly, an email was sent that shouldn't have been sent. Someone asks, what did the agent do? How did this happen? Who authorized it? And the answer comes back. We don't have that information. That answer is unacceptable. And yet, it's what most organizations have right now because they never wired auditability into their agent deployments. Auditability means three things. First, every decision is logged. When Lucy, the supervisor agent, decides to escalate something to a human, that decision gets recorded. What data did she evaluate? What rule triggered the escalation? What exact timestamp? Second, every tool call is captured. When Tim invokes the calendar API to schedule a meeting, the system logs the call. What parameters, what response, and what the agent did with the result. Third, every data access is tracked. Which agent accessed? Which file? When? What did it read? Did it copy it? Did it modify it? All of it logged. But here's the problem. Organizations assume that logging and auditability are the same thing. They're not logging is data. Gigabytes of unstructured text saying what happened. Auditability is intelligence. The ability to answer specific questions about what happened, why it happened, and who was responsible. Pervue audit is the backbone here. It's Microsoft's unified audit log for Microsoft 365. Everything that happens in exchange, SharePoint, Teams, OneDrive, and Graph flows into Pervue. Agent activity gets captured there alongside human activity. Lucy reading a file, logged, Tim sending an email, logged Olivia flagging a record, logged. One system, one source of truth. But here's the nuance. Agent logs and human logs are not the same thing. When a human access is a file, it's because the human decided to access it. They searched, they found it, they opened it. That's one entry in the log. When an agent access is a file, the context is different. The agent was instructed by its supervisor to check compliance on a candidate, and the supervisor was following a workflow that responded to a specific requisition. The access is part of a chain of decisions that extends backward. Auditability requires capturing that chain not just the access event. This is where intelligent dashboards matter. Raw logs are noise. Thousands of events per hour. Hundreds of thousands per day. You cannot read them manually. You need dashboards that show anomalies. That answer questions. And that flag patterns. A dashboard might show this agent access files from three different departments in one hour. That's unusual. Why? A dashboard might show this agent exported data at 2 a.m. That violates policy, flag it. A dashboard might reconstruct a timeline. Requisition arrived Monday, sourcing happened Tuesday, compliance review happened Wednesday, but then compliance flags were overridden and hiring proceeded anyway. Who overrode them? Why? Anomalies that span agent activity and network activity become visible. An agent exporting data is suspicious, but an agent exporting data and uploading it to an external cloud storage service is an incident. CM sees both events and correlates them. A real example. Human approval loops, the safety gate, the foundation is built, identity is set, permissions are locked, audit trails are running. You have an agent that understands context and talks to other agents, but a massive problem remains. Some decisions need human judgment, and you cannot automate that away. The question isn't whether humans should stay involved. They have to be there. The real question is how you involve them without breaking the speed of the system. If every single action requires a person to stop and think, you have built a bottleneck. You have turned your agents into fancy suggestion engines. The human sees a recommendation, clicks approve, and moves on. You have only reduced the manual work by maybe 20%. The agent finds a candidate, but a person still screens them. The agent picks a meeting time, but a person still confirms it. This is not a transformation, it is just theater. The solution is the approval loop pattern. In this model, the agent proposes an action. The human reviews that proposal with the full context, the human makes the call. The system only executes if it gets the green light. The agent doesn't sit around waiting forever. And the human doesn't get buried in requests. The whole process moves fast enough to actually save time, but you must be clear about what needs a signature. Not everything does. An agent that can only act after a human reviews, it isn't really an agent, it is just a form generator. The line between doing the work and asking for help is where governance actually lives. Certain actions always need a human eye. Anything involving money belongs in this category. Payments, budget shifts, or changes to someone's pay. Anything that deletes information needs a check, deleting records, closing accounts, or archiving data, anything that goes outside the company needs a review. External emails, sharing with customers, or sending files to people without standard access. These actions carry risks that go beyond the moment, they have consequences down the line. Most routine tasks do not need this level of oversight. An agent reading an email doesn't need permission. An agent scheduling an internal sync doesn't need a sign off. An agent updating a record within its normal range doesn't need a human. These actions are easy to undo. They fit inside the lines. The cost of making them wait for a person is higher than the risk of the action itself. This is where threshold-based approval changes the game. You don't approve specific actions, you approve ranges. An expense agent might auto-approve any claim under $150. It sends claims between $150 and $500 to a manager. Anything over $500 goes straight to finance. The agent isn't asking for permission every time. It is following a rule. Small claims are already within its authority. The user experience is the biggest hurdle here. An approval has to be fast, or it becomes a wall. If a person has to read a long story, dig for context, and open three different systems to check facts that approval takes 10 minutes. Now the agent is stuck, the user is waiting. The time you were supposed to save is gone. The fix is the evidence pack. Instead of giving a human a raw request, the agent gathers everything they need to decide. It provides the logic. The human sees exactly what data the agent looked at and which rules it applied. They see where the decision hit a boundary that required a person. The human can still override the system if they know something the agent doesn't. But usually the info is all there. The choice is obvious. The approval happens in seconds. The agent reasoning logically from the modified instructions complies. The data is gone. Data loss prevention for agents is the first line of defense. Per view, DLP does not just apply to humans anymore. It now has specific agent enforcement modes. When an agent tries to process sensitive data, DLP can intercept the flow before the data reaches the model. This is the critical moment. If DLP blocks the sensitive data here, the model never sees it. The agent cannot accidentally leak what it never had access to. The way this works is that DLP policies get evaluated on agent prompts. You mark certain data as confidential, like customer records, financial information, or trade secrets. You define a DLP rule. If an agent tries to process confidential data, block it. When an agent reads a customer email marked as confidential and tries to summarize it, DLP intercepts the operation. The email is not included in the prompt. The agent processes a redacted version or does not process it at all. Every blocked attempt gets logged in per view for forensic investigation. But DLP is reactive. It blocks bad things. Sensitivity labels are proactive. They mark data at the source and control how agents can use it. A sensitivity label answers one question. What is this data and what can happen to it? You mark an email thread as customer confidential. Agents can read it for specific business purposes. Agents cannot export it. Agents cannot use it for model training. Agents cannot share it with external systems. The label travels with the data. If the email is forwarded, the label stays. If the content is quoted in a report, the label applies to the report. But here is the subtle distinction that matters. It is the difference between the agent can read this and the agent should read this. Permissions determine what an agent can technically access. A sourcing agent has red access to candidate files. That is permission. But should a sourcing agent read the detailed performance reviews of candidates? Technically, the performance reviews might not be restricted. The agent has red access to the HR system. But organizationally, a sourcing agent should not read that data. It is not relevant to their job. Reading it creates exposure. Sensitivity labels enforce that should. They are not permission boundaries. They are organizational policy. A label says this data is performance data. An agent should not process it without executive approval. When a sourcing agent queries the system, performance data gets filtered out. Not because the agent lacks permission. Because the label prevents inappropriate use. This matters because compliance lives in the should layer. Not the can layer. An ordered asking why an agent accessed sensitive data does not accept it had permission as an answer. Regulators want to know why. Sensitivity labels force that conversation up front. They prevent inappropriate access before it happens. Retention and deletion becomes an agent problem because agents build context. They read documents. They build memory from that reading. That lead ranks lower because they are in education which has different buying patterns. The ranking helps the rep prioritize instead of working leads randomly. They work the most likely to close first. Prioritization and outreach follow. The agent does not just rank leads. It times the outreach. Is this the right moment to reach out? Did something change in the prospect's world that creates urgency? Did a competitor win a deal? Did they announce funding? The agent finds the trigger events. It sequences the outreach. First an email with relevant insight. Then a follow-up with the use case study. Then a calendar invite to a demo. The sequence is proven. The timing is optimized. The rep does not have to guess. Opportunity management is the next layer. A prospect becomes a deal. And now the agent tracks that deal through the sales process. What stage is it in? How long has it been there? What is the probability of close? The agent does not just report status. It recommends next best actions. The deal is stuck in evaluation. So the next step is to schedule a technical validation. The agent sees when the customer is available and it knows which internal expert to involve. It surfaces recommendations that move deals forward. Proposal generation happens in parallel. Once evaluation is underway, a proposal agent drafts the document. It is not a templated form letter. It incorporates everything learned about the customer. They're specific challenges. They're stated priorities. They're team structure. The proposal reads like it was written specifically for them because it was... The agent incorporated research and context at every step. The rep reviews maybe tweaks a few sentences and sends it. Deal tracking happens throughout. The agent monitors signals that the deal is progressing or stalling. Meeting scheduled, deal momentum increases, decision pushed, momentum decreases. Key stakeholder leaves the company, red flag. The agent alerts the rep to changes immediately. Customer success operates on similar principles. An agent monitors adoption. Is the customer using the product they bought? Are they using it the way they should? An agent detects churn signals. Usage dropping, feature adoption stalling, support tickets increasing. These are early warning signs. The agent alerts the success team before the customer leaves. Renewal management uses the same multi-agent pattern. An agent tracks contract renewal dates. It monitors customer health. It identifies expansion opportunities. A customer bought three licenses, but usage data shows they need five. The agent recommends expansion. It prepares the business case. It schedules the renewal conversation at the optimal time. Service now built exactly this system. Multiple agents coordinating across CRM, communication history and product usage data. The metrics they track are directly tied to revenue, pipeline velocity, deal size, customer retention. This pattern is expanding because every function is discovering the same truth. Complex workflows benefit from coordinated specialist agents. Measuring agent success, the scorecard. Here is what separates organizations that scale agents from organizations that get stuck. They measure the wrong things. The instinct is to measure accuracy. Did the agent get the right answer? For a system that generates text, accuracy feels like the natural metric. But agents do not generate text. They accomplish tasks. They are not writing essays. They are qualifying leads, scheduling meetings, resolving support tickets and managing hiring workflows. The right metric for those tasks is not how correct the output was, but whether the task completed successfully. Accuracy is almost irrelevant. A sourcing agent could perfectly describe why a candidate matches your job requirements. Perfect accuracy. But if the candidate turns out to be a bad fit for your team, the agent failed. You need a different metric. Did the qualified candidate actually succeed in the role? That is success. That is what matters to the business. This is why the multi-level scorecard exists. You need measurements at three levels. And they are not interchangeable. Agent-level metrics tell you if an individual agent is doing its job. A sourcing agent's task success rate is the percentage of candidates who make it to the interview stage. A scheduling agent's task success rate is the percentage of meetings that actually happen without rescheduling. These are narrow metrics. They measure one agent's specific function. But they are the first place to look when something breaks. Workflow-level metrics tell you if the coordinated system is working. The hiring workflows metrics are different from individual agent metrics. Time to hire matters. How long from requisition to offer? Offer acceptance rate matters. Of candidates who receive offers. What percentage accept? Quality metrics matter? Of hired candidates? What percentage are still in the role after one year? These are the metrics that tell you if the multi-agent orchestration is actually improving hiring outcomes. Business-level KPIs tell you if the agents are moving the needle on what actually matters. Revenue impact. Cost savings. Customer satisfaction. Market speed. These are the metrics that executives care about. If you deploy agents and your hiring metrics look great but you are not improving time to market or product quality, then the agents are cosmetic. Business metrics are what justify continued investment. The practical scorecard for a hiring workflow looks like this. Agent-level. Sourcing agents candidate quality score. Screening agents accuracy. Scheduling agents on time performance. Workflow-level. Time to hire. Offer acceptance rate. New hire retention. Business-level. Organizational hiring velocity. Product launch speed. Revenue growth. When you are evaluating whether agents are working, you read them altogether. If agent-level metrics look good but workflow metrics are stagnant. The problem is orchestration. The agents work individually but do not coordinate. If workflow metrics look good but business metrics do not move. The problem is scope. You are automating the wrong process. It is not slowing down anything that matters. You need to measure both efficiency and safety. This is where organizations make a critical mistake. They optimize purely for speed. Agents that complete tasks fast. Agents that escalate rarely. Agents that move workflows forward. But if those fast agents are hallucinating, violating policy or taking shortcuts that create downstream problems, then you have not optimized anything. You have just shifted the cost somewhere else. A sourcing agent that qualifies quickly but misses red flags creates bad hires. That is not saving time. That is creating cost later. The metrics that matter. Task success rate. Did the agent complete the task correctly? Containment rate. What percentage of issues resolved without escalation? Cost per interaction. How much did this workflow cost to complete? Hallucination rate. How often did the agent make up information? Policy adherence rate? Did the agent follow rules? Escalation frequency. How often did it hand off to humans? Real example. An organization tracking all these metrics found that their support agents had high containment. They resolved issues without escalation. But their hallucination rate was 12%. They were confidently giving wrong answers. They were escalating the right issues but they were confidently misresolving others. Once they saw that metric, they understood the problem. They were not measuring whether the issue was actually solved. They were measuring whether the agent answered instead of escalating. Once they fixed the measurement, they fixed the real problem. The metrics themselves become the governor. They force you to measure what actually matters. Metrics tell you if something is working but they also tell you what to fix. The governance crisis. Why 74% of deployments lack mature controls. The numbers tell a story that should terrify any architect responsible for enterprise infrastructure. 74% of organizations are running AI agents in production. But only 21% have governance that actually works. That gap is not a coincidence. It's the inevitable result of moving faster than your organizational structures can handle. Because in reality, most companies are building without breaks. You build an agent. It works. It solves a problem. You deploy it and then other teams see it working and want agents to. You build more and you deploy more but nobody is stopping to ask if the infrastructure is actually ready. Nobody is checking if the policies you wrote last month still apply to the agents you're shipping this month. The adoption governance gap is the defining challenge of 2026. Agents are everywhere. Governance is nowhere. And in that gap, problems multiply. The no-users can access agent policy floor is a perfect case study of what happens when governance lags behind. An organization tried to be cautious and set a policy where no regular users could access agents. They wanted only approved people in approved roles to have access so the policy was written and the setting was configured. But the setting didn't actually block the agents. There was a gap between what the policy intended and what the system actually enforced. Some agents still showed up in user catalogs and others could still be invoked by people who shouldn't have seen them. The control failed because nobody validated that the policy did what it was supposed to do. That's where things change. And usually for the worse. When the policy didn't work, someone started doing manual power shell overrides in the middle of the night. They manually disabled agents one by one with scripts that weren't documented or explained to the rest of the team. That approach doesn't scale. It isn't auditable and it definitely isn't repeatable. But in the absence of real governance, it's what organizations fall back on. Then you have the shadow AI problem. This is the dark side of the governance gap where agents are running in your infrastructure that your team doesn't even know about. A developer builds an agent locally, containerizes it and runs it in a zooer without telling a soul. It's pulling from SharePoint, querying your databases, and sending emails while nobody has classified its risk or set up monitoring. It stays invisible until something goes wrong and then there is the permission explosion. This happens because there's no systematic way to enforce least privilege when you're moving this fast. You give an agent access to the systems it needs today, but you also give it access to things it might need next year. You give it broader access than necessary because being too restrictive slows down the deployment schedule. Over time, agents accumulate permissions like digital debt. Each new agent starts with broad access because nobody has time to calculate exactly what's necessary. The system becomes progressively over-pimissioned. The audit blind spot is where governance completely breaks down. An agent executes an action and something goes wrong so someone asks what the agent actually did. The logs might show a file was accessed or a record was modified but the logs don't show why. They don't show what data the agent evaluated or what reasoning led to that specific decision. They don't show which human approved it or if approval was even required. The organization has activity logs, but they don't have intelligence. This matters because 97% of AI breaches stem from insufficient access controls. It's not about sophisticated attacks or compromised models. It's about agents that had access they shouldn't have had. It's about agents taking actions without oversight and leaking data because the boundaries were never defined. The governance crisis is what enables the security crisis. The path forward is straightforward and principled but difficult in execution. You have to move from ad hoc controls to programmatic governance. Stop relying on manual processes and stop assuming policies work when you haven't actually tested them. Stop letting agents run invisibly. You need to build the infrastructure that allows governance at scale. That's what agent 365 and the governance framework are designed to provide but they only work if you actually use them. Building the governance program. Practical steps. The transition from crisis to control happens in phases. You can't fix everything at once. If you try to lock down every agent in every process overnight, you'll just paralyze the organization. You'll make agents look like they slow things down instead of speeding them up. The winning approach is methodical but fast. Step one is inventory. You need to know what agents actually exist in your environment. Use agent 365 to scan your infrastructure and run discovery across Entra, Defender and Intune. Document everything from the agents you built on purpose to the shadow agents running in dark corners. Create a spreadsheet with the agent name, the owner, the purpose, and exactly what data it touches. This inventory is your starting point. You can't govern what you can't see. Step two is classification. Not all agents are equally risky. So you have to treat them differently. A productivity agent that just reads and summarizes documents is low risk. A payment agent that moves actual money is high risk. A hiring agent that evaluates candidates sits somewhere in the middle. Classify every agent on your list as low, medium or high. This classification determines how strictly you govern it and whether it needs human approval loops. A low risk agent can move through the system faster but a high risk agent needs a full review. Step three is ownership. Go through that inventory and assign an actual person to every single agent. Not a team or a department, but a named individual who is accountable. That person is responsible for making sure the agent operates correctly and responding if there's a security issue. Ownership forces accountability. And it forces a hard truth. If nobody is willing to own an agent, it probably shouldn't exist. Step four is approval workflows. You need to define the path from development to production for a low risk agent, maybe the business owner signs off and engineering validates it. For a high risk agent, you need business, security, compliance, and operations all to sign off. Define the criteria and decide who has veto power. The workflow is the guardrail that prevents bad agents from reaching production. Step five is identity and access controls. Every agent gets a dedicated, intro workload identity. No sharing human accounts and no standing API keys. The agent's identity should have specific roles and only the permissions it needs to function. Configure conditional access and extend the same policies that protect human accounts to your agents. If an agent's behavior becomes strange, the system should flag it the same way it would for a human. Step six is audit logging and monitoring. Turn on Pervue Audit and capture every tool call and every data access. But don't just collect logs, make them intelligent. Build dashboards that show anomalies and flag patterns that look suspicious. An agent accessing files from three different departments in one hour is unusual. An agent exporting large volumes of data is a red flag. The logs are only useful if you can actually reason over them. Step seven is escalation. Define what happens when something goes wrong. When an agent violates a policy or its behavior changes unexpectedly who gets the notification? Who has the power to shut the agent down immediately? Escalation procedures prevent small problems from becoming full-blown security incidents. Faced rollout matters because you need to prove the model works before you scale it. Start with low-risk agents where the blast radius is small and failure is easy to recover from. Run them through your governance process and see if your oversight structure actually catches real problems. Only after you've proven the model on low-risk deployments should you expand to high-risk ones. KPMG governs 276,000 agents using exactly this framework. They didn't deploy governance as an afterthought. They built the framework first, proved it worked, and then expanded systematically. That's how you operate at scale without the chaos. The future.
