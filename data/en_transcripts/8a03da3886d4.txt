The next question is which kind of identity to give it, because there are two and they're not interchangeable. System assigned and user assigned. Azure gives you two kinds of managed identity, and the names tell you most of what you need to know. A system assigned identity is created as part of the resource itself. You turn it on for a virtual machine or an app, and the identity is born with it and dies with it. Delete the resource and Azure deletes the identity for you automatically. The catch is that only that one resource can use it, and its name always matches the resource name. A user assigned identity works differently. You create it on its own as a standalone thing in Azure, and then you attach it to one or more resources. It has its own life, so it doesn't disappear when a resource does, and you delete it yourself when you're finished with it. That leaves the question of which one to pick. And Microsoft has a clear recommendation, which is that user assigned identities are more efficient in more situations, and they're the recommended type for Microsoft services. The reason comes down to how much bookkeeping you create. Picture four virtual machines that all need to reach two storage accounts. If each machine has its own system assigned identity, you end up making eight role assignments, one for each machine on each account. If all four share a single user assigned identity, you make two. You get the same access for a quarter of the work, with far less to keep track of when people leave and machines get rebuilt. There are situations where user assigned is the obvious pick. If you spin resources up and down quickly, like short lived test environments, system assigned identities can pile up and hit rate limits and Azure starts rejecting requests. A shared user assigned identity avoids that. The same goes for identical resources that need the same permissions. And for cases where you need the identity to exist before the resource does so, you can grant access upfront. System assigned wins in two spots. If your logs need to show which specific resource did something. System assigned gives you that because every resource carries its own identity. And if you want permissions to vanish the moment the resource is deleted, system assigned handles that for you. You don't have to choose forever either. A single resource can carry both a system assigned identity and one or more user assigned identities at the same time, which is handy when you want a shared identity for the common jobs and a private one for the sensitive ones. So the practical rule is to start with a user assigned identity. Unless you have a specific reason to want the identity to live and die with a single resource. The pitfalls to watch for. Nothing comes free of trade offs, and managed identities have a few sharp edges worth knowing before you lean on them. The first is that the security boundary is the resource itself. In Microsoft's words, any code running on a virtual machine can request tokens for any managed identity on that machine. So if someone can run their own code on your resource, they can act as the identity with all of its permissions. That isn't a flaw. Exactly. It's the design, but it means the identity is only as safe as the resource it lives on. That leads straight to the second trap, which is the escalation path. If you let someone run code on a resource that has a managed identity, you've effectively handed them everything that identity can reach. Microsoft gives a clear example a managed identity with read and write. Access to a storage account is attached to a logic app, and now anyone who can run code in that logic app can read and write that storage account, even if they never had direct access to it. Be careful who can run code where. The third thing is that permission changes take time, and this is the one that sends people hunting for a bug that isn't there. Azure caches tokens for around twenty four hours. So if you change a role assignment, it can take hours for the change to actually take effect. You can't force a refresh, which means a fix you just made might not show up until later. And that's confusing if you don't know it's coming. Fourth, managed identities don't cross tenants. They don't work across different directories, so you can't use one to reach a resource in someone else's tenant. And if you move a subscription into a new directory, the identities don't come with it. You have to recreate them and grant access again. Finally, watch the cleanup. Deleting a managed identity doesn't delete its role assignments, so you'll see leftover entries that say the identity wasn't found and those should be removed by hand. Deleting an identity doesn't instantly kill the tokens it already handed out, either because those stay valid until they expire. That window is usually about an hour, but keep it in mind. There are a couple of smaller gotchas as well. Managed identities aren't available for apps deployed in Azure Arc, and the Azure Cloud Services Classic platform doesn't support them at all. None of this should scare you off, because these are the details you learn once and then build into how you deploy. And they're far cheaper than a leaked key. A quick recap and one question.
