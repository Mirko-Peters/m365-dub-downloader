Sounds elegant, right? But like any clever system, there are catches you need to know about. First up, token expiration. If you're syncing directory objects, users, groups, devices, your Delta token is only valid for seven days. That's it. If your app doesn't sync at least once every seven days, that token expires. And when it expires, you can't just pick up where you left off. You have to start over with a full sync. This is a bigger deal than it sounds. Imagine you build an app that syncs user profiles. It runs fine for months. Then someone takes a two week vacation. When they come back, the app's token is dead. It has to download everything from scratch. That's a lot of data and a lot of time. Second, there's the dreaded 410 gone error. Even if your token hasn't expired naturally, Microsoft graph can invalidate it. This happens during internal maintenance, tenant migrations, or other behind the scenes changes you can't control. When it does, graph returns an HTTP 410 status. That's Microsoft's way of saying, I don't remember that token. Start over. And again, you need a full re-sync. Third, processing delays. Here's something that surprises a lot of people. When someone updates a user in Microsoft Enter ID, that change doesn't show up in Delta queries instantly. There's a lag. Sometimes seconds, sometimes minutes. The change has to propagate through Microsoft's internal systems before it appears in the Delta feed. So if you're building an app that needs real-time updates, Delta query alone won't cut it. You'll think nothing changed when, in fact, something just hasn't shown up yet. Fourth, untract properties. Not every property on a resource is tracked by Delta query. Take the skills property on a user object. That data lives in SharePoint, not in the main directory store. So if someone updates a user's skills, that change doesn't trigger a Delta response. Your app never sees it. You'd have to do a full read of that property to catch the update. This catches developers off guard all the time. Fifth, replace. Microsoft Graph makes a best-effort attempt to avoid duplicates, but it doesn't guarantee it. The same change might appear in two consecutive Delta responses. That means your app has to be idempotent. It has to handle the same update twice without breaking. If you're inserting records into a database, you need to check if the record already exists before adding it. If you're updating a field, you need to make sure applying the same update twice doesn't corrupt your data. And sixth, query parameter restrictions. And you can't use all the query features you're used to. You need to plan for these edge cases. Delta query versus change notifications. So if Delta query has these gaps, token expiry processing delays, untracked properties, why not just use push notifications instead? Let's compare how they work. Change notifications are push-based. Microsoft calls your endpoint when something changes. We're talking seconds, not minutes, near real time. If someone updates a user in Enter ID, your app knows about it almost instantly. No polling required. Delta query on the other hand is pull-based. You ask for changes on your schedule. Maybe every hour, maybe every six hours, maybe once a day. The latency is measured in minutes or hours, not seconds. You decide when to check and you get whatever change since your last check. So what are the pros of push? Low latency is the big one. If you're building an app that needs to react quickly, say sending an urgent email alert when a critical document is modified, change notifications are your friend. You get notified the moment it happens. But push has downsides. First, you need a publicly accessible HTTPS endpoint. That means your app has to be reachable from the internet for apps running inside a corporate network. That's a security concern. You need to open ports, manage certificates, and handle incoming traffic. Second, you have to handle validation. When you create a subscription, Microsoft Graph sends a validation token to your endpoint. Your endpoint has to return that token in plain text within 10 seconds. If it doesn't, the subscription fails. Third, subscriptions expire. You have to renew them before they expire or you stop receiving notifications. And fourth, retreats. If your endpoint doesn't respond within three seconds, Microsoft Graph retreats with exponential back off for up to four hours. If your endpoint is slow, notifications can get dropped entirely. Now for the pull side, the pros of Delta query are simpler infrastructure. No public endpoint needed, no inbound traffic to manage. You just make outbound requests from your app. That's it. You also have more control over when things happen. You can schedule them for off-peak hours. You can batch them. You can process changes at your own pace. But pull has cons too. Higher latency obviously. You only know about changes when you ask. If you pull every hour, you could be up to an hour behind. Token expiry is another risk. If you don't sync often enough, your token dies and you have to start over. And there's the wasted effort of pulling even when nothing changed. You make the request, get back an empty response and have to do it again next cycle. So which one should you choose? It depends. If you need low latency, say for urgent email alerts or real-time collaboration, use change notifications. If you're doing bulk sync, maintaining a local database or building an app that works offline, use Delta query. Each has its place. The hybrid approach. Best of both worlds. Actually, you don't have to choose one or the other. The smartest approach is to use both together. Here's the pattern. You set up change notifications to tell you when something changed. That gives you near real-time awareness. You know something happened. But you don't necessarily know exactly what changed. Or you don't want to process the full payload in every notification. So instead, you use that notification as a trigger. When you get a push notification saying something changed, you then call Delta query to fetch exactly what changed. Think about what this gives you. You only pull data when there's actual change. No wasted polling. You get the reliability of Delta tokens. You can track changes over time, handle pagination, and recover from failures. And you avoid the complexity of handling full-change payloads in every notification.
