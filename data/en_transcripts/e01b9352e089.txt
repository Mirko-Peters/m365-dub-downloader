Once a listener catches a request, a routing rule decides what happens next. That rule ties the listener to the back end pool that should receive the request. The back end pool is the group of servers that actually run your application. It's the destination. Once a request reaches the pool, the gateway spreads it across the healthy servers. It uses a round robin approach, which simply means it works through the list in order instead of hammering one machine. The part that earns its keep is the health probe. The gateway checks the health of every server in the pool on its own without being asked. It quietly stops sending traffic to any server it believes is unhealthy. The probe doesn't give up either. It keeps checking the sick server and starts routing to it again the moment it responds properly. Every instance of the gateway runs those checks separately, so a pool gets watched from several places at once rather than by one lonely process. The default check is simple it sends a normal web request to the server on the port. Your back end settings specify, and it treats a clean answer as a sign of life. The default probe has settings worth knowing because they explain how quickly all of this happens. It checks each server, every 30s, and waits up to 30s for a reply. It marks a server as down after three failures in a row. Anything that replies with a status code between two hundred and three hundred and ninety nine counts as healthy, which in plain terms means the server answered normally rather than throwing an error.
