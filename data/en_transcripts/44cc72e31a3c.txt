That's not a database problem. It's not a queue problem. It's a streaming problem. So what's the solution? That's where Azure EventHubs comes in. What is Azure EventHubs? Here's the simplest definition. Azure EventHubs is a fully managed real-time data streaming platform, purpose-built to ingest millions of events per second with low latency. Notice I didn't say message queue or database. EventHubs is not a queue, and it's not a database. It's a stream and the difference matters. The queue holds a message until one consumer picks it up and then it's gone. A database stores data so you can query it later. But a stream is different. It's a continuous flow of events that multiple readers can read independently at their own pace without removing anything from the stream. Now let's clear up a few myths. EventHubs can handle millions of events per second. We're talking about ingesting hundreds of thousands of messages every single second from thousands of producers. And it does this with very low latency. Milliseconds from the moment an event is sent to the moment a consumer can read it. Here's something that surprises a lot of people. EventHubs is Kafka compatible. So if you've worked with Apache Kafka before, you can use your existing Kafka tools and clients to talk to EventHubs without learning a new protocol or rewriting your applications. It speaks the same language. The simplest way to think about this is EventHubs as a high speed data front door. Imagine a busy office building during rush hour. Hundreds of people walk through the front door every minute and the door doesn't stop them ask questions or root them to specific rooms. It just lets them in fast. That's EventHubs. It's the front door for your data. It doesn't process it, analyze it, or decide what to do with it. It just gets it inside your Azure environment as fast as possible. So your downstream systems can do the real work. But how does it actually work? Let's break down the pieces. The building blocks, partitions, consumer groups, throughput. So inside every EventHubs, there's a structure that makes the whole thing work. The most important piece is the partition. Think of a partition like a lane on a highway. Data comes in and lands in one of these lanes. Here's the key. Within each lane, the order of events stays exactly as they arrived. Event1 comes before Event2 and Event2 before Event3. That order never changes inside that lane. So if your application needs events in the exact order, you keep them in the same partition. You can have between 2 and 32 partitions per EventHubs. And you set this number when you create the hub. You can't change it later. So you need to think about your throughput needs upfront. More partitions mean more parallel processing. If you expect a high volume of events, you want more partitions. So multiple consumers can read from different lanes at the same time. But more partitions also mean more complexity. The rule of thumb is to choose based on your expected throughput, not randomly. If you're not sure, start smaller and test. Now, partitions alone aren't enough. You also need consumer groups. A consumer group is simply a separate downstream application that reads the same stream. Each consumer group gets its own independent copy. So if you have one group for real-time analytics and another for archiving to storage, they both read the same events at the same time without interfering. The analytics group reads temperature data to detect anomalies. The archiving group reads the same data and sends it to a data lake for long term storage. Both groups see every event, neither group blocks the other, and this is a big deal. In a traditional queue, a message is consumed by one processor and then it's gone. Here, multiple consumers can read the same stream independently. That's the power of consumer groups. But how do you measure how much data your event can handle? That's where throughput units come in. A throughput unit or TU is how we measure capacity. One TU gives you one megabyte per second of incoming data and two megabytes per second of outgoing data. So if you need to ingest 10 megabytes per second, you need at least 10 TUs. You can scale up manually or you can enable auto-inflate, which automatically increases your TUs when traffic spikes. You pay for the maximum number of TUs used in an hour. So if you spike to 20 TUs for 10 minutes, you're built for 20 TUs for that entire hour. One more piece, retention. Events don't disappear from the hub after they're consumed. They stay in the hub for a configurable period. In the standard tier, that's one to seven days. In the premium tier up to 90 days, this enables something called replaying. If your downstream consumer fails or if you need to reprocess data for a new analysis, you can go back and read all the events again. That's different from a queue where once a message is consumed, it's gone forever. So now you know the parts. But how do they actually work together in a real system? How it works? The producer and consumer model. Let's walk through the flow from start to finish. On one side, you have producers. A producer is any application or device that sends events to the hub. It could be a temperature sensor in a factory, a web server, logging page views, or a banking app sending transaction data. Producers can talk to event hubs using three different protocols, AMQP, HTTPS, or Kafka. So whatever language or platform you're using, there's a way to connect. When a producer sends an event, the hub decides which partition it goes into. By default, events are distributed in round-robin fashion. First event goes to partition one, second to partition two, and so on. But you can also use a partition key. If you want all events from the same device to land in the same partition, you set the device ID as the partition key. That way, the order of events from that device is preserved. The hub itself doesn't do much processing. It buffers the events and stores them in the partitions for the retention period. Think of it as a holding area. The events sit there waiting for someone to read them. On the other side, you have consumers. Consumers are downstream applications that read from the hub. And here's the important part. Consumers use a pull model. They control their own pace. They don't get pushed events. Instead, they ask for events when they're ready. This is different from a queue where the system pushes messages to a consumer. Here, the consumer decides when to pull the next batch. Each consumer group tracks its own position in the stream. This position is called an offset. The offset tells the consumer which events it has already processed. And the consumer stores this offset somewhere durable, typically in Azure Blob Storage. This process is called check pointing. Here's why check pointing matters. Imagine your consumer application crashes halfway through processing a batch of events. When it restarts, it reads the last checkpoint from Blob Storage and resumes from that exact point. It doesn't reprocess all the events and it doesn't skip any events. It picks up right where it left off. And that's reliability without complexity. The key insight is that event hubs completely decouples producers from consumers. Producers don't know who's reading their data. Consumers don't know who's sending the data. They're independent. The hub sits in the middle, buffering and distributing events. And each side operates at its own pace. And that decoupling is what makes event hubs so powerful for building scalable, resilient systems. Let's make this concrete with real world scenarios. Now, event hubs isn't the only messaging service in Azure. Let's compare it with the others. Event hubs versus event grid versus service bus. Azure has three main services for moving data around. Event grid, event hubs, and service bus. People mix them up all the time, so let's clear up the confusion. Event grid is the smoke alarm. It's lightweight and reactive when something happens. A blob gets uploaded to storage. A virtual machine changes state. A resource gets created. Event grid fires an event. It doesn't carry the data itself. It just says, hey, something happened, and then roots that notification to handlers like Azure Functions or Logic Apps. Event grid is not a stream and it's not designed for high throughput. It's for discrete events that need a quick reaction. Best for blob upload triggers, resource state changes, and serverless workflows. Service bus is the postal service. It's reliable, ordered, and guarantees delivery. When you send a message through Service bus, you know it will arrive. It supports first and first out ordering duplicate detection and transactions. If a message fails to process, it goes to a dead letter queue where you can inspect it later. Service bus is built for business critical workflows like payment processing, order fulfillment, and approval chains. It handles thousands of messages per second, not millions. And that's fine because when you're processing a payment, you don't need millions of events per second. You need every single message to arrive exactly once in the right order. Event hubs is the security camera. It records everything for playback and analysis. It's built for high volume streaming, millions of events per second, and multiple consumers can read the same stream independently. Events stay in the hub for days or weeks so you can replay them if needed. Event hubs is not for transactional messaging. It's for telemetry, analytics pipelines, and any scenario where you need to ingest massive amounts of data and distribute it to multiple consumers. So how do you decide, ask yourself three questions? Are you reacting to a change? A blob was uploaded, a VM was created, a resource changed state. That's event grid. Do you need guaranteed delivery and strict ordering? Processing payments, running workflows, coordinating business transactions, that's Service bus. Are you streaming massive amounts of data for analytics, IoT telemetry, application logs, click streams, fraud detection? That's event hubs. Here's the thing. You don't have to pick just one. These services work together. Event hubs ingest the raw data stream. Event grid reacts to events within that stream and triggers downstream actions. Service bus handles the reliable messaging for business workflows. Use them together and you get the best of all worlds. Let's talk about the cost of running this kind of pipeline. Pricing and tears. Let's talk about cost because knowing what event hubs does is one thing, but knowing what a cost is another thing entirely. Event hubs has four tiers and basic is the cheapest. It gives you one day of retention, limited features, and the lowest cost per throughput unit. That works for simple scenarios where you don't need much, but most people skip basic and start with standard. Standard is the sweet spot. It offers up to seven days of retention, event hubs capture for automatic archiving to storage, Kafka compatibility, and up to 20 consumer groups. That covers most production workloads, so if you're building something real, this is usually where you begin. Premium is a step up. You get 90 days of retention, one terabyte of storage per processing unit, predictable performance, and vnet support for network isolation. Reserved resources mean noisy neighbors won't affect you, and this tier is built for high-end workloads where latency and isolation matter. Dedicated is the top tier. A single tenant cluster just for you with 10 terabytes per capacity unit. It's for very large workloads where you need the whole environment to yourself. Yes, it's expensive, but if you're processing massive volumes steadily, it can be more cost-effective than scaling premium. So what drives the cost? Four things. Throughput units, which is how much data you're moving, retention duration, how long you keep events, capture whether you're archiving to storage, and georeplication if you're copying data across regions for disaster recovery. Here are a few cost optimization tips. Start with standard, and scale up only when you need to. Use short retention for hot data. Keep it in the hub for a day or two, then offload it to cheaper storage like blob or data lake for long-term analysis. Monitor your throughput usage and write size, your TUs, and don't over-provision. Also use HTTP for senders instead of AMQP where possible, because AMQP connections have charges and HTTP does not.
