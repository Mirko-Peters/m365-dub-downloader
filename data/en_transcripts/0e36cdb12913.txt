The solution isn't to give up on Rags. It's to distribute responsibility. You need to add checkpoints and create agents with specific roles, specific permissions and specific constraints. That's the multi-agent model. The five-agent retrieval model. The alternative is to think about the retrieval problem as a sequence of distinct responsibilities. Each one is owned by an agent with a specific mandate and specific constraints. Not all agents need broad access and not all agents need to see the full permission model. Some agents don't touch data at all because they handle routing while others validate or generate. The idea is that by breaking the monolith into specialized components, you distribute authority in a way that prevents any single actor from making all the decisions. Here's how it works in practice. Agent one is the router. Its job is to understand what the user is actually asking for and determine if the request is legitimate. It doesn't touch documents and it doesn't retrieve anything. It receives the natural language question and evaluates whether it is a reasonable request. It asks if this person is asking for something that makes sense within their role. It checks if the question triggers any red flags like patterns that look like prompt injection or data exfiltration attempts. The router makes a simple decision to either proceed or block if something looks wrong. The request stops here. No retrieval happens. No data is at risk. Agent two is the query translator. Once the router has approved the request, the translator's job is to convert natural language into a structured retrieval query. The user asks the question in English and the translator transforms that into the exact parameters the retrieval system needs. It determines what keywords to search for, what semantic meaning to match, and what metadata filters to apply. But here's the critical part. The translator never decides which documents the user is allowed to see. It only shapes the query. It has no access to permission models and no authorization logic. It's a pure transformation function. Agent three is the retriever with authorization. This is where the security boundary lives. This agent takes the translated query from Agent two and executes it against the vector database. But before it returns anything, it applies the user's permission filter. It constructs the authorization expression we talked about earlier and verifies if this user has access to this document. It acts as a bouncer. Documents that fail the permission check never make it out of this agent. The retriever has a simple rule. If the user can't access it, they don't get to see it. Period. The retriever is narrow in scope, but absolute in its enforcement. Agent four is the validator. The retriever sent back a set of authorized documents, but the validator asks if they are the right documents. It checks if this collection of sources actually makes sense for answering the user's question and if it fits this person's role. It looks for inconsistencies or red flags in the retrieved set. The validator is a quality gate that can refuse to proceed if the retrieved documents don't pass validation. If a financial analyst queries about production logistics and the retriever comes back with internal memos from the finance department, the validator flags that mismatch. It prevents nonsensical or suspicious retrievals from reaching the next step. Agent five is the generator. This agent receives only the documents that have passed authorization and validation. Its job is straightforward. It creates a coherent, well-sourced answer using only the context provided. Here's what's crucial about the generator's position. It never sees the full permission model. It doesn't know which groups could access which documents and it doesn't have the authorization logic. It only sees documents that have already been vetted as appropriate for this user. The generator operates under a fundamental constraint where it can only work with what it was given. It cannot fetch additional context on its own and it cannot bypass the authorization layer. It has no way to know that sensitive documents exist because they were filtered out before it ever saw them. Each agent has a role. Each agent has specific permissions. Each agent has specific responsibility. The router guards the gate. The translator shapes the request. The retriever enforces access. The validator ensures coherence. The generator creates the answer. This separation of duties changes everything. No single agent holds all permissions and no single agent makes all decisions. The permission model itself doesn't live in the LLM. It lives in the retriever, which is a deterministic component outside the model. From user token to agent action, we need to look at how identity actually moves through a multi-agent system because having five specialized agents is only useful if every single one knows exactly who they are serving. When a user logs in through EntraID, the system validates them and issues a digital token. This token carries specific details like the user's unique ID. Their group memberships, their role, and their tenant. Because it is cryptographically signed, nobody can forge or change the data. So the token stands as proof that says this is user A and here is what they are allowed to do. The obvious temptation is to just pass that raw token to every agent in the chain. You might think it makes sense to let each agent use it to prove the user's identity as they talk to one another. But in reality, that is a massive mistake. You should never pass raw user tokens directly to an LLM or share them freely between agents. The problem isn't that your agents are untrustworthy since these are your own systems, but rather that the token itself becomes a massive security liability. If an agent gets compromised or a prompt injection trick forces an agent to reveal what it knows, that raw token becomes the crown jewel for an attacker. It can be replayed in other systems or even sold, acting as a secret key that grants access to places the user never authorized. Instead, you should use OAuth 2.0 token exchange, which acts like a translation layer for identity. The gateway receives the user's original token and confirms that the person is real, but then it does something different. Instead of passing that original credential forward, the gateway creates a new, scoped token. This is a derivative token that tells agent 3 it is authorized to act for user A for exactly 15 minutes and only for the purpose of retrieving documents. Every agent in your chain receives its own limited token. The router gets a token that only allows it to evaluate requests while the translator gets one that lets it shape queries without ever seeing a document. The retriever receives a token that says, "Act for user A with user A's specific access level." And the validator gets read only access to check the results. Finally, the generator gets no special access at all, since its only job is to process the text it receives. This is the core principle of delegation. Agent 3 isn't acting as a powerful service account with broad access, but is instead acting as a deputy with the exact same authority as the user. If user A is allowed to see the sales folder but is blocked from the finance folder, then Agent 3 will be blocked from finance as well. Let's look at a real scenario where user A works in sales and belongs to the North America and product feedback groups. When they ask the system a question, the retriever receives a scoped token that encodes those specific group memberships. The retriever then builds a filter that only shows documents where the ID matches user A or belongs to one of those three specific groups. The retriever happens under that strict constraint, so the user sees their sales and feedback documents but never catches a glimpse of HR or executive files. Handling group memberships is where the technical complexity usually kicks in. You generally have two choices for how to handle this. First, you can resolve groups at the moment over authentication by fetching everything from EntraID and putting it in the token. This is fast, but if a user joins a new group, the token won't show that change until they log out and log back in. The second option is to cache group memberships with a short lifespan, meaning the retriever refreshes the list every few minutes so changes propagate quickly. There is also a technical hurdle called group overage that you need to watch out for. If a user belongs to more than 150 groups, EntraID cannot fit all those IDs into a standard token. Once you hit that ceiling, the system has to choose between dropping group info or making extra API calls. This matters because if the group information is missing, your authorization filter won't know which documents to show the user. This identity model is the foundation of the whole system. This is where the architecture has to make a hard choice about where authority actually lives. When teams start building access controls for Rags, they usually have the same intuitive idea. They know the LLM understands language and context so they try to put the authorization rules right in the system prompt. They tell the model to only show public documents and to never reveal anything tagged as confidential. It sounds like a reasonable plan because the model is smart and follows instructions. But the truth is, it won't work reliably. The reason is simple. LLMs do not enforce rules, they follow instructions. Instructions can be overridden or bypassed through prompt injection and a user can easily craft a prompt that conflicts with your original setup. If a retrieved document contains text that contradicts your rules, the model doesn't have a way to prioritize one over the other. It just looks at all the information and makes a probabilistic guess, which means it will eventually violate your security rules. This isn't a problem with the quality of the model. Even the most advanced models fail at this because you are asking them to do something that should be handled entirely outside of the AI. The real security requires a policy decision point or a PDP, which sits outside the model. This is a deterministic engine that looks at an authorization request and gives a simple yes or no answer. It isn't making a suggestion or a guess, but is instead making a rule-based decision about whether a specific user is allowed to see a specific document right now. The PDP takes in structured data like the user's ID and roles, along with the document's classification and sensitivity level. It also looks at the context such as whether the user is a contractor or if they are logging in from a high-risk location. It evaluates all these factors against your rules and returns a final decision. These rules are very direct like finance employees can see budgets, but contractors cannot. You might have a rule that denies access if a user tries to view a confidential file from a VPN outside of office hours. The PDP doesn't care about your prompt or which LLM you are using because it only cares about the rules and the requests. Crucially, the PDP itself is not an LLM. It is a dedicated rule engine like openFGA or turbos that is designed to be auditable and consistent. You can see exactly which rule was triggered, you can trace every decision and you can update your policies without ever touching your code. In a real workflow, the retriever agent calls the PDP before it ever returns a document. The retriever might find 10 documents that match the user's query, but it asks the PDP for permission before moving forward. If the PDP says no to five of those documents, they are dropped immediately. Only the approved documents make it into the context window for the LLM to see. If you use Azure AI search, this logic is often built directly into the query filter. You aren't pulling a bunch of data and filtering it later, but are instead ensuring the database only scores documents that the user is actually allowed to see. The separation is how you move from probabilistic security to deterministic security. The LLM never has to make a judgment call on access and it never sees data that shouldn't be there. Everything happens in a component designed for rules and auditing. Zero trust isn't a new buzzword in the security world. The military, financial institutions and critical infrastructure providers have used this model for years because their stakes are too high to assume anyone is safe. They operate on the reality that you can't trust a user or a device just because they manage to get onto your internal network. But here's the problem. Most people think a firewall is security but in reality a perimeter is just a shell. The moment you assume a component is safe because it sits behind that shell you've created a massive vulnerability for an attacker to exploit. Zero trust rejects that assumption entirely by requiring you to verify every single interaction, every request and every piece of data moving between systems. There are no shortcuts and there is no implicit trust. Now apply that same diagnostic thinking to your multi agent rag system. Most teams don't do this. They build a specialized architecture we've been talking about with five different agents and then assume those agents are safe because they own the whole stack. Since everything is running on the same infrastructure and part of the same project they skip the hard security work. They pass tokens freely and trust that if an agent has a capability it should be allowed to use it. That's the exact assumption zero trust is designed to break. In a zero trust agent system the rule is absolute. Every agent, every retrieval and every tool call must be authenticated and authorised independently. This doesn't just happen at the front door. It happens at every single hop in the chain. Here is how that looks when the system is actually running. It starts with agent one, the router. When a user sends a request the router doesn't just pass it along. It verifies the session, checks if the token is valid and looks at the user's risk posture. It asks if they are logging in from a weird location or if they've recently changed their password and only after gathering all that evidence does it decide if the request is legitimate. If the verification fails the process stops right there. If it passes agent two receives a scope token. This is a critical distinction because that token doesn't give agent two the keys to the kingdom or the ability to call external APIs. It grants the authority to do exactly one thing. Transform natural language into a structured query. When agent two is done it passes that query and a fresh token to agent three but it never passes its own credentials or raw user data. It only passes a token representing the user's delegated authority for that specific next step. Then agent three takes over the token it receives says it can act for a specific user to retrieve documents that the user is permitted to see and nothing more. It can't modify files or write logs because its scope is strictly bounded by the token's signature. Agent three checks that signature for cryptographic proof of its source, pulls the documents that pass the filters and then hands those documents and a new token to agent four. Next agent four validates the work. It's token only allows read only access to document metadata so it can check if the results actually make sense. It can't retrieve more documents or override previous authorizations and if it rejects the results the flow stops immediately no documents ever reach the model of the validator says no. Finally agent five generates the response. By this point the token it holds only allows it to work with context that has already been pre-validated and pre-authorized. It can't go off script to call APIs or fetch new data because the token is intentionally narrow every single one of these agents logs exactly what happened. They record who called them, what tokens were exchanged and whether a request was approved or blocked. This creates a full audit trail so that if something breaks you can trace the chain and see exactly where the failure happened. To make this work you need specific technology like mutual TLS. This ensures that both the calling agent and the receiving agent verify each other's identity cryptographically before a single byte of data is exchanged. Every message is signed with a private key to prove it hasn't been tampered with and every agent has its own unique identity in the certificate system. This does add a layer of complexity. You have to maintain the certificate infrastructure and validating tokens at every hop adds latency to the system. In fact network overhead from MTLS handshakes could increase your latency by 30% compared to a basic rag setup. That is a real cost you have to weigh. But the security gain is absolute. No agent can pretend to be another and no request can bypass the verification chain. If one agent is compromised the damage is trapped within that agent's narrow scope. The architecture is built to assume a breach will happen and contain it before it spreads. Detecting when something goes wrong. Even the most perfect architecture has to assume that something will eventually fail. Whether it's a compromised agent, a malicious prompt that slips past validation or a simple configuration error, the goal isn't just to prevent failures. The goal is to detect them fast enough to stop the bleeding. Behavioral monitoring is your early warning system. You start by establishing a baseline for what normal looks like in your system. You track how many documents agent three usually pulls, how long a retrieval takes, and how often agent four rejects a result. By looking at historical data, you build a profile of how the agents should behave during a typical day. Then you watch for the moment things deviate. If agent three suddenly pulls a thousand documents instead of the usual five, that's a massive red flag. It could be a broad query, a malfunction, or an attacker trying to scrape your data, but the reason doesn't matter yet. What matters is that the pattern is broken and the system needs to react. The same applies if agent four's rejection rate jumps from 1% to 30%. This tells you that something the retriever is sending back no longer makes sense. Either the retrieval logic is broken, or the documents themselves have become problematic, but either way, the anomaly needs an answer. You also watch for agents calling tools they've never used, or making requests from unknown IP addresses. If an agent's latency spikes from 200 milliseconds to five seconds, that's a behavioral shift worth investigating. Your response framework should have layers. Low-level issues might just trigger an alert for the ops team, but high-savarity anomalies should trigger an automated kill switch. The system can disable the agent, root traffic around it, and save all the evidence for a forensic investigation. Let's look at a real scenario where agent three retrieves a thousand documents. Because this is outside the baseline, the system flags it immediately without waiting for a human to check a dashboard. It logs the details and escalates the issue to a security engineer who can see the user, the query, and exactly which documents were pulled. If it looks like a real threat, the engineer can roll back the results, clear the caches, and notify the right people. The logging requirements for this are absolute. Every retrieval must record the user ID, the agent ID, and the specific document IDs that were returned. You need the timestamp and the authorization decision to see if the user passed or failed the check. If an agent had to try multiple times, every single attempt needs to be in that forensic trail. But here is the catch. Logging itself is a risk. A log file shows exactly which users are looking at which sensitive documents, and if those logs are stolen, they become a map of your organization's most private data. That metadata is just as sensitive as the documents themselves. Because of that, you have to protect your logs as carefully as your primary data. You should use Redaction or Encryption, so the log shows the decision but hides the full document title. You can log a document ID and keep the actual title in a separate encrypted mapping. Logs should be stored in a tamper-evident system where any attempt to delete them triggers an alarm. In a real implementation, you'd use tools like Splunk or DataDog to ingest this telemetry. You define the rules, such as firing an alert if retrieval volume hits a certain threshold or if a user starts querying at odd hours from a new location. The monitoring system correlates these signals to find this suspicious activity. This is where your zero-trust architecture meets the reality of daily operations. Technical controls will stop most failures, but for the ones that slip through, detection and response are your last line of defense.
