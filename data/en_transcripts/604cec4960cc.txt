In deterministic SaaS, the workflow is defined at design time. Someone models a process, writes a flow, builds a form, configures a connector, assigns a role. What post-SAS actually means in enterprise architecture. Post-SAS doesn't mean SAS is dead. It means SAS stopped being the place where work completes. In the SAS era, enterprise architecture leaned on a stable contract, a user interface, an API surface, and predictable state transitions. You could argue about quality, uptime, licensing, or integration pain, but the shape of the system was consistent. A request came in, the platform executed a defined operation, and a record-changed state operators could observe it, architects could bound it, auditors could test it. When something went wrong, you knew where to look. It might take time, but the system gave you a finite set of places to interrogate. Logs, policies, permissions, connectors, runbooks. Post-SAS is what happens when you add a probabilistic overlay that sits above those contracts and starts interpreting intent instead of executing commands. That overlay has four parts that matter architecturally. Prompts, tools, memory, and delegation. Prompts are not user input. They're runtime policy. They shape behavior. They constrain scope, and they change faster than change management can track. Tools are not integrations. They're executable capabilities. Connectors, plugins, graph calls, flows, APIs. Memory isn't just chat history. It's what the system can remember, retrieve, and treat as context across sessions, across users, across time. Delegation is the quiet multiplier. One agent hands work to another agent, which calls another tool, which triggers another workflow. So the system, you thought, was Microsoft 365 plus some automations becomes a distributed orchestration fabric that assembles execution parts on demand. Here's where the contract breaks. In SAS, the boundary lives at the API. If the API call happened, you can trace it. If a permission allowed it, you can justify it. If an audit log recorded it, you can defend it. The system is still deterministic enough that what happened and why it happened are linked. In post-SARS, interpretation replaces execution as the dominant mechanism. The agent doesn't just call create event. It decides whether the user meant schedule, draft, delegate, or summarize, then chooses which tools to invoke in what order, with what parameters, based on context, that is not visible to the user, and often not visible to the operator. The output looks like a single experience. The reality is a tool chain. That distinction matters because architecture is fundamentally about controlling side effects. In deterministic systems, side effects come from explicit calls. In probabilistic systems, side effects come from implicit plans. And you don't control implicit plans with documentation. You control them with contracts and boundaries. The orchestration layer can't casually step over. This is why more automation is the wrong frame. Automation assumes you're codifying a known sequence. You design it, you test it, you deploy it. If it breaks, it breaks in the same place until you fix it. Post-sass systems don't just run sequences. They synthesize them. Two users ask the same thing. And the system takes two different paths because context differs, tool availability differs, permissions differ, or the model selection differs. You get different execution, not because you change configuration, but because the runtime interpreted the intent differently. So Post-sass is a new control surface. The control plane is no longer only policies, roles, and settings inside each SAS workload. It becomes the orchestration layer. What tools exist? Who can use them? They think the agent is the worker. Architecturally, the agent is the planner. The worker is your existing automation layer. APIs, workflows, cues, transactional systems, and the parts of the platform that already know how to do reliable work. The agent should not replace those. It should call them through a controlled interface with narrow capabilities. So the first design move is separation of agent types. Task agents versus decision agents. Task agents operate inside a deterministic envelope. Collect these inputs, fill this template, open this ticket, post the summary, schedule this meeting. Their decisions are bounded and their actions are reversible or at least compensatable. Decision agents are different. They decide what should happen, not just how to do it. They classify urgency. They choose who gets notified. They decide when to escalate. They choose between competing workflows. They are a policy surface. And that means you can't casually mix them. If the same agent both decides and acts, it will eventually act on a decision you can't defend. Not because it's evil, because it's operating on incomplete context, changing context, and shifting tool availability. Over time, it becomes a probabilistic policy engine with production permissions. So agent first architecture forbids a common anti-pattern. One smart agent that does the whole thing. Instead, it forces explicit handoffs. A decision agent can propose an action plan with confidence scores and rationale. A task agent can execute steps only when given a signed, deterministic instruction set. A separate policy boundary can enforce whether the plan is allowed at all. That separation sounds bureaucratic until you've lived through a side-effect incident where nobody can answer the only question that matters. Who authorised this? The second design move is treating human in the loop as a boundary condition, not a checkbox. Human in the loop is not, someone can stop it if they notice. It is an architectural gate where the system must pause, present the decision context, and require an explicit authorization to proceed. That gate should trigger on risk, not on vibes, sensitive data access, external sharing, financial transactions, permission changes, customer facing communications, or any action that can't be undone cheaply. And when a human approves, that approvals becomes part of the execution record. Not a team's message, not a meeting note, a first class artifact tied to the agent identity and the tool call. The third design move is legibility as a non-negotiable requirement. Most leaders treat explainability like a compliance slogan. Agent first architecture treats it as a scaling constraint. If the organization cannot reconstruct the decision path quickly, inputs, selected context, selected tools, prompt a version, identity used, and resulting side effects. Then the organization is not allowed to scale that agent beyond a small blast radius. It is not legibility is not a nice to have. It is the only antidote to MTT, and this is where the post-sass paradox finally gets a counterforce. Entropy grows when decision pathways multiply faster than explanation. So you design for explanation first. You don't ask, can we build this agent? You ask, can we explain this agent under pressure during an incident to security to audit and to the business owner who just got burned? If the answer is no, then it's not an agent. It's a liability with a chat interface. The final design move is to formalize boundaries as contracts. Tool contracts. What is callable with what parameters with what scopes? Data contracts, what sources are allowed, what labels are required, what grounding rules apply. Behavior contracts. What the agent is allowed to decide and what it must escalate. Life cycle contracts. Who owns versions? Who owns deprecation? Who owns the kill switch? This is how agent first architecture turns AI strategy back into architecture. Not by slowing down intelligence, by forcing intelligence to operate inside boundaries that remain deterministic, enforceable, and legible at scale. And once those boundaries exist, then you can talk about the thing, most organizations skip. The control plane that enforces them. The agent control plane. Identity, telemetry, life cycle, and kill switches. At this point, most leaders hear control plane and their brain jumps to an admin portal. That's not what this is. A control plane is not a UI. It's an enforcement layer for assumptions. Identity, authorization, observability, and life cycle. The system either has that layer or it slowly devolves into conditional chaos with nicer branding. In deterministic sass, the control plane lived in the service itself. Exchange online had admin boundaries, SharePoint had admin boundaries. The workload owned its own behavior surface and your job was to configure it. In post-sass behavior sits above workloads. It sits in orchestration. Agent selecting tools, selecting context, delegating tasks, and executing side effects. So the control plane has to move upstack too. And it has to be boring on purpose. The first requirement is agent identity, not the maker who built it. Not the user who clicked it. The agent itself. If an agent can act, it needs a first class principle with a stable identity that survives org charts, team reorganizations, and the inevitable, this started as a pilot. That identity needs ownership metadata who is accountable what business process it supports, what environments it's allowed to run in and what category of authority it holds. Without that, you can't do least privilege. You can only do optimism because least privilege is not a philosophical stance. It's an authorization graph. If you can't point to an agent as an actor, you can't draw the graph. You can't review it. You can't revoke it cleanly. You can't even explain what happened when it does something expensive. The second requirement is tool authorization as a contract, not a convenience. Most organizations let tool reach ability emerge organically. Connectors added, plugins enabled, graph permissions granted, and then everything gets called integration. That's how you build an accidental super user. The control plane needs a capability catalog. These are the tools this agent can call. These are the operations exposed. These are the scopes. These are the data classifications allowed. And these are the conditions under which the call is permitted. If you can't express that in a machine enforceable way, then the agent is not integrated. It's armed. The third requirement is telemetry that answers the questions people actually asked during incidents, not did it run. Who acted on what? Using which identity? With which authority? Based on what retrieved context, through which tool calls? In what sequence? With what fallbacks? And what side effects landed in which systems of record? That's the minimum. Anything less is performative observability. This is also where the industry keeps lying to itself with dashboards. Dashboards are summaries. Incidents are specifics. You need event-grade traces that can be stitched into a narrative at human speed. If the only thing you can produce is a chat transcript, you don't have observability. You have theater. The fourth requirement is lifecycle management because entropy loves abandoned artifacts. Agents are not set and forget. Prompts drift. Tools change. Connectors rotate. Models update. Data sources get cleaned up. People leave. The agent keeps executing anyway because the system does not care about your org structure. So the control plane needs explicit version ownership and decommissioning. Every agent needs a named owner, a versioning scheme, a change log, and a retirement path. And owner can't mean the last person who touched it. It has to mean accountable for behavior and side effects. Otherwise, your agent estate becomes a museum of half-owned automation. And then finally, kill switches. Not as a last resort security fantasy as an architectural primitive. If an agent can execute side effects, you must be able to pause it, revoke its tool access or force it into a safe mode without redeploying half your environment. And you need escalation paths that are defined before the incident, not negotiated during it. Because the incident you're trying to prevent is not an outage. It's an agent doing the wrong thing quickly, repeatedly across multiple systems while everyone argues about whether it was expected behavior. A real control plane makes that argument irrelevant. It enforces intent at runtime. And here's the uncomfortable truth. Once you have identity, tool contracts, telemetry, life cycle, and kill switches, you've built the thing most AI strategies quietly avoid. You've made agents operationally legible, which means you can finally scale them without scaling ambiguity. Now, the next question becomes obvious. If tools brawl is one of the fastest entropy surfaces, what happens when MCP makes tool integration dramatically easier? MCP's integration relief and a new entropy surface if unmanaged. MCP is going to sound like the part of this story where the clouds part and the architecture gets easier. Because mechanically, it does. The integration problem in the agent era is brutal. Every agent wants to call tools. Every tool has an API, every API has an else model, and every team wires it differently. That creates the classic MXN mess. You end up with bespoke connectors, brittle adapters, duplicated wrappers, and a constant tax every time anything changes. MCP's promise is to collapse that mess into something more linear. One side speaks agent, the other side speaks tool. The protocol becomes the contract discovery, schemers, and a standard way to call capabilities. So instead of building 10 different custom integrations for 10 different co-pilots, you build or adopt an MCP server once and any MCP capable agent can use it. That's real relief. It reduces the integration surface area you have to handcraft. It reduces the number of places where tool calling gets implemented poorly. And it makes tool reuse realistic, which is the difference between an agent program and a thousand snowflakes. But here's what most people miss. MCP doesn't remove complexity. It relocates it into the one place enterprises are already failing to control capabilities, brawl. MCP turns tool exposure into something that can scale as fast as copying a config file. That's the upside. It's also the failure mode, because once integration becomes easy, the default organizational behavior becomes expose one more tool at one more server, publish one more capability, let one more agent use it. We can always tighten it later when you want. That distinction matters. In architectural terms, MCP is not an integration convenience. It is a tool distribution system and every distribution system becomes an entropy accelerator unless you force contracts around what gets distributed, who can publish it, and what safe to consume actually means. So MCP introduces a new entropy surface, standardized tool sprawl. Before MCP tool sprawl was slowed by friction. Every integration required effort, which acted like a crude control. With MCP, the friction drops, so the sprawl becomes limited only by imagination and urgency. That's not a moral critique. It's system behavior. The first risk is server registration becoming an accidental marketplace. Teams stand up MCP servers for their own needs, a Giro server, a service now server, a CRM server, an internal data server. Each one exposes a slightly different schema, different naming, different guardrails, and different assumptions about authentication. Then agents discover them, and now the enterprise has created an internal app store for capabilities. Without the review rigor that app stores evolve to require. The second risk is capability catalogs drifting away from least privileged tools are never neutral. A tool is authority packaged as an API. If a tool can create a ticket, send an email, update a record, or change access, then exposing that tool through MCP isn't integration. It's delegation. So the question isn't, can the agent call the tool? It's under what identity? With what scopes? With what constraints? And with what audit narrative? If MCP makes it easy to call tools, it also makes it easy to call the wrong tools with the wrong authority, especially when teams treat servers as shared utilities instead of controlled boundaries. The third risk is change management collapsing into surprise. MCP supports dynamic discovery. That's the feature. agents can learn what tools exist without hard coding. But dynamic discovery, without change control, is how you turn production behavior into a moving target. A server adds a new capability. A schema changes, a parameter meaning shifts, and all the requirement changes. The agent doesn't break in a neat way. It adapts, it selects different actions. It fails over. It produces different side effects. And your MTT spikes because the execution path changed without a deployment event you can point to. That's the paradox. Again, interoperability increases the need for contracts, not less. So if an organization adopts MCP as integration relief, but doesn't treat MCP servers as first class production surfaces, versioned, owned, restricted, observable, then MCP becomes the fastest way to industrialize conditional chaos. This is why the agent control plane matters even more once MCP shows up. You need enforced server registration rules. What qualifies as publishable, who approves, and what metadata must exist? You need capability classification. Read only tools versus side effect tools versus privilege tools. You need identity boundaries, which agents can call which servers, and whether those calls are on behalf of a user or under a service principle. And you need change discipline. Versioning, deprecation, and explicit compatibility promises because otherwise every small improvement is a behavioral drift event. MCP can absolutely reduce integration dead, but it will also let you scale bad integration faster than you ever could before. The protocol isn't your safety net. It's your multiplier. And once you accept that, the next move is obvious. Don't scale agents first. Scale legibility first. Which is why the only sane way forward is a controlled pilot that proves you can explain behavior before you amplify it. The 90-day agent first pilot, prove legibility before scale. The worst way to respond to all of this is to announce an agent program and then let every team build whatever they want faster because the board is excited that just turns entropy into a KPI. The only sane move is a 90-day pilot that proves one thing before you scale anything. The organization can explain agent behavior under pressure. Not in a demo. In a messy week, with real inputs, with real side effects, with real stakeholders who get angry when the system improvises, so pick one cross-functional process with consequences, not drafting content, not summarized meetings. Pick something that touches a system of record and triggers downstream work. Onboarding, access requests, supplier onboarding, service triage, invoice exceptions. Something where the organization already knows what wrong looks like. Then design the agents like products, not helpers. That means you name an owner who owns behavior, not just the repo. You give it a backlog, versions, a deprecation plan, and a defined blast radius. You decide what production means for this agent, you decide who can change it. And you decide how change gets reviewed because prompt edits are still logic edits even when they look like English. Now you establish the boundaries the pilot exists to validate. The deterministic core comes first. The workflow steps that must be correct, auditable, and idempotent. The things that create records, update fields, send external messages or change access. Then you wrap that deterministic core with probabilistic reasoning. Classification, extraction from messy inputs, drafting, summarization, prioritization, and recommendations. Reasoning can propose actions. It can't execute side effects directly. It must call the deterministic layer through explicit tool contracts and you don't let the pilot cheat. If the agent needs a tool, you register the tool. If it needs data, you define which sources are allowed. If it needs authority, you assign an identity and scope it. If it needs to escalate, you define a human gate with a named approver and a clear stop condition. This is also where you design for failure as a first class feature. Agents will hit ambiguous inputs. Downstream APIs will throttle. A connector will fail. A human will ignore an approver request. A model update will change behavior slightly. None of that is surprising. What matters is whether the system fails legibly. So your pilot needs two kill switches. One to pause the agent and one to force safe mode where it can only draft and recommend, not act. And those switches can't be buried in a runbook. They have to be operational muscle memory. Now, measure it. Not vanity metrics like prompts per user. Measure the entropy signals this episode is built on before and after. Mean time to explain is the headline metric. How long it takes to answer why did it do that with a coherent narrative and evidence? If MTT drops, you're building a system you can scale. If MTT stays high, you're building a mystery generator. Track incident ambiguity. How many incidents involve behavior drift instead of outages? Track drift frequency? How often prompts, tools or connectors change without a corresponding change record tied to the agent product? Track agent to human ratio inside the pilot, not as a brag, as a budget conversation. If one agent produces a thousand decisions a day, then you just created a new operational workload whether you planned it or not and then do the part most pilots avoid. Proof decommissioning. At day 90, you either promote it with stronger boundaries or you retire it. That retirement must revoke identity, disconnect tools, archive traces, and remove it from discoverability. If the organization can't cleanly kill an agent, it can't claim it controls agents. It just accumulates them. The output of this pilot isn't a slide deck. It's a repeatable pattern, a reference architecture, a decision rights model, and a telemetry story that compiles into explanation. That's what scale actually requires. Conclusion.
