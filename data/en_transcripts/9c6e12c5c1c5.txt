It does not try to be smarter about keywords. It abandons keywords entirely. Here's how it actually works. You take a document and run it through an embedding model, which is a neural network trained specifically to convert meaning into numbers. Similar documents cluster near each other while the similar documents stay far apart. Now, when a user submits a query, the same thing happens on the other side. It does not care whether the words matched. It cares about proximity in that mathematical space. And proximity in that space correlates with similarity in meaning. This is why the system can retrieve complaint resolution pathway in response to escalating a complaint. Since they describe the same concept, their vectors are close together. You compare the query vector against every single document vector in your index, calculate the distance for each one, sort them and return the top results. Disk N, the architecture of the answer, disk N stands for disk accelerated nearest neighbors and the name tells you exactly what the goal is. It isn't just faster or smarter search, it's disk accelerated. The designers asked a simple question, what if the index didn't have to live in RAM? It sounds like an obvious fix because SSDs are significantly cheaper than RAM. If you can move the index to an SSD without ruining your query speed, the cost of scaling changes completely. The hard part is that random disk access is much slower than memory access. If a search algorithm has to make thousands of random reads for every single query, it would be too slow to use on anything other than RAM. The breakthrough with disk N is the realization that the storage medium isn't the bottleneck. Random access is the bottleneck. If you design the graph and the layout on the disk to minimize those random reads, NVMe SSDs are actually fast enough to compete with in-memory search. Microsoft bet on this engineering shift and the production data shows that the bet paid off. The system uses something called the Vamanagraph. Unlike the multi-layer setup you see in H&SW, Vamanag uses a single layer with edges that are specifically designed to be long and sparse. While H&SW uses different layers for local and long-range connections, Vamanag focuses on long-range jumps that let the search move through the data in fewer steps. These vectors aren't full precision, but they are detailed enough to help the search navigate the graph and find the right neighborhood. When you run a search, the system uses the RAM-based navigation layer to get close to the answer at memory speeds. Then it jumps to the SSD to pull the full precision data and re-rank the results. For any team running a RAC system that pulls in new data every day, the real problem is operational. You have to ask what actually happens to your index when the data behind it starts changing. H&SW is actually pretty good at handling new inserts as they come in. When you embed a new document and need to add it to the index, the algorithm just wires it into the existing graph as a new node without needing a full rebuild. This incremental approach is why H&SW feels so comfortable for teams that need to keep their knowledge bases current. You can publish a new policy on Monday morning, have it embedded by lunch, and see it show up in support ticket results by the end of the day. But when you need to delete something, things get a lot messier. Most H&SW setups don't actually pull nodes out of the graph. The moment a document is deleted or replaced, instead they just mark that node with a tombstone flag to hide it from search results while leaving all its physical connections in the graph structure. Over time these tombstone nodes start to pile up and waste memory without helping your search at all. They can even hurt the quality of your graph by hogging connections that should belong to live data. You can run periodic compaction to clean them out, but doing that on a massive H&SW index is a heavy lift for your hardware. The process usually requires holding the old graph and the new one in memory at the same time, which can easily crash a system that was already running near its limit. A SQL Server disk A& has a completely different way of failing. If you look at the official documentation for building a vector index in SQL Server, it's very honest about the trade-offs. The source table might be locked in read-only mode for the entire time the index is building. On a large data set, we aren't talking about a few minutes of downtime during a maintenance window. We are talking about hours. If you have other services that need to write to that table, they are completely blocked until the build finishes. For an enterprise knowledge base that needs constant updates, this isn't just a minor annoyance, it's a massive architectural wall. The limitations don't stop there either. Once you build a SQL Server disk and index, it stays effectively static. You can't just add new vectors one by one, like you can with H&SW. If you have new documents to index, the standard move is to copy the table, add the new content, build a fresh index, and then swap it into production. That works fine if you only update your data once a month or once a quarter, but if your Ragsystem needs to show new information within an hour of it being written, there is a fundamental mismatch between what you need and what this technology can actually do. Cosmos DBDISCAN was designed from a totally different perspective. The 2025 research paper on this implementation shows that search accuracy stays stable even as your data shifts around. You can add, change, or remove vectors without the index falling apart or needing a total reset. The system integrates the disk and graph directly into the existing Cosmos DB partition structure so that everything stays in sync as data flows through. Having your content available for search in near real time wasn't just a bonus feature for them. It was a core requirement they built the entire system around. The lesson here for how you manage your data is very clear. If your Ragsystem is constantly ingesting new product docs, regulatory updates, or customer support tickets, your choice of disk and N-version matters. It's the difference between a pipeline that runs quietly in the background and one that turns into a recurring emergency for your ops team. The math behind the algorithm might be the same, but the service wrapped around it is what actually determines your experience in production. How the index choice affects your Rags pipeline. By the time we get to 2026, Rags retrieval isn't just a simple database call anymore. It has turned into a multi-stage pipeline where queries get rewritten, hybrid searches run in parallel, and a re-ranker scores the best results before the LLM even sees them. Every choice you make at the vector index stage is going to ripple forward through that entire process. The algorithm itself lives in the retrieval stage but its impact shows up in two places you might not expect. It changes your total pipeline latency and it changes the quality of the data your re-ranker has to work with. We have to start by admitting that pure vector search isn't a silver bullet. Embeddings are great at capturing meaning, but they often struggle with the specific details a production system needs to get right. Things like SKU numbers, contract IDs, or specific ticket references often get blurred during the embedding process. The model tries to turn character-level differences into general similarity, which is usually helpful, but sometimes exactly what you don't want. Negation is another big problem because a sentence about who is eligible for a benefit looks almost identical to a sentence about who isn't. The model just doesn't have a reliable way to turn logical opposites into a large distance in vector space. This is why hybrid search is now the standard for enterprise rag instead of just being an optional upgrade. You use BM25 to handle exact matches and keywords while the vector side handles the concepts and meaning. Azure AI search runs both of these at the same time and merges them into one list that covers all your bases. If your system needs to handle the messy, specific questions that real users actually ask, you really can't afford to skip either side of that equation. This is where the specific index algorithm finally plugs into the rest of the pipeline. H&SW pulls results from RAM at incredible speeds, usually in less than 10 milliseconds. This can take a bit longer because of its two-stage process, usually landing between 15 and 20 milliseconds at scale. Both of those results go into the same fusion process and then move on to the re-ranking step. Once you hit that re-ranking stage, the speed difference between the two algorithms basically vanishes. A standard re-ranker looking at the top 100 candidates takes about 30 to 60 milliseconds to run on most hardware. When you add the overhead of the semantic ranker and the hundreds of milliseconds it takes for the LLM to generate a response, the gap disappears. The 15 millisecond difference between H&SW and DISCAN doesn't matter when the whole pipeline takes two full seconds. Your users won't feel it and your performance logs won't even care. It's a difference that only exists on a benchmark sheet, not in the real world. What the index choice actually changes is the quality of the candidates that the re-ranker has to sort through. Both H&SW and DISCAN are aiming for the same high accuracy rate of over 95%. This means the list of results they hand off should be basically the same at the query level. If a re-ranker gets 50 candidates from a DISCAN and index, it's working with the same quality of material it would get from H&SW. The algorithm changes how much it costs you to find those candidates, but it doesn't change how relevant they are. Your chunking strategy is the final piece of this puzzle. The way you split your documents before you ever embed them is what really determines how precise your answers will be. If you create semantically coherent chunks that follow section headings and logical units, your retrieval will improve no matter which algorithm you use. A well-organized set of data running on DISCAN will always outperform a messy, poorly chunked data set running on H&SW. At the end of the day, the index algorithm tells you what the infrastructure costs to run, but the chunking tells you if the content was even worth finding in the first place. You have to look at the pipeline as a single system. If you spend all your time optimizing the index algorithm without looking at re-ranking or chunking, you are tuning the wrong part of the engine. The index choice is important, but it's a decision about cost and scale, not about the tiny millisecond differences you see in a lab report. Enterprise rag failure modes and how index choice relates. Most teams get it backwards when a rag system starts spitting out wrong answers. The assumption is that the language model broke, the model hallucinated, the model made something up, you think you need to swap it for a better one. But in reality, the evidence we see heading into 2006 points somewhere else entirely. The main reason enterprise rag fails is retrieval, not generation. When your model gives a plausible but wrong answer, it usually isn't because the model invented a lie. It's because the right context never actually made it into the prompt. The model just answered with the data it was given, and that data was wrong, incomplete or totally outdated. That is a retrieval problem. No amount of model upgrades will fix a system that feeds the wrong information to the generator. These failure modes follow very predictable patterns. Negation is one of the biggest ones. If you ask about employees not eligible for leave versus employees eligible for leave, those two queries sit right next to each other in a vector space. The vocabulary is almost identical even though the logical distance between the correct answers is huge. The semantic distance is tiny. HR systems and compliance tools built on pure vector search fail this test all the time. The worst part is they don't fail loudly. They just give you a confident, well formatted answer about the wrong group of people. Exact identifiers are another place where the system breaks. Think about contract numbers, invoice IDs or SKU codes. The embedding process takes those character level differences and squashes them into similarity scores. A search for contract number 2024 EU7731 might pull up 2024 EU7732 because the model sees them as basically the same thing. In procurement or legal work, that kind of near miss is a disaster. It's the wrong document being handed to a decision maker who trusts the system to be right. Then you have temporal failures which are quieter but get worse over time. Vector similarity doesn't understand the concept of new. An old policy and the one that replaced it look almost identical to a vector index because they use the same language to describe the same ideas. When both exist in your data the system just grabs whichever one ranks higher. Without metadata filters to check for version status or dates, stale content competes with current content on a level playing field. In a regulated environment that isn't just a bug. It's a structural risk you built into the architecture the moment you ingested the data. The most important thing to realize is that none of these are problems with your index algorithm. Switching from H&SW to disk and won't fix how the system handles negation. It won't help with ID matching. It won't make the index aware of time. These failures live in the retrieval architecture itself. They depend on whether you're running hybrid search, whether your metadata filters are right, and whether you have a re-ranker cleaning up the results before they hit the model. If your pipeline has these gaps, H&SW and disk and NN will fail in exactly the same way. What the algorithm actually changes is the scale where these errors start to matter. If you have five million documents, you have fewer chances to mess up than if you have five hundred million. The odds of an old document outranking a new one are lower when the pile is small and clean. You can't have one without the other. If a company moves to disk and to save money but ignores hybrid retrieval, they just end up with cheaper infrastructure that makes the same mistakes across a much larger data set. The algorithm choice handles the cost. The pipeline design handles the quality. These are two different problems. If you confuse them, you'll end up with an architecture that is either too expensive to run or too wrong to use. Neither of those is a win. Metadata filtering, the underused lever. Most teams spend months obsessing over embedding models and chunk sizes. They spend weeks benchmarking re-rankers. Then they design the metadata schema in a single afternoon because they just use whatever fields seem obvious at the time. That lopsided focus is exactly where production failures come from. Azure AI Search uses hybrid search to apply all data filters across both keyword and vector retrieval at the same time. This is the specific mechanism that keeps an intern in marketing from seeing documents meant for the legal team. It's how you make sure a policy search pulls the active version instead of something that expired two years ago. It's also how you keep one customer's data away from another in a shared system. But none of that works if you didn't design the metadata before you started ingesting data. The first rule is that metadata has to be granular. It needs to live at the chunk level, not the document level. A single policy might have different sections for different regions or different levels of sensitivity. If you only tag the parent document and then chop it into 50 pieces, every piece gets the same tags. That means your filters will either hide the whole document when they shouldn't or show sensitive sections to people who don't have access. You have to attach the right metadata to each individual chunk even if that makes the ingestion process more work. If you want high quality retrieval, you need to focus on a few specific categories. You need department and business unit for scope. You need region and jurisdiction for regulations. You need document types to tell a policy apart from a reference guide. You also need version status for recent C, sensitivity labels for security, and tenant IDs for isolation. Most enterprise systems already track these things. The problem is that teams forget to carry those details through the pipeline and into the index. They leave them sitting in the source system where the search engine can't see them. Azure AI Search recently added a parameter called filter override. This lets you apply one filter to the vector search and a different one to the keyword search within the same query. This is huge because sometimes you want your semantic search to cast a wide net across all departments while your keyword search stays locked onto official manuals. Or maybe you want the opposite. You might want strict security filtering on the vectors but a broader lexical sweep on the text. The two sides of a search often need different boundaries and this parameter stops you from having to compromise. Security is the biggest reason to get this right. In Azure AI Search, the filter happens on the server before any results ever leave the search layer. This is much safer than trying to filter results in your application code after the search is done. Application layer security is brittle. It requires every single API and every single developer to get the logic right every time. If one person misses a check, you have a security breach. Server-side filtering puts the lock on the data layer where it can't be bypassed by a mistake in the app. Your index design is what determines if filtering is fast or even possible. When you create an index, you have to mark specific fields as filterable. This tells the system to build the internal structures it needs to handle those queries efficiently. If you forget to mark a field as filterable, you can't use it in a filter at all. To fix that later, you have to rebuild the entire index from scratch. On a massive dataset, that means downtime or a very expensive parallel build. You don't pay for a bad schema when you design it. You pay for it months later when the system is live and your under pressure to fix the gap the index wasn't built to handle. Multitannant rag governance at scale. Most enterprise rag deployments don't actually serve one single group of people. In reality, they serve HR, legal engineering and finance all at once. The query routing logic was simple when there was only one index but it becomes a constant source of bugs once you have many. Those architectural decisions that felt like options during a pilot program suddenly become load-bearing walls in a production system. Two specific patterns handle this isolation in Azure AI search. The first is a single global index that uses rich metadata filters which means one index holds content from every tenant while every query is restricted by filters to keep users inside their own documents. The second approach uses separate indexes for every tenant or domain. These are isolated instances with their own schemas, their own capacity and their own specific performance tuning. The single global index approach offers some real advantages for your operations team. You only have one index to manage and one schema to maintain which makes it much easier to monitor your ingestion pipelines. If you need to run analytics to see how the whole organization is using the system, the data is already in one place. From the perspective of the application layer, the logic is very simple because you just send the query with a tenant filter and get back the right results. But here is the problem. The risk is just as big as the convenience. Your entire security model depends on those metadata filters being applied correctly every single time a query is made. If a filter gets dropped in one API endpoint or if a developer takes a shortcut during testing that accidentally makes it into production, you have a massive data exposure incident on your hands. It will just silently return results and you might not realize there is a problem until an audit happens or a user sees something they shouldn't. The separate index approach trades that simplicity for much better architectural isolation because each tenant has their own index, a query for tenant A physically cannot return documents from tenant B. The security is enforced by the structure of the system rather than the logic of a filter. The most sophisticated enterprise architectures in 2026 don't actually try to settle the H&SW versus disk and debate. In database circles, this pattern is known as tiered storage. The logic is straightforward because hot data stays in fast expensive storage, while cold data sits in slower cheaper tiers. The system handles the movement between these layers automatically based on how people actually use the data, and it turns out that vector search follows the same lopsided access patterns that make tiered storage work everywhere else. In a typical company deployment, a tiny sliver of the total content handles the vast majority of the traffic. People check the same HR policies over and over, or they look for documentation on the five products that drive 80% of the support tickets. Archived contracts and old incident reports stay in the index, but they almost never actually surface in a real production query. H&SW is the right choice for that hot working set because it keeps those high traffic documents in a compact in memory graph. This allows retrieval to happen at memory speeds without ever touching an SSD, making sub 10 millisecond responses a reality. For the small group of documents that handles most of your traffic, the cost of the RAM is worth it because you aren't trying to shove the entire massive corpus into memory at once. Disc-Anne takes over for the cold tier, which includes the full library of documents that people rarely ask for. You can't leave these out of the index because any one of them might be the exact answer a user needs someday, but you don't want to pay to keep them in RAM. Most teams build a rag system and run a few test queries on topics they already know by heart. When the answers look reasonable, they ship the product to users. But this creates a massive evaluation gap. It isn't a matter of laziness, but rather the result of working under tight deadlines without a real baseline to measure against. The problem won't show up on the day you launch, but it will show up six months later when users have quietly stopped using the tool because they no longer trusted. The metrics that actually define retrieval quality are split into two groups. One group tells you if you found the right documents and the other tells you if those documents actually help the model give a grounded answer. You need both to see the full picture because looking at either one in isolation will lead you to the wrong conclusion. Precision at K measures what percentage of your top results are actually useful. If the system pulls 10 documents and seven of them help answer the question, your precision at 10 is 0.7. This metric is vital because it punishes systems that fill the results with nearby documents that don't actually help. High precision matters because irrelevant documents take up space in the context window, which makes it much more likely that the model will focus on the wrong information. Recall at K asks the opposite question by looking at all the relevant documents in your library and seeing how many actually made it into the top results. A system might have great precision but terrible recall, which means it finds good documents but misses the most important ones. In a corporate setting, missing a specific policy or a legal requirement isn't just a minor inconvenience. It is a massive gap in the model's knowledge that leads to incomplete answers even if the few documents it did find were technically correct. Mean reciprocal rank tracks exactly where that first right answer appears in the list. A relevant document in the first slot is much better than one in the fifth slot and both are better than a result at rank 20. Most systems give more weight to the first few results they see. So this metric captures whether the right information is showing up early enough to actually influence the final answer. Normalized discounted cumulative gain takes this a step further by using graded scores for relevance. It recognizes that an official policy is more important than a random FAQ and it discounts the value of a result if it shows up too low in the ranking. This is the best metric to use when your library contains documents that have different levels of authority or importance. Those four metrics tell you how the retrieval layer is doing but you also need to bridge the gap to the generation phase. Context precision looks at the snippet sent to the prompt and asks how many were actually needed. A high score here means your pipeline is efficient and clean while a low score means you are drowning the model in noise and hoping it can figure things out on its own. Context recall is the inverse measuring if the information needed for the answer was actually present in the retrieve text. When this score is low the risk of hallucination goes through the roof because the model will try to fill in the blanks using its own internal memory. Faithfulness happens at the very end of the process but it is really a reflection of how well retrieval did its job. It checks if every single claim in the final answer is backed up by the retrieve text. If a system fails faithfulness test consistently you are usually looking at a retrieval failure that is just wearing a generation costume. The tools to measure all of this are already available. You can use Raga so RS for open source evaluation or look at Langsmith and Azure AI Studio for managed pipelines that handle these metrics at scale. Deepivol is also great for looking at specific components like contextual precision. However, none of these tools will work unless you build a golden dataset which is a curated list of 50 to 100 real queries with known correct answers. A one-time evaluation is a good start but it isn't enough to keep a system healthy. Models get updated in content changes and user behavior will eventually shift away from what you originally planned for. Quality that looks great at launch can drift downward for months before anyone notices a problem. To stay ahead of it your measurement has to be a continuous part of the process rather than a one-time ceremony. Observability and drift keeping the system honest. Before you ever launch you need to run an evaluation using a golden dataset.
