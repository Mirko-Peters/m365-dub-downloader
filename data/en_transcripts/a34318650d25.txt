The name suggests something vague. Elastic could mean anything. But the technical definition is precise. Elastic tables are a distinct table type inside dataverse. From the outside, they look almost identical to standard tables, same web API endpoints, same security model, same power pages integration, same OD data query syntax. That single change in the storage engine produces a fundamentally different performance profile. Not because Cosmos DB is universally better than SQL, but because it was designed for a different workload. Cosmos DB is horizontally scalable, partitioned, and document oriented. Data isn't concentrated in a single database instance that scales up. It distributes across partitions. Each partition independently handling its slice of the total load. When traffic increases, the system scales out by adding partitions, not by adding capacity to a single node. Microsoft introduced elastic tables, specifically for the workload patterns that break the SQL back model. Telemetry ingestion, application logs, event streams, audit records, time series data, activity feeds. The defining characteristic of these workloads is that they're mostly writes, mostly append only, and they grow continuously. They don't look like CRM data. They look like operational exhaust. The continuous output of a running system rather than the carefully maintained records of a business process. The partition ID column is the mechanism that makes this work. Every elastic table record has a partition ID field, and that value determines which logical partition in Cosmos DB holds the record. Records with the same partition ID land in the same logical partition. Records with different partition IDs distribute across different partitions. This is how Cosmos DB achieves horizontal distribution, not through automatic load balancing, but through deliberate assignment at right time. The partition key controls the distribution model, which is why choosing it correctly is the most important decision in any elastic table design. We'll come back to that in detail. Two more characteristics are worth understanding before we move on. First, elastic tables include built-in TTL support, time to live. You can set a TTL value on any record, expressed in seconds, and Cosmos DB will automatically delete that record when the TTL expires. For operational data that only needs to be retained for 30, 60, or 90 days, audit logs, session events, telemetry samples, this means you never need a manual cleaner process. The storage footprint stays bounded automatically, which directly controls your storage costs over time. Second, and this matters for implementation. The dataverse web API surface is the same. You're not learning a new SDK. You're not configuring a separate Azure resource or managing Cosmos DB connection strings. The elastic table sits inside your dataverse environment, responds to the same rest API calls, and participates in the same solution, packaging, and deployment model as any other dataverse table. The abstraction is clean. The complexity is contained underneath, managed by the platform. And the single most consequential design choice in the elastic table layer, the one that determines whether the whole system actually scales is the partition key. Partition key design, the decision you can't undo. The partition key is where most elastic table implementations either succeed or fail. Not because it's technically complicated to set, you specify it when you create the table, it populates a field called partitioned E.D. on every record, and the Cosmos DB layer handles the rest. The problem is that it's irreversible. Once a Cosmos DB container is created with a specific partition key, that key cannot be changed. Ever. The only way to change a partition key after the fact is to create a new container with the correct key and migrate every record from the old one into it. At millions of rows across a live production system, that migration is expensive, disruptive and entirely avoidable if the decision is made correctly upfront. This is not a minor operational footnote. It's the most consequential architectural decision in any elastic table design, and it needs to be treated as such, not as a schema detail you revisit later, but as a one-way door that you walk through deliberately. So what makes a good partition key? Three requirements, and all three need to be satisfied simultaneously. First, high-cut inality. The partition key needs many distinct values, enough to spread your data across a meaningful number of logical partitions. A key with only a handful of possible values concentrates your data into a small number of partitions, which undermines the horizontal distribution that makes elastic tables fast. Think thousands of distinct values at minimum, not dozens. Second, even distribution of both storage and request units, it's not enough for a key to have high-cut inality if 90% of your data and 90% of your traffic lands on a small subset of those values. The partition key needs to produce roughly balanced partitions. Similar amounts of data per partition, similar RU consumption per partition. Inbalanced partitions produce hotspots, and a hot partition absorbs disproportionate load while the rest of the container sits under utilized. You pay for the full provision throughput, but only effectively use a fraction of it. Third, alignment with your most common query patterns. Every query that includes the partition key in its filter is a single partition query. Fast, cheap, and predictable. Every query that doesn't include it becomes a cross-partition scan, fanning out across multiple physical partitions and consuming RUs proportional to how many it touches. Your partition key should be the field that appears most naturally in your highest frequency queries. For a multi-tenant SAS, the instinctive answer to all three requirements is tenant ED. And that instinct is correct, of partially. Tenant ED has high-cut inality if you have many tenants. It aligns perfectly with query patterns because virtually every meaningful query in a multi-tenant system is scoped to a specific tenant. And for small and medium-sized tenants with predictable data volumes, it distributes storage reasonably well. The failure mode arrives when your tenant distribution isn't uniform. It almost never is real SAS platforms develop what the industry calls elephant tenants. A small number of customers who generate a wildly disproportionate share of the total activity. One enterprise customer with a thousand users generates more events per day than 50 small business customers combined. When tenant ID is the partition key, and that enterprise customer's data accumulates on a single partition key value, you end up with a hot partition. One logical partition absorbs the majority of your RU consumption. The other partition sit quiet. And because Cosmos DB enforces throughput limits per physical partition, that hot partition throttles returning 429 errors, while the rest of the container operates well within its capacity. There's also a hard storage ceiling that makes this worse. A single logical partition in Cosmos DB, meaning a single partition key value, cannot exceed 20 gigabytes of data. For a large enterprise tenant generating millions of records over months, 20 gigabytes is a real limit, not a theoretical one. When that ceiling is hit, new rights fail. The resolution requires data migration. There's no in place fix. So tenant ID works until it doesn't. The question isn't whether to use tenant ID. It should be the foundation of your partition strategy in any multi tenant system. The question is whether tenant id alone is sufficient for the tenant distribution you expect to have, not just the distribution you have today. Planning for that limit before you go to production is what separates architectures that scale from architectures that get rewritten. And Microsoft built the answer to this problem directly into Cosmos DB. Hierarchical partition keys, solving the elephant tenant problem. Hierarchical partition keys are the answer. And understanding how they work changes the design model for every multi tenant elastic table you'll ever build. The concept is straightforward once you see it. Instead of a single partition key field, just tenant id, you define an ordered hierarchy of up to three fields. Level one is tenant id. Level two is something that distributes data within a tenant, user id, customer id, project id, depending on what your domain looks like. Level three is something more granular still. Session id, order id, or in many cases, just the records own id. The effective logical partition becomes the concatenation of all three values in order. So instead of one logical partition per tenant, a large tenant automatically gets thousands of sub-partitions, one for each unique combination of tenant id, user id, and session or order identifier. The elephant tenant problem disappears. That enterprise customer generating 80% of your traffic no longer concentrates everything onto a single partition key value. Their data distributes across as many sub-partitions as they have users and sessions. The 20 gigabyte ceiling we discussed doesn't apply to the tenant as a whole. It applies to each individual logical partition and no single user session data comes close to that limit. The system scales with the tenant's growth automatically without any manual intervention and without migrating to a dedicated container. Here's what makes HBK genuinely elegant compared to alternative approaches like synthetic or salted keys. Query rooting stays intelligent. When your application queries for all records belonging to a specific tenant, which is the most common query pattern in any multi-tenant system, Cosmos DB knows that level one is tenant id. A filter on tenant id alone fans out only across that tenant sub-partitions, not the entire container. You're not paying the cost of a full cross-container scan. The query touches only the physical partitions that hold data for that tenant and nothing else. For a query that includes both tenant id and user id, the scope narrows further. Only the partitions holding that user's data within that tenant get touched. Each additional level you specify in the filter reduces the fan out and reduces the RU cost. Compare that to a synthetic key, say tenant id concatenated with a hash of the record id. You get good distribution, but you lose the intelligent rooting. A query filtering on tenant id alone can't be efficiently routed because the partition key value isn't just tenant id anymore. The system has to scan more broadly to find the matching records. HPKs preserve the routing semantics of a simple tenant id key while adding the distribution properties of a composite key. You get both. One constrained worth naming explicitly. HPKs must be configured at container creation time. This reinforces everything set in the previous section about partition key decisions being irreversible. You can't add hierarchical levels to an existing container any more than you can change the partition key entirely. If you've already shipped an elastic table with a flat tenant id partition key and you later decide you need HPK to handle a growing enterprise customer you're looking at a migration. That's why the design time decision matters so much. You're not just choosing a key for the data you have today. You're choosing a key for the distribution profile. You'll have 18 months from now. For a B2B SAS platform, the practical HPK layout that handles most tenant distribution scenarios looks like this. Level one is tenant id, Level two is user id, or customer id, Level three is the item's own id. That three level structure handles heterogeneous tenant sizes without any application level rooting logic. Small tenants with 10 users produce a modest number of sub-partitions. Enterprise tenants with thousands of users spread across thousands of sub-partitions automatically. One more thing worth confirming for architects who are planning event-driven workflows on top of the storage layer. The Cosmos DB change feed still works at the physical partition level, completely unaffected by whether you use HPKs or a flat key. If you're building real time processing pipelines that react to record creation or updates, HPKs don't break that pattern. The event architecture remains intact. Service side rendering via liquid versus asynchronous client side loading via the web API. For small data sets, a few hundred records or fewer, this decision barely matters. For elastic tables specifically, there's a fourth requirement that overrides everything else. Every query must include the partition key in the filter. Every single one. The partition ID field or the tenant ID that maps to level one of your HPK hierarchy must appear in the filter expression on every call. Without it, the query becomes a cross-partition scan. Cosmos DB fans out across physical partitions looking for matching records. RU consumption multiplies proportional to how many partitions exist and response time increases accordingly. With it, the query roots directly to the relevant partitions executes in bounded time with predictable RU cost and returns quickly. This is the elastic table query discipline that separates implementations that perform well from implementations that look fine in development where data sets a small and collapse under production load when data accumulates across many tenants.
