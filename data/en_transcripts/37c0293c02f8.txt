And under the asset you can separate state events, condition data, or production counts. That makes subscriptions easier to control. Align supervisors app might receive events from one line, a central engineering team might receive approved condition data from several sites and a cloud pipeline could subscribe only to the topic selected for enterprise analysis. But don't let the topic name carry facts that belong in the message itself. A topic tells a consumer where a message belongs in the event structure, but the payload should still state what happened when the source observed it, which asset produced it, what the value means, and whether the source considered it good data. If a message gets stored, replayed, or routed elsewhere, it should remain understandable without asking somebody to decode a long topic string. Now here's where it gets interesting. Live state needs a different approach from events. A machine state is often a current fact. When a new consumer joins, it may need to know whether the machine is running or faulted right now, not wait until the next state change. MQTT brokers can retain a current message for a topic, so a new subscriber receives the latest published state. That works well as long as the team defines what the retained message actually represents. Is it the last reported state? Is it still trustworthy after a source outage? How does a consumer tell the difference between the machine is stopped? And the system hasn't heard from the machine for 20 minutes. A retained value needs a timestamp, a source quality indicator, and a freshness rule, or a stale state, can look live. That brings us to session behavior. Some consumers need messages only while they are connected, while others need the broker to hold messages until they reconnect. Those choices affect local storage, delivery behavior, and how much history the broker should carry. It also affects recovery after a network fault, which is why MQTT settings shouldn't be selected from a default template and forgotten. Message size is another quiet design choice. MQTT can transport large payloads, but that doesn't mean every message should carry a whole machine snapshot, recipe, alarm list, and batch record. Small focused events tend to travel and recover more predictably. If a use case needs a large file, an image, or a document, move the object through a suitable storage path, and publish an event that points to it. MQs also have limits. When consumers slow down or disconnect, the broker needs a clear policy. It may retain messages for selected clients, reject new traffic, or hit storage limits. You need to know which events are high priority, which can be aggregated, and which can safely expire. A queue that fills without an alert is just a delayed data loss mechanism. MQTT gives you a clean event backbone at the site, reducing coupling, and giving local and cloud consumers a common way to receive approved data. But a tidy hierarchy of MQTT topics doesn't create shared meaning by itself. A topic tree can tell you where a message came from, but it can't define who owns the data contract, how a fault relates to an active order, or whether two systems mean the same thing when both use the word running. That takes a unified namespace, used as a shared operational contract rather than a giant folder structure with better branding. Unified namespace. Useful pattern? Easy to misuse. A unified namespace, often shortened to UNS can help here, but the term gets used so loosely that it creates its own confusion. Some people describe it as one huge MQTT topic tree for the whole company. That's too narrow. Others treat it as a new central system that replaces every existing source, but that creates a different problem because ERP, MES, maintenance, and engineering systems still own facts they were built to manage. A useful unified namespace is a shared operational data contract. It gives producers and consumers a common way to identify assets, publish agreed events, understand payloads, and find information without building a private integration for every new use case. The contract covers names, identifies as message shape, ownership, security, and change rules. MQTT can carry that contract, but MQTT alone doesn't define it. Start with the hierarchy people already use to describe the factory. ISA-95 gives a useful structure, enterprise, site, area, line, cell, and asset. You don't need to force every building process or machine into a perfect textbook hierarchy, real plants rarely cooperate with textbook diagrams, but you do need a stable way to answer where an asset belongs and how it relates to the production structure around it. Take a filling machine as an example. It belongs to a named cell on a named line inside a defined production area at a specific site, and that relationship should mean the same thing, whether someone reaches it through an MQTT topic, a maintenance record, an MS work center, or a fabric table. Without that agreement, the same machine becomes line 3 filler in one system, filler 0, 3 in another, and PLC 2 in a third. The data can still move, but nobody can reliably join it. A good UNIS also separates different kinds of information. Live state is one kind. It answers questions such as whether an asset currently reports running, stopped, blocked, faulted, or in changeover, and that data changes often and needs clear freshness rules. Definitions are different. An assets manufacturer, model, installed capability, engineering unit, or stable identifier might change rarely. You don't need to publish those details with every machine state event, although the event should carry enough identity to find the approved definition. All data needs its own space as well. OE data, energy data, quality measures, and maintenance condition indicators can describe a cell or line rather than one physical device. That distinction helps because a line level performance measure shouldn't pretend to be a raw control attack just because it travels through the same broker. Then there is ad hoc data. Every plant has it, a temporary diagnostic topic during commissioning, a short-lived feed for a new sensor, a local experiment that hasn't earned a place in the shared contract yet. So separate from governed operational data or temporary work slowly becomes the factory's permanent interface. That tends to happen more often than anyone admits this separation protects consumers. If a planning app subscribes to a governed production state contract, it should not break because an engineer adds a temporary test field to an unrelated message. If a quality team relies on an agreed reject event, it needs versioning and notice when the payload changes. A unified namespace works when it makes these expectations explicit. Spark plug can help in some environments. Spark plug is a specification built on MQTT that defines topic patterns, payload conventions, and session behavior for edge nodes and devices. It can give a team a disciplined way to report device birth, device death, current metrics and state reducing custom work when the ecosystem already supports it. But Spark plug isn't a requirement for a unified namespace. Forsing every device, app, and enterprise event into Spark plug can make a clean design harder, especially when you need business events that don't behave like device telemetry. Use Spark plug where its device lifecycle and metric model fit and use a clear governed event contract where they don't. Standards should reduce friction, not become another piece of machinery people work around. Governance is where the pattern either holds or falls apart. Someone needs authority over the asset naming rules, someone needs to approve a new topic or event type, and someone needs to own the message contract and communicate changes. That ownership should sit with the domain that understands the data not only with the team that operates the broker. OT may own the meaning of machine state, maintenance may own failure classifications, production may own OEE loss rules, IT can operate the platform and enforce access controls, and fabric can analyze the events. None of those responsibilities cancel the others. So, before you map an OPC UA source into MQTT, define the contract around the event. Its asset identity, its event type, its timestamps, its quality status, its owner, and its expected consumers. Then the protocol translation has a clear target rather than becoming another exercise in moving tags from one place to another, from OPC UA subscription to MQTT message. So, you've got your event contract in place and now the connector has a clear job. It subscribes to the approved OPC UA nodes, receives data changes from the server, and turns those into MQTT messages that other parts of the site can consume. You might think that's just protocol translation, but here's the thing, it's more than that. The connector needs to take an OPC UA notification and create a message that keeps the evidence from the source while fitting the shared contract. Drop too much detail and you lose the ability to investigate bad data later. Forward every technical field without structure and every consumer has to become an OPC UA specialist. Neither option works. Take a machine state change. The OPC UA server might report a source timestamp, a server timestamp, a status code, a node identifier and a value, say a number or an enumeration. What I recommend is normalizing that into an event with a stable asset ID, a govern signal name, the observed value, its unit where relevant and the quality status while also keeping the original node identity. That source reference may not appear in every business facing report, but it belongs in the record because when an engineer asks why an event from a packaging machine suddenly changed meaning after a controller update, you need a route back to the exact source node and connection that produced it. Time needs similar care. An OPC UA source timestamp tells you when the source observed the value, the edge received time tells you when the connector saw it, and the MQTT published time tells you when the event entered the local broker. These are different points in the journey and they can diverge during an outage, reconnect or queue backlog. Don't replace one with another. Use the source timestamp as the event time when the source provides it and the quality is acceptable and keep the receive and publish times as operational evidence. Later when fabric receives a late batch of messages, your team can separate an old machine event from a new message delivery, the same applies to quality. If OPC UA reports a bad or uncertain value, publish that status with the message. You may root it differently, exclude it from a production calculation or raise a data quality issue. What you should not do is strip the quality code at the edge and let a downstream calculation treat every value as equally trustworthy. Now consider the message itself. For a machine state event, a focus payload may include the asset ID, signal name, value, source time, quality and a reference to the original OPC UA node. For a temperature measurement, add the agreed unit. For an alarm or fault event, include the event identifier, fault code, severity of the source provides it and the text only if that text is fit for wider use. Keep the message type clear. A current state message is not the same as a fault event and account update is not the same as a quality reject. When you force all of them into one vague telemetry shape, consumers need hidden rules to figure out what they received. Clear event types, reduce that guesswork. You also need to decide whether the connector publishes each update as soon as it arrives or batches several updates into a message, publish on change works well when the decision depends on a fast change, a machine fault or a transition into a blocked state. But it can also create heavy traffic if a value change is constantly or several nodes report at once. Batching reduces message overhead and can make cloud transport more efficient, but it adds delay and can blur the order of events if the payload doesn't preserve individual timestamps. A batch may suit routine condition data, but it may be the wrong choice for alarms that need a quick local response. Choose based on decision speed, not transport convenience. Deadband settings help with noisy analog signals. Instead of sending every small movement in a temperature or pressure value, the connector publishes only when the value changes by a meaningful amount and the threshold should come from process knowledge, not from somebody guessing how much traffic the broker can tolerate. Rate limit solver related problem, a source can produce more events than a downstream consumer needs. It's decided to publish no more than one routine value per interval while still sending any threshold, breach or quality change immediately. That rule needs to be visible and documented because a rate limited signal is no longer a full record of every source change. There is no universal setting, fault codes may require every change, utility values may work well as periodic readings, and high frequency waveforms may need a local calculation before any message leaves the edge. The signal contract should state which behavior applies and why. At this point the connector has done its work and approved OPC UA notification has become a structured MQTT event with its origin, time, quality and meaning intact enough for other systems to use. Now let's test that design against the packaging cell because this is where clean message contracts meet the messier behavior of a real production process. A packaging cell walk through. Let's put this into one packaging cell and see where the design holds up. Picture a machine that receives filled products, applies the final packaging, checks the label, and sends the finished unit toward palatizing. It reports a machine state, a good part count, a reject count, current speed and fault conditions through its OPC UA server. On paper that looks like five simple signals, but on a real line each one needs context before anyone uses it to judge production. Start with the machine state. The controller might expose a numeric state or a few separate bits for running, faulted automatic mode and ready. The edge contract should translate that into an agreed state model, but it must preserve the source values too. If the machine enters change over, that state needs to travel as change over, not as a generic stop. That changes the downstream interpretation. During a change over, the good part count may stop, the machine speed may fall to zero, and an operator may open guards, load new film, change label stock, or just guides for a new product format. None of that automatically means loss production time. If your event stream sees only speed equals zero, it will often create false downtime, and that is how a dashboard can look very precise and still be wrong. So the packaging cell needs an explicit change over state, either from the machine, the MES, or a controlled operator event. The source depends on the plant, but what matters is that the production calculation can tell the difference between a planned format change and an unexpected fault. Now look at short interruptions. Packaging equipment can stop for very brief periods, a carton misfeeds, a sensor misses a product, or a downstream conveyor blocks for a moment. The machine stops, recovers, and runs again before anyone has time to open a maintenance ticket, and those microstops can matter because repeated short stops can reduce output long before a major fault appears. But sending every pulse, state, flicker, and sensor edge to the cloud may create a noisy stream that nobody can interpret. The edge can help by keeping the detailed signal evidence locally while creating useful events upstream. For example, it can detect repeated stop and run cycles within a defined time window and publish a microstop summary that carries the asset ID, the time window, the number of interruptions. The total stopped time and the dominant reason if the machine provides one. The rule needs agreement from production and maintenance. A five second interruption may count as a microstop on one process and mean nothing on another. There is no universal threshold hiding in a vendor manual. Fault events need more detail than routine state changes. When the packaging machine enters a fault state, the event should include the fault code, source time, machine identity, and source quantity. If the machine provides an alarm class or severity included and if the machine can expose a current job reference that can travel to, but label it as machine reported context rather than assuming it is the final authority for the active order. That distinction saves travel later. A fault event might report that the label detected missing labels. Maintenance can use the code to begin diagnosis and production can see that the cell cannot produce finished packs. Yet the full order impact still depends on the M.S. record of the active operation and the latest execution state. The machine tells us it stopped, but the wider production model tells us what it interrupted. Reject data follows the same pattern. A reject counter can show that units left the normal flow, but it may not tell you which product variant they belong to, which batch produced them or which inspection point caused the rejection. A reject from an in-line vision check may have a different meaning from a reject caused by a packaging seal check. The event needs a clear source reference and time and later in the data flow, it can link to the product variant, batch and process step that applied during that period. But later link matters because packaging cells may switch products, materials and label formats during the same shift. Speed brings another trap. A speed value can help show whether the machine runs below its expected rate, but expected rate changes with the product, pack size, setup and sometimes the material. Comparing every run against one nominal maximum speed produces a neat performance metric and a fairly poor production conversation. The cell needs a product aware target from the process definition, not just a fast number from the controller. So this small packaging cell produces a useful pattern, state events tell us whether the machine can run, counts show output, rejects show losses, speed shows behavior against an agreed process expectation and faults provide evidence for maintenance. Each event needs a source, a timestamp and a meaning that can survive beyond the machine. Once the cell publishes those events locally, the next question is how they leave the site and reach Microsoft fabric without losing that meaning on the way, getting events from the site to Azure and fabric. So the packaging cell is already publishing approved events locally that handles distribution within the plant, but it does not put anything into Microsoft fabric yet. Now here's the cloud bridge. Its job sounds simple in theory. Grab selected events from the site, push them through an authenticated outbound connection and land them in the cloud without losing the evidence you need to make sense of them later. There are a couple of common Microsoft patterns to pick from. With Azure IoT operations, a data flow at the edge can subscribe to local MQTT topics and forward selected events to a cloud destination that keeps the local broker as the source for site events while the data flow decides which events leave the plant and what shape they take. With Azure IoT Edge, the usual path goes through IoT Hub. Edge modules send telemetry upstream, IoT Hub receives it and downstream consumers read the event stream through the compatible event hubs endpoint or a configured route. Both patterns can reach fabric. Neither one gives you production context by itself. The choice should follow the edge design you already made. If the plant uses Azure IoT operations as a site data layer, then use its data flows and broker integration as part of that operating model. If you have a focused IoT Edge gateway connected through IoT Hub that can still work fine for a defined workload, don't create two cloud paths for the same event unless you have a clear reason. Duplicate paths look harmless in a proof of concept. Then one path gets a schema update, the other gets a different retry rule and two dash boards start disagreeing about the same machine stop. The factory does not need another argument about which number is correct. Once events arrive in Azure, fabric event stream works as a streaming intake and routing layer. It can consume data from supported streaming sources, apply light shaping where that makes sense and send the stream onward to fabric destinations. Think of event stream as the hand off point into fabrics real time data services. It receives events in motion and directs them to places where they can be stored, queried or used by downstream processes. Before connecting it though, you have to deal with the unglamorous work. Identity, network access and delivery monitoring. The edge host or edge cluster needs a narrowly scoped identity for the cloud destination. Avoid shared connection strings that get copied between sites, environments and applications. When one of those ends up in a config file or a support ticket, you have no clean way to know who used it or what else it can reach. Use separate credentials or managed identities where the services support them and restrict each one to the smallest set of permissions needed. A site that can send telemetry does not need broad rights to read other sites data, administer fabric workspaces or change cloud resources. Network egress needs the same discipline. The plant network team should know exactly which outbound destinations the edge layer requires. The cloud endpoint, the protocol, the ports and any proxy or name resolution dependency. If the path crosses a DMZ, tested under the actual rules rather than assuming a successful laptop test proves the production route works. Consumer isolation also matters after the messages reach the cloud. Several consumers may need the same source stream. One may feed fabric. Other may support a historian, a quality application or an operational archive. Give those consumers independent positions where the transport supports it so one slow or broken consumer does not interfere with another team's data path. That separation gives you cleaner incident handling. If the fabric consumer stops reading for a while, you should be able to see its lag, reconnected and assess the affected time range without changing the source connector or interrupting local users. A data pipeline needs the same operational visibility as any other production service. Watch delivery, not just connection status, a green connector status can hide a growing queue, delay events, rejected messages or a consumer that has silently stopped moving data. Measure the age of the newest received event, the gap between source time and cloud arrival time, error counts, retry activity and backlog size were available. Those checks tell you whether the data is still useful for the decision it was meant to support. Design for duplicates from day one. Reliable message delivery often means an event can arrive more than once after a reconnect or retry that is not automatically a fault. It becomes a problem when a downstream calculation treats every arrival as a new machine stop, a new reject or a new production count, give events stable identifiers where the source can provide them. Preserve sequence numbers when they exist. Combine acid identity, event type, source time and source sequence carefully when you need a deduplication rule. Then test that rule with real replay scenarios, not just a happy path stream, delayed events need equal care. A fault that occurred during a site outage may arrive after production has already moved on. Fabric should still store it as a historical event but the alerting or operational logic must know it is late. Otherwise a technician gets a new alarm for a problem that someone fixed an hour ago. Arrival time and event time both belong in the message path. With that in place the data has crossed from the factory into fabric without pretending that delivery equals meaning. Next we can follow the stream inside fabric and look at what event stream should handle and what it should leave alone. Fabric event stream, routing, not manufacturing context. Once the event reaches fabric, event stream gives you a place to receive it, apply basic stream processing and send it to one or more destinations. That is useful. It is also where teams can give event stream too much responsibility. Event stream works well for actions close to the moving data. You can filter out messages no consumer needs, select or rename fields, split streams based on content, apply straight forward transformations and send different event types to different fabric destinations. For example, a site may send state changes, fault events, counters and condition readings through one controlled intake path. Event stream can root fault and state events toward a low latency operational path, while also sending selected data to a longer term history path. That fan out is a sensible design. The maintenance team may need recent fault events quickly. A reliability engineer may need months of condition history later. Finance may only need a daily measure of energy per finished unit. Those are different uses of the same source data and they do not need the same refresh rate or storage pattern. Keep the routing decision close to the event purpose. A fault event might go to a live analysis destination with little delay. A high volume routine measurement might go through a filter or aggregation first. Raw source events may also need a protected landing route, especially while the team is still learning how the machine behaves. That last point matters more than it sounds. If you transform an event aggressively at the first step, you can lose the evidence needed to challenge your own assumptions later. Someone may decide a state transition is irrelevant, filter it out, and then discover months later that the missing transition explained a recurring production loss. Preserve recoverable source data before you start simplifying it. This does not mean you must keep every bite forever. It means retention, filtering and aggregation need an explicit reason. You should know what remains available for investigation, how long it remains available, and which transformation created a derived event or measure. Event stream can also handle light cleanup that prevents obvious friction downstream. You may discard a field that no approved consumer can use, standardize a field name, filter out known test messages, or separate a machine event stream from a stream of connector health messages. Those are contained jobs they are easy to test, complex production logic belong somewhere else. Suppose you need to decide whether a machine stop counts as planned downtime, an equipment failure, material starvation, or a change over delay. That decision may depend on machine state, shift plan, MES execution events, operator input, and an agreed loss model. Trying to bury that rule in a streaming canvas usually creates logic that becomes hard to inspect, change and govern. It may work right up until the next product launch, line rebuild, or shift pattern change. Keep event stream focused on stream handling. Put business rules where the domain team can test version explain and own them. Schema variation is another issue that appears quickly in industrial data. A connector may send one shape for a simple state change, another for an OPC UAL arm, and another for a batch of measurements. A machine supplier may add a field after a firmware update. One older asset may represent a value as text, while a newer asset sends a number. Jason makes this look flexible at first, then a downstream table, query or transformation, expects one shape and meets another. You need a deliberate approach here. For mixed event types, keep a clear event type field and a stable envelope around the payload. The envelope can carry common facts such as event ID, asset ID, source time, arrival time, quality, and contract version. The payload can retain source specific detail without forcing every signal into a giant flat record full of empty fields. When a schema changes, treat it as a control to change. Ask whether existing consumers can handle it. Decide whether a new version is needed. Test the change with representative production messages. Do not wait for an overnight failure to discover that a fault code arrived as a nested object instead of a string. There is also a practical limit to no code transforms. They are helpful for simple rooting and shaping. But once you need state for logic, difficult joints, historical correction or complex quality rules, move the work to a place built for that job. Otherwise the stream turns into a not a visual rules that only one person understands, and that person is always on holiday when it breaks. So treat fabric event stream as a controlled front door and routing layer for events in motion. It can receive, filter, shape, and direct industrial data with very little delay. It cannot decide what a machine fault means for production, simply because the fault reached fabric quickly. For live investigation of those events, event house and its KQL database usually fit the next part of the path better than a lake house alone. Event house and KQL for live industrial events. If you are working with live industrial events, event house is usually the next place to look. Event house is fabric's container for real time event analysis. Inside it, a KQL database stores the events and lets you query them with custochury language. KQL for short. The question it answers is straightforward. What happened on this asset during this time window and what changed around it? That fits factory telemetry really well because machine data shows up as a stream of time-stamped events. Event flips from running to blocked, a fault code fires, a temperature drifts outside an expected band, a counter stops climbing when the schedule says it should be producing. You can dig into those patterns without waiting for a scheduled data load. KQL is built for asking questions over events and time. You filter for one asset, look at the last hour group events into time intervals, compare recent behavior with earlier periods, and trace a sequence of state changes. For example, say the packaging cell stops. A production engineer wants to know whether the stop started with a fault, whether the machine moved through a blocked state first, and whether similar stops happened during the same shift. That is a time series question. The engineer doesn't need to extract a file, wait for a batch job, and hope the latest refresh finished. They need to query the recent event history, isolate the cell and inspect the sequence by event time. Event house can support that kind of investigation. It's well suited to recent machine states, alarms, condition readings, connector health events, any data that arrives continuously and needs fast analysis. But fast queries only help if the event design supports them. If every incoming message lands as an unstructured block of JSON with no consistent asset identifier, event type, timestamp, or quality field, the data may be present but awkward to use. You end up spending your time unpacking payloads instead of answering production questions. A useful event house table keeps the common event facts easy to query. That usually includes the stable asset ID, event type, source time, fabric arrival time, source quality, contract version, and a source reference. The raw payload can stay available as evidence, while the fields that operations repeatedly need sit in a consistent form. That gives you both speed and traceability. Say a supervisor asks, which machines entered a fault state during the last shift and how long did each one stay there? With a clear state event structure, KQL can retrieve the relevant transitions quickly. If the answer looks wrong, the team can still inspect the original source payload and trace it back through the edge path. That's a much better position than arguing over a chart with no source evidence. Retention needs a decision too. Event house works best when you treat it as a live and recent event store for questions people genuinely ask. How much recent history should stay immediately available depends on the operation? Maintenance may need weeks or months of recent fault history. A shift team may focus on the current shift and recent days. Engineering may need longer windows for some condition signals. There isn't a standard number that fits every event type. A high rate measurement retained at full detail for a long period can consume capacity without helping anyone. A fault event or state transition carries far more operational meaning per record and may deserve longer immediate retention. That retention based on investigation needs legal or quality obligations, event volume and cost, then review it after people start using the data. Anomaly detection can also run against time based data in event house. This is useful when you have a defined signal problem. A temperature drifting from its normal pattern and unusual vibration trend or a machine cycling between states more often than expected. But the wording matters. And anomaly means the data differs from an expected pattern. It does not diagnose a root cause. It does not prove a bearing will fail. It does not create a maintenance plan. A detection result should begin in investigation. If a vibration trend looks unusual, the maintenance team still needs asset history, process conditions, inspection evidence and their own knowledge of the equipment. An anomaly tool can point attention toward a problem. It can't replace the work of determining whether the problem is real and what action is safe. Use it whether signal, baseline and response are clear. For example, a known process temperature may have a normal range that changes by product and operating state. If the data model captures those conditions, a detected deviation can become a useful event for engineering review. Without that context, the system may simply alert whenever the plant runs a different product. That is not intelligence. That is a calendar problem wearing an AI label. So event house and KQL give fabric a strong place to store and investigate live industrial events. They support rapid questions over false states, thresholds and time windows while retention keeps the live store tied to real operating needs. Still, live event analysis is only one part of the data path. Some questions need longer history, broader joins and slower engineering work. That brings us to the lake house path next. The two speed data path, event house and lake house. Most factory data platforms need two different paths after ingestion because live operations and long term analysis ask different questions. Event house supports the live path. It keeps recent events ready for fast investigation, operational queries and responses that need to happen while a shift is still running. A fault, a state change or a missing count can enter the event store and become available for a new live operational view. Lake house supports the longer path. It keeps durable history in a form that engineering, data teams, quality teams and planning teams can work with over time. That includes historical telemetry, production records, maintenance history, material data and derived measures that need more involved processing than a live event query. The same machine event can belong in both places. That isn't wasteful duplication for its own sake. It gives each destination a job. The event house copy supports the person asking about the last few hours. The lake house copy supports someone asking whether a fault pattern changed across several product variants after a maintenance action over a season or across sites. Those questions don't need the same speed. A shift supervisor may need to know that a packaging cell stopped and hasn't returned to running. A reliability engineer may need to analyze months of vibration trends alongside work orders, spare part changes and operating conditions. Trying to force both questions through one storage and query pattern usually creates a compromise that does neither job well. So think of it as a two-speed path. The fast path receives event data that supports live operational awareness. It stays focused on state changes, alarms, recent condition signals and the data needed for quick queries. Retention and table design should support the time window people use during operations. The slower path receives data for durable history, broader analysis, engineering work, machine learning preparation and cross-domain reporting. It can absorb transformations that take more time, historical corrections and joins across data sets that don't arrive at the same moment. That separation also keeps us honest about the word real time. Not every production question needs an answer within seconds. A daily production review, a capacity analysis or a model training pipeline can run later without reducing its usefulness. If you push every one of those jobs into a low latency path, you spend more effort and capacity without helping the decision. Real time should follow the decision, not the technology demo. The data design must stay consistent across both paths. If an event appears in event house and lake house, both copies need the same stable identifiers for the asset, event, source system and source time. Without that consistency, the live fault record and the historical fault record become two versions of the same event that don't join cleanly later. That becomes painful during an investigation. A team may identify a stop in the live path, then move to longer term data to see whether it repeats. If the asset ID changed between destinations or if the timestamps use different rules, the team spends time reconciling the pipeline instead of studying the machine. Carry the event identity through the whole journey. The source timestamp should remain intact. The arrival time at the edge, cloud and fabric can remain available where it helps diagnose delay. The contract version should travel with the record. And if the connector generated a sequence number or stable event ID, preserve it. These are the details that let you trace one event through both paths without guesswork. Storage lifecycle needs an explicit plan too. Raw data rarely needs to remain at full resolution forever. Some sources produce a high rate of readings that become less useful as they age. After a defined period, you may retain daily or hourly summaries while moving the raw records to lower cost storage or removing them when policy allows. But don't downsample blindly. You may safely summarize a routine temperature trend for some use cases. You may not safely summarize traceability events, quality records or fault transitions where the exact sequence matters. Retention depends on operational questions, quality obligations, investigation needs and the cost of keeping data available. Write those decisions down per event type, which data stays hot for live investigation, which data moves into durable historical storage, which events remain at full detail, which values can become a 5 minute, hourly or daily aggregate after a set period. And when someone challenges a production number, can you still find the source evidence behind it? That is the purpose of the two speed path. Even Tows gives you a place to ask live questions without waiting for a batch process. Lake House gives you the history needed to learn, compare and improve over time. Yet neither destination knows which order a machine was running, which product variant applied, or what a stoppage means for the plan. The events have arrived, the production context still sits elsewhere, the context gap inside fabric. So here's the problem, most manufacturers don't talk about. Once telemetry reaches fabric, it knows a few things with confidence, a value when the source reported it which asset or connector sent it, and for fault events, maybe the code and machine state around the stop. That's useful, but it still leaves the production team with unanswered questions. Picture this, a fault event from the packaging cell lands in Event House at 10 past 11, the machines in a faulted state, the good part count stopped, and the source reports a label feed alarm. Fabric stores all of that cleanly, but none of those facts tell you which operation the machine was performing, which work order it interrupted, or whether the delay puts a customer delivery at risk. The machine event describes an asset condition. Production meets to understand a production consequence. Now that event context usually lives in the manufacturing execution system, the MES. The MES knows what work is executing on the shop floor, the active operation, work order, production status, operator activity, quantities reported, and the timing of production events. It gives the machine event a place in the execution story. If the MES records that packaging cell for began operation 30, on work order 4827 at 10 o'clock, a fault at 10 past 11 becomes more than an isolated machine problem. It may now link to a specific operation, product, quantity, target, and execution state. Even then you need to handle time carefully. The MES might receive confirmation events after the physical machine event, an operator reports a change over late, or a work order appears active while the machine is actually being cleaned or waiting for material. That's not a reason to ignore mess data. It's a reason to treat the timing and authority of each fact with care. The MES tells you what production intended and recorded at the execution layer. The machine tells you what the asset reported. A good model keeps both pieces of evidence rather than forcing one to overwrite the other. Then there's the ERP system. Enterprise resource planning holds the planning and commercial side. Command, planned orders, rootings, due dates, material commitments, and often the broader supply picture around the work order. That context changes the question entirely. A machine stop, during a low priority internal replenishment order, is one kind of problem. The same stop during a late customer order, where the next operation depends on that output, and a material substitution needs approval, creates something completely different. Fabric can bring the ERP data close to the event data, but it doesn't become the owner of the ERP facts just because it copied them into one lake. The ERP stays the authority for the plan, demand, and formal order commitments. Fabric provides a place to combine those facts with telemetry for analysis and decision support. Maintenance adds another layer, a computerized maintenance management system, CMS, or an enterprise asset management system carries information neither the MES nor ERP normally own. Asset structure, maintenance plans, known failure modes, prior work orders, service history, and the approved response procedure for an alarm class. So when the label feed fault arrives, maintenance needs more than a chart of fault codes. They need to know whether the feeder has shown the same pattern recently, whether a preventive task is overdue, whether the alarm relates to a known component, and whether a technician needs a permit, spare part, or machine safe isolation procedure before touching it. The event starts the conversation. The maintenance system provides the maintenance context. Now this is where many fabric designs run into trouble. The data team can often connect the sources and join them by time. The fault at 10 past 11, the MES operation record overlapping that time, the ERP work order linked to that operation. So the model creates a connection. It may even look convincing. But time overlap is not proof of a business relationship. A machine might report a delayed event after reconnecting. The MES might close one order and open another around the same time. A cell could process rework, samples, or test units that don't follow the normal order flow. A clean looking join can still connect the wrong fault to the wrong order. That's why the event needs stable identifiers wherever the source can provide them. And why the context model needs explicit rules for how machine events relate to execution records. Sometimes the right answer is a direct identifier. Sometimes it's a controlled time window rule with a confidence level. And sometimes the data isn't sufficient. And the system should say so. That's better than quietly inventing certainty. The next step is to define the context that turns this event from a machine record into an input for a production decision. Production context, product process resource. Production context starts with four connected things. The product, the process, the resource, and the order currently moving through that process. The product is more than a material number in ERP. It can mean a specific variant batch pack format revision recipe, quality rule, and customer requirement. A packaging machine may run the same basic product family all day, but one variant needs a different label, carton, ceiling temperature, or inspection rule. That changes how you read the machine, Deuter. A reject count of 10 units means one thing for a low volume regulated batch and something else for a high volume standard run. A speed of 60 units per minute may be normal for a large pack and poor for a smaller format. The number doesn't explain itself. The product context tells you what the number should mean at that moment. Then you have the process. It describes the work required to turn the product into the next valid state. In discrete manufacturing, that may be a rooting with defined operations. In a batch process, it may be a recipe phase, a process step, or an inspection stage. Either way, it tells you what should happen in what sequence and under what conditions. For the packaging cell, the process might include feeding the product, applying the label, sealing the pack, checking the label, and releasing the finished unit. Each step carries its own cycle expectation, setup requirement, quality check, and completion rule. That detail matters when the machine stops. If the fault happens during label application, you may have a packaging issue. If it occurs after a sealing step, but before final inspection, you need to understand the status of units already in the cell, were they completed, rejected, held for review, or still physically inside the machine. A simple machine stop does not answer that. The process gives the stoppage a place in the work sequence. Now at the resource, a resource is not just the machine. It includes the tool, fixture, mold, test station, material interface, and sometimes the worker skill needed to run or change it. A resource can also include a shared constraint. One label printer that supports two lines, or one specialist who can approve a product change. This is where planning becomes more difficult than moving a work order from one machine name to another. Imagine the packaging machine fails. Another machine may appear capable of handling the same product, but does it have the right tooling installed? Is the correct film available at that cell? Can it meet the required inspection rule? Is a qualified operator on shift? Does moving the work create a conflict with an order already running there? Capacity is always conditional. A resource may have physical capacity, but not qualified capacity for this product and operation at this time. That is why a resource model needs to describe capability and constraint. It's just an asset ID and a nominal rate. The fourth part is the order. The order connects the planned work to actual execution. It tells you which demand the factory intends to satisfy, how much needs to be produced, what has already been reported, what remains, and where the work sits in the production flow. But orders have two different lives. The planned state comes from the scheduling and planning side. It may show that an order should run on a given machine during a given period. The actual state comes from execution. It tells you whether the order really started, whether the operation paused, whether quantities were confirmed, and whether someone changed the sequence on the floor. Those two views often differ. That is normal. A plan is an intention under constraints. Execution is what happened in the presence of real machines, real materials, and real people. The architecture needs both because neither one replaces the other. There's another complication. These relationships change over time. During a change over the same machine may switch from one product variant to another. A tool may be removed. A worker might move to a different cell. A planner could reschedule an order after a fault. If your model assumes a machine belongs to one product or one order for an entire shift, it will create wrong links at exactly the moments when people need trustworthy answers. So the context model needs effective time. It needs to capture not just that a resource can run a product, but when that capability applied. Not just that an order belongs to an operation, but when that operation became active on a specific resource. Not just that a quality rule exists, but which version applied to the batch being produced. This sounds detailed because it is detailed. Production changes over time. Once you can connect product, process, resource, and order around an event, the fault code becomes useful. It can point to a stopped machine during a defined operation on a known product variant against an active order with a specific set of feasible constraints around recovery. That context shouldn't live as a clever calculation hidden inside one dashboard. It needs to be placed deliberately in the architecture where contextualization should happen. So once you accept that production context changes over time, the real question becomes where each part of that context belongs. Teams usually try to solve it in one spot. They either put everything at the edge or push every join into fabric. And both approaches cause problems because context moves at different speeds, has different owners, and exists for different reasons. Let's start with the edge. The edge should enrich an event with facts it already knows locally and needs right away. That could be the site ID, the local asset ID, a connector ID, the OPC UA node reference, an engineering unit or a machine state mapping the OT team has approved. Those facts travel with the event from the very beginning. Say a connector picks up a fault state from a packaging machine. It can attach the agreed asset ID and tag the signal as a fault state event while keeping the original fault code timestamp and quality status. That way every downstream consumer gets a consistent minimum record, even if the cloud path gets delayed. But the edge shouldn't become a shadow ERP or MES. It should not carry a copied set of work orders, routing, shift plans and maintenance history just because someone wants every event fully decorated before it leaves the site. That leads to stay a local reference data, difficult updates and a second source nobody formally owns. Keep local enrichment close to what the local system can know with confidence. The streaming layer can add another level of context. This works when you need a current operational lookup and the reference data is small enough, stable enough and refreshed well enough for the purpose. A practical example might link a machine event to a currently active cell, line or approved asset class. And attach the current shift based on a govern shift calendar, it may also apply a known mapping from a fault code to a common failure category, if maintenance owns that mapping and the rule is controlled. That can support a live operational question without waiting for a large batch process. Still, be careful with live joins that look more certain than they are. If a streaming process links an event to an active work order, it needs clear rules for late messages, overlapping execution records and order changes during a shift. The system should record how it linked the data, not quietly turn a best guess into effect. Then you have the lake house or warehouse layer, this is where slower domain joins and historical correction belong. A machine event can join with MES execution history, ERP order and routing data, maintenance records, quality results and material information. These joins can take time because they need checks, effective dates and sometimes correction when a source system posts a late transaction. That's fine. Not every answer needs to arrive within seconds. Suppose a quality engineer investigates a rise in rejects over several weeks. They need the product variant material batch operating state inspection result and maybe a maintenance action that happened before the rate changed. This is not a job for a thin event payload or a fast stream rule. It needs governed historical data and a transparent transformation process. The source systems must retain ownership. ERP owns the formal order, material and routing facts, MES owns execution facts, engineering owns equipment capability and process definitions. Maintenance owns asset records and service history. It can hold copies for analysis and connect the dots between IT and OT but copying a record into fabric does not transfer authority over its meaning. That distinction prevents a lot of quiet conflict. When an order status differs between a report and the MES, the team needs to know which system can correct it. When a machine capability changes, engineering needs a controlled way to update it. When a failure category changes, maintenance needs to approve the new definition. Fabric should carry identifiers in the event payload. These identifiers let the platform retrieve or join the governed meaning from the right source. The payload might include an asset ID, operation ID, work order reference when available, product reference and contract version. But an identifier is not the full definition. It points to the definition, the current or historical version of it and the domain owner who can explain or correct it. That approach keeps messages compact while avoiding a pile of copied reference data that drifts apart over time. So place context based on when it is needed, who owns it and how often it changes, put immediate local facts at the edge. Use streaming enrichment for controlled live lookups, use the lake house or warehouse for broader history and domain joins. Keep authority with the systems that run the business process. Then when relationships become more complex than a few joins can express clearly, you need a model that holds those relationships directly. Digital Twin and Knowledge Graph, different jobs. Once you need to hold changing relationships across assets, orders, processes and rules, normal table joins can start to feel fragile. They still work for many cases, but A join only answers the relationship you designed for at that moment. A factory often needs to ask new questions later and those questions cross the boundaries between maintenance, production, quality, engineering and planning. That's where digital twins and knowledge graphs become useful, but they solve different problems. A digital twin models a physical environment. In manufacturing, that may mean a site contains an area, the area contains a line, the line contains cells and each cell contains assets. The model can also describe properties and states such as whether a machine supports a product family, whether a tool is installed or whether a cell currently reports a blocked condition. It creates a digital representation of the physical world and its structure. Think about a packaging cell. A digital twin can describe the packaging machine, the labeler, the inspection unit, the conveyor and their place in the line. It can record that the labeler connects to the packaging machine that both belong to the same cell and that the cell supports a defined set of formats. That gives machine events a physical home. A fault does not arrive as an isolated record with an asset ID that only means something to a few people. It connects to a machine inside a cell on a line at a site. You can then ask questions at the right level, is this one machine faulted? Is the cell constrained? Are several assets on the same line reporting a related condition? A knowledge graph goes further across the operational domain. It holds facts and links between many types of things, not only physical assets. A graph can connect a packaging machine to an operation, the operation to a work order, the work order to a product variant, the product variant to a quality rule and the quality rule to an inspection event. The graph focuses on relationships and the meaning of those relationships. For example, a machine may be capable of running a product but only with a specific tool. That tool may be installed only during certain periods. The product may require an inspection step before release. A work order may use that product but the order may move to a different cell after a reschedule. A graph can represent those links directly with their types and effective dates. That matters because production questions rarely stay inside one source system. A planner might ask which current orders are exposed if a machine remains unavailable. A maintenance engineer might ask which product families depend on an asset with a repeating fault. A quality lead might ask which released batches passed through a cell during a period of unstable process conditions. These are relationship questions. Neither model appears automatically because you collected a lot of tags. Telemetry can tell you a machine name, a node ID, a timestamp and a value. It can't reliably infer that a machine supports a certain product that a fixture is required for a root step or that a quality rule changed last month. Those facts come from engineering, MES, ERP, maintenance and people who understand the process. Someone has to model them. Someone has to own them. Microsoft Fabric includes digital twin builder in preview as one root for modeling and ontology, which is a formal model of the things in a physical domain and how they relate. It can help teams map source data into a shared model and use those links alongside fabric data that does not give you a finished factory model. A tool can help store query and work with an ontology. It cannot decide what available capacity means in your plant whether a change over counts is planned downtime or which machine and tool combination is qualified for a regulated product. Those decisions remain domain work. I'd start much smaller than most architecture diagrams suggest. Make one decision path. Maybe it is the question of how a machine fault affects the active production operation. Then model only what that question needs. The asset, the sell, the operation, the order, the product and the rules that determine whether another resource can perform the work. Make those relationships trustworthy first. Once the model supports one real decision and people can correct it when the plant changes, you have a foundation worth extending. If you start by trying to create a complete digital copy of the enterprise, you'll spend a long time naming things while the production team still has no answer when a machine stops. The model should earn its detail through use. That brings us back to the original stoppage. We now have the event path and a way to model the relationships around it. Next we can reconstruct the stoppage as a production problem rather than just a machine alarm, reconstructing the stoppage with context. Think back to that packaging machine fault at 10 past 11. The event arrives in Event House with a stable asset ID, the label feed fault code, the source timestamp, source quality and the original OPC UA reference. So now you have a trustworthy statement from the machine. This asset entered a faulted condition at that moment and with that you can ask better questions. The context service or governed data model checks which production operation was active on that asset when the event fired, finds the current execution record from the MES and links the fault to the work order and product variant the cell was processing. That link needs rules. If the MES record covers the event time and the execution status supports it, the system connects the fault to that operation with confidence. But if the machine event arrived late after a network outage or two execution records overlap during changeover, the model should keep the link uncertain until someone or another source resolves it. A system that admits uncertainty is more useful than one that invents precision. Assume the active operation is confirmed, the fault now connects to a work order for a product that needs a specific label stock, inspection setting and packaging format. The machine never reported any of that. The wider production model supplied it. That changes the conversation from "machine 4 has a label alarm" to "the active packaging operation for this order has stopped" and the next process cannot receive finished packs from this cell. Maintenance needs its own branch of context. The fault code can link to the asset record in the CMS or EAM system which may show prior incidents, the last service activity, known fault causes, spare parts and the approved procedure for working safely on that part of the machine. Notice what the system is doing here. It isn't diagnosing the machine from a dashboard. It's bringing the technician the evidence that belongs with the fault, including the source event, the asset history and the response procedure that maintenance owns. A repeated label feed code after a recent component replacement might point to a setup issue, a material issue or a faulty replacement part, the data can narrow the search, but a qualified technician still decides what to inspect and what work is safe. Planning follows a different path. The production event can now expose the affected operation, remaining quantity, due date and downstream dependency, so a plan I can ask whether the order can move to another resource without creating a larger problem somewhere else. At first, that sounds like a simple machine substitution, but it rarely is. The alternate machine may support the product family but not the exact packaging format, or it may need a tool already in use. The right label stock may still sit at the original cell, a skilled operator may not be available, and moving the order could delay another order with an earlier customer commitment. This is a feasibility problem and fabric can bring together the facts needed to frame it. Current asset status, order state, resource capability, tooling, material and time. A specialized advanced planning and scheduling system, often called APS or an optimization engine, can then evaluate feasible reschedule options against the full set of constraints. Keep that split clear. A data platform can tell the planner which work is exposed and what constraints appear relevant, support scenario inputs and record the outcome. But it doesn't automatically become a scheduling engine just because it can query the data quickly. For some plans, the next action may be simple. Control the operation, call maintenance and notify the supervisor because no alternate resource exists. For others, the system may identify two candidate cells. One can run the product after a short change over and the other has immediate physical capacity but lacks the required inspection setup. The planner can compare those options with the actual production rules in view rather than calling around the plant with partial information. That is decision support. It doesn't mean an automated reschedule should release work to the shop floor without approval. The cost of a wrong recommendation can include material loss, missed quality controls, overloaded resources and a plan that looks clever and software but fails when it meets the physical line. The event also creates a shared timeline. Production sees the interrupted operation, maintenance sees the fault in approved response and planning sees the order exposure and resource constraints. Each team still owns its part but they now work from linked evidence instead of separate timestamps and phone calls. That is the practical value of production context. A fault code alone tells you that a machine needs attention but a fault code connected to the operation, order, product, resource constraints and maintenance history tells each person what they need to consider next. And that same discipline matters when teams calculate OEE because counters and machine states can look objective while hiding a lot of unagreed business rules. OEE needs rules not just counters. Overall equipment, effectiveness or OEE looks simple when you write the formula down. The probability times performance times quality. The trouble starts when a team assumes the machine can calculate all three on its own because a counter, a state tag and a speed signal only provide evidence, not the agreed production rules that turn that evidence into an OEE result. Take availability first, a machine can report that it stopped at a given time but that doesn't tell you whether the stop counted as planned downtime, an unplanned equipment loss, a scheduled cleaning activity, a material shortage, a quality hold or a deliberate production pause because the next order wasn't ready. Those categories change the calculation. Imagine the packaging cell stops while an operator performs an approved format change. The machine sees zero speed and no good parts so if the OEE logic treats every zero speed period as unplanned downtime, the availability number drops even though the plant expected and planned the work. On the other hand, if someone labels every stop as change over after the fact, the number can look better without production getting better, which is why downtime categories need ownership, definitions and a controlled way to correct them. The machine state helps establish when the asset could not run. The MES can add execution state and plant activity, operator input may explain a material issue, a safety intervention or an unusual condition that neither system can infer reliably and maintenance records can confirm whether a stop became a failure event and what work followed. Each source brings different evidence and none owns the whole answer. Performance has a similar problem, a controller may report a current speed or a part count, so you can calculate and observe rate from that data. But OEE performance compares actual output with an expected rate and that expected rate must relate to the product and operation running at that time. There isn't one correct rate for a machine across every job, a small pack may move through the packaging cell faster than a large format. A regulated product may require extra inspection, a start-up period after change over may have a different approved expectation from steady production and even the same product can require a different target after an engineering change or a new packaging material. So the ideal cycle time needs a govern source, whether from the MES master data, an engineering standard or a process specification, the source matters less than the discipline. The rule must identify which cycle expectation applied to this product on this operation during this period, otherwise you aren't measuring performance, you're comparing the factory to a number someone chose because it looked plausible in a report. Quality needs the same care. A reject count tells you that the machine diverted units, but it may not tell you whether those units count against finished goods quality.
