Apps that call each other directly break the moment one service is slow or offline. This episode explains Azure Service Bus in plain English for developers and cloud architects: queues, topics, message lifecycle, dead-lettering, sessions and when to pick Event Hubs, Event Grid or Kafka instead. You will understand how to build systems that keep working when things go wrong.

In this episode

  • 00:47 – What a message broker is
  • 02:31 – Anatomy and lifecycle of a message
  • 05:19 – Dead-lettering, sessions, duplicate detection and transactions
  • 08:07 – Service Bus vs. Storage Queues, Event Hubs, Event Grid and Kafka
  • 09:41 – Real-world use cases
  • 12:50 – The big picture: decouple, buffer, route

Key takeaways

  • Azure Service Bus is Microsoft's fully managed message broker that decouples applications so senders and receivers can fail, scale and change independently.
  • Queues deliver to one consumer, topics with filtered subscriptions fan out to many, and features such as dead-letter queues, sessions, duplicate detection, transactions and scheduled delivery handle the hard edge cases.
  • Choose Storage Queues for simple background jobs, Event Hubs and Kafka for high-throughput streaming, Event Grid for lightweight reactive events and Service Bus for reliable business workflows.

Worth quoting

“When two apps are decoupled, they can fail independently. If the receiver crashes, the sender doesn't even notice. The message just sits in the broker waiting.” – Mirko Peters (01:07)

“If you're regularly sending data larger than that, you probably shouldn't be putting it in a message. Store the large data somewhere else and put a reference in the message.” – Mirko Peters (03:57)
