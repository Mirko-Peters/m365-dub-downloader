Vector search that looks cheap at ten million embeddings can turn into a RAM budget crisis at a billion. This episode is for Azure and AI architects building RAG and enterprise search on Azure AI Search, Cosmos DB or SQL Server. You get a practical framework for choosing between HNSW and DiskANN based on scale, update frequency, latency and cost.

In this episode

  • 00:00 – Why the HNSW default becomes a budget problem
  • 04:07 – Vector search and approximate nearest neighbor basics
  • 07:24 – HNSW explained and the memory wall
  • 13:39 – DiskANN architecture and production numbers
  • 20:15 – DiskANN in Azure and the four-variable decision framework
  • 27:19 – RAM vs. SSD cost model and index mutability
  • 33:34 – RAG pipelines, failure modes, metadata filtering and multi-tenancy
  • 54:03 – Evaluation, observability, roadmap and the decision guide

Key takeaways

  • HNSW keeps the whole graph in RAM and is the right choice for smaller corpora with strict latency needs, but at roughly a billion vectors it needs terabytes of memory per replica.
  • DiskANN keeps a compressed navigation layer in RAM and the full graph on SSD, reaching similar recall at a fraction of the memory, with Cosmos DB suited to dynamic data and SQL Server to static data.
  • Index choice drives cost, while answer quality depends on hybrid search, reranking, chunking, chunk-level metadata filters and continuous evaluation and observability.

Worth quoting

“The main reason enterprise rag fails is retrieval, not generation. When your model gives a plausible but wrong answer, it usually isn't because the model invented a lie. It's because the right context never actually made it into the prompt.” – Mirko Peters (37:37)

“The vector index itself should never surface a document the user isn't allowed to see no matter how relevant that document is to the search. Semantic similarity is a great tool for finding information but it is not an authorization mechanism.” – Mirko Peters (47:22)
