## Key takeaways

- DLP policies built to block drive users to invisible workarounds, so design policies that use context and guide people with tips before enforcing.
- Run every policy in simulation for weeks, then with tips but no enforcement, and block only high-confidence, high-volume risks with a reporting path.
- Treat DLP as an ongoing practice with a named owner, weekly tuning from overrides and triage, owned and expiring exceptions, and metrics like true positive rate instead of block counts.

## FAQ

**Why do DLP policies that block everything fail?**

Block-first DLP policies fail because they push people to workarounds the policy cannot see. When an unexplained block stops legitimate work, users switch to personal email, phone photos or USB drives. The data still leaves, only now through channels nobody monitors, while the dashboard keeps showing rising block counts that look like protection but measure only activity.

**How long should a DLP policy run in simulation mode?**

A DLP policy should run in simulation for at least two weeks, and four is better. If the protected data follows a monthly or quarterly cycle, the window should cover one full cycle. Business has rhythms such as month-end finance work and quarter-end contracts, and a three-day test misses those peaks before enforcement meets them.

**What metrics show whether a DLP program is working?**

Track true positive rate, override rate, time to triage and repeat offender rate, plus coverage of sensitive data, instead of block counts. Block counts rise with mail volume and loose rules, so they cannot separate success from failure. Chart each measure weekly and read the trend first, because early numbers before tuning are almost always poor.
