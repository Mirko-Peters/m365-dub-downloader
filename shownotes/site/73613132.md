## Key takeaways

- PCF is not a UI skin but an enforcement layer: once a code component is packaged in a solution it becomes a versioned, traceable dependency that every app inherits.
- Use standard controls first and PCF only for structural gaps, and back every component with a governed catalog, ALM pipeline, managed environments and a review process.
- Citizen developers are not the risk; missing guardrails are, so a federated model with a central catalog lets business users build safely while leadership funds governance as platform infrastructure.

## FAQ

**When should you build a PCF component instead of using standard controls?**

Use standard controls first and build PCF only for a structural gap. The episode names three: complex visualization such as Gantt charts or custom maps, high traffic screens used by hundreds of people daily, and reusable patterns across many apps. Making something look nicer is a preference, not a reason to take on lifelong maintenance.

**Are PCF components faster than HTML web resources?**

Well-built PCF components load 50 to 70 percent faster than legacy HTML web resources and use less memory, because they share the page rendering context instead of running in an iframe. That gain is a ceiling, not a guarantee: bloated bundles, unnecessary libraries and constant re-renders can make a PCF control slower than the native field.

**What does ALM for PCF components look like?**

ALM for PCF means source control, Power Platform CLI builds, build validation and versioned solution pushes through dev, test and production. The manifest version must increment before every push so changes stay traceable and rollback is possible. Production should run managed solutions inside managed environments, and breaking changes should roll out in stages.
