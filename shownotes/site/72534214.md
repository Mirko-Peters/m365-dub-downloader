## Key takeaways

- Sending SharePoint content to cloud AI moves it into logs and legal jurisdictions you do not control, while a local stack with Llama, a vector database and on-premises embeddings keeps every query inside your perimeter.
- Retrieval quality depends mostly on chunking: use heading-aware chunks for Word, page-aware chunks for PDFs, row groups with headers for Excel and slide-level chunks for PowerPoint, and keep source metadata on every chunk for citations.
- Mirror SharePoint permissions exactly by tagging every vector with a permission tier at ingestion and filtering by the user's [Entra ID](https://www.m365.fm/entity/entra-id/?utm_source=podcast&utm_medium=shownotes&utm_campaign=stop-leaking-data-how-to-run-local-llama-on-your-sharepoint-files) groups at query time, backed by local audit logs and regular permission reconciliation.

## FAQ

**Why isn't sovereign cloud enough to keep SharePoint data private?**

Because sovereign cloud is still run by a provider bound to its home jurisdiction. The episode explains that US laws like the CLOUD Act can compel US companies to hand over data even when it is stored in Europe, so contracts and region settings improve transparency but cannot create real sovereignty over your documents.

**What hardware do you need to run Llama locally for a SharePoint RAG pilot?**

A single server with a mid-range GPU can run the whole stack for a pilot. The episode cites guidance for Llama 3 of an NVIDIA GPU with at least 16 GB of VRAM, 32 GB of system RAM and about 50 GB of disk, and notes a small quantized Llama 3 model fits in under five gigabytes.

**How does a local RAG system respect SharePoint permissions?**

The ingestion service reads each document's effective SharePoint permissions and stores a matching permission tier with every vector. At query time, the interface resolves the user's Microsoft Entra ID groups to a tier, and Qdrant only searches vectors at or below it. A second check in the interface and weekly reconciliation catch permission drift.
