## Key takeaways

- Dataverse security decides which rows a user can reach by combining identity, privilege, scope and record ownership, and access is always additive.
- Business units should model real data boundaries such as legal, regulatory or contractual walls, not the org chart, and teams should own long-lived data.
- Sharing, organization depth and one-off roles are shortcuts that erode the model, so roles, teams and profiles belong in solutions with reviews and auditing.

## FAQ

**Why shouldn't Dataverse business units mirror the org chart?**

Because a business unit is a data boundary, not a reporting line. Roles, users and row ownership are all tied to units, so every reorg ripples through access when the tree copies the org chart. Create units only where law, regulation or contracts require data to be walled off, and keep the tree two or three levels deep.

**Why is organization-level access depth risky in Dataverse?**

Organization depth ignores the business unit tree, so the user can reach every row in that table. Admins often raise a privilege to organization depth to close an access ticket quickly, and nobody notices the extra reach. Treat it like a master key reserved for admins, integration accounts and perhaps a data steward or two.

**In what order does Dataverse check whether a user can see a row?**

Dataverse checks the table privilege first, then access depth against the row's owner and owning business unit, then hierarchy security, then shares stored in the principal object access table. Passing any one of those four gates grants access. Column security comes last as a filter that masks secured values on a row the user can already open.
