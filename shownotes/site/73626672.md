As Azure environments grow, per-VM managed disks lead to paying for idle performance while busy workloads hit limits. This episode helps cloud architects and database teams understand Azure Elastic SAN, its building blocks and shared performance model, and decide when pooled block storage beats managed disks.

## Key takeaways

- Azure Elastic SAN pools high-performance block storage so that volumes share IOPS and throughput instead of each VM disk being sized for its own worst-case peak.
- A SAN is organized into volume groups, which hold network and access rules, and volumes, which connect to workloads over iSCSI and whose performance scales with their size.
- Elastic SAN fits groups of SQL Server databases, clustered workloads, Azure VMware Solution and supported Kubernetes designs whose peaks do not overlap, while small or isolation-sensitive workloads are often better on managed disks.

## FAQ

**What is Azure Elastic SAN?**

Azure Elastic SAN is managed block storage that pools high-performance storage for many workloads instead of locking it inside separate VM disks. Volumes connect over iSCSI and look like local disks to the workload. Azure runs the hardware, while you configure capacity, performance, network paths and the volumes inside volume groups.

**How does performance work in Azure Elastic SAN?**

Performance comes from base capacity and is shared across the SAN's volumes. The episode states that each TiB of base capacity adds 5,000 IOPS and 200 MBps of throughput to the pool. A volume's performance also rises with its size, up to 80,000 IOPS per volume, so a tiny volume cannot draw much from a large pool.

**When should I use managed disks instead of Elastic SAN?**

Choose managed disks for a small app server, a VM with steady low storage demand, or a workload that needs strict performance isolation. In those cases they are easier to set up and often cheaper. Elastic SAN pays off when several performance-heavy workloads need block storage and their busiest periods do not overlap.
