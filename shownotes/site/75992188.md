## Key takeaways

- Autopilot rollouts fail at scale because a device is a sequence of dependent steps with different owners, not a thing you configure once.
- Most stalls trace back to networks, group timing, app dependencies or conflicting policies, so name the failing layer before reading logs or chasing error codes.
- Treat every profile, app and update change as a small ring-based deployment, with named owners, rollback notes and metrics such as time to productive desktop.

## FAQ

**Why do Autopilot pilots succeed but large rollouts fail?**

Pilots only test the happy path under controlled conditions: clean networks, hand-picked hardware and patient volunteers. At scale, variance arrives through more hardware models, firmware, proxies, home and hotel networks and users who restart mid-setup. A one percent failure rate invisible across fifty devices becomes one hundred broken laptops across ten thousand.

**Should I use Microsoft Entra join or hybrid join with Autopilot?**

Use Microsoft Entra join unless a specific, named dependency requires hybrid join. Hybrid adds a second chain: line of sight to a domain controller during setup, the Intune connector, a service account with the right permissions, the correct OU and sync between directories. Write each dependency down and ask what replacing it would take.

**Why does the Autopilot enrollment status page get stuck?**

The enrollment status page waits on everything actually assigned and marked as blocking, not the list you intended. Broad assignments and pushed security agents quietly grow that list, so a page built for five apps may wait on fifteen. When it times out, find the last item to report in, and check that prerequisites install first.
