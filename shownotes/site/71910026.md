## Key takeaways

- In distributed .NET systems, a slow dependency often does more damage than a crashed one because waiting work quietly consumes threads, sockets and queue capacity.
- Retries should only be used for brief, random faults; against an overloaded dependency they multiply pressure, so bulkheads and scoped circuit breakers are needed to contain the blast radius.
- Resilience is a business policy: define service quality tiers, degraded modes and per-dependency rules for timeout, retry, breaker, fallback and isolation, then test them deliberately.

## FAQ

**Why is a slow dependency worse than a failed one in microservices?**

A slow dependency often does more damage because a hard failure is rejected immediately while a slow call is admitted and held. Waiting requests keep threads, sockets, connections and request state busy, so throughput drops even when CPU looks calm and health checks pass. Adding replicas only enlarges the waiting room if they share the dependency.

**When should you use retries in a distributed .NET system?**

Use retries only for brief, random faults that are cheap to try again, such as a one-off network interruption, with short bounded attempts, jitter and idempotent operations. Against an overloaded API, slow database or struggling identity service, retries multiply traffic, fire in sync across clients and accelerate collapse, so classify the failure first.

**How does a circuit breaker work and how should it be configured?**

A circuit breaker watches a dependency and stops calls once failures cross a threshold in a time window, then lets a few test calls through before resuming normal flow. Scope breakers per client and dependency path, tune thresholds and sample windows per dependency, and compose a timeout first, then the breaker, then a fallback.
