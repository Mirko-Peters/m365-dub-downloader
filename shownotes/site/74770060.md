In this interview Ian Tweedie explains to Power Platform makers, developers and architects how modular features, server-side logic, Key Vault, Git-based ALM and intent-based governance keep enterprise solutions maintainable.

## Key takeaways

- Low-code is not no-code: once Power Platform solutions become business-critical, classic clean-architecture principles such as single-purpose, decoupled features apply just as in pro-code.
- Business-critical logic should run server side, and secrets belong in a governed store such as Azure Key Vault rather than in reversible places like environment variables.
- Governance works best when it defines intent and lets makers show how they meet it, while source control in Power Platform always means choosing the least-worst option.

## FAQ

**Where should business-critical logic run in a Power Platform solution?**

Business-critical logic should run server side. Ian Tweedie points out that JavaScript in Power Apps or Power Pages runs client side, where users can manipulate it in the browser. If a result must always be accurate, execute it on the server, for example through plug-ins or custom connectors, and then decide whether it needs to run synchronously.

**Should I store secrets in Power Platform environment variables?**

Not as plain values. An environment variable is ultimately a table under the hood, so administrators can read it and it can be exposed by accident. Ian recommends Azure Key Vault, which an environment variable can reference, and an Azure Function behind an API only when you need extra logging, usage limits or a shared service.

**How do you handle source control and ALM for Power Platform with Git?**

You pick the least-worst option, because Ian says there is no perfect way. Ideally each feature gets its own developer environment and Git repository. With a shared build environment, he runs an Azure DevOps pipeline per sprint into test, plus a scheduled export to Git every six hours to track changes.
