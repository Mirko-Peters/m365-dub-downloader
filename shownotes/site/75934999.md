## Key takeaways

- OAuth 2.0 grants an app limited, temporary access through scoped tokens instead of sharing your password, but it does not prove identity.
- The authorization code flow with PKCE is the modern default for user sign-in, while the implicit flow and password grant are deprecated.
- In Microsoft 365, [Microsoft Entra ID](https://www.m365.fm/entity/entra-id/?utm_source=podcast&utm_medium=shownotes&utm_campaign=oauth-2-0-simply-explained) issues the tokens and Microsoft Graph accepts them, with delegated or application permissions granted by least privilege.

## FAQ

**Is OAuth 2.0 a login system?**

No, OAuth 2.0 grants an app access to your data; it does not prove who you are. It is built to say that an app may read one specific thing for a limited time. Identity is the job of a companion standard, OpenID Connect, and developers who skip it may trust a token never meant to prove anything.

**What is the difference between delegated and application permissions in Microsoft Graph?**

Delegated permissions let an app act as you, so it can only reach what you can already reach. Application permissions let an app act on its own with no signed-in user, reaching anything the permission covers across the organization, which is why only an administrator can approve them. Microsoft recommends delegated permissions whenever they are enough.

**Why should the authorization code flow use PKCE?**

PKCE stops an attacker who intercepts the authorization code from cashing it in. When sign-in starts, the app invents a one-time secret and must show it again when it trades the code for an access token. Mobile apps and apps running entirely in the browser cannot store a hidden secret, so PKCE is especially important there.
