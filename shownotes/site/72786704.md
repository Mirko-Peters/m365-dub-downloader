## Key takeaways

- Configuration drift from manual portal changes is a governance failure, and only declarative infrastructure as code makes the actual state visible, reviewable and correctable.
- Bicep compiles to ARM JSON but removes its syntax noise, which is why new [Azure](https://www.m365.fm/entity/azure/?utm_source=podcast&utm_medium=shownotes&utm_campaign=arm-templates-were-a-mistake-lessons-from-the-bicep-shift) projects default to it while legacy ARM templates persist because of switching costs.
- AI agents can generate infrastructure code quickly, but it must flow through policy as code, human review and CI/CD so that automation never outpaces control.

## FAQ

**What is the difference between ARM templates and Bicep?**

Bicep compiles to standard ARM JSON, so every ARM capability remains available, but the authoring experience is far simpler. Keywords like resource, param and module replace deeply nested JSON, symbolic references replace concatenated resource IDs, and the VS Code language server flags errors while you type instead of failing at deployment time.

**Should I use Bicep or Terraform for Azure infrastructure?**

Use Bicep if you are essentially Azure-only and Terraform if you genuinely run workloads across several clouds. Bicep offers day-zero support for new Azure services and fits Azure Policy and landing zones directly. Terraform gives one workflow across AWS, GCP, Azure and third-party services. Many enterprises run a hybrid of both.

**How can AI agents generate infrastructure code safely?**

Treat agent output as a proposal that must pass policy as code, human review and a CI/CD pipeline before deployment. Syntax validation and plans do not catch insecure defaults such as public storage access. Agents should get scoped, short-lived permissions, and every action they take should be logged so decisions can be traced.
