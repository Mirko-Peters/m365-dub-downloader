## Key takeaways

- Factory cloud cost is driven by data movement across boundaries, zones, gateways and return paths, not just by storage.
- Estimate volume from sample rate, payload size and retention rather than device count, and move data only when a named consumer needs it for a named decision.
- Use an edge, site and cloud layer pattern: filter, aggregate and infer near the machine, and send governed operational facts to the cloud.

## FAQ

**Why is my factory cloud bill higher than expected?**

Because data movement, not storage, usually drives the cost. Internet egress, cross-region replication, cross-zone traffic, NAT gateway processing and return paths such as dashboards, exports and restores each meter bytes. One sensor stream can be copied and read many times, so a low storage bill can sit beside a high transfer bill.

**How do I estimate IoT data volume for a factory?**

Count samples, not devices. Multiply samples per second by payload bytes, by the seconds the signal runs, by the number of assets and channels, then add protocol and context overhead. In the episode's example, one vibration channel at 32 kilohertz and two bytes per sample produces about 5.5 gigabytes of raw data per day.

**Which factory data should stay at the edge and which should go to the cloud?**

Raw high-rate data such as waveforms, images, video, debug logs and control-related signals stays local by default, in bounded buffers. Filtered events and aggregates move selectively, while MES shift and order facts, quality outcomes and cross-plant trend data belong in the cloud, because their consumers sit beyond one site.
