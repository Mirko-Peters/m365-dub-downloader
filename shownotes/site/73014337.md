## Key takeaways

- GitOps makes Git the single source of truth for infrastructure, so the cluster always matches what is declared and versioned in the repository.
- In the pull-based model an operator such as Flux or Argo CD reconciles the cluster with Git continuously, which removes drift and keeps cluster credentials out of CI pipelines.
- On Azure, Flux v2 is built into AKS and Azure Arc, so a team can start with one small cluster pointed at a Git repo and gain instant rollbacks and a full audit trail.

## FAQ

**What is the difference between push-based and pull-based deployments in GitOps?**

In push-based deployments a CI pipeline holds cluster credentials and applies changes directly. In the pull-based GitOps model, CI only builds the image and updates a manifest in Git, and an operator inside the cluster pulls that state. A compromised pipeline can then only change a repository, not touch the cluster itself.

**Should I use Flux or Argo CD on Azure Kubernetes Service?**

For most Azure engineers Flux is the natural starting point, because Microsoft built the native GitOps integration in AKS and Azure Arc around Flux v2. Argo CD remains a strong choice when teams want a web UI, a central control plane for many clusters or progressive delivery with Argo Rollouts.

**Does GitOps replace CI/CD pipelines?**

No, GitOps replaces only the CD part. CI still builds code, runs tests, scans for vulnerabilities and pushes container images to a registry. What changes is deployment: instead of the pipeline pushing images into the cluster, the GitOps operator pulls updated manifests from Git, so both work together rather than one replacing the other.
