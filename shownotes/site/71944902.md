## Key takeaways

- Cost alerts and dashboards provide visibility, but only enforcement at the Azure Resource Manager request path, such as Azure Policy deny effects, actually prevents waste before billing starts.
- Encode financial intent as policy: deny high-cost SKUs and regions where they do not belong, use modify to inherit cost tags, and package rules into initiatives assigned through management groups.
- Roll out in stages - time-boxed audit, platform and template repair, deny in non-production, then production with owned, expiring exceptions - and measure prevented cost and cost-weighted adherence rather than [compliance](https://www.m365.fm/entity/compliance/?utm_source=podcast&utm_medium=shownotes&utm_campaign=azure-policy-isnt-enough-the-secret-to-real-time-cloud-savings) percentages.

## FAQ

**Why don't Azure budgets and cost alerts stop overspending?**

Budgets and cost alerts give visibility, but they do not block a single deployment. By the time a report flags an expensive resource, it is already running and billing. The episode treats budgets as signal systems that identify failing patterns, while Azure Policy deny effects enforce what can be deployed at the Azure Resource Manager request.

**Which Azure Policy effects should I use for cost control?**

Use deny for anything never allowed, such as high-cost VM families or premium disks in dev, and modify for cost tags that should be inherited from a resource group. Use deployIfNotExists for supporting controls that need not block creation. Package related rules into initiatives and assign them through the management group hierarchy.

**How do you roll out Azure Policy deny rules without slowing teams down?**

Start with a narrow cost surface like VM sizes, premium disks, allowed regions and cost tags. Run an audit phase with an end date, repair templates, IaC modules and landing zones, and mirror rules in pipeline checks. Then deny in non-production first, and extend to production with exceptions that have an owner and an expiry.
