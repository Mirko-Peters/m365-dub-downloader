## Key takeaways

- An Azure Virtual Network is a regional, private network boundary, and its address space should be planned large enough and free of overlaps before anything is deployed.
- Subnets separate application tiers, private IPs should be the default, and network security groups plus route tables control what traffic is allowed and where it goes.
- VNet peering connects networks privately over the Microsoft backbone but is not transitive, so growing environments typically use a hub-and-spoke design.

## FAQ

**Is Azure VNet peering transitive?**

No, VNet peering is not transitive. If VNet A is peered with B and B with C, A cannot reach C through B; each peering links exactly two VNets. To scale, the episode recommends a hub-and-spoke design where spokes peer with a central hub that holds shared services such as a firewall or VPN gateway.

**How many IP addresses does Azure reserve in each subnet?**

Azure reserves five IP addresses in every subnet for internal purposes such as routing and DNS. A /24 subnet therefore offers 251 usable addresses instead of 256. The episode calls this a common gotcha and advises adding some headroom when sizing subnets, and planning separate subnets for web, application and data tiers early.

**Which address space should I choose for an Azure Virtual Network?**

Choose a private RFC 1918 range that does not overlap with any network you plan to connect, such as your on-premises data center or other VNets. Pick a larger range than you think you need, for example a /16 instead of a /24, because changing the address space after resources are deployed is messy.
