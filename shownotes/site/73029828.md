## Key takeaways

- A network security group filters traffic at layers three and four by source, destination, port and protocol, and it is stateful, free and the first line of defense in Azure.
- Rules are evaluated by priority with the first match winning, so leave gaps between priorities, attach one NSG per subnet and check effective security rules when troubleshooting.
- Avoid opening sensitive ports to the internet, use application security groups and service tags instead of hard-coded IPs, and add Azure Firewall when you need centralized deep inspection.

## FAQ

**Do Azure NSGs need an outbound rule for reply traffic?**

No, network security groups are stateful, so reply traffic for an allowed inbound connection goes back out automatically. If you allow inbound traffic on port 80, you do not need a separate outbound rule for the response. Outbound rules still matter, though, because the default outbound rule allows internet traffic from compromised VMs.

**Should I attach an NSG to a subnet or to a network interface?**

Attach NSGs at the subnet level in most cases, with one NSG per subnet so every VM inside inherits the same rules. Use NIC-level NSGs sparingly for exceptions, such as a database VM needing stricter rules. When combining both, check the effective security rules in the Azure portal to see the result.

**When do I need Azure Firewall instead of an NSG?**

Add Azure Firewall when you need centralized inspection across multiple VNets, controlled internet access, FQDN filtering, TLS inspection or threat intelligence. NSGs are free and filter only at layers three and four, which is enough for small deployments. The episode recommends combining both: NSGs for subnet segmentation and Azure Firewall in the hub for deeper inspection.
