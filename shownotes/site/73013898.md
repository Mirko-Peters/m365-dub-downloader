## Key takeaways

- RAG first retrieves relevant content from your own data and passes it to the model with the question, so answers are current and grounded instead of guessed from training memory.
- On Azure, Azure AI Search indexes and retrieves chunks with vector or hybrid search, [Azure OpenAI](https://www.m365.fm/entity/azure-openai/?utm_source=podcast&utm_medium=shownotes&utm_campaign=rag-on-azure-simply-explained) generates the answer, and Azure AI Foundry wires the agent together.
- Start with your data, get retrieval right before adding the LLM, and choose agentic RAG only for complex questions where accuracy is worth the extra tokens and latency.

## FAQ

**Is RAG the same as fine-tuning a language model?**

No. RAG retrieves relevant content from your own data at question time and passes it to the model, while fine-tuning trains the model further on your data. The episode explains that fine-tuning is expensive, still leaves the model frozen at one point in time and cannot keep up with frequently changing data like pricing.

**Which Azure services do I need to build a RAG solution?**

You typically combine Azure AI Search, Azure OpenAI and Azure AI Foundry. Azure AI Search indexes and retrieves chunks of your documents, Azure OpenAI supplies the model that writes the answer, and Azure AI Foundry is where you create the agent, deploy the model and connect the search index as a knowledge source.

**When should I use agentic RAG instead of classic RAG?**

Use agentic RAG for multi-step, ambiguous or cross-domain questions where accuracy matters more than cost. According to Microsoft tests cited in the episode, it improves answer relevance for complex questions by about 40 percent but uses three to ten times more tokens and adds latency, so classic RAG remains better for routine, high-volume questions.
