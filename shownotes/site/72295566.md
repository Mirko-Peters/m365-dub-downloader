Vector search that looks cheap at ten million embeddings can turn into a RAM budget crisis at a billion. This episode is for Azure and AI architects building RAG and enterprise search on Azure AI Search, Cosmos DB or SQL Server. You get a practical framework for choosing between HNSW and DiskANN based on scale, update frequency, latency and cost.

## Key takeaways

- HNSW keeps the whole graph in RAM and is the right choice for smaller corpora with strict latency needs, but at roughly a billion vectors it needs terabytes of memory per replica.
- DiskANN keeps a compressed navigation layer in RAM and the full graph on SSD, reaching similar recall at a fraction of the memory, with [Cosmos DB](https://www.m365.fm/entity/cosmos-db/?utm_source=podcast&utm_medium=shownotes&utm_campaign=the-billion-vector-problem-hnsw-vs-diskann-in-azure-ai-search) suited to dynamic data and SQL Server to static data.
- Index choice drives cost, while answer quality depends on hybrid search, reranking, chunking, chunk-level metadata filters and continuous evaluation and observability.

## FAQ

**How much RAM does HNSW need for a billion vectors?**

Roughly six terabytes, based on the Cosmos DB benchmark figures cited in the episode. One million vectors already need more than 12 GB for the HNSW index alone. Because every replica keeps its own full copy in memory, two replicas push the requirement to 12 terabytes and three replicas to 18 terabytes.

**When should I choose DiskANN instead of HNSW on Azure?**

Plan for DiskANN once your corpus is heading past 100 million vectors, and start modeling costs between 50 and 100 million. Below 50 million, HNSW in Azure AI Search is usually the right call. Update frequency, latency and cost sensitivity also matter: a hard sub-five-millisecond retrieval requirement still favors HNSW.

**Should I use Azure Cosmos DB or SQL Server for DiskANN vector search?**

Use Azure Cosmos DB for data that changes often and SQL Server for large, mostly static datasets. Cosmos DB keeps its DiskANN index in sync as vectors are added, changed or removed. A SQL Server vector index can lock the source table read-only for hours, and updates require rebuilding on a copy and swapping.
