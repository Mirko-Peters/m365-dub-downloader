## Key takeaways

- Workload identities give applications, automations and AI agents their own [Entra](https://www.m365.fm/entity/microsoft-entra/?utm_source=podcast&utm_medium=shownotes&utm_campaign=entra-workload-identities-simply-explained) identity instead of shared service accounts or passwords in code.
- An application registration is the app's global design, a service principal is its local identity in each tenant, and a managed identity is a service principal that [Azure](https://www.m365.fm/entity/azure/?utm_source=podcast&utm_medium=shownotes&utm_campaign=entra-workload-identities-simply-explained) manages for an Azure resource.
- Prefer managed identities inside Azure and workload identity federation outside it, use certificates over client secrets, grant minimal permissions and give every workload identity an owner.

## FAQ

**What is the difference between an app registration and a service principal?**

An application registration is the app's master design, while a service principal is its local identity inside one Entra directory. The registration describes the app and the permissions it may request; the service principal receives the actual permissions in your organization, so each company using the app controls its own local copy.

**Does turning on a managed identity give an app access automatically?**

No. A managed identity only gives an Azure resource an identity in Microsoft Entra ID; it does not grant access by itself. Someone still has to assign a role or permission, for example allowing a logic app to read one specific secret in Azure Key Vault. Azure creates the badge, but you decide which doors it opens.

**How can a GitHub Actions pipeline sign in to Azure without a secret?**

Use workload identity federation. GitHub proves which workflow is running, which repository it came from and under what conditions it started; Entra trusts that proof for a defined setup and issues a short-lived token. That way no long-lived Entra secret needs to sit in the GitHub settings waiting to be copied.
