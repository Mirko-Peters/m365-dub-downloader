## Key takeaways

- Azure PaaS services such as Storage, SQL and Key Vault ship with public endpoints, and a subscription is a billing boundary, not a network boundary.
- Azure Private Link places a private endpoint with a private IP inside your virtual network, and private DNS zones make the existing service URL resolve to it so applications need no changes.
- Creating a private endpoint does not disable public access, on-premises clients need DNS forwarding, and the extra per-endpoint cost is best justified for sensitive, regulated production workloads.

## FAQ

**Does creating a private endpoint disable public access to an Azure storage account?**

No, creating a private endpoint does not turn off the public endpoint. Both can exist at the same time, so the storage account stays reachable from the internet until you explicitly disable public network access in its networking settings. The episode calls this the biggest gotcha, because skipping that step leaves nothing actually secured.

**Do I need to change my application's connection string when using Azure Private Link?**

No, the application does not change. The URL stays the same and only its DNS resolution changes. With private DNS zone integration, the public name returns a CNAME pointing to the privatelink zone, where an A record maps it to the private endpoint's IP, so traffic flows over the Microsoft backbone instead of the internet.

**What is the difference between Azure Private Link and service endpoints?**

Service endpoints keep the service's public endpoint and add a rule that only allows traffic from your virtual network, while Private Link gives the service a private IP inside your VNet. Because there is no public endpoint to attack, the episode describes Private Link as more secure and the gold standard for private PaaS access.
